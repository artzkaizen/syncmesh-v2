## Context

The client grew its own data API — `create` / `get` / `list` / `update` / `delete`, a `tx` recorder, `query()` descriptors over a single-table IVM, `scoped({ as })` acting as a caller — and when the first oRPC procedure was written against it, it read as a second, weaker ORM beside the one the app already has: a handler that reads from `mesh.jobs.get()` and writes through `mesh.tx((c) => c.jobs.update(...))` while the real queries happen in Drizzle. Two surfaces, two sources of truth, one handler. The question is what the *one* data API is.

The deciding fact is what the unit of sync is. Zero's unit is the **query**: a client syncs exactly the rows its active queries need, so the query must cross the wire as data (ZQL), the server must maintain thousands of them incrementally (IVM), and the client must run the same language locally. syncmesh's unit is the **partition** plus the read policy enforced where rows leave the relay (D07, RFC-0008). A device holds its partitions; what it does with them locally never crosses the wire. Nothing in that model needs a query language or an IVM.

## Options

- **A · Our own query language** — extend the descriptors into a ZQL: operators, `related`, aggregates, an IVM with joins on the device, a SQL compiler on the server. Airtight permissions (we own the AST) and one semantics both ends, at the cost of building and maintaining a query engine — the same thing D10 refused to do for RPC.
- **B · SQL is the data API.** The state store materialises rows into real per-table SQLite tables on a device and Postgres on the server (API.md §13.2's shape: app tables plus a stamps sidecar). Reads are the app's ORM over those tables; writes are the app's ORM too, captured at commit into one signed event. The mesh never appears at a call site. Drizzle first; other ORMs through the same substrate.
- **C · Hybrid** — SQL for reads, mesh verbs for writes and live UI. Rejected: it is the two-surface handler this decision exists to remove.

## Decision

**B — the app reads and writes its database with its ORM; the mesh is the layer underneath that turns commits into events and folds events into tables.**

```ts
export const jobs = sqliteTable("jobs", { id: text().primaryKey(), status: text(), assignee: text() })
export const schema = defineSchema({ tables: { jobs: { table: jobs, partition: "org",
  allow: ({ role, owner, any }) => ({ read: role("viewer"), update: any(role("dispatcher"), owner("assignee")) }) } } })

// a route: read from the db, write to the db — nothing else exists
.handler(async ({ input, context: { db }, errors }) => {
  const job = await db.query.jobs.findFirst({ where: eq(jobs.id, input.id) })
  if (!job) throw errors.NOT_FOUND()
  await db.update(jobs).set({ status: "assigned", assignee: input.tech }).where(eq(jobs.id, input.id))
})
```

1. **SQLite on the device, Postgres on the server; adapters, not one ORM.** The mesh's contract is SQL tables, generated triggers, filtered views and a `SqliteDriver`. `@syncmesh/drizzle` is the first face — `fromDrizzle` already makes a Drizzle table the definition — and the manifest keeps our own `table()`/`t.*` so a Kysely or raw-SQL adapter is an addition, not a rewrite. PGlite is not an option for the device: it does not run on React Native, and a phone is not a Postgres host.
2. **Reads are permission-filtered by construction.** `mesh.as(principal).db` is the app's ORM over table sources that are subqueries with the principal's `read` rule compiled to SQL — `owner("assignee")` → `assignee = :account`, `rowIs` → equalities, `claimHas` → `IN`, `role()` → a constant, `any/all/not` → `OR/AND/NOT`. The raw tables are not reachable through that handle. A row the principal may not read is absent, so `findFirst` returns nothing and the app never has to check.
3. **Writes are captured at commit, one transaction = one event.** Generated `AFTER INSERT/UPDATE/DELETE` triggers on every synced table log `OLD`/`NEW` per row into `_syncmesh_changes`; at commit the mesh turns the log into field-level patches (only the columns that changed, so concurrent edits to different columns both survive), evaluates the schema's rules for the principal with the old row and the patch, and either appends and signs the event or **rolls the transaction back** with `PolicyDenied`. Triggers are the portable baseline (every SQLite driver, and Postgres); SQLite's session extension replaces them behind the same interface where a driver exposes it (`node:sqlite` today); Postgres logical decoding is for CDC (RFC-0021), not the authority's own writes — it is after commit and outside the transaction, so it cannot refuse.
4. **Live queries are re-runs on exact invalidation.** A live query is an ORM query the mesh re-runs when a fold batch touches one of its tables — read off the query object, never parsed from SQL — after the state store has committed, then diffs by primary key and notifies once per batch only if the result changed. Sharing is keyed by the query's SQL and params. Keyset windows only. LiveStore's model; D11's "equal to a re-run, always" holds by construction.
5. **The client's own query machinery is retired from the app surface.** Collection verbs, the `tx` recorder, `query()` descriptors and the single-table IVM stop being API; the kernel, engine, wire, policy, transport, storage, `delivered`/`received` and `history` stay. The IVM's one future is RFC-0020's thin client — a device with no store asking the relay to maintain a query — and there the engine is TanStack's `db-ivm`, not ours, fed by a small serializable AST shared with interest rules (RFC-0019) and the compiled read filter. One grammar, three consumers; not a ZQL.

## What this costs, accepted

- sqlite-wasm in the browser (size, OPFS, COOP/COEP) where Zero has a pure-JS store.
- Trigger DDL the mesh owns on the customer's database and must carry through schema evolution (E18).
- Two dialects: SQLite on device, Postgres on server; the same query can differ at the edges.
- No query-driven partial sync: a device gets its partition. Interest rules (RFC-0019) reopen most of that door as server-evaluated row predicates.
- Live-query cost is query cost; the remedy is an index, which is the app's.

## Status

Landed through the consolidation of 2026-08-26: `packages/storage` owns capture, projection,
read-filter and the writer; `packages/drizzle` is the first adapter (`meshDrizzle` → `db` /
`read` / `live`, `db.transaction()` as the capture boundary, `taggedCause` for unwrapping
refusals); `packages/client`'s `createMesh` hands out handles via `mesh.on(instance?, { as? })`
and the collection-era surface is deleted; `@syncmesh/orpc`'s `withMesh` pins a handle per
caller and maps `PolicyDenied` to `FORBIDDEN`. Point 5's retirement is complete. Locality is
inferred: a transaction wholly on `local` tables becomes a local event (never outbound); a
transaction mixing local and synced tables rolls back as `LocalOnly`. Still open: the
Postgres half (E17).

## Watch out

- The fold of peers' events and the app's own SQL are two writers to the same tables. The fold applies through the state store as UPSERTs with stamps in the sidecar; the app's writes get their stamps at commit. One ordering rule, tested, before anything else.
- `_partition` rides on every row: injected on insert by the pinned handle, filtered on read, never settable by the app.
- Triggers must not fire for the fold's own UPSERTs, or every received event would be re-captured as a local one. A per-connection guard, tested.
