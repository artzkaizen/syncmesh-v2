title: What a cursor means to a peer that asked for less

## Context

Two features that were each right alone now contradict each other.

**E13** filters at the sender. A client joins with an `Interest`, and the relay's catch-up ships
only what matches — `packages/relay/src/catchup.ts` drops every entry `matchesInterest` refuses.
That is the whole bandwidth win: a phone that belongs to two of eight teams pays for two.

**E18** redefined what a cursor claims, on D13's reasoning. `packages/engine/src/sync.ts`:

> Per author, the highest sequence number below which a peer holds **every** event — the
> contiguous half of D13's `{ contiguous, ahead }`. What travels, because it is the only half
> anti-entropy can ask a question with: "send me everything after this" is a lie the moment the
> number sits above a hole.

A client that asked for less **never holds every event** below any point past the first sequence
the filter dropped. So its contiguous cursor pins there permanently, and — since delivery walks
the run from the cursor — its holdback stalls behind a hole the relay will never fill, because
the relay is filtering it out on purpose.

Reachable today through `relayTransport({ interest })`. Not reachable through `createMesh`, which
is the only reason it is not a live outage.

The collision is not an oversight in either feature. It is that "I hold everything below N" and
"send me only what I asked for" cannot both be true of the same number.

## Options

- **A · A scoped coverage the client adopts.** Filtered catch-up ends by handing the client a
  coverage *for that interest*: "for this slice, you now hold everything below N." The client
  adopts it, exactly as `installSnapshot` already adopts a snapshot's coverage. A cursor then
  means "everything below N **that I asked for**", and widening the interest is a re-join.
- **B · Stop filtering catch-up.** The relay serves the full history and filters only the live
  fan-out. Cursors keep their unqualified meaning; E13 keeps its win for the steady state and
  loses it for the join, which is the expensive part.
- **C · Two cursors.** Carry a filtered cursor beside the unfiltered one and let anti-entropy ask
  with whichever matches the asker's interest.

## What the research points to

**A**, and the precedent is already written down. RFC-0019 §"Widening the scope resets the
cursors" decided this for snapshots:

> Exactly as with interest predicates (RFC-0018): a max-based cursor cannot describe the holes
> that scoping left, so a device that joins a third team must re-request rather than assume.
> Narrowing is free.

That is the same sentence about the same problem, reached before contiguous cursors existed and
independent of them. The join path already adopts a scoped coverage and already treats widening
as a re-request; A is catch-up being made to agree with the snapshot path rather than a new idea.
E14's `Snapshot.scope` is the shape to copy — a coverage that says which slice it is complete for
is exactly what a filtered catch-up needs to hand over.

B is the safe retreat and gives up the wrong half. A join is where the bytes are — the whole of
E14 exists because replaying a room costs 24 MB against a scoped snapshot's 0.34 — so filtering
the steady state and not the catch-up optimises the cheap case.

C is honest and doubles the surface: two numbers on the wire, two invariants to keep in step, and
every existing consumer of `cursors()` newly ambiguous about which it is holding. It also does
not answer what happens when the interest changes, which is the actual hard part.

## Watch out

- **A scoped cursor must say what it is scoped to, or it is a lie with better manners.** Whatever
  the client adopts has to carry the interest it was computed for — `interestKey` already exists
  for exactly this, and the digest exchange already refuses to compare across differing scopes.
- **Widening must be unmistakable.** A device that widens and keeps its cursor silently skips
  every event the old filter dropped, forever. It is the same trap as adopting a snapshot's
  coverage without its rows, and it fails silently, which is the worst kind.
- **Narrowing is free and must stay free**, or a device that loses access to a partition pays for
  a full re-sync it does not need.
- A peer that never named an interest must be unaffected. Its cursor keeps its plain meaning, and
  nothing on the wire may become ambiguous for it — an older build's silence about scope is not a
  claim that it asked for less.
- Whatever is chosen, two peers holding the same events and the same interest must agree. A
  scoped cursor that depends on which events the relay happened to have when it answered is the
  divergence class this repo has shipped six times.

## Decision

**A.** A filtered catch-up ends by handing the client a coverage **for the interest it asked
with**, and the client adopts it the way `installSnapshot` already adopts a snapshot's. A cursor
then means *"everything below N that I asked for"*, carrying the scope that makes it true.
Widening the interest is a re-join. Narrowing stays free.

This is not a new rule, and that is most of the argument for it. RFC-0019 reached the same answer
for snapshots before contiguous cursors existed, and E14 shipped it — a snapshot already carries
the slice it is complete for and a widened scope already re-requests. What was wrong was that
catch-up filtered without saying so, leaving the client to compute a cursor from a stream it had
not been told was incomplete. The relay knew the slice; it simply never handed it over.

Four things this settles:

- **A scoped cursor travels with its scope.** `interestKey` already exists and the digest exchange
  already refuses to compare across differing scopes; a cursor is the third thing that needs the
  same treatment. Without it a scoped number is a lie with better manners — indistinguishable on
  the wire from an unscoped one, and read as the stronger claim.
- **Widening is a re-join, and must be impossible to do accidentally.** A device that widens and
  keeps its cursor silently skips every event the old filter dropped, forever. It fails silently,
  which is the worst kind, so the client must not be *able* to hold a cursor whose scope it no
  longer matches — the mismatch is what triggers the re-request, not the app remembering to.
- **An unscoped peer is unaffected.** Its cursor keeps its plain meaning, and an older build's
  silence about scope is never read as a claim that it asked for less. Additive, like everything
  else on this wire.
- **The scoped coverage is computed from the interest, not from what the relay happened to hold.**
  Two peers with the same events and the same interest must adopt the same number, or this becomes
  the seventh instance of the divergence class — and this one would be invisible, because both
  peers would be behaving exactly as their own cursors described.

What this does **not** settle: whether a device may hold *several* scoped cursors at once — one
per interest — rather than one cursor and one interest. That is what a client watching two
unrelated slices would want, and nothing here forecloses it; it is simply not needed yet, and
inventing it now would mean designing the merge rule between scopes with no caller to check it
against.
