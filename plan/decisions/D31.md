## Context

Zero has a deploy order. Expand runs DB → API → client, contract runs client → API → DB, and
when a client and a server still disagree about the schema, `onUpdateNeeded` fires and the
client is told to refresh. Every one of those steps assumes there is a place to stand between
"the old shape" and "the new shape" where nobody is writing.

syncmesh has no such place. **There is no deploy order because there is no order: a phone six
versions behind is still a valid signer, its events must fold on every newer peer, and every
newer peer's events must reach it** (`plan/api-gaps.md:34-35`, `:294-298`). The log is
append-only and the events in it are signed by their author, so nothing can be rewritten on the
way through (D13's own watch-out: an upcaster at decode time breaks every signature). Two builds
meeting is not a rollout window to be minimised; it is the steady state.

**What is already settled, and holds.** D13 chose additive-only by rule and no upcasters: add
nullable columns (D19 removed defaults, so an absent cell reads `null`), remove columns (readers
ignore unknown keys), never change a type or a meaning, and turn a rename into an add plus
`assignee ?? owner` at the read site. E18 then built the machinery the rule needs, and it does
what D13 asked:

- **A newer build's table parks, it does not drop.** The ladder's schema rung returns
  `UnknownTable` for a table not in this build's manifest (`packages/engine/src/validate.ts:118-120`),
  `quarantineReason` files it under `unknown-table` (`packages/engine/src/quarantine.ts:49-53`),
  and `admit` parks the bytes verbatim with the verdict beside them
  (`packages/engine/src/admit.ts:138-142`). The author's cursor stops **below** the parked event
  (`admit.ts:117-121`), and `holding()` lets the run continue past it so one refusal does not
  stall an author for the life of the device (`packages/engine/src/engine.ts:143-148`).
- **A newer build's change kind parks the same way.** D22-A widened the kernel's `Change` union
  with an opaque variant, so a kind this build cannot fold arrives as `unknown` carrying its tag
  (`packages/engine/src/columns.ts:17-23`) and the `unfoldable()` rung parks it as `unknown-kind`
  before anything reads its cells (`admit.ts:29-46`, `:138`). `UnknownChangeKind` has its own
  tag precisely because it is "the refusal an upgrade is expected to reverse"
  (`packages/engine/src/errors.ts:82-91`).
- **A newer build's column is ignored, not refused.** The column check filters a change's cells
  down to the columns this build declares and drops the rest from the *check only*; the fold
  stores the change as it arrived, so both builds keep the same record and each read side shows
  the columns its own schema names (`columns.ts:25-35`). Reserved tables take the same path
  (`validate.ts:243`).
- **The telling is per mesh, never per event.** `unknownHandling` is `"warn" | "ignore" | "fail"`
  and all three park; none folds (`quarantine.ts:31-46`, `packages/engine/src/options.ts:28-33`).
  For the `refused` bucket the setting is not consulted at all — it always warns
  (`admit.ts:172`).
- **Retry after upgrade exists.** `retryQuarantined()` re-offers everything parked to the
  ordinary path (`quarantine.ts:224-233`); `withRetry` re-offers only the `refused` bucket after
  any batch that folded something, because new state can clear a refusal but cannot teach a
  build a table (`quarantine.ts:201-222`, `:269-296`). `$recovery.run()` is the operator's
  nudge for it (`packages/client/src/recovery.ts:75-76`).

That is a real floor. A device three weeks offline meets a build it has never seen and neither
loses nor mangles anything. E18's acceptance line — *"Two app versions on one mesh converge, and
the older one shows the newer's rows minus the columns it cannot read"* (`plan/epics/E18.md:54`) —
is the additive case, and it is covered.

**What the floor does not cover.** RFC-0013 left G18 open — *"a peer that upcast an event and one
that applied it natively … can hold legitimately different rows, so digest mismatch ≠ divergence"*
(`research/rfcs/0013-schema-evolution.md:227`) — and the gap audit records that it still has no
mitigation (`research/gap-audit.md:84`; `plan/epics/E16.md:28`). Read against today's code, G18
is four concrete cases, and none of them is the additive case:

1. **An authority corrects a column an old client cannot see.** A correction is one signed event
   carrying the overwrite and a `_corrections` row, folded by the ordinary merge
   (`packages/engine/src/authority.ts:123-131`, `:134-155`). On the old build the new column is
   dropped from the check and stored unseen (`columns.ts:28-32`), while the `_corrections` row
   folds because the reserved table is known. So the old device renders "changed by the office,
   because …" beside a value it never saw change. Not divergence — the records are identical — but
   the two builds' digests differ, and the correction the reason explains is invisible to the
   person it was written for.
2. **A renamed or re-typed column.** D13 forbids both and says the rule "is lint-checked, or it is
   not a rule". **No such lint exists**: nothing in `packages/schema/src` checks a manifest
   against a previous one (searched for `additive`, `compat`, `version`, `fingerprint`; no hits
   outside tests). A build that re-types `hours` from text to integer sends events every older
   build refuses with `SchemaViolation` (`columns.ts:52-64`), which files under `refused`
   (`quarantine.ts:52`) — the bucket whose doc says "an upgrade rarely helps" (`quarantine.ts:28`)
   and which `retryRefused` re-walks after every fold that lands anything
   (`quarantine.ts:210-222`). The rule is currently held by review, which D13 named as the
   failure mode.
3. **A removed table still being written by old clients.** This is the case the code does not
   expect, and it is the one that costs the most. The new build has no entry for the table, so
   the old client's write returns `UnknownTable` (`validate.ts:118-120`) and lands in
   `unknown-table` — the bucket whose doc comment describes it as "the shape a **newer** peer's new
   table arrives in" (`quarantine.ts:18`). Three consequences follow from that mis-filing:
   - **It shares a bounded bucket with the events it was bounded to protect.** The cap is per
     reason, default 128, oldest first (`quarantine.ts:110`, `:127`, `:151-162`), and the stated
     purpose of a per-reason cap is that forged load "must not be able to push out the one event
     from a newer app version that this device is holding for its next upgrade"
     (`quarantine.ts:12-15`). A middle build that has dropped a table the oldest clients still
     write, and lacks a table the newest clients have added, parks both streams in one bucket —
     and the oldest fleet's ordinary traffic evicts the newest build's events, loudly
     (`QuarantineEvicted`, `quarantine.ts:89-94`) but irrecoverably: the peer that sent them "has
     long since been told we hold up to our cursor" (`quarantine.ts:85-87`).
   - **It pins compaction for every peer.** The new build's cursor on that author stops below each
     dropped-table write (`admit.ts:118-121`), its cursor frames say so
     (`packages/transport/src/holdback.ts:15`), and D15's floor is the per-author minimum across
     acknowledged peers (`plan/decisions/D15.md:30`). One upgraded device holding a shop's log
     therefore stops every device compacting that author below the first write to the retired
     table, until `forgetPeersAfter` drops the upgraded device from the count — which is the wrong
     device to forget.
   - **The old client is never told.** Its write reads `local` forever, indistinguishable from a
     device that has not synced (D26's watch-out; D32 is the report that would close it).
4. **A new `allow` rule an old client predates.** This one is *mostly* handled, and the
   remainder is sharper for it. Permissions are data: `setPolicy` publishes the `_policy` row
   into the instance it governs and "every validator prefers it over the bundled manifest"
   (`authority.ts:68-71`; `validate.ts:131`). So a rule change does not need an app release, and
   both builds evaluate the same rules once the row syncs. The residue is the interpreter:
   `syncedRules` documents that "absent or unparsable, the bundled manifest stands"
   (`packages/engine/src/rules.ts:48-52`), and a doc this build cannot parse falls to `undefined`
   and then to `entry.allow` (`rules.ts:69-70`; `validate.ts:131`). A newer build that publishes a
   policy using an AST node the older build has no parser for silently puts the two builds on
   **different rule sets for the same event**, and the older one folds what the newer one refuses,
   or the reverse. That is exactly the deterministic-refusal assumption §1 of the plan rests on —
   *"every peer computes the same verdict"* (`plan/api-gaps.md:59`) — failing in a way nothing
   reports, because on each device the local verdict is correct by its own lights.

**Two things that look like a version and are not.** Events carry `v` at core key 0
(`packages/wire/src/event-codec.ts:24-33`). It is the *wire format* version, written as the
literal `1` (`event-codec.ts:150`) and refused when it is anything else (`event-codec.ts:121`;
RFC-0013's axis table at `0013-schema-evolution.md:23-26` calls it "the wire shape itself —
rare, last resort"). It says nothing about the app schema and must not be made to. `_policy`
has a `version` column (`packages/schema/src/reserved.ts:40`), but `setPolicy` defaults it to
`Date.now()` (`authority.ts:88`); it orders policy rows, not builds. RFC-0013 proposed a
`schemaVersion` under a fresh core key precisely because neither of these is it
(`0013-schema-evolution.md:70-72`); a search of every package finds no such field on the wire
or in the manifest.

**One thing that is a fingerprint and not a version.** `schema-fingerprint` is the app-schema
DDL text hashed and stored in `meta`, so "a launch that changed nothing installs nothing"
(`packages/storage/src/dialect.ts:158-166`). Its test's own title is the point: *"a changed
manifest is installed again, with no version for anyone to bump"*
(`packages/storage/src/__tests__/schema-fingerprint.test.ts:71-85`). The same hash names the
state file (`packages/storage/src/open-stores.ts:129-131`, `:139-140`). A hash is unordered: it
can say two shapes differ, never which is newer, and it lives on the device that computed it.
It is install idempotence, not a fleet reading.

**One thing that is the template.** `_policy.grace` is a per-instance floor that tightens how
long an old grant is trusted (`reserved.ts:41-46`; RFC-0016). It travels as data, and the rung
judges it **against the event's own stamp, not the receiver's clock**, for a reason written out
in full: judged at arrival, "the author would keep a write that every peer receiving it after the
boundary quarantined, and the two would never agree again" (`packages/engine/src/author.ts:67-77`,
`:89-93`). That is the shape any schema floor has to take if it is to be a floor and not a
divergence engine.

## Options

- **A · Additive-only forever, park, and nudge the person to upgrade.** Today, written down.
  Keeps D13 whole and adds a UI affordance over `unknownHandling: "warn"`. Rejected as the whole
  answer: it has nothing to say to cases 2–4, and D13 already declined to say it — *"what an app
  does when it must genuinely break compatibility … is not settled here"*. Contraction has to be
  possible eventually or every table ever shipped is a table forever; A makes the honest cost of
  that invisible until the first drop.
- **B · A manifest version stamped on every event, and a minimum-version floor enforced at
  admission.** The stamp half is right and is used by C. The floor half is rejected: a refusal at
  the fold is the failure state the plan names — *"it fails badly: the quarantining peer's cursor
  never rises past the parked event … so the author's write reads `local` forever and is never
  told why"* (`plan/api-gaps.md:67-70`). A version floor refuses *legitimate offline work* by
  construction — the phone that was in a drawer through two releases is exactly the author whose
  backlog the floor would park — and unless it is judged against the event's stamp with the
  floor's own effective-at, as grace is (`author.ts:67-77`), two peers that learned the floor at
  different moments reach different verdicts on the same event. It is Zero's `onUpdateNeeded`
  built on a system that has no server to refresh from.
- **C · Expand/contract as an operator rule, with the tooling that makes it a rule.** Three
  parts, each small. *(i)* The lint D13 asked for: `syncSchema` compared against the last
  shipped manifest, refusing a re-type, a rename, a `NOT NULL` add, and a repurpose — RFC-0013's
  verdict table (`0013-schema-evolution.md:103-110`), enforced where the other schema checks
  are. *(ii)* A monotone `schemaVersion` declared in the manifest, stamped on each event under a
  fresh core key (additive: the decoder ignores unknown keys, `event-codec.ts:107`) and carried on
  the cursors frame as a trailing element, the way `ahead` already is
  (`packages/transport/src/frame.ts:27-33`, `:87-91`; `packages/transport/src/frame-parts.ts:74-77`
  explains why a trailing element is what an older build reads past). *(iii)* A fleet reading:
  "the oldest schema still writing", per author, off the per-peer acknowledgements the engine
  already keeps with a timestamp (`engine.ts:165-174`), surfaced through `$inspect`. Contract
  then has a definition an operator can check instead of guess: a table or column moves to
  **retired** — still declared, refused for local writes, still folded from peers — and is
  physically dropped only when the fleet reading says no author below the retiring version has
  written since, and the retention floor has passed. Old writers' events keep folding the whole
  way through, so case 3 never arises.
- **D · Per-partition schema epochs.** Rejected. What varies between two devices is the *build*,
  and a device runs one build across every partition it holds; an epoch per partition multiplies
  the version matrix without adding a fact. It also makes the schema describe custody again,
  which §2.1 of the plan just finished removing. RFC-0013's per-table question
  (`0013-schema-evolution.md:228`) is answered by retiring per table under one app-wide version,
  not by versioning per partition.

## Decision

**Recommend C, with B's stamp as its instrument and never its gate.** The rule is expand →
wait for the fleet → contract; the tooling is what turns "wait for the fleet" from a feeling
into a number.

| | do | why |
|---|---|---|
| **now** | the additive lint, against the last shipped manifest | D13 said "lint-checked or it is not a rule"; today it is not a rule. Closes case 2 at build time |
| **now** | rename the bucket, or split it: `unknown-table` for a table this build has *never* declared, `retired-table` for one it declared and dropped | the two mean opposite things (case 3), share one 128-slot cap, and only one of them is ever cleared by an upgrade |
| **now** | fix `quarantine.ts:20-26`, whose doc says a newer build's kind "does not yet arrive as something to park" | D22-A landed (`columns.ts:17-23`); the comment describes the code before it |
| **next** | `schemaVersion` in the manifest; on the event core under a new key; trailing on the cursors frame | the stamp is what makes "oldest still writing" a reading and not a guess. New frozen vectors under README rule 3 |
| **next** | `retired` as a table and column state: declared, write-refused locally, still folded | contract without a cliff — old writers keep folding, and their events never enter quarantine at all |
| **next** | `$inspect.fleet.oldestSchema()` off `acksAt` | the operator's number; a build below it is still writing, so do not drop yet |
| **later** | G18 digests over the common-subset projection: compare cells both builds declare | the correct answer to "mismatch ≠ divergence" once the stamp says which subset that is |
| **not** | any floor that refuses an event for its `schemaVersion` | B, for B's reasons |

Written as the operator's rule, which is what the docs should carry:

1. **Expand** — ship the build that adds the table or nullable column. Old builds ignore the
   column (`columns.ts:28-35`) or park the table (`admit.ts:138-142`); nothing is lost.
2. **Wait** — until `oldestSchema()` is at or above the expanding version for every author that
   has written in the retention window. This is the step Zero does not need and we cannot skip.
3. **Retire** — ship the build that marks the old table or column `retired`. Writes to it refuse
   locally with a typed value; events for it from older builds still fold.
4. **Contract** — drop it physically only above the compaction floor for every author. Case 3's
   pin never forms because the event never parked.

## What this costs

- **A wire addition, frozen.** A new core key on every event and a trailing element on cursors;
  both additive, both need vectors in `conformance/` before they ship (README rule 3). The cost is
  small in bytes and permanent in maintenance.
- **A reading that is only as good as who has talked.** Acknowledgements live in memory and start
  empty after a restart (`plan/decisions/D15.md:30`); `oldestSchema()` is a reading of the peers
  seen since boot, and a device in a drawer is not in it. The rule in step 2 therefore leans on
  the retention window, and an author that returns from below it rejoins from state, which D15
  already accepted as the tooth.
- **A third table state.** `retired` is a manifest concept the schema builder, the validator, the
  read filter and the lint all have to know; it is the price of contracting without a cliff.
- **The rule is still a rule.** The lint stops the illegal change; nothing stops an operator
  skipping step 2. The tooling makes the skip visible in a number, which is as far as tooling
  goes.

## Watch out

- **Never overload `v`.** Core key 0 is the wire shape (`event-codec.ts:24-33`), refused when it
  is not `1` (`:121`). A schema version that borrowed it would make every peer on the old wire
  refuse every event from the new — the whole log, not the new column. New key, or nothing.
- **A floor judged by the receiver's clock is a divergence engine.** If any part of C ever grows a
  refusal — "events below version *n* are no longer accepted after date *d*" — it must be judged
  against the event's own stamp with the floor's effective-at carried as data, exactly as
  `checkStale` does (`author.ts:71-77`). Anything else makes the verdict depend on when a peer
  happened to validate.
- **The policy interpreter is a version axis nobody stamps.** `syncedRules` falling back to the
  bundled manifest on an unparsable doc (`rules.ts:51-52`, `:69-70`) is the one place today where
  two builds *deliberately* evaluate different rules on one event. Either the AST is frozen the
  way the wire is, or a doc with an unknown node has to park the event rather than quietly
  choosing a different rule set. RFC-0013 listed this as open (`0013-schema-evolution.md:231`);
  it is not open, it is decided by the fallback, and decided the wrong way.
- **Two doc comments contradict the code; one is load-bearing.** `authority.ts:96-98` says an
  older build's "schema check refuses a row carrying" an undeclared column, which is why `grace`
  is written only when set. `columns.ts:28-35` drops undeclared cells from the check instead,
  and reserved tables reach it through `validate.ts:243`. Whichever is current, the other is a
  developer being told the wrong rule for adding a reserved column. I did not trace which landed
  later; check before relying on either.
- **The bucket split is not cosmetic.** Until `retired-table` exists apart from `unknown-table`,
  an old fleet writing a dropped table evicts a newer build's parked events from a middle build's
  quarantine, and the eviction is exactly the loss the per-reason cap was written to prevent
  (`quarantine.ts:12-15`).
- **Corrections need a target the reader can see.** Case 1 is not fixed by C; it is made
  diagnosable. An authority correcting a column added in version *n* should know, from
  `oldestSchema()`, that a device below *n* will fold the `_corrections` row and not the value.
  Whether it then corrects an older column too, or waits, is app policy; what it must not do is
  believe every device saw the change.
- **The quarantine is memory** (`engine.ts:263`; `createQuarantine` holds `Map`s and no storage
  implementation exists). A restart forgets what was parked; the cursor below it is durable, so
  peers re-offer and it parks again. That is correct today and it means every reading in this
  decision that depends on "what this device has parked" is a reading since boot.
