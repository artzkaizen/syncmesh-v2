## Context

An append-only log means an event written in January carries January's row shape forever; a phone offline for three weeks must still be readable by the new app. Client-server systems dodge this by migrating the DB and forcing an update; a mesh cannot.

## Options

- **A · Additive-only by rule, no upcasters** (LiveStore's model): add columns — *nullable only, since D19 removed defaults: an absent cell always reads as `null`, so there is nothing to backfill with* — remove columns (readers ignore unknown keys), never change a type or meaning; a rename becomes an add plus `assignee ?? owner` at the read site; an `unknownHandling: "warn" | "ignore" | "fail"` knob for events a peer cannot understand.
- **B · Versioned upcaster chains** — `version: 3, upcasters: { 2: row => …, 3: row => … }` run at fold time. A migration system the app author maintains forever; the exploration designed it and dropped it.

## What the research points to

A. LiveStore's third rule ('state is derived, just rematerialise') does not transfer — our events carry changes, not intent — but the additive rule and the knob transfer whole. Contiguous cursors are the prerequisite: with MAX cursors a dropped event leaves a hole the cursor advances past, so 'park and retry later' is impossible.
## Watch out

An upcaster at *decode* time would rewrite bytes and break every signature; only fold-time is possible, and even that is off the table under A.
