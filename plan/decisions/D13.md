## Context

An append-only log means an event written in January carries January's row shape forever; a phone offline for three weeks must still be readable by the new app. Client-server systems dodge this by migrating the DB and forcing an update; a mesh cannot.

## Options

- **A · Additive-only by rule, no upcasters** (LiveStore's model): add columns — *nullable only, since D19 removed defaults: an absent cell always reads as `null`, so there is nothing to backfill with* — remove columns (readers ignore unknown keys), never change a type or meaning; a rename becomes an add plus `assignee ?? owner` at the read site; an `unknownHandling: "warn" | "ignore" | "fail"` knob for events a peer cannot understand.
- **B · Versioned upcaster chains** — `version: 3, upcasters: { 2: row => …, 3: row => … }` run at fold time. A migration system the app author maintains forever; the exploration designed it and dropped it.

## What the research points to

A. LiveStore's third rule ('state is derived, just rematerialise') does not transfer — our events carry changes, not intent — but the additive rule and the knob transfer whole. Contiguous cursors are the prerequisite: with MAX cursors a dropped event leaves a hole the cursor advances past, so 'park and retry later' is impossible.
## Watch out

An upcaster at *decode* time would rewrite bytes and break every signature; only fold-time is possible, and even that is off the table under A.

## Decision

**A.** Additive-only by rule. Nullable columns are added, unknown keys are ignored, a type or a
meaning never changes, and a rename is an add plus `assignee ?? owner` at the read site. No
upcasters, at fold time or anywhere else.

The argument against B is not that upcaster chains are hard to write — it is who has to keep
writing them. A chain is a migration system the app author maintains forever, and every peer must
agree on it to converge, so the chain itself becomes a thing that has to be versioned and
distributed. B trades a rule you can state in one sentence for a mechanism that grows without
bound and whose failure is silent divergence between two app versions.

Four things this settles, and one it deliberately does not.

- **Contiguous cursors are the prerequisite, not a nicety.** With MAX cursors a dropped event
  leaves a hole the cursor advances past, so "park it and retry when the app understands it" is
  impossible — the position already claims the event was delivered. `{ contiguous, ahead }` per
  author is what makes an unknown event a thing a device can hold rather than lose. E18 must do
  that task first; the rest of the epic is unbuildable before it.
- **`unknownHandling` is per-mesh config, never per-event guesswork.** `"warn"` for an app that
  wants to know, `"ignore"` for one that does not, `"fail"` for a test. What it must never be is a
  per-event decision, because two peers choosing differently is the divergence this whole rule
  exists to avoid.
- **A parked event keeps its bytes verbatim.** The quarantine store holds what arrived, not what
  this build could make of it, because the only thing that will ever understand it is a later
  build reading those same bytes. Anything reconstructed from a partial parse is a forgery of the
  author's event, and re-signing it is impossible — which is also why an upcaster at decode time
  was never on the table.
- **The rule is lint-checked, or it is not a rule.** "Never change a type" enforced by review is a
  rule that holds until the first busy afternoon. It belongs beside the other schema checks.

What this does **not** settle: what an app does when it must genuinely break compatibility. There
is no answer here beyond "ship a new table and read both" — which is the honest cost of an
append-only log, and should be written into the docs as such rather than discovered.
