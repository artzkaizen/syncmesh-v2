## Context

Three gaps from one question: what a copy of a device's files, or a write behind the mesh's back,
can do (gaps U4, U5, U24; `plan/security/threat-model.md` N26, review items 6 and 11).

- **U4, the device seed.** `deviceIdentity` kept the Ed25519 seed as hex in the `_device` table
  of the device's own SQLite file. In the file on purpose (a key that outlives its database
  names an author whose log is gone), but in plaintext: anyone who reads the file, a backup or a
  lost disk signs as the device and unwraps every content key its grant carries, until the grant
  is revoked and expires.
- **U5, an unarmed write.** Capture triggers log only while capture is armed, so the fold's own
  writes are not re-captured. A write to a synced table made with capture at rest — raw SQL on
  the mesh's connection, an ORM call outside `mesh.write`, a cron job on the same Postgres — changed
  the row and left no event behind it. The device then disagreed with every peer, and nothing
  said so (gap-audit №30).
- **U24, a sealed checkpoint's snapshot.** RFC-0023 §11 says a sealed partition's checkpoint
  snapshot is sealed to the partition key, so the opaque host that stores it keeps ciphertext.
  `produceCheckpoint` already left key 8 (derived values) empty for a sealed partition, but sent
  the snapshot bytes in the clear.

## Options

- **A · Seal at rest, refuse the unlogged write, seal the blob.**
  - U4: a `SeedVault` seam. The seed is sealed under a key a platform keystore holds, and the
    sealed bytes stay in the database. Plaintext is a vault of its own that must be asked for by
    name, and it says so at every boot. A plaintext seed from an earlier build is sealed in place
    at the first boot with a vault.
  - U5: strict capture on by default. A guard trigger refuses a write to a synced table made with
    capture at rest. The fold's own writes pass through a third guard state. Opt out per mesh
    (`strict: false`) or per table (`{ except }`).
  - U24: the snapshot sealed with the partition's content key, the hash in key 7 taken over the
    ciphertext, and a host that refuses an unsealed one.
- **B · Encrypt the whole database** (SQLCipher or similar). It covers rows too, but it is a native
  build per platform and a key-management question of its own, and the seed would still need a
  keystore to hold that key. Not chosen.
- **C · Leave U5 opt-in** (gap-audit №30's first wording). The default would then stay the silent
  divergence the gap is about.

## Decision

**A**, decided 2026-11-08 (Jace delegated the call). Strict capture is **on by default**, with an
opt-out. Plaintext is an explicit opt-in for tests and development, with a boot notice.

## Built (2026-11-08)

### U4: the keystore seam (`packages/client/src/vault.ts`, `identity.ts`)

- `SeedVault { kind, seal, open, notice? }`. `deviceIdentity(driver, { vault, onNotice })`, and
  `vault` on `createClient`'s options. The `_device` `"seed"` row holds `sealed:<kind>:<hex>`. Bare
  hex is a plaintext seed, as before, so an older build reading a sealed row is refused rather
  than minting a new key.
- Vaults:
  - `createWebCryptoVault()`: AES-GCM under a non-extractable `CryptoKey` kept in the origin's
    IndexedDB (`syncmesh-keystore`, written with `add`, never `put`). It is the default wherever IndexedDB and `crypto.subtle`
    exist (`platformVault()`), so a browser, the tab worker included, needs no setting.
  - `createSecretStoreVault(store)`: a 32-byte wrapping key in any string secret store,
    XChaCha20-Poly1305. `createClient` forwards `onNotice` too, so an app can route the boot
    notice. The recipe for an OS keychain on Node or Bun (`@napi-rs/keyring`), with
    no dependency added.
  - `createSecureStoreVault()` in `@syncmesh/react-native/keystore`: the iOS Keychain or Android
    Keystore through `expo-secure-store`'s native module, `AFTER_FIRST_UNLOCK_THIS_DEVICE_ONLY` by
    default. `apps/issues-native` uses it.
  - `createPlaintextVault()`: says `DEVICE KEY IN PLAINTEXT` through `onNotice` (default
    `console.warn`) at every boot.
- **One wrapping key per seal, never one per device** (fix round 1). Every keystore vault mints a
  fresh key at each seal, under a name of its own (`<prefix>.<32 hex>`: `syncmesh.device-seed-key.…`
  in a secret store, `device-seed.…` in IndexedDB), and the sealed bytes start with the 16-byte id
  that names it. With one shared name, two first boots on one device (two databases, or two tabs
  over one) each minted a key under it, and the later write replaced the key the earlier boot had
  already sealed its row under, so that database never opened again. With a name per seal no seal
  can overwrite another's key. Two boots over one database still race for the row as before U4:
  the loser's insert fails and the winner's seed opens. The loser's key is left in the keystore,
  unread, since `SecretStore` has no delete.
- A vault's `kind` must be letters, digits and `-`, and `deviceIdentity` refuses any other before
  it writes, since `sealed:<kind>:<hex>` could not be split back.
- With no vault and none on the platform (Bun, Node, React Native) the open is refused as
  `DeviceKeyUnavailable`, naming the vaults.
- A vault's first seal is read back before the row is written. A vault that cannot open what it
  sealed, or a store that keeps nothing, fails the first boot and writes nothing.
- Migration: a plaintext row opened with a sealing vault is sealed and overwritten in place, with
  `PRAGMA secure_delete` on for that statement and the WAL checkpointed (`TRUNCATE`), so neither
  the database file nor its WAL keeps the hex. Anything the connection could not make sure of is
  reported through `onNotice`.
- Never downgraded: a sealed row is refused by a plaintext vault and by a vault of another kind.
- Tests: `client/identity.test` (copy to another device, tamper, migration with the files
  scanned for the old bytes, downgrade, refusal on Bun, the boot notice), `react-native/keystore.test`
  (backup restored onto another phone, a binary without the module), and
  `browser/keystore.test` (real Chromium IndexedDB: survives a reload, `exportKey` refused,
  two seals at once both open, cleared keystore refused). Concurrent first boots on one keychain
  and one IndexedDB holder, and on one database, are in `client/identity.test`.

### U5: strict capture (`packages/storage/src/guard.ts`, `dialect-guard.ts`)

- `StrictCapture = boolean | { except: string[] }`, default `true`. Set as `openStores({ strict })`,
  `installCapture(..., { strict })`, `installGuard`, `sqlite({ strict })` and
  `postgres({ strict })`.
- SQLite: `BEFORE INSERT/UPDATE/DELETE` triggers `"_syncmesh_strict.<table>.<op>"` that
  `RAISE(ABORT)` while the guard row's `armed` is 0.
- Postgres: one `syncmesh.capture_guard()` function, a row trigger and a `BEFORE TRUNCATE`
  statement trigger per table, both `ENABLE ALWAYS`. So `session_replication_role = replica`
  does not skip them, and a `TRUNCATE` is refused even inside a capture, which no row trigger
  could log.
- The fold passes in state 2 (`CaptureSql.fold`/`unfold`, `folding()`): `tablesProjection`'s
  apply, derive, clear and remove, and the partition stamp after a capture. Capture triggers fire
  only on 1, so nothing the fold writes is logged.
- The guard has its own `meta` row (`'guard'`), apart from the schema fingerprint. Turning it on
  or off neither renames the state file (`schemaName`) nor counts as a shape change a compacted log
  refuses (U33). A database from before U5 gets the guard at its next open.
- Tests: `storage/driver-tests/strict` runs on every driver suite (bun, node, wasm, expo, DO,
  Rivet, PGlite, real Postgres). It covers each op refused, fold and capture passing, a fold
  that throws leaving the guard at rest, off and `except`, and Postgres `TRUNCATE` and replica
  role. Also `storage/strict.test` (default on, upgrade, toggle over a log that cannot refold)
  and `client/strict.test` (through `createMesh`).

### U24: sealed checkpoint snapshots (`packages/docs/src/sealed-snapshot.ts`)

- In a sealed partition, `produceCheckpoint(..., sealed, keys)` seals the snapshot with the
  partition's newest content key. The AAD is the document address and the lineage, and the bytes
  start with a 4-byte marker. Key 7 hashes the sealed bytes, so the host stores and serves
  exactly what was signed.
- With no key for the partition, the checkpoint is refused as `SnapshotUnsealable`, never produced
  in the clear.
- `installProvisional` (the host) refuses a sealed partition's checkpoint whose snapshot is not
  sealed, and keeps the ciphertext.
- `installCheckpoint(..., sealed, keys)` (a device) opens the seal under the epoch it names before
  the adapter reads it, and keeps the plaintext locally (it holds the key). It refuses a plain
  snapshot, a missing key, a wrong key, and bytes lifted onto another document.
- `createDocuments({ keys, sealedKinds })` threads both. `sealedKinds` defaults to `derive`'s, so
  a runtime with no derive functions still knows which partitions are sealed.
- Tests: `loro/derive.test` covers ciphertext at the host with no plaintext and none of the text
  inside, the no-key refusal, the host refusing a plain snapshot, and a joiner opening the
  host's bytes, with the keyless, wrong-key and lifted cases each refused.

### Where it departs

- **The relay seed and Durable Object session keys stay plaintext.** N26 names three secrets;
  this builds the device's. `relay/src/host.ts` and `adapters/cloudflare-do` are servers with no
  keystore, and the `SecretStore` vault does not reach them yet.
- **Not one vault per backend on Node.** No OS keychain module is a dependency. Node and Bun
  refuse without a vault, and the keychain is the app's `SecretStore` (the doc example uses
  `@napi-rs/keyring`).
- **`secure_delete` is defence in depth, not a measured fix.** On the SQLite builds tested
  (bun's, `secure_delete = 2` by default, and with it forced to 0) the WAL checkpoint is what
  takes the old bytes out of the files, and the test fails without it. Overwriting the row in
  place did not leave them in free space in any case tried, so no test fails without
  `secure_delete`.
- **Strict capture guards against mistakes, not a hostile writer.** A role that can set
  `syncmesh.armed` (Postgres) or update `syncmesh_capture` (SQLite) gets past it. That is the
  threat model's §4.5, unchanged.
- **Postgres `ENABLE ALWAYS` needs the table's owner.** A migrating role that holds `TRIGGER` but
  does not own the table fails the install, and it fails loudly.
- **An opaque host with the adapter configured still tries to materialise a sealed partition's
  document.** It holds no key, so the load fails and is reported through `onError`. Sealed
  partitions' events carry no readable doc changes there anyway (§7.2).
- **Breaking, and where a boot is now refused.** Raw SQL writes to synced tables raise by
  default. `deviceIdentity` with no vault is refused on Bun, Node and React Native. In a browser
  where `indexedDB` exists but opening it fails (older Firefox private windows, some locked-down
  webviews), `platformVault()` is still chosen and the boot is refused, where before it opened with
  a plaintext seed. Such an app passes `createPlaintextVault()` knowingly.
- **A data-only restore into Postgres needs `--disable-triggers`.** The guard refuses a
  `pg_restore --data-only` or a `COPY` into a synced table, because those writes are made with
  capture at rest. A full restore is fine: triggers are created after the data.
- **The opaque host must be told which kinds are sealed.** Its refusal of an unsealed snapshot
  fires only when it knows the partition is sealed, from `createDocuments({ sealedKinds })` or
  `derive`'s `sealedKinds`. A host built with neither keeps a plaintext snapshot it is sent.
- **No wire change.** The seal is inside the blob key 7 names, so `DocCheckpoint` and its vectors
  are unchanged. Rust has no doc checkpoints yet.
