---
id: D44
title: A gated room checks blob puts and fetches against the socket's grant
status: decided
decided: A
epics: [E15, E24]
---

## Context

D40 gates a room's rows by grant: a socket is served the partitions its verified grant covers.
Blobs were left outside that gate (E15):

- **Puts.** `blob-put` carries the partition the bytes are billed to, as the putter's claim. The
  relay does not check it, so one socket can fill another partition's quota with junk bytes and
  that partition's real puts are refused until the junk is swept.
- **Fetches.** A blob is addressed by its hash. Anyone holding the hash can fetch the bytes from
  the room, whatever their grant. A hash leaks easily (a row a device was once entitled to, a log
  line, a URL), so in a gated room the hash works as a bearer secret: the posture D40 rejected
  for rows.

RFC-0023 §10 already says blob fetches of doc bytes require custody of the partition.

## Options

- **A · Check both in a gated room.** A put whose claimed partition the socket's grant does not
  cover is refused with `blob-refused` code `ungranted`. A fetch is served only when the blob is
  referenced by a row in a partition the socket is entitled to, or the socket put it itself. The
  relay already tracks references for the sweep (`blob-keeper.ts`), so the check reuses them.
- **B · Check puts only.** Closes the quota attack, keeps hash-as-bearer for reads.
- **C · Leave both.** Document that a blob hash is a bearer secret.

## Decision

**A**, decided 2026-11-08 (Jace delegated the call). An open room (`open: true`) keeps today's
behaviour, where a room name is already a bearer secret. Sealed partitions are checked too: the
bytes are ciphertext, but a fetch still costs the operator bandwidth and reveals size and timing.
An unreadable blob is answered `blob-missing`, the same as an absent one, so a refusal does not
confirm the blob exists.

**What authorises a fetch: where the bytes were put, not who names them** (amended 2026-11-08,
before the build). Option A as first written served a fetch when "the blob is referenced by a row
in a partition the socket is entitled to". Review found that unsound: any socket can write a hash
it has seen into a row of its own partition, so a leaked hash plus one write would authorise the
read. The rule built instead:

- A put in a gated room is checked first: billed to a partition the socket's grant does not name,
  it is refused `blob-refused` code `ungranted`, nothing is stored, and the client answers
  `BlobNotGranted { partition }`.
- Every put that lands records the partition it was billed to as one of the blob's **homes**. A
  put carries the bytes and the relay verifies them against the hash before recording anything,
  so a home is claimed only by someone who held the bytes. A second put of the same bytes into
  another partition adds that partition: a member holding the bytes shares them with it.
- A fetch is served when the socket's grant names one of the blob's homes. A row naming the hash
  authorises nothing. "The socket put it itself" needs no separate record: it was checked against
  its own grant when it put.
- A put that names no partition has no partition home and is readable by every seated socket, as
  an unpinned row is. An app that wants a blob gated names the partition, which it already does to
  be billed to one.
- Sealed partitions need nothing extra: the partition rides in the clear on `blob-put`, so the
  relay checks and records it without reading a sealed row.

Homes are kept beside the bytes: a `blob_homes` table on the same database, opened by every
durable host (`startRelay`'s file-backed rooms, the Durable Object, the Rivet actor). A room with no
durable store keeps them in memory.

## Watch out

- **Blobs put before this build have no home.** A gated room answers `blob-missing` for them until
  somebody holding the bytes puts them again, which records the home. Failing closed was chosen
  over serving every seated socket: the room cannot tell whose they were.
- **No race with the row.** Because the put, not the row, authorises, a fetch never waits on a row
  event reaching the relay. The earlier text leaned on a client retry after `blob-missing`; there
  is none (`createBlobs.fetch` asks each carrier once), and none is needed now.
- A narrowed grant narrows fetches at once (the socket is closed and re-seated, D40); bytes already
  on a device follow D45.

## Built (2026-11-08)

On `feat/gated-blobs-and-purge`:

- `relay/src/ingest.ts` `serveBlob`: the put check (`ungranted`) and the fetch check, given the
  seat's partitions — `seat.ts` `blobPartitions()`, which reads the grant the socket sat down
  under (or its renewal) and is `undefined` in an open room.
- `relay/src/blob-keeper.ts`: every verified put records its home; `readable(hash, partitions)`
  answers the fetch check; a sweep forgets the homes of what it deletes.
- `storage/src/blob-homes.ts`: the `BlobHomes` port, `memoryBlobHomes()` and `sqlBlobHomes(driver)`.
  `RoomStore.blobHomes` carries it; `durableRoomStore`, `adapters/cloudflare-do` and
  `adapters/rivet` open it next to the blob store.
- Wire: `blob-refused` code `ungranted` with the partition (no new tag). `BlobRefusal` is now a
  union (`quota` | `ungranted`); `@syncmesh/client` exports `BlobNotGranted`.
- Tests: `relay/src/__tests__/gated-blobs.test.ts` (the ungranted put; served to the right grant
  only; the leaked hash written into the attacker's own row; junk bytes under the hash; unpinned
  puts; a second put opening another partition; homes surviving a reopen over SQLite) and
  `client/src/__tests__/narrowing.test.ts` (`BlobNotGranted`, and a leaked hash answering
  `BlobNotFound`, through a real relay).

Where it departs from the text above: the Rust room does not check grants (it has no gate), and a
blob's homes are never pruned when a partition is removed from every grant — the bytes stay
readable by whoever is granted that partition later.
