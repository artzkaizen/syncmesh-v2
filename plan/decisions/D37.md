## Context

D35 put a Rust core beneath the TypeScript and gated it on the vectors: canonical CBOR, identity,
the HLC, the lattice fold, every codec, framing, the handshake and the relay's control frames all
pass byte for byte from `crates/syncmesh-core`. What the core deliberately is not is a running
thing. It can sign an event and open a sealed frame; it cannot join a room, hold a log, fold a
page in order, re-dial a relay or keep a cursor alive. Every one of those still lives only in
TypeScript, and the owner's native app (licnep, Rust, GPUI) — the consumer D35 named first — has
no way to sync a row without a JavaScript runtime beside it.

The TypeScript client is about 19 000 lines across `engine`, `client`, `relay`, `transport`,
`storage` and `wire`. Most of it is the mesh manager, the radio media, the policy ladder, the
Drizzle and React faces and the devtools — none of which a first native consumer needs. What it
needs is the device: numbering, signing, appending, folding, a durable log, the relay protocol
(D33/D36), presence (D16) and blobs (D18).

## Options

- **A · Bind the TypeScript client into the native app.** A JavaScript engine in a design tool
  to sync rows. Rejected by D35 already, for the same reasons.
- **B · A second crate, `syncmesh-client`, on top of the core: the device, sans-IO.** The engine
  (`mutate`, `receive_batch`, coverage, quarantine), the store contracts with memory and SQLite
  implementations, the relay link as a state machine that takes socket bytes and clock readings
  and hands back frames and facts, an in-process room (the server half, as the test double and
  later the embeddable relay), presence and blobs and the grant registry, and one optional tokio
  WebSocket driver behind a feature. Nothing inside the crate owns a socket, a timer or a
  runtime; a GPUI app, a test and a tokio task drive the same machine. The TypeScript client, its
  hooks, Drizzle, the radios, policy and devtools stay where they are.
- **C · Port the whole client.** Rejected as D35 rejected C: the parts above the fold have no
  reason to leave the language their consumers are written in, and a Rust mesh manager for radios
  a Rust app does not have yet is work with no consumer.

## Decision

**B.** `crates/syncmesh-client`, `@syncmesh/client-rs` in the Bun workspace so `bun run test`
runs its `cargo test`. What it is measured against, in order:

1. **The TypeScript relay and client, live.** `tests/interop.rs` starts `startRelay` and a
   TypeScript peer under Bun, joins from Rust over a real WebSocket through the D36 handshake,
   and proves convergence in both directions with the relay key pinned. This is the acceptance
   test of the crate the way the vectors are the acceptance test of the core; a slice that does
   not survive it is not done.
2. **An in-process room** (`room.rs`), the server half ported from `relay/src/connection.ts`
   and friends, so every link behaviour — pinning, version refusal, the challenge path for rooms
   listing 2, liveness, backoff, holdback and resync, scoped coverage, presence, grants, blobs —
   has a synchronous test with explicit clocks and no sockets.
3. **Property tests** on the engine: several devices, random writes across strategies and
   partitions, every delivery order and batching, one state.

Deliberate differences from the TypeScript, each stated in the code:

- **Signing at `mutate`.** A Rust entry this device authored always carries its core and
  signature; the TypeScript signs in the transport and special-cases own writes when forwarding.
  Nothing on the wire changes — the bytes are the same envelope — and a log can never hold an own
  write it cannot send.
- **A validator only when given one.** With `EngineOptions.validator` a Rust device runs the
  TypeScript's ladder over the manifest as data (gap U3, below); without one it folds what
  verifies and parks only what it has no fold for (D22-A) and the doc changes the declared doc
  columns refuse, as a TypeScript device with no schema does. Grants are registered, kept and
  forwarded either way so a TypeScript peer's ladder sees them.
- ~~**No local scope.** `Coverage.local` travels empty. A device that needs writes which never
  leave it gets them when something asks.~~ Built (gap U3, below): `Engine::mutate_local`.
- **Stores are synchronous.** SQLite is called on the thread that holds the engine; a host that
  wants the work off its UI thread moves the whole device there (the driver does).

## What this costs

- A second Rust crate to keep beside the TypeScript. The interop test is what keeps them honest:
  a protocol change now costs a vector, a TypeScript change, a core change and a client change.
- rusqlite (bundled) and, behind a feature, tokio and tungstenite in the build.

## Watch out

- **The room speaks first (D33/D36).** A driver that subscribes to socket frames after the
  connection opens has already lost the hello on some runtimes; the driver reads before it
  hands the socket to anything else, and the link's `on_bytes` is the only entry for bytes.
- **Holdback and `holding()`.** The cursor alone is not "how far this device holds an author":
  a parked event is held and never folded. Draining from the cursor would hold every later event
  from that author back forever (D13). The Rust holdback asks `Engine::holding` exactly as the
  TypeScript asks `engine.holding()`.
- **A scoped cursor is a claim about a slice (D23).** Widening the interest past the scope
  re-pages from nothing; narrowing keeps the cursor. `interest::narrows` answers `false` when
  unsure, on purpose.
- **Cursor order on the wire.** The TypeScript encodes its `Map` in insertion order; the Rust
  stores use `BTreeMap`. The join core is re-encoded by the room from what it decoded, so the
  order a client sends never has to match another client's — but a vector that froze a join with
  several cursors would freeze one order, and a port must reproduce the vector's, not its own.

## Landed

- **2026-09-27 — `crates/syncmesh-client`, the whole device.** `engine` (sign at `mutate`, dedup,
  fold, quarantine, coverage tracker, D34 clock), `store` (contracts + memory), `sqlite` (log, rows,
  coverage, blobs; one file, WAL), `interest` (`JSON.stringify`-exact text, `narrows`), `holdback`,
  `relay` (`RelayLink`: D36 handshake, pinning, version refusal, the D33 challenge path for rooms
  listing 2, liveness at 2.5× keepalive, backoff 500→30000, pages and holdback, scoped coverage
  and re-paging, push after the last page, cursors on remote folds, presence/grant/blob frames as
  `Action`s), `room` (the server half: hello, join, catch-up pages, ingest + ack + fan-out, grants,
  presence replay, blobs), `presence` (codec against `presence-vectors.json`, store, tier with
  heartbeats), `blobs`, `grants`, and behind `tokio`: `driver::run_link`, `driver::serve_room` (a
  room behind a WebSocket listener) and `mesh::Mesh` (engine + link + tier + registry + blobs as
  one object). Proven by `tests/interop.rs` (Rust device ↔ TypeScript relay + peer under Bun, both
  directions, key pinned), `tests/relay_link.rs` (13 link behaviours against the Rust room with
  explicit clocks), `tests/mesh.rs` (two meshes through `serve_room`: rows, presence, blobs, a
  wrong pin refused), `tests/convergence.rs` (proptest: 4 engines, every order and batching, one
  state), `tests/sqlite_stores.rs` (reopen after a crash between append and commit). 42 unit +
  25 integration tests; clippy clean. First consumer: licnep's `canvas-sync`.
- Ported faithfully and worth a look upstream: the client hangs up on *every* `error` frame,
  including non-fatal ones (`bad-event`, `malformed`), then redials; and under a scoped interest a
  live relayed event above a filtered hole waits in the holdback until the next re-join (the
  scanned coverage only rides catch-up pages).
- Deviation: nothing but our hello leaves before the room has spoken; a presence or grant asked
  for earlier is `Dropped` rather than sent in the clear, which a v3 room would refuse anyway.

## Built: the policy ladder (gap U3, #32)

Decided 2026-11-08 (Jace delegated the call): port the shared validator whole, driven by the
manifest as data, rather than a `replace` check on its own (RFC-0023 §11).

- `portableSchema(schema)` (`packages/schema/src/portable.ts`) writes what every rung reads: each
  table's partition kind, visibility, retired flag, columns (kind, nullability, merge, document
  adapter, derived source, retired) and `allow` block; every kind's roles; the reserved tables'
  columns; the dropped tables. `syncmesh_client::Manifest` reads it back.
- `syncmesh_core::policy` is `@syncmesh/policy`: the AST, `resolve` (with `replace` falling back
  to `update`), `evaluate` (strings ordered by UTF-16 code unit, as JavaScript orders them) and
  the `_policy` row parser.
- `syncmesh_client::validate` is `engine/src/validate.ts` with `author.ts`, `reserved.ts`,
  `retired.ts`, `columns.ts`, `doc-rules.ts`, `rules.ts` and the link half of `accounts.ts`: the
  same rungs in the same order, the same `ValidationError` tags (and rungs), the same buckets.
  The engine judges a batch with what it already admitted (`admit.ts`'s overlay), re-offers
  refused events once after a fold (`withRetry`), and judges its own writes as probes. `Mesh`
  makes the validator granted, over its registry, when an issuer is configured and the caller
  supplied no grant source, as the TypeScript client does. Its link registers a page's grants (and
  a grant frame's) into that registry before anything beside them folds, as `session.ts` onPage
  does, so a late joiner admits an event whose grant came on the same page
  (`RelayLink::with_grants`). A grant the registry refuses is said as `Dropped`.
- The ladder judges doc changes against the doc columns the engine folds by: the manifest's, or
  `EngineOptions.docs` when given. A `_links` signature is verified once per wire, as
  `accounts.ts` memoises it, not once per event judged.
- Merged with #31: a persisted lineage cell of another rule makes `Engine::open` clear the state
  and refold the log (`refused_at_open`) whichever source the doc columns came from, the manifest's
  included; `EngineOptions.derived` still refuses a local write naming a derived column on an
  engine with no validator, and with one the probe refuses it first as `DocColumnWrite`.
- `conformance/policy-vectors.json` freezes the verdict per event, the rows after, and the probe
  verdicts; `conformance/src/__tests__/policy-vectors.test.ts` and
  `crates/syncmesh-client/tests/policy_vectors.rs` replay it.

Where it departs:

- ~~A column's `check()` schema is a function and is not ported; the manifest marks those columns
  `check: true` and `Manifest::checked_columns` lists them. A write only a check refuses folds
  here and parks on a TypeScript peer.~~ Ported as JSON Schema (below).
- ~~This crate writes no local events, so the `local` rung always says `LocalOnly`.~~ Built (below).
- The quarantine is now bounded per reason (default 128, the TypeScript's), not 1000 in all.
- A retry's fold is merged into the `Received` the batch returns rather than notified on its own.
- A `_links` row whose `at` is not a whole number is refused (`columns`); the TypeScript throws
  building the instant from it.
- ~~The UI's `can()` is not ported; nothing in this crate asks it.~~ Ported (below).

## Built: `check()`, `can()`, the local rung and the join exchange (gaps U3, U31)

Decided 2026-11-08 (Jace delegated the call): close #32's departures and give the device D46's
join exchange.

- **`check()` as JSON Schema.** `portableSchema` writes a column's check as `checkSchema` when its
  validator implements the Standard JSON Schema extension (`~standard.jsonSchema.input`, draft
  2020-12; zod 4 carries it), and the Rust validator runs it with the `jsonschema` crate. That
  crate translates an ECMA pattern's `\d`, `\w`, `\s` and `.` to JavaScript's sets only when the
  pattern has no lookaround or backreference; one with a lookahead runs as written in
  fancy-regex, where they are Unicode's. So `portableSchema` spells those sets out (below), and a
  zod `.regex()` or `z.email()` pattern means the same thing in both. A failing value is
  `SchemaViolation`, as in TypeScript. A host's own `ValidatorOptions::checks` entry for a column
  replaces its schema there; `Manifest::unported_checks` lists checked columns with no schema.
  `conformance/policy-vectors.json` gained a `checked` table (regex, integer bounds, an email,
  an object with an enum) whose verdicts both runtimes reach.
- **`can()`.** `Validator::can` is `engine/src/can.ts` (the synced `_policy` row preferred over the
  manifest's block, the reserved kinds' defaults), `Validator::principal` resolves a device the
  way the ladder does (grant, else a `_links` row in an accounts mesh), and `Engine::can` is
  `client/src/can.ts` (`mesh.can`: the account's own instance for a `user` table). In an
  accounts mesh with no instance named, the principal is the account every one of the device's
  `_links` rows agrees on (`linkedAccount`), none when two instances name two accounts. `Mesh`
  has `can` and `mutate_local` too. The vectors'
  `can` list (22 questions over the rows the steps left) is answered by both runtimes.
- **The local rung.** `Engine::mutate_local` numbers a write in its own run (`peer-L1`), folds and
  keeps it (`StoredEvent::local`, a `local` column in the SQLite log, added to an older log on
  open), never signs it and never offers it to a peer (`EventStore::all_since` is synced only,
  `local_since` and `last_local_seq` are the local run). `Coverage.local` counts it, a boot
  replays it, and a revert of one is local too, as `engine/src/revert.ts` keeps the locality of the
  write it answers. The validator's probe carries `local`: a `local`
  table takes it, any other write to one is `LocalOnly`, and a document change on one is
  `DocChangeRefused` (rung `local`), with or without a validator. The vectors' probes include
  local writes.
- **The join exchange (U31)**: `syncmesh_client::join` and `rejoin`, D46's "Built in Rust".

Where it departs:

- **A port's check is never stricter than the function** (decided 2026-11-08, Jace delegated the
  call; PR #35 review). zod's converter can say more than the function accepts: a `/…/i` regex
  becomes a flagless `pattern`, a `.catch()`, `z.preprocess` or `z.coerce` becomes the inner
  type, a `.trim()` or other rewrite drops out before the length it bounds, `.min(n)` counts UTF-16
  units where JSON Schema counts code points, and a fractional `multipleOf` is float division in
  the `jsonschema` crate. A Rust device would then park an event every TypeScript peer folds.
  `portableSchema` passes zod an `override` that leaves those parts out: catch, preprocess and
  coerce accept any value, a rewritten string or one whose regex carries `i`, `m` or `s` keeps
  only its type, `minLength` becomes `ceil(n / 2)`, a fractional `multipleOf` is dropped. Only
  zod's converter shows `portableSchema` each node, so a check from any other vendor travels as
  the `check` flag alone. `portable.test.ts` holds each case, and the vectors' `checked` table
  has an `/…/i` column and a `.min(2)` column with an event (`"AB"`, `"😀"`) TypeScript folds and
  Rust parked before the fix. Round 2 of the review: without `u`, JavaScript matches `.`, a
  negated class and `\D`, `\W`, `\S` one UTF-16 unit at a time, so `/^.{2}$/` passes `"😀"` and
  Rust's engine, counting code points, refused it. `portableSchema` keeps a pattern only when every
  such atom is a `*` run (which takes the same strings either way) and it has no literal outside
  the BMP, no `\b` (Unicode-aware in Rust, ASCII in JavaScript), no backreference, named group,
  lookbehind, `\p`, `\u` or `\c` escape, no nested or empty class and no `v` flag; otherwise
  the string keeps only its type. zod's own formats (email, uuid, the ISO dates, IPs, base64)
  still travel. The vectors gained a `dotted` column (`/^.{2}$/`) on `c9`. A `checkSchema` this
  build cannot compile (a JavaScript-only regex) no longer makes the manifest unreadable: the
  column is flagged with no schema (`Manifest::unported_checks`), so one regex cannot lock a Rust
  device out of the ladder. Round 3: a pattern with a lookahead skips the crate's translation, so
  `/^(?!x)\D*$/` refused `"٣"` (Arabic-Indic three, no ASCII digit) in Rust while zod took it.
  `portableSchema` now writes every pattern with `.`, `\d`, `\w`, `\s`, `\D`, `\W` and `\S`
  spelled as the literal classes JavaScript means (`.` is `[^\n\r\u2028\u2029]`, `\s` its
  whitespace list), which every engine reads alike, translated or not. A negated shorthand inside
  a class, a shorthand beside a `-` in a class, and `{,n}` (JavaScript's literal text, Rust's
  count) keep only the type. It now also reads the pattern a `z.templateLiteral` states (zod's
  check is that regex alone: `^[\s\S]{2,2}$` passed `"😀"` in zod and failed in Rust) and a
  `z.looseRecord`'s key patterns (`patternProperties`). zod's email keeps its pattern, spelled. A
  match fancy-regex stops at its backtrack limit is undecided, and the `jsonschema` crate's
  `is_valid` calls that invalid where JavaScript would backtrack to the end; `CheckSchema::accepts`
  takes a value whose only errors are such undecided matches. The vectors gained a `looked`
  column (`/^(?!x)\D*$/`) and a `templated` column on `c9` (`"٣"`, `"😀"`), each of which Rust
  parked alone before the fix.
- JSON Schema says what a check accepts only as far as the validator can say it: a `.refine()`
  is dropped from zod's output, so such a column carries a weaker schema and a Rust device folds a
  write only the refinement refuses, unless the host registers a check for it. A check with no
  JSON Schema at all (`z.custom`, or a validator without the extension) is flagged `check` with
  no schema and not run here. A blob column's value has no JSON form, so its check is the host's.
- JSON Schema `format` is read as an annotation, as draft 2020-12 has it; zod writes the pattern
  it validates by beside the format, and that pattern is what runs. Asserting formats would make
  Rust stricter (zod's `z.iso.datetime({ local: true })` says `date-time`, which an asserting
  validator refuses for a local time), so `CheckSchema::compile` must not turn it on. Where zod
  writes a format and no pattern (`z.url()`, `z.jwt()`), the check runs in Rust as its type only
  and is looser than zod's.
- ~~Still open, and U3's: radios (a Rust peer link). Without one, `PeerJoin` is driven by a host's
  own link.~~ Built: see "Built: radios" below.

## Built: radios, a Rust peer link (gap U3, #48)

Decided 2026-11-09 (Jace delegated the call): the TypeScript's upgrader and bridge are ported
whole as one sans-IO machine over a byte duplex, rather than a Rust BLE stack or a Rust mesh
manager. D37's option C stays rejected: discovery, the door's policy, the route scorer and the
link budget stay the host's, and a host hands the link whatever its medium reached.

- `syncmesh_client::peer`: `PeerLink` is `upgrade.ts` + `session.ts` + `framing.ts` +
  `bridge.ts`. Both ends send a signed hello unprompted; the keys come from the pair, and every
  frame after is sealed. A second hello from the proved peer supersedes the session (answered with
  a fresh hello only once the peer has used ours, so two live sessions never re-key each other
  forever), and one this link already agreed a session under is dropped (64 remembered, as
  `KEYS_REMEMBERED`). `peer_key` pins the far key; `admits` is the door, asked once the hello
  proved the peer. `PeerSession` is the bridge over plaintext frames: grants then cursors on open
  (`ahead` always present, the floor at 4 and the schema at 5, as `cursorsAfter` writes them); a
  cursors frame answered with the events the far side lacks less what it holds above its cursor,
  a digest, the refusals still parked for it, a join request when this device is below its floor,
  then our cursors when it is ahead; the holdback's gap rule on arrival, a fold announced with our
  cursors, a receipt per fold when an `incarnation` is set and a signed refusal per newly parked
  event (once per seating); presence slotted by `(topic, instance, author)`; and the join exchange
  through `PeerJoin` over the `Rejoins` the options name. Liveness is `createLiveness`: prodded with
  our cursors after a keepalive of silence (5s), hung up on past 2.5 times it.
- `Framing`: `STREAM` (the four-byte length of `framed`), `Messages` (one frame per message, the
  upgrader's `frames`), and `fragments(write_limit)` (the BLE header of `fragment.ts`, ported as
  `syncmesh_core::fragment` and measured against `conformance/fragment-vectors.json`, reassembled
  in any order with the TypeScript's caps; a marker for a message past the size cap counts
  against the table's bound in both runtimes, where the TypeScript let markers pile up past
  `maxAssemblies` until a live partial arrived).
- `syncmesh_client::digest` is `engine/src/digest.ts` and `divergence.ts` (`interest_key` is
  `interestKey`): a peer link answers every cursors frame with one, which is also what keeps the
  far side's liveness deadline from firing on a quiet link, and reports `Divergence` only over the
  same slice, cursors and events held above them.
- Behind `tokio`: `driver::run_peer` over any `PeerMedium`, which splits into a `PeerRead` and a
  `PeerWrite` half so a queue drains to the medium while the link keeps reading (two devices that
  each owe the other more than the medium buffers do not block each other in a write; a presence
  value still queued is replaced under its slot, D16) (`StreamMedium` for `AsyncRead +
  AsyncWrite`, `MessageMedium` for a `Stream + Sink` of messages), and `Mesh::attach_peer`, which
  shares the mesh's registry and `Rejoins`, hands the link every write, presence value, heartbeat
  and fold from elsewhere, hands the relay and the other links what it folds, and says its other
  facts (a grant request it carried included) as `MeshEvent::Peer` under a `PeerLinkId` unique per
  attach. It returns a `PeerHandle` that hands the link any `PeerCommand`, so D46's accept, a
  snapshot or grant request, grants and a close reach a link `Mesh` runs.
- Proven by `conformance/peer-link-vectors.json` (`generate-peer-link-vectors.ts`, frozen by
  `peer-link-vectors.test.ts`): a holder's open and its answers to five cursors frames, and a
  receiver's frames after each event in three arrival orders, which `tests/peer_vectors.rs` matches
  byte for byte; by `tests/peer_interop.rs`, a Rust device linked to the TypeScript LAN transport
  (`lan` on `@syncmesh/lan-node`, TCP) and to the TypeScript BLE link (`bleLink` as the
  peripheral, its packets over a socket) through `conformance/src/interop/peer-device.ts`: rows
  both ways, presence both ways, a snapshot asked each way, and, over the LAN, 13 quiet seconds
  past both sides' deadlines with the link still up; by `tests/peer_link.rs` (20 cases with explicit
  clocks: each framing, a stream split byte by byte, fragments reversed, the pin, the door, a
  restart superseding the session and a replayed hello dropped, the gap rule and its overflow, the
  answer to cursors, divergence, receipts, refusals once per seating, presence slots, a join, a
  floor accepted, liveness, an oversized length, hellos crossing on a live link settling rather
  than re-keying forever, an event parked ahead of its author's grant folding when the grant
  arrives on the link, as `RelayLink` does since gaps U42, and a grant the registry refuses said
  dropped rather than reported); and by `tests/mesh.rs`, two meshes whose relay is unreachable
  converging over a peer link, two meshes each owing the other 60 events over a 1 KiB pipe
  converging, a hub's two same-named links handing each other's folds on, and a
  host commanding a link through its handle (a grant asked and answered, a snapshot, a close).

Where it departs:

- No read gate (D40) and no route table (book ch. 17), as a TypeScript bridge with neither: every
  event goes to every peer, an arriving `withheld` frame is ignored (the TypeScript takes one only
  under a gate), and `routes` frames are neither sent nor read. A Rust device that must withhold
  per peer is not one this builds.
- The outbox orders by tag within one call, which is the TypeScript's turn of the event loop;
  cursors that follow an exchange or a fold leave after it, as the TypeScript queues them. The
  vectors are built so this is the same bytes.
- A frame offered before the session is open has nowhere to go: the TypeScript attaches the bridge
  only after the hello and the door, so nothing is offered earlier there either. A local write
  made then crosses with the cursors the session opens with; a presence value is dropped, as D16
  drops rather than queues.
- A grant that arrives is registered and reported, and not echoed back down the link it came on
  (the TypeScript's registry hook sends a newly registered grant to every link, that one
  included). Further than that: `Mesh` forwards no grant between links at all, so a grant learned
  on the relay or on one peer link reaches another peer link only when that link opens, or when
  the host sends it through the link's `PeerHandle` (`PeerCommand::Grants`). Decided 2026-11-09
  (Jace delegated the call): a registry hook that forwards only newly registered grants is the
  fix, and is not built here.
