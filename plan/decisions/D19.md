## Context

In a database, `default` is DDL: the server fills the column once, at insert, and the stored row carries the value forever. syncmesh has no server engine — the client is the writer of record, and the replicated log is the source of truth — so a default has to be resolved *somewhere*, and where it is resolved decides what two peers on different app versions read for the same row.

The schema DSL shipped with `.default(value)` and resolved it in two places at once: `withDefaults` pinned the value into the log at insert (rows written after the column existed carried it forever), while `fromWireRow` re-applied the *current* default to any row lacking the cell (rows predating the column floated with the reader's schema version). Changing a default therefore had two different meanings depending on row age, and peers on different app versions disagreed about the content of the same legacy row — same log, different rows, diverging live-query results.

## Options

- **A · Keep defaults, pin at write only** (Drizzle's stored-row shape): drop the read-time fallback. A row that predates a non-nullable defaulted column then reads `null` where `Row<T>` promises `T` — the type lies exactly where the feature was supposed to help.
- **B · No defaults** (Zero's posture): a column is required on insert or it is `.nullable()`; an absent cell always reads as `null`, on every peer, at every app version. App-level fill values live at the call site or in the app's own insert wrappers.
- **C · Read-time only** (LiveStore's posture): never write the default, always resolve absence at read. One uniform rule, but the value a row "has" changes with the reader's schema version by design — coherent for LiveStore because its tables are a disposable materialisation of an event log; incoherent here, where the tables *are* the synced thing.
- **D · Keep both, freeze defaults in the manifest**: changing a default becomes a refused schema change. Keeps the ergonomics, but the two-sided semantics stays and must be explained forever.

## Decision

**B — columns have no defaults. Absence always means `null`.**

- One rule a reader can hold: no value is ever conjured by the reader, so peers on different schema versions cannot disagree about a row's contents. What the log says is what every peer sees.
- `InsertRow<T>` optionality is nullability alone. An insert still writes explicit `null`s for omitted nullable columns (`withNulls`), so the wire shape of inserted rows is unchanged and existing logs stay valid.
- `fromDrizzle` never carries a default — literal, `defaultFn` or SQL. Every Drizzle default warns and leaves the column required (or nullable-reading-as-null), because a value the database would have filled is a value no other peer would ever see.
- Deliberately accepted, and what this constrains in **E18**: adding a column to a table with existing rows must be `.nullable()` — there is no backfill mechanism, and this makes that honest instead of papered over. D13's additive-only option narrows accordingly: *add nullable columns*, not "optional/defaulted".

## Watch out

The pressure to reintroduce defaults will come back as "every insert now spells `starred: false`". The answer is an app-layer wrapper around `insert`, not a schema feature — the moment the schema carries a fill value, the where-is-it-resolved question returns with it. If E26's rich column kinds ever need a seed value (a counter's zero), that is the strategy's identity element, defined by the kind, not a per-table default.
