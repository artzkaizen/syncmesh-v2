## Context

E27 opens with "Decide first: is this a supported shape or a demo?" Company OS has decided the
question for us: the inbox, the call log and the mail store are tables of millions of rows, and a
web tab shows a window of fifty. A device that folds holds whole partitions (book ch. 3, E13's
rescope), and a mail partition is not something a browser tab should replicate to render one
screen. Without a windowed shape, the web half of Company OS has nowhere to stand.

Three facts on `main` (2026-11-07) bound the answer:

1. **The relay folds nothing.** A room holds a log of signed event bytes (`relay/src/room.ts`).
   It has no state store, no rows and no projection. To window a table it would have to fold
   one first.
2. **The relay holds no payload keys.** A sealed partition's events reach it as opaque bytes
   (`SyncEvent.sealed`, D22-A). An unsealed event's cells can be read, but reading cells is not
   holding rows. The relay would still have to fold every event for the room to know what a row
   *is* now.
3. **Interest narrows by partition and nothing finer** (`engine/src/interest.ts`). The table and
   `where` filters were removed from the wire filter because a filtered log does not fold to
   identical state. A window is the place where row-level narrowing belongs, because a window
   is *not* folded.

## What the relay can and cannot order or filter on

|                                                                | relay room (log only) | row-holding peer |
| -------------------------------------------------------------- | --------------------- | ---------------- |
| partition (envelope, always cleartext)                         | filter                | filter           |
| author, sequence, HLC (envelope)                               | filter, order         | filter, order    |
| table, row key, cells of an **unsealed** event                 | read, never fold      | fold, filter, order |
| anything inside a **sealed** event                             | nothing               | fold if it holds the key |
| the current value of a row                                     | nothing (no rows)     | everything       |
| `ORDER BY column LIMIT n` over current rows                    | nothing               | yes              |

So the relay can serve partition interest (E13, built), and that is where its reach ends. Any
query that names a column ordering or a cell predicate needs folded state, so it runs on a peer
that has folded state.

## Options

- **A · A demo.** Keep E27 as a sketch. Company OS's web client then replicates whole
  partitions or uses a bespoke REST endpoint beside syncmesh. Either option leaves two
  read paths that disagree about freshness.
- **B · Supported: the row path runs on a row-holding peer, not in the relay room.** One
  socket's server windows (`createServerWindows`) live in a peer that already holds rows: a
  server beside the app's Postgres, where the rows are the app's own tables and E20's logical
  replication says when they change. The relay package ships the socket handler
  (`serveWindows`) and its E12 backpressure, so any host can mount it over a `PageSource`. A
  relay room with no `PageSource` serves no windows. The relay keeps its current posture ("the
  relay interprets nothing").
- **C · Supported, and the relay folds.** The relay grows a state store per room and maintains
  views itself. This contradicts fact 2 for sealed partitions, multiplies relay memory by every
  room's state, and turns the one component an attacker can reach (E24) into one that executes
  queries. Rejected.

## Decision

**B**, decided by the owner on 2026-11-07, in the windowed-sync thread, on this draft's recommendation. The wire is three tags in the relay's control space, deliberately above the range the
gated-visibility and read-permission work is filling: `desire` 32, `undesire` 33 and `rows` 34
(`conformance/window-vectors.json`). They are additive in D14's sense: a build that does not
know them reads `unknown` and ignores them.

### The app-facing shape (revised 2026-11-07)

The first cut put a second read API beside `api.*`: `createWindowClient().desire(id, { table,
where, order: [["receivedAt", "desc"]], limit })`. The owner rejected it: wire words in app code,
tuple-array ordering ("this would never be api ever"), and a second thing to learn. A windowed
read is now **just a procedure**, and nothing about it is new to the app:

- **The schema marks the table.** `sync: "window"` is one flat table option beside `partition`
  and `allow`. The server keeps the table and serves pages of it; devices never replicate it.
- **The read is an ordinary `query`.** Its handler is the whole query, written in Drizzle like
  every other read: `where`, `orderBy`, `limit`, and a keyset `after` in its flat input.

  ```ts
  export const inbox = query
    .input(z.object({ folder: z.string(), limit: z.number().int().max(100), after: Cursor.optional() }))
    .handler(({ input, db }) =>
      db.select().from(mail)
        .where(and(eq(mail.folder, input.folder), input.after && sql`(${mail.received}, ${mail.id}) < (${input.after.received}::timestamptz, ${input.after.id})`))
        .orderBy(desc(mail.received), desc(mail.id))
        .limit(input.limit),
    );

  const { data } = useLiveQuery(api.mail.inbox({ folder: "inbox", limit: 50 }));
  // the next page: the same call, with `after` naming the last row shown
  ```

- **Where it runs is decided by the table, not the call.** The device builds the handler's query
  (never runs it), sees that it reads a `sync: "window"` table, and sends `{ path, input }`
  over the window channel instead of reading SQLite. The server runs the same handler against
  Postgres and the rows come back as the same `T` a local read returns: each cell travels as
  its column's driver value and is mapped back through the same column, so a timestamp is a
  `Date` on both sides. `createClient({ windows })` is the one construction-time line; absent,
  such a read fails naming itself rather than showing an empty table.
- **Permission is the procedure's ordinary path.** `servedReads({ router, schema, db, principal })`
  is built for the principal the host authenticated on the socket. Every table the handler
  selects from is replaced by the table as that principal may read it, the read rule compiled
  into SQL (E13: the handler's `where` only ever narrows). It **fails closed**: a table that is
  not `sync: "window"`, or has no rule, is refused, never read. Beneath that, Postgres holds every
  read to the rule (2026-11-08, after review). The read role `servedReadDdl(schema, { role,
  grantTo })` creates may `SELECT` only the served tables that have a rule, and each rule is a
  restrictive row-level policy for it. Served reads connect as a **login of their own**
  (`grantTo`), a member of that role and nothing else: a transaction can always go back to its
  login with `set_config('role', 'none', true)`, so on the app's connection a fragment could read
  as the app. The **principal is a row, not a setting**: `syncmesh_served.enter` writes it into an
  unlogged table before the transaction turns read-only, the policies read it back through
  `syncmesh_served.principal()`, and the transaction is rolled back, so the row is never
  committed. A setting can be changed by any statement that can name it; the row cannot be
  written once the transaction is read-only. So a table named inside a raw `sql` fragment, which
  no query-tree check can see, is filtered or denied by Postgres, whoever the fragment claims to
  be. `readRole` is required; a server without it refuses every read. `enter` checks the login
  on every read, not only when the DDL ran (second review, 2026-11-08): the roles whose
  privileges it has (`pg_has_role(…, 'MEMBER')`, so `pg_read_all_data` or an app role granted to
  the read role counts) must be itself and the read role, it may own or be granted nothing in the
  database, and the read role may be granted no table the DDL does not serve. A handler's `db`
  is **for its read**: it is revoked when the read's rows are in, so one a handler kept (a timer,
  a closure) is refused before it reaches the connection, instead of running in the next
  reader's transaction on that connection, or in none.
- **Live updates come from the database.** `commitFeed` turns any `ChangeSource` (E20's logical
  replication for Postgres) into the tables each commit touched. A window whose read touched one
  of them is read again; the patch carries only rows that changed. The old "can this change move
  the window" check needed the order and `where` as data; with the handler as the query, the
  check is per table. Keyset reads on an index cost one page, so a re-read of a window is
  `limit` rows (measured: 50 of 1M, `served-million.test.ts`).
- **The protocol is the hidden transport.** `desire`/`undesire`/`rows`, epochs, versioned
  patches, per-socket refcounts, `maxWindows` and gap → reset are unchanged. A `desire` carries
  the request text `[path, input]`, and rows are namespaced by the read (`readKey`: the path and
  the input with its keys in order), because two reads, or one procedure called with two inputs,
  may project one row differently (a search snippet).

### The protocol

- **The query is the procedure.** There is no wire query language: a window names a `query`
  procedure and its input, and the procedure's schema parses the input on the server. A page is
  keyset-read (`after` names the last row shown, the row key breaking ties, text under
  `COLLATE "C"`), never `OFFSET`, so a page 500k deep costs what the first does.
- **Patches are versioned (E24).** A socket's stream is `(epoch, version)`, with `version`
  incremented by exactly one per `rows` frame. A frame that is not `last + 1` in the same epoch
  is a gap. On a gap the client re-desires with `since: [epoch, last]`. A server whose stream is
  anywhere else answers with a reset: a new epoch, then every window as a snapshot. A client
  with no position yet names `["", 0]`, which no stream is at. Every reset starts a new epoch,
  so a client still waiting for its reset that sees a patch in an epoch it never saw reset knows
  the reset was lost, and asks again; a `rows` frame that does not decode makes it ask again at
  once. A dropped patch, the reset included, therefore costs one resnapshot, never a silently
  wrong or frozen screen (RFC-0010's lesson). Replaying the missed run
  from a bounded ring is what `since` leaves room for; it is not built. A gap is seen only when
  the next patch arrives: there is no heartbeat, so an idle stream that lost its last patch
  shows the screen before it until the table changes or the client opens another window.
- **A reconnect never blanks a window.** The client rebuilds its rows beside the old screen and
  swaps them in once the new socket has named or refused every window it holds open.
- **Rows are refcounted per socket.** A row reaches the client once, however many of that
  socket's windows hold it, and is evicted (a `del`) when the last window that held it moves
  off. Each window's order travels as its key list, so the thin client needs no engine to
  render in order. The client drops a row only on the server's `del`: until the server reads a
  close it still counts that window's rows as held, and can move one into another window as a
  key with no put. A patch sent in that time may also still name the closed window, and the
  client ignores it. Only with no socket, so no server counting, does a close drop the window's
  rows at once.
- **Work on a socket is serial, and coalesced.** Reads are async, so one step runs at a time.
  While it runs, a window's frames collapse to the latest (a `since` survives any later frame
  for that window, an `undesire` included, as the reset it asks for is still owed), every commit becomes one set of dirty tables, and windows asking the
  same read are read once. A socket has at most one read in flight and one pending per window,
  however many frames or commits arrive: 2000 desires for one id cost one read, not 2000.
- **A read is refused or it failed.** `ReadRefused` (no such procedure, an input the schema
  refuses, a handler that throws while building its query, a table the reader may not read,
  Postgres SQLSTATE classes 42/22/0A/25) closes the window. Two of those, `42501` and `42P01`,
  are also what a deploy looks like while the code is ahead of its migration, so they are
  `ReadFailed` for `grace` (1 minute by default) and refused after. Each statement runs under
  `statement_timeout` (`timeout`, 5 seconds by default); a cancelled read failed. `ReadFailed` (a timeout, a lost connection, anything else) keeps its rows and marks it
  failed in the patch's `failed` list (a ninth, optional element of `rows`, absent when empty, so
  a patch with no failure is the bytes it was). The window is read again after
  `retry` (`{ first: 1s, most: 30s }`, doubling, `backoff` in `@syncmesh/temporal`) or on the
  next commit to a table it reads, whichever is first. On the device, a failed or refused window
  is `status: "error"` with `answered` and its last rows kept, as a local query's failed re-run
  is; a later answer turns it back to `success`.
- **The change feed can die.** `resumableCommitFeed(start)` restarts a failed stream with the same
  backoff and reports `lost` and `resumed` (`PageSource.onFeed`). On `lost` every window is failed
  with the feed's reason and no timer runs, because a read with no feed is stale as it lands; on
  `resumed` every window is read again, since the new stream may have missed any commit. The
  Postgres source rides out a dropped walsender by itself; `lost` means its reconnects ran out.
- **A send that throws closes the socket** (`close` on `createServerWindows`, the socket's own
  `close` in `serveWindows`), rather than leaving a stream with a hole the client can never see.
- **A one-shot read of a served table** (`await api.mail.inbox(…)`) with no socket fails at once
  with `AuthorityUnreachable`, as a call to the authority does, and fails the same way if the
  socket goes before the answer.
- **The thin client** (`@syncmesh/window`'s `createWindowClient`) holds rows and windows in
  memory, applies patches and detects gaps. It imports no engine, store or signer, and the app
  never calls it: the api does.

## What a thin client cannot do (its honest name)

- **Write.** It has no log and no signer for events. Writes go through the app's procedures
  (oRPC, per the procedures decision) on the server peer, and the window then reflects the
  committed row. Nothing in its API looks like `mutate`.
- **Verify rows.** Signatures cover events, and the server peer folded those. The thin client
  trusts the row-holder for the content of a row, as a REST client trusts its API. This is the
  threat-model change E27 warned about, stated here rather than implied away.
- **Work offline beyond the last window.** It can render what it last received and nothing
  else. A reconnect resnapshots.

## What this costs

- The server keeps per-socket state: each window's page and key list. It is bounded by
  configuration and never by table size: a socket holds at most `maxWindows` windows (64 by
  default), each at most the `limit` its procedure's schema allows, and a desire for a new
  window past that is refused.
- A commit to a table re-reads every open window that read it, on every socket. A keyset page on
  an index costs `limit` rows, so the work per commit is `distinct reads × limit` row reads per
  socket, whatever the table's size. Commits that arrive while a socket is reading are one
  re-read after it, and a socket's windows asking the same read share one. Measured on 1M rows,
  one unrelated commit, same harness before and after the 2026-11-08 hardening (local
  Postgres 17): 20 sockets × 64 distinct windows of 50 rows is 1280 reads both times (719 ms →
  970 ms to quiesce, the difference being each read's transaction, before re-reads were batched into one transaction per socket); 20 sockets × 64 *identical*
  windows is 1280 reads → 20 (745 ms → 344 ms); 50 commits in a burst over 20 × 64 is 2560
  reads both times, two passes per socket, which the old code already managed; 2000 desires
  for one window id is 2000 reads → 2. `orpc/served-cost.test.ts` holds the identical-window
  and burst bounds at 10k rows. Narrowing a re-read to the windows a change can move, and
  sharing one read across sockets of the same reader, are not built.
- Each served read is a transaction that is rolled back: `BEGIN`, one entry statement (the
  principal's row, the read role, read-only, the timeout), the read, `ROLLBACK`. A re-read hands
  every distinct read of a socket to `PageSource.readPages`, which runs them in one transaction
  and one snapshot: `BEGIN`, `SET TRANSACTION ISOLATION LEVEL REPEATABLE READ`, the entry, N
  reads, `ROLLBACK`, so N + 4 statements rather than 4N. Since the third review each read ends
  with `ROLLBACK TO SAVEPOINT`, so a read Postgres refuses no longer ends the pass: the reads
  after it run in the same transaction and snapshot. Measured on 200k rows, local Postgres 17,
  20 sockets × 64 distinct windows of 50 rows, one commit: before, about 335 ms and 5,120
  statements to quiesce; after, about 240 ms and 1,360. Opening those windows is about 540 ms
  both times: each open is still its own transaction, and batching desires is not built. Since
  the second review a pass is two statements longer, a `SAVEPOINT` after the entry and
  `pg_advisory_unlock_all()` before the rollback, so N + 6; and since the third a
  `ROLLBACK TO SAVEPOINT` after each read, so 2N + 6. Measured on 2,000 rows, local
  Postgres 17, 500 one-read passes and 100 eight-read passes: 0.46 → 0.50 ms per one-read pass,
  1.60 → 1.65–1.87 ms per eight-read pass.
- **Every pass writes a row, so it takes a transaction id.** The principal's row is an insert,
  and an insert assigns an xid: 500 reads take 500 xids (`txid_current()` before and after, both
  before and after the second review), and leave 500 dead rows in the unlogged
  `syncmesh_served.principal` for autovacuum. So served reads cannot run on a hot standby, nor
  on a login with `default_transaction_read_only = on`, and a busy server advances the xid
  horizon at the rate it reads. The write-free alternatives were measured and do not hold: a
  temporary table's insert assigns an xid as well; a `SECURITY DEFINER` function's `SET` clause
  is undone when the function returns; and a custom setting can be set by any statement,
  whichever function set it first. A setting signed with a secret the app holds and the read
  role cannot read would avoid the write; it needs that secret configured on both sides, and is
  not built.
- A read must `.limit()` its rows to at most `maxRows` (1000 by default) or it is refused before
  it runs; a page that returns more than `maxRows` is refused rather than sent.
- A reset is the costly frame, and a client can ask for one. A desire whose `since` is not the
  stream's position makes the server send every held row again: up to `maxWindows` pages,
  encoded into one frame before the sender's byte ceiling is checked. The rows are ones the
  reader may already read, so this leaks nothing, but nothing rate-limits it either. A host that
  serves untrusted clients lowers `maxWindows`; a per-socket reset budget is not built.
- A refusal is sent once, in the patch that answers its desire. When that patch is lost, the
  reset that answers the gap does not name the window, and the client counts it as settled
  without a reason: it shows no rows and `refusal` says nothing until it opens it again.
- A refusal's reason names what it refused: `no read <path>` for a procedure the router does not
  have, `<table> has no read rule` for a served table with none. Procedure paths ship in the
  app's bundle and table names are the schema's, so neither is secret today.
- A served read must select one table's rows with its primary key (the shape a live query keys
  by); anything else is refused, because the key is how a page names its rows.
- An index must lead with what the read rule and `where` narrow on (`owner, folder, received,
  id` for an inbox), or Postgres scans past other people's rows to fill a page.

## Watch out

- The read rule is applied before the handler's `where` (E13), by substituting the table, never
  by trusting the handler to filter, and again by Postgres under the read role. A
  `sync: "window"` table with no rule is unreadable. The substitution holds whatever is chained
  before a join (`where`, `$dynamic`, `orderBy`), and an `alias()` is read under its source
  table's rule, on devices too.
- A served table is matched by its schema-qualified identity (`tableIdentity`: `crm.mail` outside
  `public`), which is also how the Postgres change feed names its commits. A manifest name has
  no dot, so a table outside `public` is never served: it is refused, not read under the rule of
  a `public` table that shares its name.
- `servedReadDdl` runs in a migration, as the served tables' owner, after every change to them
  (`@syncmesh/storage`'s README has the whole deployment). It enables row-level security on each
  served table; a table that had none gets an open policy for every role
  (`syncmesh_served_others`), so nothing else changes for them. `rlsDdl` (what
  `createMesh({ rls: true })` installs at boot) drops that policy, since permissive policies OR
  together and an open one would read every row past the app's own rule; the DDL does not add it
  to a table that already has row-level security. So the two compose in either order (third
  review: run served first, the app's role read bob's rows as alice). The rule's policy is restrictive, so another policy open to `PUBLIC` does
  not widen what the role reads. A table that lost its rule or `sync: "window"` loses the role's
  grant and policies. The DDL refuses a `grantTo` login that owns or is granted a table, or holds
  another role; `enter` refuses a login it was not given, on every read. A migrator without
  CREATEROLE passes `createRole: false` once the role is made for it.
- A column rule (E06, `fields`) applies to a served read as it does on a face, and Postgres
  holds it too (second review). A served table with a ruled column gets a `security_barrier` view
  in `syncmesh_served` (`servedView`: `"syncmesh_served"."read:mail"`): its rows are the ones the
  read rule admits, and each ruled column is `CASE WHEN <rule> THEN column END`. The read role
  may `SELECT` the view, and of the table only the columns no rule hides, so a raw `sql`
  fragment that names a hidden column of the table is `permission denied`, and one that reads
  the view reads `NULL` where the rule refuses. A served read selects from the view under the
  table's own name (`readFrom`), so the handler's columns resolve as before. The DDL rebuilds the
  view from the table's columns each time it runs, and drops it when the table loses its last
  ruled column or its rule.
- What the read role can still do: run a `SECURITY DEFINER` function (it runs as its owner; the
  DDL warns of each one the role can run, since `PUBLIC`'s `EXECUTE` is not the role's to give
  back); read a table granted to `PUBLIC`, which every role holds (the DDL warns of each one the
  role can read that the manifest does not serve, and only when it runs: `enter` does not look
  again on each read, so a `GRANT … TO PUBLIC` after the migration is readable until the next
  one warns of it); read `pg_class.reltuples`, `pg_stat_*` counters and the like for a served
  table, which Postgres shows every role, so the size of a table (everyone's rows, not the
  reader's) is visible, though no row is; change `statement_timeout` for the statements after
  its own, which a watchdog backs: a pass still running `timeout × (reads + 1)` after it began,
  and every `timeout` after that, cancels each statement still running with postgres.js's
  `query.cancel()`, a cancel request on a socket of its own, so it needs no connection of the
  pool and holds with a pool of one or a full pool (third review: it went through the pool and
  starved). A statement the cancel races may already be done; then the cancel can land on the
  connection's next statement, which fails and is read again.
- A read's statements go through one gate, at the point postgres.js sends them (third review): each must
  start `SELECT`, `WITH` or `(`, and goes over the extended protocol, which runs one statement
  (postgres.js sends a statement with no parameters as a simple query otherwise, which runs every
  statement in its text). The `revocable` fence checks at the same point, when a statement is
  sent rather than when it was built: a prepared query whose `sql` a handler rewrote, or an
  executor kept by `getOwnPropertyDescriptor`, is refused once the read has ended, and the
  session and its client answer reflection only with fenced values. Served reads therefore need
  a postgres.js Drizzle (`drizzle-orm/postgres-js`); `servedReads` throws on any other.
- Each read ends with `ROLLBACK TO SAVEPOINT`, once every statement its handler started has
  settled, so a statement a handler left running (an un-awaited `then` chain) lands inside its
  own read and is undone with it: it can no longer abort the next read, nor the
  `pg_advisory_unlock_all()` before the rollback, which used to leave its session lock on the
  pooled connection. A setting a read changes (`statement_timeout`, `role`) is undone with it.
  A statement Postgres answers with `25P02` (the transaction was already aborted) is a failure,
  read again, not a refusal of a read that did nothing wrong.
- Every served read logs in as the same login, so one read can see the others' statements in
  `pg_stat_activity` (their SQL, never their bound values: Drizzle binds every value) and can
  `pg_terminate_backend` them, as a member of their role. A terminated read fails and is read
  again. A host that does not want that revokes `EXECUTE` on `pg_terminate_backend` and
  `pg_cancel_backend` from `PUBLIC`: the watchdog needs neither, as it sends postgres.js's own
  cancel request.
- When a backend dies inside a served read, postgres.js 3.4.9 sends its `ROLLBACK` on the dead
  connection, and `socket.write` on the closed socket throws inside a `setImmediate`, outside
  every promise a served read holds: it is an uncaught exception, which a Node or Bun process
  dies of unless the host handles `uncaughtException`. Nothing in `servedReads` can catch it.
- The tags 32–34 are chosen to stay clear of parallel relay work. If those land first and
  overlap, the vectors file is the place to renumber, before anything ships.
- Not built: replay of missed patches (a gap or reconnect costs one resnapshot), a host that
  mounts `serveWindows` on the mesh's own sealed link (an app attaches `createWindowClient()` to
  its own socket today), and narrowing a re-read to the windows a change can move.
