## Context

There is no way to see inside a running mesh today; the inspector in the old repo fed from the legacy engine.

## Options

- **A · One discriminated-union `onEvent` seam on engine, mesh and relay** — a consumer's `switch` is exhaustive, so adding a variant is a compile error at the inspector rather than a silent gap.
- **B · A `(name, payload)` string map** — flexible, and silently incomplete.

## What the research points to

A, early — half a day now, a touch-every-call-site retrofit later.

**Prior art — automerge-repo.** Every subsystem emits metrics with sizes and durations (`doc-loaded`, `doc-saved`, `doc-compacted`, `generate-sync-message` with `durationMillis`), re-emitted by the repo as one `doc-metrics` event. Built in from the start, not retrofitted. See `research/prior-art-automerge.md` §3, §5.

## Decision

**A.** One discriminated union, emitted from the engine, the mesh and the relay, and consumed
through a `switch` that the compiler checks. B's string map buys flexibility nobody asked for and
pays for it in silence: a variant added at the source and never handled at the sink is a gap that
compiles, ships, and shows up as a blank panel in the inspector months later. Under A it is a type
error at the consumer the moment the variant exists, which is the only property that keeps an
observability seam honest as the system grows.

The engine already works this way. `TelemetryEvent` is that union — `engine.mutate` and
`engine.fold`, each carrying `sizes` and a `duration` — and `engine.onTelemetry` is that seam. So
this decision mostly ratifies what is there, and E24's job is to extend it rather than invent it:

- **The same union across all three layers**, namespaced by its `type` prefix (`engine.*`,
  `mesh.*`, `relay.*`), so one consumer subscribes once and switches over everything.
- **Sizes and durations on every variant**, following automerge-repo: the useful question is
  almost never "did it happen" but "how big was it and how long did it take".
- **The mesh re-emits the engine's**, as automerge-repo's repo re-emits its subsystems', so an
  app wires one listener rather than three.
- **A listener never affects correctness.** Telemetry is emitted after the work it describes, a
  throwing listener is reported and not propagated (the `ListenerFailure` rule already in the
  engine), and nothing in the mesh waits on a subscriber.

What this decision does **not** settle, and E24 must: whether the relay's variants carry peer
identity (a privacy question, not a design one), and what the inspector is — a library that
consumes the seam, or a shipped app.
