## Context

D15 lets a device compact its log below the per-author minimum of what its peers have
acknowledged, and stops counting a peer silent for longer than `forgetPeersAfter`. Its stated
tooth: a peer that returns below the floor "cannot delta-sync and rejoins from state" (RFC-0015
§3). Nothing peer-to-peer does that.

`packages/transport/src/__tests__/resurrection.test.ts` pins the state, on main at `d01bb92`. x
goes quiet, b deletes a row and compacts past the delete, x comes back on a fresh session:

- **x keeps the deleted row.** Its cursor for b stays 0, so it never sees the delete.
- **b's later writes never reach x.** They sit in x's holdback behind a hole no log can fill.
- **Nobody notices.** The cursors frame carries cursors and `ahead`, never a floor
  (`cursorsFrame` in `transport/src/frame.ts`, sent by `cursorsAfter` in `outbound.ts`);
  `divergenceAgainst` declines to compare because x's coverage is below b's; `joinIfEmpty` fires
  only on empty coverage; `$recovery.rebuild` is manual and refuses by default while the device has
  pending writes, which a device that wrote while dark will have.

The passing test beside it shows the cure works once someone calls it: `bx.requestSnapshot()`
installs b's state, the delete merges over x's stale row, x adopts b's coverage, and the ordinary
path resumes. The `test.todo` is that nobody calls it. The relay is the one place that knows a
floor (`relay/src/retention.ts`), and it refuses a below-floor join with a typed `retention` error
rather than paging a hole; the device is told to fill the gap "from somewhere else".

**A hole that exists today.** The join exchange accepts a manifest nobody asked for.
`onManifest` in `join.ts` stores any manifest it is sent, with no check for a pending request;
`unvouchedMayAdopt` starts `true` in every exchange, and `bridge.ts` (`joinFor`) creates one
exchange per session; `complete` adopts `held.at` whenever `vouched || unvouchedMayAdopt`; and
`adopt` raises every cursor to the adopted value (`engine/src/coverage.ts`). So, with or without
`trust`, any connected peer can send an unsolicited manifest with no pages and `at` `{A: 2^40}`,
and the device adopts that coverage and never fetches A's real events again. This was
reproduced on `014abc5` with a throwaway test: a bridge with `trust` set, and a raw far end that
sends `snapManifestFrame("evil:1", 0, 0, {A: 1000000})` without any `snap-req`. Afterwards the
victim's synced coverage for A was 1,000,000. A session where a `joinIfEmpty` request has
already run is safe only by accident, because that request left the variable `false`. D46's
receiver is built on the same exchange, so it closes this hole (see "One policy per exchange").
Until then it is gaps U20.

Two facts make the cure safe to automate. `adopt` only ever raises a cursor (`join.ts`,
`complete`), so a device's own pending writes and its own author cursor survive an install. And
the rows merge through the ordinary field-level merge, so a snapshot cannot undo a newer stamp.

## Options

- **A · The floor on the wire, and the receiver asks.** The cursors frame gains an element at
  index 4: the sender's per-author `compactedBelow()` floor, absent when empty. A receiver whose
  contiguous cursor for some author is below the sender's floor for that author asks that sender
  for state with the `requestSnapshot` the bridge already has, scoped to its interest if it
  joined with one. Additive only at index 4 or later: an older build decodes indexes 0 to 3 and
  ignores the rest (`decodeCursors` in `transport/src/frame.ts`, `tag::CURSORS` in
  `crates/syncmesh-core/src/frames.rs`).
- **B · The server notices and pushes.** The sender, seeing the far side's cursors below its own
  floor, sends a snapshot unasked. Needs no new frame element, but it spends a radio's bandwidth
  on a decision the receiver did not make, and the receiver may hold several peers above its
  cursor and prefer the one on the cheaper link. It also makes "a peer sent me state I did not ask
  for" a normal event. RFC-0019 says the receiver names the exchange, so the join exchange should
  never accept that. Today it does (the hole in Context), and A closes it; B would have to keep
  it open.
- **C · Report, do not repair.** Surface "below the floor of peer b" as a `$recovery` issue and
  leave `rebuild` to the operator. Honest, cheap, and leaves the `test.todo` red: the row stays
  resurrected on x until a person acts.

## Decision

**A**, decided 2026-11-08 (Jace delegated the call). The device that is behind is the one that
knows it wants state and which link to spend on it, so it asks; the peer that compacted is the one
that knows the floor, so it says. RFC-0015 §3's "rejoins from state" becomes something a device
does, not something a document says it does. C is kept as A's fallback for the case A cannot
finish (see "Fallback" below). B is rejected for the reasons above.

**The open question, decided 2026-11-08 (Jace delegated the call): a mesh with no `trust` does
not adopt an unvouched snapshot on its own.** A device below a peer's floor in such a mesh asks
for nothing: it raises a `$recovery` issue naming the peer and the floor, and stays where it is
until the app or an operator accepts it (`$recovery.acceptState(peer)`). Accepting asks that peer
for state and adopts, per author below the floor, at most the floor it claimed. A mesh with
`trust` asks on its own and adopts what the issuer vouched for. The trade: the row a device
resurrected stays on its screen, and the author's later writes stay stalled, until someone
acts, in exchange for no peer being able to make a device in a mesh with no `trust` stop
fetching an author's real events by lying about its floor and its rows. The "Who may adopt"
row for no `trust` below now reads "nothing until accepted".

## What building it involves

- **Wire.** The floor is index 4 of the cursors frame (`[[peer, seq], …]`, the cursor pair
  shape). Index 3 stays `ahead`. Today `cursorsFrame` leaves `ahead` out when it is undefined, and
  the relay sends cursors without it (`relay/src/connection.ts`, `relay/src/session.ts`). Both
  decoders read index 3 strictly as `ahead` pairs (`decodeAheadPairs` in
  `transport/src/frame-parts.ts`; `outer.get(3)` in `frames.rs`), so a floor put at index 3 would
  fail as "ahead sequences are not an array" and an older build would drop the whole frame. So
  whenever a floor is sent, `ahead` is sent too, as an empty array when there is nothing ahead.
  The shapes this decision freezes:

  | Sender has | Frame |
  | --- | --- |
  | no `ahead`, no floor | `[kind, from, cursors]` (today's relay frame) |
  | `ahead`, no floor | `[kind, from, cursors, ahead]` (today's peer frame) |
  | floor, no `ahead` | `[kind, from, cursors, [], floor]` |
  | floor and `ahead` | `[kind, from, cursors, ahead, floor]` |

  The "floor, no `ahead`" row is there for the decoders and the vectors. No sender today emits
  it: a peer always sends `engine.ahead()` (`outbound.ts`, `cursorsAfter`), and the relay, the
  one sender without `ahead`, never sends a floor.

  An empty floor is sent only when a later index follows it. A sender that has compacted nothing
  stops at index 3, unless it also sends D31's `schemaVersion` at index 5; then it sends `ahead`
  and the floor as empty arrays to reach index 5. A receiver reads an empty floor exactly as no
  floor. The shapes with index 5 are D31's to freeze, in its own vectors, not this decision's.
  New frozen vectors for the four shapes above go in `conformance/frame-vectors.json` (the repo
  README's rule 3), and `frames.rs` decodes index 4 (the Rust `Frame::Cursors` already carries an
  optional `ahead` the same way).
- **Sender.** `cursorsAfter` reaches the engine, not the event store, and the store's
  `compactedBelow()` is async and returns a `Result`. So the engine keeps the `synced` half of the
  floor as a plain value, read at open (`engine/src/boot.ts` already reads `compactedBelow`) and
  replaced after each compaction run, and `cursorsAfter` sends it the way it sends
  `engine.ahead()`. The local half never travels: a device's local-only events are nobody else's
  business.
- **What "below" means.** `compactBelow` removes events at or below the floor and records the
  highest seq it removed (`engine/src/store.ts`; `storage/src/driver-tests/compaction.ts`, "records
  the highest removed"). So a receiver whose contiguous cursor for an author is `c` and whose
  peer's floor for that author is `f` needs state only when `c < f`. At `c = f` it already holds
  everything the peer removed.
- **Receiver.** On a cursors frame, compare each floor entry against this device's contiguous
  coverage, per author. A floor entry above the sender's own cursor for that author in the same
  frame is ignored: a peer cannot have removed events it does not hold. If any author is still
  below, send one `requestSnapshot` on that bridge with the interest this device joined under,
  carrying the claimed floor for the authors that are below it (see "Who may adopt"). At most one
  request per (peer, floor) per session, so a floor that does not move cannot become a request
  loop. An ignored floor entry does not use up that guard. This matters during a repage: there
  `cursorsAfter` sends an empty `at` (`fromNothing` is `repage.asks`, `outbound.ts` and
  `bridge.ts`), so every floor entry in that frame is ignored, and the request goes out on the
  next cursors frame that carries cursors.
- **One policy per exchange.** Today `request` keeps the adopt policy in one variable that the
  next request overwrites (`unvouchedMayAdopt` in `join.ts`), and its comment relies on the two
  existing callers never running at once. The automatic request is a third caller and can overlap
  a cold join or a manual rebuild on the same bridge. So the policy moves from one variable to a
  queue: each `request` pushes its policy, and each arriving manifest takes the oldest one. A
  manifest that arrives when the queue is empty was not asked for: it is dropped, installs
  nothing, adopts nothing, and its pages are dropped too (`onChunk` already ignores a page for an
  exchange it holds no manifest for). There is no default policy, and never a default of `true`.
  This is what closes the hole in Context. The queue is sound because every frame on a bridge
  comes from that bridge's one far side, the same side the requests went to; the far side
  answers them in the order they arrive (`serve` sends the manifest synchronously) over an
  ordered link; and a lost frame drops the link, which clears the queue with the session.
- **Who may adopt.** `requestSnapshot` takes `adoptUnvouched`, which defaults to `true` (`join.ts`,
  `request`); the automatic request never takes the default. What an install that answers the
  automatic request adopts, per case (a manifest nobody asked for installs nothing, see above):

  | The install is | It adopts |
  | --- | --- |
  | vouched (a certificate from `trust` that matches the rows, `vouchedFor`) | the sender's coverage, as any vouched install does; per author at most what the certificate signs (fix round 3) |
  | unvouched, `trust` set | nothing: the rows merge, the coverage stays this device's own |
  | unvouched, no `trust` | nothing until the app accepts the issue (decided 2026-11-08); then, for each author that was below the floor, `min(manifest at, claimed floor)`, and nothing for any other author |

  With `trust` set it follows the cold join's rule (`client/src/join.ts`, `joinIfEmpty`, which
  passes `adoptUnvouched = false`): a peer's floor is an unsigned claim, and adopting unsigned
  coverage because of it would retire the signatures that would have checked the rows (the doc
  comment on `complete` in `join.ts`).

  With no `trust` this **departs from `joinIfEmpty`'s rule** on purpose. Events are still
  author-signed and verified in such a mesh (`wire/src/envelope.ts`); what no `trust` removes is
  any way to vouch for a *snapshot*. Not adopting would leave the device stalled behind the hole
  for good, which is the bug this decision exists to fix. The cost: in a mesh with no `trust`, a
  connected peer can trigger an unvouched install by claiming a floor. For example, a peer sends
  floor `{A: 2^40}` with a cursor to match, then a manifest with `at` `{A: 2^40}` and forged rows.
  The victim adopts, its cursor for A jumps past every real event, and A's genuine, signed events
  are never fetched again. This attack is not new. Today any connected peer can do the same, in
  every mesh, with or without `trust`, by sending the manifest without being asked (the hole in
  Context). D46 narrows it. With the queue, an unasked manifest installs nothing, so a peer can
  only cause an install by claiming a floor; with `trust` set that install adopts nothing; and
  with no `trust` the bound in the table applies (only the authors below the floor, never past
  the claimed floor, and a floor above the sender's own cursor ignored). The bound limits what an
  honest peer's mistake can do and stops the snapshot widening coverage for authors nobody
  claimed. It does not stop a peer, in a mesh with no `trust`, that lies about both its cursor
  and its floor. Whether a mesh with no `trust` should adopt automatically at all was left to
  Jace; decided 2026-11-08 (Jace delegated the call) that it does not (see "Decision"). Building the bound means `complete` takes the claimed floor with the policy
  and caps the adopted coverage per author.
- **Not while doc columns lack checkpoints.** A snapshot carries rows, not the document
  snapshots in `doc_snapshots`, and compaction removes doc updates once they are materialised
  (`engine/src/compaction.ts`, the clamp). A device that adopted coverage past such updates would
  never see the document content they held. Until E30's DocCheckpoints ride snapshot pages, a
  schema with a document column gets the rows and adopts no coverage, and the fallback below
  raises the issue. The manual rebuild has the same hole today; this decision does not widen it.
  **Lifted 2026-11-09** (E30 P5, #49, Jace delegated the call): a page from a sender with a
  document runtime carries its rows' checkpoints and says whether it carries all of them; a
  joiner taking documents installs them after the rows and adopts the coverage only once every
  page was complete and every checkpoint's floor is held. Otherwise, and on a Rust device (no
  document runtime yet), the rule above still holds. Fix round 1: the joiner checks the pages'
  `complete` rather than take it, so a row whose cell names a lineage with no checkpoint on the
  pages earns no floor whatever the sender says. A document never replaced names no lineage in
  its row, so for it the sender's `complete` is still taken. A checkpoint whose producer may not
  edit its row is not installed, and earns no floor. Fix round 2: that makes the whole install
  answer `false`, so a joiner adopts no floor from a peer that may not edit some documented row it
  serves (a read-only member, an owner-only `update` rule, a relay that is not the authority); it
  takes the rows and catches up on the rest from the log. A sender whose document runtime throws
  while serving sends its pages with no checkpoints, marked incomplete, so the exchange closes. Fix round 3: a
  document runtime that rejects on either side reaches `JoinDeps.onError` (`SnapshotDocsFailed`),
  and a joiner whose install rejects still settles, adopting no floor.
- **Sender holds the scope it serves.** `snapshotOf` labels the rows with the interest it was
  asked for, and `serve` does not check that the sender holds that slice. A sender whose own
  coverage is scoped (D23) to a slice that does not contain the asked interest answers with a
  manifest that claims no coverage (an empty `at`). The receiver then adopts nothing and the
  fallback raises the issue. Without this, a sender that joined only partition A could hand a
  receiver interested in B an `at` for rows it never held.
- **Fallback.** After every automatic install, vouched or not, compute the authors this device
  is still below the peer's floor for. If there are any, raise a `$recovery` issue naming the
  peer and those authors, and stop asking that peer this session. That covers each case where
  the install cannot finish the job: `trust` set and no certificate the device trusts; a sender
  that withholds gated tables and so drops the authority's run from the coverage it serves
  (`servable` in `transport/src/withheld.ts`); a sender that does not hold the asked scope; and a
  schema with doc columns. It is option C, and it is the honest answer when nothing vouches for
  the state.
- **Retry.** A lost page drops the link, and the next session re-requests (the header of
  `join.ts`). An exchange still open when its session ends counts as never asked, so the
  once-per-floor guard does not block the next session. If the same (peer, floor) has been asked
  in three sessions and no install has completed, raise the same `$recovery` issue instead of
  asking again. The count is kept in memory by the mesh, which outlives each session's bridge,
  keyed by (peer, floor). It is not persisted: a restart starts it again, as it starts the
  once-per-session guard again, so a device that restarts often asks at most three times per
  run.
- **Test.** The `test.todo` in `resurrection.test.ts` becomes a passing test with no manual
  `requestSnapshot`; further tests pin: the fallback in a mesh with `trust` set and no
  certificate; the bound (a claimed floor below the manifest's `at` caps the adopted cursor, and
  an author not below the floor keeps its own cursor); a floor above the sender's own cursor
  ignored; a cold join and an automatic request overlapping on one bridge, each install taking
  its own policy; a manifest that arrives with no request queued (no pages, `at` far above this
  device's cursor, `trust` set and not set) installing nothing and leaving coverage unchanged,
  which fails on today's `join.ts`; an ignored floor in a repage frame not using up the
  once-per-floor guard; a partial install (gated tables withheld) raising the issue; and an older
  build's cursors frame (no floor) changing nothing.

## Watch out

- **A peer can no longer make a device install state it never asked for**, but in a mesh with
  `trust` it can still make the device ask. Before D46 any peer could, in any mesh, send a
  manifest unasked and have it adopted (gaps U20). With the decided default, a mesh with no
  `trust` installs nothing below a floor until the app accepts the issue; the exposure there is an
  app that accepts a lying peer's floor, and the bound limits it to the authors that peer claimed
  and to the claimed floor.

  **A mesh with `trust` is exposed differently** (every `createMesh` with an `issuer`, now that the
  transports' context carries `trust`). There the device asks on its own on any peer's floor
  claim with a cursor to match (`rejoin.ts`, `onCursors`), and `complete` in `join.ts` installs
  the answer's rows whether or not they were vouched; only the coverage is withheld. Snapshot rows
  are unsigned and merge by stamp, so a connected peer that claims a floor and answers with forged
  rows carrying high stamps gets those rows merged into state, past event signatures and `allow`
  rules. It costs that peer one floor claim per forged install (a floor that does not move is
  asked once). This is the "unvouched, `trust` set: the rows merge" row of the table, the same
  rule `joinIfEmpty` already applies to a cold join; D46 makes it reachable on a device that is
  not empty. Not merging unvouched rows on the automatic request would close it, at the price of
  the resurrected row staying until a certificate arrives or someone accepts; that is a change to
  the agreed table and is left to Jace. The general question of who vouches for a snapshot is
  RFC-0019's "Who vouches for a snapshot?".
- **A vouched install adopts what was signed, not what was claimed.** The manifest's `at` is
  unsigned; the certificate's `coverage` is what the issuer signed for those exact rows. Until fix
  round 3, `complete` adopted `at` whenever the rows were vouched, so in a mesh with `trust` a
  peer holding any genuine certificate and its rows could claim a floor, answer with `at`
  `{A: 2^40}`, and have the victim adopt it: the cursor jumped past every real event of A, the
  floor rose to match, was persisted, and was sent to every peer, which then asked this device
  for state. The cold join (`joinIfEmpty`) had the same hole. A vouched install now adopts, per
  author, the lower of `at` and the certificate's coverage, and nothing for an author the
  certificate does not name (`adopted` in `join.ts`, `join.test.ts` "a vouched answer to a floor"
  and "to a cold join").
- **A cold join's vouched floor covers every author.** A device that joined from a vouched
  snapshot holds no log for anything it adopted, so its floor names every author in it, and every
  older peer below that floor asks it for state even when another peer could have delta-synced it
  (the "may take two snapshots" departure). In a mesh with no `trust` such a peer shows a
  transient `untrusted` issue, and `mesh.status` reads `blocked-recovery`, until another link
  catches it up and the issue clears on its own.
- **A lying floor can hold the status.** In a mesh with no `trust`, a peer that claims a floor
  far above every real event, with a cursor to match, raises an `untrusted` issue that never
  clears on its own (no author ever reaches that floor), so `mesh.status` reads
  `blocked-recovery` until someone accepts or the peer stops claiming it. Accepting adopts at most
  that floor for the authors named, which is the exposure above. Nothing caps a floor against
  other peers' cursors; a cap is cheap to add if a deployment meets it.
- **An unvouched install adopts nothing in a trusted mesh** once D46 is built. Today an unasked
  manifest still adopts there (gaps U20). After D46, a device that pins an issuer and is
  handed rows without a certificate keeps its own coverage, so it is still below the floor
  afterwards. Without the once-per-floor rule that is a snapshot every cursor exchange; with it,
  it is one request and an issue.
- **Two additions share the frame.** D31 puts `schemaVersion` on the cursors frame too. Its index
  is 5, after this floor, and D31 says so. Whichever is built first fixes the order in the frozen
  vectors.
- **The relay still refuses, it does not help.** A relay folds nothing and holds no state to send
  (D38, RFC-0023 §7.2 for doc bytes). A device refused by the relay's `retention` check still has
  to reach a peer that folds. The client should raise the same `$recovery` issue on that
  refusal, so "below the floor" reads the same whichever side said it. A relay also passes a
  peer's cursors frame on byte for byte (`relay/src/connection.ts`, Rust `room.rs`), so a floor
  reaches relay clients; `relay/src/session.ts` only acknowledges it and never consults the
  rejoin record. That is right while a relay serves no state (gaps U30).
- **Rows are per scope; adopted coverage is per author.** The snapshot carries every row in the
  scope, so a device below b's floor for one author re-reads rows it already had for the others.
  Under the bound it adopts nothing for those others, so their history still flows as before.
  Cost, not correctness.
- **Scoped joins.** A device that joined with an `Interest` must request with that interest, or
  it adopts coverage for rows it never asked to hold. D23's scoped coverage is what keeps the
  cursors honest afterwards.
- **Dedup below the floor is a separate gap.** `admit` dedups by `store.has(event.id)`, which a
  compacted store cannot answer (`plan/api-gaps.md` §3.7, gaps U1). A device that rejoins from
  state and is then re-offered old events still re-admits them; state stays right only because
  `mergeRecord` is a max-join. Not fixed by this decision.

## Built (2026-11-08)

On `feat/rejoin-from-state`. U20 is closed in the same change.

- **Wire.** `cursorsFrame(from, cursors, ahead?, floor?)` in `transport/src/frame.ts` writes the
  four shapes in the table; `decodeCursors` reads index 4 as cursor pairs, only after index 3. A
  sender sends its floor only when it is not empty. Two new frozen vectors (20, 21) in
  `conformance/frame-vectors.json` ("floor, no `ahead`" and "floor and `ahead`"); the other two
  shapes were already vectors 3 and 4. `frames.rs` carries `floor: Option<Cursors>` on
  `Frame::Cursors`, writes `ahead` empty when a floor follows, and re-encodes all four byte for
  byte.
- **Sender.** `engine.floor()` (`engine/src/compaction.ts` `createCompaction`): per author, the
  highest synced sequence at or below this device's coverage that its log does not hold. Two
  things raise it: a compaction run (what the store recorded in `compactedBelow()`), and a
  snapshot install, which adopts coverage with no events behind it (`unheldBelow` over the range
  the install raised, less what the device had folded past a gap). It never lowers. The install
  half is `Coverage.floor`, raised only by the tracker's `adoptUnheld` (the snapshot path) and
  persisted with the cursors it qualifies: the memory state store keeps it, and the SQL state
  store writes it as `cursors` rows with `local = 2`, so there is no migration (a build from
  before reads such a row as a synced cursor at or below the real one, and only re-asks). An
  install commits the coverage as soon as it has adopted, so a restart before the next fold keeps
  both. Coverage a pass-over adopted (D24, D40, `adoptCoverage`) or a purge left (D45) is no
  floor: the relay or the authority fills that gap, not state. `openEngine` reads only the log
  tail above coverage, as before (fix round 2: round 1 recomputed the floor at boot from every
  hole in the log, which counted pass-overs and so changed what a device advertised on every
  reboot). A snapshot a device serves never carries its own floor. `outbound.ts` `cursorsAfter`
  sends it. Without the install half, a device that joined from state (a cold join,
  or this decision's own rejoin) advertised no floor, and a peer behind it delta-synced into a
  hole nothing filled: D46's bug one hop on (fix round 1, `resurrection.test.ts`, "a device that
  joined from state advertises the coverage it holds no log for").
- **One policy per exchange.** `join.ts` keeps a queue of `JoinPolicy` values; each manifest takes
  the oldest, and a manifest with none queued is dropped with its pages. `requestUnder` asks under
  a whole policy (the floor, `adoptUnvouched`, and a `settled` callback). `adopted` is the table
  in "Who may adopt", including no coverage at all on a schema with document columns
  (`engine.hasDocColumns()`). `serve` claims no coverage when the sender's own cursors are scoped
  to a slice the asked interest is not inside (`heldScope`).
- **Receiver.** `transport/src/rejoin.ts`: `belowPeerFloor` (the rule), and `createRejoins`, the
  mesh's record, shared by every bridge through `TransportContext.rejoins` and created by
  `createMesh`. Each bridge's session (`session-join.ts`) asks once per (peer, floor), counts
  sessions asked per (peer, floor) across sessions, and raises an issue with one of four reasons:
  `untrusted` (no `trust`, nothing asked), `unvouched` (`trust` set, no certificate: rows merged,
  nothing adopted), `incomplete` (an install left authors below: withheld tables, a scoped sender,
  doc columns) and `unanswered` (three sessions asked, no install completed; a refused install,
  `LineageCellRefused`, counts as unanswered). `$recovery.belowFloor()` lists them,
  `$recovery.onBelowFloor(listener)` says when that list changes, `$recovery.acceptState(peer)`
  accepts one (`"requested"` on an open session, `"deferred"` to the next one that sees the same
  floor; the issue stays listed until an install answers it), and `mesh.status` reads
  `blocked-recovery` while any is open and its `subscribe` fires when one is raised or cleared. An
  issue clears once every author in it reaches the floor, however it got there, and the change is
  told. Two links to one peer (LAN and BLE) put one request on the wire between them, and count it
  once; a second `acceptState` while the accepted request is still open sends nothing more (fix
  round 3). An install that completes and leaves the device below a floor ends the asking for that
  floor in every later session, not only the one it ran in, so a peer whose answer is always
  unvouched costs one snapshot per floor per run, not one per reconnect.
- **Rust.** `syncmesh_core::rejoin::below_peer_floor` runs the same rule, measured against the
  new `conformance/rejoin-vectors.json` in both runtimes.
- **Found while building.** `createMesh` passed `trust` and `certificate` to
  `transportContextFor`, which dropped both: no snapshot a mesh took was ever vouched for, so a
  mesh with `trust` could never adopt a vouched floor. Fixed in `client/src/transport-context.ts`,
  with a test.
- **Tests.** The `test.todo` in `transport/src/__tests__/resurrection.test.ts` is a passing test
  (with `trust` and a relayed certificate, x drops the row on its own and delta-syncs again), with
  two more there (no `trust`: the issue, then accept, adopting the floor and not the snapshot's

## Built: the relay's retention refusal (gaps U30, 2026-11-08)

- A relay built before this change refuses with no floor; the device then redials on its backoff as

- `BelowFloor` became a union, so code that read `.peer` off every issue narrows on `reason` first.

- `wake()` releases the hold every time, and the client wakes every transport on each foreground

## Built: the install's floor in the log (gaps U33, 2026-11-08)

Decided 2026-11-08 (Jace delegated the call): every rebuild keeps the rows a snapshot installed, or
refuses with `StateCorrupt`. The floor an install leaves is kept in the log as well as with the
state's cursors: `EventStore.installedBelow()` / `recordInstalled(floor)` (raised, never lowered),
in `meta` under `installed` on the SQL logs (a row in the existing table, so no ladder step), in a
third `<name>.below` key on `localStorage`, and in memory. A snapshot install records it right
after the state's cursors take it (`persistInstall` in `engine/src/coverage-path.ts`). Cursors
first is what makes a crash between the two safe: the next readable boot copies the cursors' floor
into the log, while a floor recorded first over a state whose cursors never landed read as an
empty state no boot could open (found in review of #34; the crash test in `compaction.test.ts`
fails with the order reversed). The record is written only when the state store committed those
cursors: a commit that fails (disk full, quota) or a log with no state store leaves no state that
holds the rows, and a floor recorded over it bricked the device on every later boot instead of
folding the log again and asking for the snapshot again (found in the second review of #34; "an
install whose state commits fail leaves no floor in the log" fails with the check removed).
`openEngine` refuses an empty state or an unreadable one over a log
with that floor, whether or not the cursors read, and `refoldable` answers `false`, so
`openStores`' schema change refuses as it does over a compacted log. A state installed before the
log kept the floor gives it to the log at its next readable boot. Tests in
`engine/src/__tests__/compaction.test.ts` ("below the floor"), the driver suite and
`storage/src/__tests__/local-storage.test.ts`; each fails with the record disabled.

Where it departs: the refusal is the typed open error (`StateCorrupt`, "rejoin from a peer"), not a
`$recovery` issue — the mesh does not open, so there is no `$recovery` to list it on, which is how a
compacted log already refuses. The recorded floor never lowers, so a device that later receives the
history below it as events still refuses a rebuild: cost, not correctness.

More departures, from the third review of #34:

- A state store that does not survive a restart (`createMemoryStateStore`) over a persistent log
  is now refused on every boot after one snapshot install: the in-memory commit succeeds, so the
  floor is recorded, and the next boot finds an empty state over it. Before this change the same
  setup refolded without the installed rows in silence. The remedy, a rejoin, means wiping the log
  and so any of this device's writes no peer has acknowledged. Documented on
  `EngineOptions.stateStore` and `createMemoryStateStore`: a volatile state store must sit over a
  volatile log. No `volatile` marker was added; a pairing the docs forbid is refused, not guessed at.
- Every device that joined by snapshot, which is the normal path for a new one, now refuses a
  table-shape schema change as a compacted device does (`refoldable` is `false`). RFC-0022 says so;
  a migration that copies rows from the old state file is planned, not built.
- `recordInstalled` on the SQL logs reads, raises and writes the floor in one transaction, under an
  advisory lock on Postgres (`GapSql.lockInstalled`), so two installs at once both land (fix round
  3; the driver suite's "two installs at once both raise the installed floor" fails without it).
- A log compacted by a build from before gaps U1 already pruned its gap rows below that floor, so
  an event withheld or evicted there reads as compacted and is skipped: silent loss on those logs.
  No "holes are trustworthy above floor X" marker was added, because every such log is pre-release.

## Built: one cell order for a certificate (gaps U34, 2026-11-09)

Decided 2026-11-09 (Jace delegated the call): a certificate hashes each record with its cells in
one canonical order, by column name compared as UTF-8 bytes, in both runtimes, and the certificate
format is versioned so an older one is refused rather than checked and found to differ.

- **The order is the encoding's.** `encodeRecord` (`wire/src/record-codec.ts`, `canonicalCells`)
  writes a record's cells sorted by `codePointOrder` (now in `@syncmesh/kernel`, the order of UTF-8
  bytes and of Rust's `str`); `encode_record` already wrote them in that order, from a `BTreeMap`.
  One record has one encoding wherever and in whatever order its cells were written, so the
  checkpoint hash (over `encodeRecord`'s bytes) is the same on every holder. The snapshot page
  (`encodeSnapshotRows`) writes cells in the same order, so a TypeScript and a Rust holder of the
  same events serve the same bytes, the unsorted row included. `rowDigest` dropped its own sort,
  which compared UTF-16 code units: a column name above U+FFFF now digests as Rust digests it.
- **Version 2.** `CheckpointCertificate.v` is `2` (`CHECKPOINT_VERSION`,
  `CheckpointCertificate::VERSION`). A core of any other version is refused at decode, before its
  shape is read, as `UnknownCheckpointVersion` / `CheckpointError::UnknownVersion { version }`: a
  version 1 hashed cells in first-written order, which no device can re-derive from a decoded row,
  so it is refused, never silently mismatched. A refused certificate vouches for nothing; the rows
  install by the policy as unvouched state.
- **The joiner re-derives.** Either runtime hashes the decoded record in column order, so a page
  from a holder built before U34 (cells out of column order) still vouches under a version 2
  certificate.
- **Vectors.** `checkpoint-vectors.json` re-minted at version 2, with `refused`: the same rows
  under a version 1 (byte for byte the old frozen certificate) and a version 3, refused by both
  runtimes. `snapshot-vectors.json`: `unsorted` is now the same bytes from a Rust holder of
  `unsortedEvents`; `legacy` (that page with its cells reversed, as an older holder served it)
  still vouches; `stale` (the certified frames re-signed as version 1) installs unvouched. Tests:
  `wire` `record-codec.test.ts` and `checkpoint.test.ts`, `kernel` `primitives.test.ts`,
  `conformance` `checkpoint-vectors` and `snapshot-vectors`, Rust `checkpoint.rs`,
  `signed_vectors.rs`, `snapshot_vectors.rs`; each fails with its fix disabled.

Where it departs:

- A version 1 certificate is refused, not re-derived. An authority on a build before U34 mints
  certificates no device after it accepts, so its snapshots install unvouched until it upgrades.
- The order is on the encoding, not only on the hash: state stores now write records in column
  order too. A stored record read back keeps whatever order it was written in until it is written
  again, which changes no value and no hash.
- `SnapshotRow::columns` and `encode_record_in` are gone from `syncmesh-core`: a decoded row no
  longer keeps its arrival order, because nothing hashes it.

## Built: local tables stay home (gaps U36, 2026-11-09)

Decided 2026-11-09 (Jace delegated the call): by manifest kind. `snapshot()` leaves out every table
the manifest puts in the `local` kind, whatever the interest, in both runtimes. The engine reads the

## Built in Rust: the relay's refusal and the install's floor in the log (gaps U37, 2026-11-09)

The Rust halves of U30 and U33, ported from #34.

- **The relay's refusal.** `RelayLink` reads `RelayFrame::Error { floor }` on a `retention`
  refusal, cuts it to the authors its next join is still below (`syncmesh_core::rejoin::
  below_relay_floor`, the TypeScript's new `belowRelayFloor` that `retained.ts` now uses), and
  when any are left says `Action::BelowFloor { floor }`, closes with `RETAINED` and does not
  redial. `RelayLink::on_remote_fold` (after any fold or install from another source) dials at
  once when the next join holds the floor and says `Action::FloorCleared`; `wake` makes one dial; a
  served join and `stop` clear the issue. `Rejoins::relay_refused` / `relay_cleared` keep the issue
  beside the peers' (`FloorSource::Relay`, `BelowFloorReason::Retention`, the TypeScript's message
  word for word). The tokio driver waits on commands while the link holds off instead of ending,
  and `Mesh` applies the two actions itself: `Mesh::below_floor`, `MeshEvent::Recovery`,
  `Mesh::rejoins` (one record with a host's own `PeerJoin`s) and `Mesh::folded_elsewhere`.
  Vectors: `rejoin-vectors.json` `relay`, run by both runtimes. Tests: `relay.rs` unit tests,
  `tests/join.rs`, and `tests/mesh.rs` against a room that refuses every join (one dial, then a
  second once the floor is held); each fails with the hold disabled.
- **The floor in the log.** `EventStore::installed_below` / `record_installed` (raised, never
  lowered): in memory, and in SQLite as `sm_log_meta` key `installed`, a JSON list of
  `[peer, seq]` pairs (the TypeScript logs' value), read, raised and written in one immediate
  transaction. `Engine::install_snapshot` records the floor once a state store committed the rows;
  `Engine::open` refuses an empty state store over a recorded floor, and a lineage-refused state

- A relay issue is cleared by the link, not by `Rejoins::sweep`: the link reads the cursors its

- A failed record of the floor is the install's error (the TypeScript reports it on `onError` and
  completes): the rows and coverage are committed, so the exchange counts as unanswered and asks
  again, and the next open copies the floor into the log from the state.
- With no state store an install records nothing, as in the TypeScript; such a device rebuilds
  from its log on every open, which was already true.

## Built: a lost install is a `$recovery` issue, not a refusal (gaps U33, 2026-11-09)

Decided 2026-11-09 (Jace delegated the call): the original delegated default. A state rebuilt
from the log below the floor an install left is raised as this record's `$recovery` issue instead
of refusing the open with `StateCorrupt`. #34 refused; this replaces that refusal, and nothing
else of #34's floor record (the log still keeps `installedBelow`, raised in one transaction, cursors
first).

- **Boot rebuilds.** `openEngine` folds an empty state over a recorded install floor from the log,
  and clears and folds an unreadable one, whether or not its cursors read. When only the cursors
  carried the floor (a state from before the log kept it), the floor goes into the log first. A
  compacted log is still refused with `StateCorrupt`: the log cannot rebuild what compaction took.
- **The engine names what the rebuild lacks.** `Engine.rebuiltBelow()` answers, per author, the
  log's install floor that the synced coverage is below (`belowFloor`, now in `@syncmesh/engine`;
  the transport's `belowRelayFloor` is that function). On a healthy state it is empty, since an
  install adopts its floor; it empties again once peers' events or a peer's state bring the
  coverage up, on this boot or any later one.
- **The mesh raises it.** `recoveryDeps` calls `Rejoins.rebuilt(floor, ours)` at open, which lists
  a third kind beside the peers' and the relays': `BelowInstalledFloor` (`reason: "rebuilt"`, no
  `peer`, no `relay`), swept like the others when the coverage reaches the floor. `mesh.status`
  reads it as `blocked-recovery`; `acceptState` answers `nothing-to-accept` for it, since there is
  no peer to accept from. The way back is a new device's: delta sync from a peer that still has the
  events, D46's own ask when that peer compacted, or `$recovery.rebuild`.
- **`refoldable` asks the compaction floor only.** A schema change that opens a new state file
  over a snapshot-joined device folds and raises the issue instead of refusing; RFC-0022 says so.
  The departure "every device that joined by snapshot refuses a table-shape schema change" above

Where it departs:

- **The installed rows are gone from the device until peers send them.** The rebuild is honest
  about it (the issue, `blocked-recovery`) but a device offline at that moment shows fewer rows
  than before the state was lost. Keeping them through a schema change needs the planned
  state-file migration (RFC-0022).
- **A readable state is cleared too when the open refuses it.** A state whose rows read but are
  refused over a lineage cell (a docs-rule mismatch, U22 in `doc-fold.test`) is cleared and folded
  from the log like an unreadable one, so rows that came only from a snapshot leave the state file
  rather than staying on disk where a rejoin could find them, as #34 kept them. The issue names
  them, and peers send them again.
- **Rust still refuses.** `Engine::open` in `syncmesh-client` refuses an empty state over a
  recorded floor with `StateCorrupt` (U37); its half of this is gaps U45.
