## Context

Reads must re-render on every write from any peer without re-scanning tables, and the write path must have no optimistic overlay because the local commit is the truth.

## Options

- **A · Own thin layer** — a `LiveQuery` keeping the sorted result plus a key index, maintained from the fold batch's exact touched keys (enter / leave / move / update), O(changed · log n); a ref-counted registry; `useLiveQuery` taking a query *descriptor* (data, no deps array) or a builder. Single-table.
- **B · TanStack DB** — validated and rejected in the exploration: its write path requires a `mutationFn`, which encodes an optimistic-overlay model we do not have; the read seam would fit in ~150 lines but writes are where it breaks.
- **C · TanStack's `db-ivm` operator graph behind A's registry** — the only thing it adds over A is joins.

## What the research points to

A, property-tested against a full-re-run oracle (a maintained result must equal a re-run, always). Add C only if real queries need joins and the operator graph survives Hermes. One render per fold batch is the invariant to protect.
## Watch out

Hermes returns `"[native code]"` for `fn.toString()`, so a builder callback needs a mandatory deps array; a descriptor does not. Offset pagination is unstable under live edits — keyset windows only.
