## Context

Reads must re-render on every write from any peer without re-scanning tables, and the write path must have no optimistic overlay because the local commit is the truth.

## Options

- **A · Own thin layer** — a `LiveQuery` keeping the sorted result plus a key index, maintained from the fold batch's exact touched keys (enter / leave / move / update), O(changed · log n); a ref-counted registry; `useLiveQuery` taking a query *descriptor* (data, no deps array) or a builder. Single-table.
- **B · TanStack DB** — validated and rejected in the exploration: its write path requires a `mutationFn`, which encodes an optimistic-overlay model we do not have; the read seam would fit in ~150 lines but writes are where it breaks.
- **C · TanStack's `db-ivm` operator graph behind A's registry** — the only thing it adds over A is joins.

## What the research points to

A, property-tested against a full-re-run oracle (a maintained result must equal a re-run, always). Add C only if real queries need joins and the operator graph survives Hermes. One render per fold batch is the invariant to protect.
## Watch out

Hermes returns `"[native code]"` for `fn.toString()`, so a builder callback needs a mandatory deps array; a descriptor does not. Offset pagination is unstable under live edits — keyset windows only.

## Superseded in part by D20 (2026-08-27)

Option A's *mechanism* is retired: the client no longer maintains a `LiveQuery` from touched
keys, because D20 made SQL the data API and E10 replaced the whole layer with `live(query)` —
re-run on exact table invalidation, structural-equality cutoff, one notification per fold batch.
The invariant this decision existed to protect is unchanged and now holds by construction: a
maintained result must equal a re-run, and a re-run *is* the implementation.

What still stands: B (TanStack DB) stays rejected for the same reason — its write path assumes an
optimistic overlay this engine does not have. C (`db-ivm`) remains the answer if a **thin client**
(E27) ever needs an operator graph on the relay; it is not ours to write.

## Decision

**A — our own thin layer, property-tested against a full-re-run oracle.**

`createLiveQuery(table, spec, visible)` keeps the filtered result sorted (spec order, then row key, so equal rows have one stable position) plus a key index. A fold batch reaches it through the registry with the batch's exact `writeKeys`; each touched key is decided enter / leave / move / update-in-place by binary search. A full scan happens only on first run and when `activate` re-points the visible set — and a rescan that lands on identical content notifies nobody.

`createQueryRegistry(engine)` holds one `onFoldBatch` subscription for every open query: structural specs (`{ done: false }`) share one maintained result by key, predicate filters never share, `release` ref-counts down. Listeners fire after all queries have applied the batch, at most once per query per batch — pinned by the load test (200 open queries, a 5,000-event catch-up, exactly one notification each).

The safety invariant is the oracle test in `live-query-ivm.test.ts`: randomized inserts, updates and deletes, and after every event the maintained result must equal filter-sort-from-scratch. B (TanStack DB) stays rejected — its write path assumes an optimistic overlay we do not have. C (`db-ivm` operator graph) waits until a real query needs joins.

The builder form and the React hooks are E10; they normalise onto these descriptors. The descriptor is data, so Hermes' `fn.toString()` limitation never applies to the shared path.
