## Context

D26 §9 settled the principle: *"A write made offline on Tuesday syncs on Thursday; by then the promise from that call is gone, the component unmounted, the process restarted twice."* So sync state is **observed per row, not awaited per call**. §7 then rejected a `.confirmed` promise on two counts — it conflates arrival with acceptance, and it is a promise that legitimately never resolves, because being offline is the normal state of a local-first device and not a failure.

The shipped `Write` handle (`packages/orpc/src/write.ts`) honours the first half and then reintroduces the second. Its header states the principle again — *"a write is a statement, not a promise… a write's interesting states outlive any call site"* — and the interface underneath it is `id`, `committed`, `status()`, `subscribe()`, and:

```ts
w.waitFor({ milestone: "replicated", remoteCopies: 2 })
```

That is `.confirmed` with a number attached. The number is the part this decision is about.

**What the count is, mechanically.** `remoteCopies` is the size of the set of distinct `holder` ids that have receipted this device's own `(peer, seq)` (`write.ts:141`). A receipt row is two fields — `{ holder: PeerId, atMs }` (`storage/src/operation-store.ts:44`) — and the rows are written in `client/src/operations.ts:122` out of `engine.acks()`, which is the map fed by `engine.acknowledge(from, theirs, now())` on every arriving **cursor frame** (`transport/src/bridge.ts:239`, `relay/src/session.ts:194`). A relay counts as one: it sends `cursorsFrame(identity.peerId, engine.coverage().synced)` under its own identity (`relay/src/session.ts:187`). The authority counts as one. A second browser profile on the same laptop counts as one. Nothing in the row says which.

**Four things are wrong with asking for a number.**

1. **The caller cannot know it.** Copies are not a resource the app allocates; they arrive because a radio came up. At the moment of the call the honest answer is almost always `0`, and that is not an error. The app author writing `2` is guessing at a deployment they do not control — how many devices this person owns, whether there is a relay in this room, whether anyone else is awake.
2. **The satisfying event is minutes or days away.** Write now with nobody in range, connect to five peers ten minutes later: the promise's call site is gone. The 30-second default and `WaitExpired`'s message — *"has not reached replicated yet; delivery continues"* — are the API explaining that its own failure is not a failure, which is the shape of an answer that resolved the wrong way round.
3. **It is not a guarantee even when satisfied.** `write.ts:50` claims *"Distinct peers that signed for it. Two copies on one host are one failure domain."* Nothing is signed (see below), no row names a host, and distinctness is by `PeerId`. `remoteCopies: 2` can be one relay and your other browser profile.
4. **Nobody has ever called it.** `waitFor` with a `replicated` milestone has no call site outside `packages/orpc/src/__tests__/write.test.ts`. Not in `apps/issues`, which was written precisely to find this API's friction, and not in `rounds-web`.

**What the codebase reached for instead, twice, when it actually needed custody.** Both are standing questions over a *set*, used to **refuse an action**, and neither takes a number:

```ts
// packages/storage/src/detach.ts:39 — will not detach a store nobody else holds
const unsettled = yield* Result.await(ledger.unsettled());
if (unsettled.length > 0) { … `${scope} holds ${n} unsent write(s)` }

// packages/storage/src/blob.ts:88
/** Every hash this device is the only holder of — what a backup must include,
 *  and what an eviction sweep must leave alone (RFC-0022). */
readonly irreplaceable: () => Promise<readonly BlobHash[]>;
```

The shape was invented independently in two packages. The per-write count was invented once, in a package, and used nowhere.

## What the trace found, true under every option

Three defects that want fixing whichever way this goes:

- **The doc says signed; the implementation counts claims.** The signed path is complete and wired to nothing: `custody.vouch()` signs after a durable `receiveBatch`, `verifyReceipt` checks the far side, and `onReceipt` — the only way a verified receipt could reach the ledger — is passed nowhere outside `packages/transport/src/__tests__/receipt.test.ts`. So verified custody receipts are decoded, checked and dropped, and the ledger is fed from cursor frames. `custody.ts`'s own header says why that is not the same thing: *"A cursor says 'I have your events' and proves none of it, so a device counting copies off cursors is counting claims."*
- **`incarnation` is on the wire and not in the table.** `CustodyReceipt` carries the holder's storage lineage so an author can tell *"still holding"* from *"holding again, having lost what it had"*. `ReceiptRow` has no column for it, so a relay that wiped its disk and resynced still counts as a holder of a write it no longer has.
- **"Remote" means two different things.** `SyncState` (`client/src/sync-state.ts:15`) uses `"remote"` for **authorship** — somebody else wrote this row. `remoteCopies` uses it for **custody** — somebody else holds my write. A row can be `"delivered"` with three remote copies, and a `"remote"` row has no copies question at all. One of the two words has to go.

## Options

- **A · Keep `remoteCopies` as it stands.** Rejected on the four counts above; kept here because doing nothing is always an option and this one has the virtue of being already written.
- **B · Make the count relative to what is reachable** — "two of the peers I can currently see". Rejected, and this is the important rejection: custody facts are **monotonic** (receipts only accumulate, which is what lets the ledger be read six weeks later and still mean something), while reachability is not. A goal defined against a flapping denominator can go from satisfied to unsatisfied when someone walks out of the room, and then the ledger has stopped being a record and become a reading.
- **C · Drop the count. Custody is a standing question over a set, plus one named-peer wait for handoff.** The two shapes the codebase already invented, made general.
- **D · A quorum, but in the manifest.** If a fleet genuinely requires every write to reach the authority before anyone calls it final, that is an operator policy and a property of the room, which the UI *reports*. It is not an argument at a call site, because the app author is the last person who knows it. Composes with C rather than competing with it.

## Decision

**C, with D available later and neither A nor B — staged by whether a caller exists today.**

| | do | why |
|---|---|---|
| **now** | delete `Milestone`, `waitFor`, `remoteCopies`, `WaitExpired`, `WaitUnreachable` | no call sites. Pure deletion, and `{ milestone: "committed" }` is `await w.committed` with a worse type |
| **now** | keep `unsettled()` as the custody reading; fix the copy to say *"nobody has told me they have this"* | the reading `detach.ts` already uses. Only the words are wrong |
| **now** | the custody spelling of `"remote"` goes with the count; `SyncState` keeps the word | falls out free |
| **later** | `mesh.custody.sole()` + `useSoleCustody` | wanted, but gated on the compaction question in *Watch out* |
| **not until a caller** | `w.until({ peer, within })` | building it today repeats the mistake being deleted here |

The three questions apps actually have, and only one is per-write:

1. **"Am I the only one holding anything?"** — device-level, standing, subscribable. This is what gates the destructive and the irreversible: clear site data, sign out, hand the phone back, detach a store, close the lid before a flight. Answerable offline (the answer is *everything*), monotonic, and already half-built in `unsettled()` and `irreplaceable()`.
2. **"Has the authority got it?"** — a named role, never a number. And usually the app does not want the acknowledgement, it wants the *consequence*: `claimNumber` minting `ENG-42` needs the row to arrive, which a live query already shows. The number appearing **is** the receipt, and a better one, because it is the thing the person cares about.
3. **"Does that device over there have it?"** — a named peer, with a human standing at the table watching a spinner. Here waiting is legitimate; the argument is *which peer*, and the bound is the session.

```ts
// per write — unchanged, and already correct
w.id            // allocated before the commit
w.committed     // the local, durable commit; a Result, never rejects
w.status()      // OperationRow, durable, survives reload
w.subscribe()   // custody changed: a receipt landed, a correction displaced it

// 1 — the reading that gates destruction
mesh.custody.sole()          // the writes only this device holds
mesh.custody.subscribe(…)    // useSoleCustody() → "3 writes only on this device"

// 3 — the only wait that survives
w.until({ peer, within })    // the bound is required; expiry is an answer, not an error
// → "held" | "not-yet"      // neither arm is a failure, so neither is an Err
```

Gone: `Milestone`, `waitFor`, `remoteCopies`, `WaitExpired`, `WaitUnreachable`. The `{ milestone: "committed" }` variant goes with them and is not missed — `await w.committed` already is it, with a better type.

Also under C: fix the three defects above. Wire `onReceipt` into `operationStore.acknowledge` so the ledger holds signed custody rather than claims; add `incarnation` to `ReceiptRow` so a rebuilt holder stops counting; and rename one of the two `"remote"`s — `SyncState` keeps it (it is the older and the more visible), so the custody side says *holders*.

## What C would cost

- **A real capability leaves.** "Do not let the courier drive off until the depot tablet has this" is expressible today and would not be, until `until({ peer })` lands. That is the handoff case, and it is the one legitimate use; C keeps it and narrows it to the argument that can actually be known.
- **`sole()` over the whole ledger is a `LEFT JOIN` with no `LIMIT`** — `devtools/src/source/writes.ts:12` already says as much about `unsettled`. Fine as a guard on a destructive action, wrong as a subscription a list re-reads on every fold. It needs a cached count with the rows fetched on demand.
- **Two packages and the react surface move together.** `@syncmesh/orpc` (the handle), `@syncmesh/storage` (the receipt row, and whatever `sole()` is built from), `@syncmesh/transport` (the `onReceipt` wire-up), `@syncmesh/react` (`useSoleCustody`). No new package.
- **D is left unbuilt**, so an operator who wants "nothing is final until the authority has it" has no way to say so and must express it in app code, which is exactly where this decision says such a rule does not belong.

## Watch out

- **`sole()` is delivery, not approval, and a refused write sits in it forever.** D26's own watch-out has the mechanism: a quarantining peer's cursor never rises above the event it parked (`transport/src/holdback.ts`), so its acknowledgement never covers the refused write. The honest reading of `sole()` is therefore *"nobody has told me they have this"* — not *"this is unsaved"* — and a UI that renders it as a stuck spinner will be lying in the one case that matters. Until a quarantine report exists on the wire, the copy has to say the weaker thing.
- **Check what compaction does to the operation and receipt tables before `sole()` is trusted as a guard.** `sync-state.ts:50` leans on the inverse assumption — *"anything absent has either been acknowledged or been compacted away, and compaction only removes what every peer already holds"* — and a sole-custody reading that inherits that rule backwards would report a compacted write as sole-held, or worse, license a wipe of one that is not.
- **Do not let `mesh.custody` become a second sync API.** `useSyncOf` answers per row and `sole()` answers per device; if a third thing appears that answers per query or per table, the surface has grown back into the count it replaced.
- **`until({ peer, within })` has a timeout, and must — the rule is not "no clock", it is that expiry has to mean something.** `waitFor`'s bound meant nothing: it fired, the write carried on unchanged, and `WaitExpired` had to say so in its own message (*"delivery continues"*). `until`'s bound is the opposite — somebody is standing at the table, and expiry is the moment the screen says "that device did not take it; move closer or hand a paper copy". A bound whose expiry changes nothing is the smell; a bound whose expiry is a decision is the point.

  Two consequences. **`within` is required, not defaulted** — a default is a number every caller inherits without thinking, which is how `waitFor` got its 30 seconds, and there is no honest default across a tablet at a counter (seconds) and a van at a depot (a minute). And **expiry returns `"not-yet"`, not an `Err`** — nothing failed, the write is intact and still on its way, so an error arm would be the same apology in a new place. An `AbortSignal` may ride alongside for the screen that unmounts, but it is not a substitute for the bound: leave it off and every call site writes its own `Promise.race`, which is the timeout back again, unnamed, in N places, each one leaking the ledger subscription `watch()` refcounts.
