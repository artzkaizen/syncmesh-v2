## Context

RFC-0023 P1–P2 made document columns fold, log and compact with no adapter at all. P3 is the
adapter: `@syncmesh/loro` over `loro-crdt` (WASM) and `syncmesh-loro` over the `loro` crate, both
pinned to 1.17.1, behind one SPI (`packages/docs/src/adapter.ts`, `crates/syncmesh-client/src/docs.rs`).

D38's draft named the gate for choosing Loro over Automerge: loro#1163 (an insert concurrent with
a delete baked into an imported snapshot lands at the wrong place) closed and covered by a vector.
It closed on 2026-09-29, and `conformance/loro-vectors.json` freezes that exact scenario in both
runtimes (`abXef`, not `abefX`).

Building the vectors turned up something the RFC assumed away. RFC-0023 §13 and the first SPI
draft said two runtimes "agree byte for byte on snapshot, version and since". They do not. Loro
writes its version vector and the peer tables inside snapshots by walking an `FxHashMap`, and
`rustc-hash` hashes differently on 64-bit and 32-bit targets. Native Rust on aarch64 and the
wasm32 build write one document's bytes in two orders whenever it holds several peers. Compiled to
`wasm32-wasip1`, the Rust matches the TypeScript exactly. Native, with Loro's own version encoding,
12 frozen values differed: every multi-peer final snapshot and version. The documents are the
same. Two wasm replicas of one history can also write
different snapshot bytes for the same version, depending on how they got there.

## Options

- **A · syncmesh owns the version encoding; snapshots and updates agree as documents.** (built)
  `loro@1`'s `version` is `0x01` then `(peer u64 BE, end counter u32 BE)` per peer, ascending.
  It is byte-identical on every target, so a checkpoint's `version` (DocCheckpoint key 6) can be
  re-derived and compared anywhere (§7.3's audit). Snapshots and `since` updates are compared by
  importing them: same version, same value. A snapshot's hash names the producer's bytes, which
  is all D18 needs.
- **B · Byte-identical everything, by patching Loro to sort its maps.** A fork of the library, or
  an upstream change we do not control. Even then, snapshot bytes depend on import order within
  one runtime, so "byte for byte" would still be false for snapshots.
- **C · Run the WASM build everywhere, Rust included.** Byte identity bought by putting a WASM
  runtime inside licnep, which D35 rejected for the JavaScript one.

## What the research points to

**A.** It is the only option where the promise is true. Nothing in RFC-0023 needs snapshot bytes to
match across devices: the column snapshot is local state (§6.1), a checkpoint names its own bytes
by hash, and §7.3's provisional-snapshot audit compares the **version**, which A makes canonical.

Four smaller choices were made the RFC's proposed way. Jace confirmed the two that were RFC-0023
§16 questions on 2026-11-08 (§16.5 and §16.8), and §16.7's numbers, which item 4 relies on:

1. **D38's gate is met, so Loro first.** This decision covers RFC-0023's doc columns. D38's option
   B (a lattice inside a cell) is a separate mechanism, and D38 was later decided D (2026-11-08):
   document columns are the answer and B is not built.
2. **The SPI lives in `@syncmesh/docs`** (the package main scaffolded for this), not a new
   `@syncmesh/documents` (§16.8, decided: the SPI with a builder; no `syncmesh-derive` macro until
   a Rust app needs one).
3. **Device snapshots are full, not shallow** (§16.5, decided). Shallow-at-the-stable-floor is
   smaller, but it fails when a forgotten peer comes back. Full is the default until a size
   budget says otherwise.
4. **A burst past 64 KiB is refused, and the handle is invalidated** (§5.4, §10; the 64 KiB
   threshold is §16.7's, decided). The blob path
   for big updates (D18) is not built. A large paste is the case that will hit this first.

## Watch out

- **Two empty layouts are two roots.** If two editors seed an empty ProseMirror document at the
  same time, Loro merges both layouts: two root structures, which is RFC-0023 §5.3's lineage
  problem in miniature. The editor test has the note's author lay the document out first. P4's
  `ctx.docs.change` on create is where an app should do it.
- **React Native.** `loro-react-native` is at 1.10.3 while `loro-crdt` and `loro` are at 1.17.1.
  Under A that still interoperates, because the contract is "same document", not "same bytes".
  But it is not covered by vectors, and its `version` must go through this decision's encoding,
  not Loro's. The path is either (a) a `@syncmesh/loro/native` entry over `loro-react-native`
  once it reaches ≥1.17, run through the same vector file, or (b) UniFFI over `syncmesh-loro`,
  which D35's slice 5 already plans. Neither is bound yet. (b) is one implementation instead of
  three.
- **Bundle.** `loro-crdt` is about 1 MB of WASM, loaded on first `open()`. The relay does not fold
  documents and does not carry it.

## Decision

**A**, decided 2026-11-08 (Jace delegated the call; taken as recommended and as built), with the
four choices above. syncmesh owns the `loro@1` version encoding, so a checkpoint's version
re-derives byte for byte on every target; snapshots and updates are compared as documents.
Choices 2 and 3 are the owner's answers to RFC-0023 §16.8 and §16.5.

The Rust adapter's `snapshot()` panics through `.expect` on an export failure. Under this
decision an adapter is total (RFC-0023 §10), so it returns the failure as a value instead.

**Built** (`feat/doc-lineage-versioning`): `DocumentAdapter::snapshot` in
`syncmesh-client::docs` returns `Result<Vec<u8>, UpdateRejected>`, and `syncmesh-loro` runs the
export through the same guard as `apply` and `since`, so a Loro error or panic comes back as
`UpdateRejected`. Departure: no test reaches the error branch, because `loro` 1.17.1 exports a
snapshot of every document state we could build (pending operations, checked out at an old
version, an uncommitted edit, imported from a shallow snapshot). The test pins that each of those
is a value. The TypeScript SPI's `snapshot` still returns bytes and would throw on an export
failure; this decision named the Rust adapter only.

The lineage rule changed under this decision on 2026-11-08 (RFC-0023 §16.1: first genesis wins,
as a tree), which the "two empty layouts" note below is unaffected by: those are two roots inside
one lineage, not two lineages.
