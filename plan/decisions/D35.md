## Context

D01 chose TypeScript everywhere and kept a Rust core "possible later without a rewrite" on the
strength of two things: runtime imports behind ports, and a wire frozen by byte-for-byte vectors
(D03). Both held. As of 2026-09-26 the vectors cover every wire a peer speaks — event cores,
grants, accounts, receipts, checkpoints, session frames and framing, the link handshake, the
relay's control frames and the v2 join proof (E24) — so a second implementation is now something
that can be *proven* rather than believed.

Two pressures make it worth building. Every engine that reached many platforms in 2026 has a
Rust core with thin bindings (Automerge, Loro, Yrs, PowerSync's SQLite extension, Turso, Ditto):
Bun and Node, the browser through WebAssembly, iOS and Android through UniFFI, and native apps
consume one implementation of the parts that must be bit-identical. And the owner's own native
app (licnep, Rust) has no way to speak syncmesh at all without embedding a JavaScript runtime.

## Options

- **A · Stay TypeScript; bind the native app through a JS runtime.** No second implementation
  to keep honest. Rejected: a design tool that ships a JavaScript engine to sync rows pays for it
  on every frame, and a phone's BLE path already runs in Swift and Kotlin around a TypeScript
  core it cannot call directly.
- **B · A Rust core for the parts that must be bit-identical; TypeScript keeps the rest.** The
  crate owns canonical CBOR, hex, identity (Ed25519 sign/verify, X25519 agree), the HLC and its
  drift bound, stamps, records and the four lattice joins, the fold, the event codec and
  envelope, grants, receipts, accounts, checkpoints, the session frame codec and length framing,
  the link handshake and sealing, and the relay control frames — roughly the kernel, wire and
  transport-frame layers, later the SQLite event and state stores and the sync bridge. Exposed as
  a plain crate (licnep), `wasm-bindgen` (browser, Bun, Node) and UniFFI (Swift, Kotlin). The
  client, hooks, Drizzle face, relay host, devtools and plan stay TypeScript.
- **C · Rewrite everything in Rust.** Rejected as D01 rejected it: building two things, and the
  parts above the fold — live queries, React, Drizzle — have no reason to leave the language
  their consumers are written in.

## Decision

**B.** The crate lives in this workspace under `crates/syncmesh-core`, wrapped by a
`package.json` whose scripts call `cargo`, exactly as D01 reserved for non-TypeScript packages.
It is measured against `conformance/*.json` first and its own property tests second: a slice is
done when the vectors it claims pass from Rust, byte for byte, and until then the TypeScript
implementation of that slice stays the reference. Order of slices, each gated by its vectors:

1. `cbor`, `hex`, `identity` — wire-vectors (decode → re-encode → verify).
2. `hlc`, `stamp`, `record`, `strategy`, `apply` — the fold; property tests for the lattice
   laws (commutative, associative, idempotent) and convergence under permutation, mirroring
   `kernel/__tests__/apply.test.ts` and `strategy.test.ts`.
3. `event` codec and envelope; `grant`, `receipt`, `account`, `checkpoint` — their vectors.
4. Session frames, framing, relay control frames, the join proof, the handshake and sealing —
   frame-, relay-, join- and handshake-vectors.
5. Bindings: the plain crate is the first consumer (licnep); wasm and UniFFI follow when a
   TypeScript or native caller needs a slice the TypeScript no longer owns.

Nothing in TypeScript is deleted until the Rust slice replacing it has passed the same vectors
and the same acceptance suite (`runDriverTests`, `runTransportTests`) through its binding.

## What this costs

- A Cargo workspace and toolchain in a Bun repository; CI runs `cargo test` beside `bun test`.
- Two implementations for as long as a slice is in flight. The vectors are what keep them from
  drifting; a change to the wire now means a vector, a TypeScript change and a Rust change.
- The `Result`/`TaggedError` discipline has a Rust twin: every failure is a typed error value,
  never a panic, and decoders never throw on foreign bytes.

## Watch out

- **Canonical CBOR is the whole contract.** Shortest heads, integer keys before text keys, text
  keys in the order JavaScript's `<` gives them (UTF-16 code units — identical to UTF-8 byte order
  inside the BMP, not beyond it), safe integers as integers and every other number as f64, no tags, no
  indefinite lengths, no trailing bytes. A port that gets one of these wrong verifies nothing.
- **Do not port the cleverness, port the bytes.** Where the TypeScript keeps arrival bytes rather
  than re-encoding (`VerifiedEvent.core`, relayed grants), the Rust must too — the additive rule
  (D14) depends on it.
- **The counter's normal form is `{p: {author: n}, n: {author: n}}` and an increment is `{"+":
  n}`;** both are plain JSON cells and must round-trip through the row codec unchanged.
- **f64 in cells.** JavaScript numbers that are safe integers encode as CBOR integers; a Rust
  port must make the same decision from the value, not from a static type.

## Landed

- **2026-09-26 — `crates/syncmesh-core`, slices 1 and 2 and the event half of 3.** Canonical CBOR
  (encode + strict decode), hex, Ed25519 identity, HLC with the D34 clamp, stamps, records,
  canonical JSON as `JSON.stringify` prints it, the four strategies, the fold (`apply_change`,
  `merge_record`), the row codec, the event codec (keys 0–8, unknown change kinds kept whole per
  D22-A, sealed payloads carried unread) and the `[core, sig]` envelope. `conformance/wire-vectors.json`
  decodes, verifies and re-encodes byte for byte from Rust; grant, account, receipt and checkpoint
  envelopes split, verify under the key their document names and prove canonical (their cores are
  not yet shaped into Rust types — that is the rest of slice 3). Property tests: the four joins are
  commutative, associative and idempotent over their normal forms; the fold is order- and
  replay-independent. `cargo test` runs from `bun run test` through the `crates/*` workspace entry.
