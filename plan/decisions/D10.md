## Context

Zero runs a named mutator on the server, LiveStore hooks `onPush`, reflectdb runs `mutate` per op — all at the point where a *mutation* enters the server, which they can do because the client sends intent. Our events carry captured changes applied by a fixed routine (D1: receivers never run app code), so that point does not exist. Yet an app still has logic that can only run in one place: a cross-row invariant ("a tech holds at most one assigned job"), an external effect ("closing a job charges the card"), a question that needs an answer now.

## Options

- **A · The server is a peer; procedures are oRPC.** Business logic is an ordinary oRPC procedure running at the authority; its handler reads and writes through the authority's own `mesh` (`mesh.jobs.get`, `mesh.tx`) so a procedure's writes are one signed event like any other. syncmesh ships no router, no request channel, no handler map — only what an oRPC middleware needs from the mesh: the account behind the call, `mesh.can`, and `correct`. A call is `fetch`: it fails offline, which is right for a payment and wrong for nothing.
- **B · A request channel** — a reserved `_requests` table of request rows the authority executes once and settles, so a procedure call commits offline and runs on reconnect. The exploration built this, then deleted it: it rebuilt RPC on a system that had made RPC unnecessary, and needed a second permission model.
- **C · A hand-rolled procedure builder (`sm`)** — `.meta().input().use().errors().handler()`, bound to an engine. Built in the exploration (`src/core/router.ts`), never exported. It is oRPC with fewer features and our maintenance burden.
- **D · An `onChange` reactor on the server with an idempotency key** — built, then deleted: it was a mutator moved to fold time, and the idempotency it solved is better solved by writing the outcome back as data.

## What the research points to

A. Three attempts at B, C and D collapsed under the question "doesn't the log already do this?". The one thing the server *does* need is a materialiser — the state-store port pointed at your Drizzle tables (E17) — and the two authority verbs (`setPolicy`, `correct`, E16). Everything else is the app's own server, and the app already has an RPC layer; ours would be a worse copy of it.

## Decision

**A — procedures are oRPC procedures whose handlers use the authority's mesh. syncmesh does not ship an RPC system.**

```ts
import { os } from "@orpc/server"
import { z } from "zod"

const authed = os.$context<{ mesh: Mesh; account: string }>()

export const jobs = {
  assign: authed
    .route({ method: "POST", path: "/jobs/{id}/assign" })
    .input(z.object({ id: z.string().uuid(), tech: z.string() }))
    .errors({ NOT_FOUND: { status: 404 }, TECH_BUSY: { status: 409 } })
    .use(requireRole("dispatcher"))                       // a plain oRPC middleware over mesh.can / the grant
    .handler(async ({ input, context: { mesh }, errors }) => {
      const job = mesh.jobs.get(input.id)
      if (job === undefined) throw errors.NOT_FOUND()
      if (mesh.jobs.list({ where: { assignee: input.tech, status: "assigned" } }).length > 0)
        throw errors.TECH_BUSY({ data: { tech: input.tech } })
      const receipt = (await mesh.tx((c) =>
        c.jobs.update(input.id, { assignee: input.tech, status: "assigned" }).map(() => undefined),
      )).unwrap()                                          // ONE event, or the throw above and no event
      return { eventId: receipt.eventId }
    }),
}
```

- **A throw before `mesh.tx` is a rejection with no event.** The handler decides in app terms (`errors.TECH_BUSY`); oRPC carries the typed error to the client; the mesh never saw anything. This is the "reject by judgment" path, and it needs no reserved table.
- **What the mesh gives the handler is what any client gets** — `get`/`list`/`tx`/`can`/`history` on the authority's own `createMesh`. No second write path, no second permission model: the schema's `allow` still runs on the authority's write like on every peer.
- **Offline is `fetch`'s problem, deliberately.** A procedure call from an offline device fails at the call site; the app retries or queues in its own terms. Anything that must work offline is a direct collection write, and a direct write the server later disagrees with is a `correct()` (E16, §9d) — the only after-the-fact rejection there is.
- **The relay is unchanged by this.** It carries events, grants and blobs (E12); it never carries procedure calls. oRPC traffic is ordinary HTTP to the app's server, which is also where the authority mesh runs (API.md §14 shape A).
- **What syncmesh ships for this, and nothing more:** a documented example of the `requireRole` middleware over `mesh.can`/the grant registry, and `mesh.account`/`grants.grantFor` so a middleware can map a session to the mesh's notion of who is asking. If a `@syncmesh/orpc` helper package ever exists, it is that middleware and nothing else.
- **B is not rejected forever; it is re-homed.** If an offline-queued procedure call is ever genuinely needed, it is an oRPC *link* (client transport) over a request row plus a server-side adapter — an oRPC integration, not a syncmesh subsystem — and it gets its own decision then.

## Watch out

- If a procedure only writes a synced collection, it should not exist: the client can do that offline with no round trip. The test for "needs a procedure" is *other rows, the clock, or the outside world*.
- A column the authority may need to overrule must be `lww`. A correction that lowers a `max` column loses the lattice join.
- `_requests` is no longer reserved. The reserved tables are `_policy` and `_corrections` (E16).
