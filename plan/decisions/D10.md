## Context

Zero runs a named mutator on the server, LiveStore hooks `onPush`, reflectdb runs `mutate` per op — all at the point where a *mutation* enters the server, which they can do because the client sends intent. Our events carry captured changes applied by a fixed routine, so that point does not exist.

## Options

- **A · None. The server is a peer that materialises synced rows into your database; anything you want to *do* is your cron, queue or request handler over that database. A question needing an answer now is `fetch`.**
- **B · A request channel** — a reserved table of request rows the server executes once and settles. The exploration built this, then deleted it: it rebuilt RPC on a system that had made RPC unnecessary, and needed a second permission model.
- **C · An `onChange` reactor on the server with an idempotency key** — built, then deleted: it was a mutator moved to fold time, and the idempotency it solved is better solved by writing the outcome back as data.

## What the research points to

A. Three attempts at B and C collapsed to it under the question 'doesn't the log already do this?'. The one thing the server *does* need is a materialiser — the state-store port pointed at your Drizzle tables — and that is E17.
## Watch out

If a server op only writes a synced collection, the op should not exist: the client can do that offline with no round trip.
