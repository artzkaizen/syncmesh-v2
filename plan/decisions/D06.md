## Context

This is the surface an app author lives in. The exploration converged on one manifest with everything about a table in one place, but the code never caught up. You get to decide it before writing a line.

## Options

- **A · One manifest** — `defineSchema({ partitions, roles, tables: { name: { columns, partition, allow, merge? } } })`. Conflict rules on the column (`t.float().onConflict("max")`); `allow` is a function receiving combinators *bound* to this table so `role("…")` and `owner("…")` are typed to your roles and columns (a typo is a compile error, not a rule that silently matches nobody). Tables from Drizzle via `fromDrizzle` with a table-level `merge` fallback.
- **B · By concern** — `schema.ts` (tables), `access.ts` (partitions + roles + allow), `conflicts.ts`. A security reviewer reads one file; understanding one table means opening three.
- **C · Builder chain on the table** — `table(...).in("site").allow(...)`. The strings are unbound and mean nothing on their own; rejected in the exploration for that reason.

## What the research points to

A, and it was the shape agreed in the exploration. The bound-combinator types are the only genuinely new engineering; the runtime is unchanged (they return the same policy AST, which stays JSON so it can sync as a `_policy` row). Keep definitions *data* — no functions in the manifest except `allow`'s builder — so a Rust port can read the schema and `fromDrizzle` can generate it.
## Watch out

`t.json<T>()` with no schema is a phantom that accepts anything at runtime — the same hole the exploration criticised in reflectdb, then found in its own code. Give `json` a schema (`t.json(zod)`) and `.check(schema)` on every kind; keep them synchronous and pure.
