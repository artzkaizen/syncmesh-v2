## Context

BLE is 3–50 KB/s with a 128 KiB reassembly cap; a photo in the event log blocks convergence for everything and is replicated to every peer forever.

## Options

- **A · Content-addressed side channel** — rows carry the sha-256, bytes travel outside the log; the relay verifies before storing (junk cannot squat a hash), the client verifies on fetch. Memory cache first; persistent store, range fetch, refcount GC and per-partition quotas later.
- **B · Blobs in the log** — simple, and exactly the failure mode above.

## What the research points to

A. The open questions with teeth are *who is obliged to hold a blob* and what happens when a delete races an offline reference — answer them in the RFC before building GC.

## Decision

**A — content-addressed, out of the log, verified at both ends.**

A row carries the sha-256; the bytes travel on their own channel and are never an event. The
hash *is* the identity, so a put is idempotent, a re-upload after a loss is free, and two rows
that reference the same photo reference the same bytes. Both ends verify: the relay before it
stores, so junk cannot squat a hash, and the fetcher after it receives, because a reference is
a **proof** of content, not a promise about a server. Failures are values —
`BlobCorrupt / BlobNotFound / BlobTimeout` — because every one of them is a thing an app must
decide about, not a crash.

B is the failure mode the context describes: a photo in the log blocks convergence for
everything behind it, replicates to every peer forever, and cannot be compacted away because
the event carrying it is the row's history.

### The three questions with teeth

**Who must hold a blob.** The author holds it until a relay acknowledges it — that is the only
window where the bytes exist in one place, and the author is the only peer that can still
produce them. The relay holds it while any row it can see references the hash, which makes it
the durable home. Every other device treats what it fetched as a **cache** it may evict at any
moment, because a phone that must keep every photo it ever saw is a phone that fills up.

**A delete racing an offline reference.** A row's deletion does not delete the blob. The relay
sweeps a blob only after no visible row has referenced it for a retention window, and a device
that reconnects holding a stale reference gets `BlobNotFound` — a value, not corruption. That
is recoverable precisely because the identity is the content: any peer that still has the bytes
can put them back under the same hash, and the reference starts working again. The alternative,
refcounting to zero the instant a row dies, would break exactly the offline device this engine
exists for.

**Quotas.** Per-partition byte budgets, refused at the put with a typed value, so an app can
tell someone their upload did not fit rather than silently dropping it. Deferred with GC, since
both need the sweep to exist first — and neither should be guessed at before a real workload.

## Built: references follow rows (gaps U18, 2026-11-08)

Decided 2026-11-08 (Jace delegated the call). "No visible row has referenced it for a retention
window" is built as far as a relay can follow it without folding cells: a row holds the blobs
its writes named until a delete stamped after its latest write (the kernel's max-joins, so order
of arrival changes nothing), and a blob is swept a `keepUnreferencedBlobsFor` window after the
delete that released it — not at the delete, which is the offline device this decision protects.
The references outlive log trims in a ledger beside the blobs (`sqlBlobLedger`), saved before
every trim. `relay/src/blob-references.ts`, `relay/src/blob-keeper.ts`,
`storage/src/blob-ledger.ts`.

Where it departs from "visible row":

- **A cell written over still references its old blob** until the row is deleted, because
  whether the newer write won depends on the column's merge rule, which the relay does not know.
- **A delete of a row the relay was not tracking is not remembered**, so an insert older than it
  that arrives later makes a live row here. Both keep; neither frees too soon.
- **A sealed event keeps the blobs of its partition** (and of no partition), not the whole room's.
- **A room whose log was trimmed before it had a ledger** keeps an earlier run's blobs, unbilled.
