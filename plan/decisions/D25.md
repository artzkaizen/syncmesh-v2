## Context

A developer defining a column faces one question that matters and cannot see it:

> When two devices write this while apart, is losing one of them acceptable?

`t.integer()` answers *yes* and says nothing. The answer is right for most columns — a title, a
status, a price — but it is never stated, and the alternative lived in a different constructor
you had to already know existed:

```ts
t.integer()                      // last write wins. silently.
t.integer().onConflict("max")    // the conflict menu: lww | max | min
t.counter()                      // a running total — not in that menu
t.set(t.text())                  // a set — not in that menu either
```

Someone thinking hard about concurrent writes types `.onConflict(` and is shown three options,
none of which is the one that keeps both writes. The two that do are constructors, and a
constructor is not somewhere you look when you are choosing a merge rule.

Underneath, the two hidden constructors were a second change model: `CellChange` beside `Change`,
`applyCellChange` beside `applyChange`, wire tags 3–5 beside 0–2, `crdt-codec.ts`, a frozen
`cell-vectors.json`, and a per-cell tombstone compaction that needed a causal stability frontier
nothing computes.

## What the demonstration showed

`packages/engine/src/__tests__/atomic-cells.test.ts`, run against two engines that went apart and
came back:

```
json array   A ["urgent","billing"]  B ["urgent","design"]  → both settle ["urgent","design"]
text         A "urgent,billing"      B "urgent,design"      → both settle "urgent,design"
integer      A 11                    B 11                   → both settle 11
a row per tag                                               → both settle billing AND design
```

Three declared types, one failure, because **a cell holds one value and one stamp and the
declared type decides nothing about merging.** And the escape is not a cleverer merge: it is a
different key. `patientTag/"p1:billing"` and `patientTag/"p1:design"` are different cells, so
there is nothing to compare and nothing to discard.

That reframes what the lattices were for. A tag is three rows either way. A view count is one row
per view — unbounded, and uncompactable, because every `+1` is a distinct fact.

## Options

- **A · One constructor per type; `merge` as its option; both lattices deleted.**
  `t.integer({ merge: "max" })`. Lists go in tables. The chain keeps `nullable`, `primaryKey`,
  `unique` and `check`, which are independent of each other and read well chained.
- **B · Keep the lattices, add the option as an alias.** `t.integer({ merge: "sum" })` sugar over
  `t.counter()`. Discoverable, nothing deleted.
- **C · Change no code; document it.** One JSDoc line on each builder saying what it merges by.

## What the research points to

**A.**

The case for the counter is real and the case for the set is not, and they were built as a pair.
A set in a cell reimplements — one layer down and less completely — what a row already does: its
own identity, its own tombstone, its own compaction. The engine's version of all three works; the
cell's tombstone compaction needs a causal stability frontier that nothing computes, so the cell
version is the same design with worse growth and no provenance.

The counter is the one shape rows lose at, and it is the one no use case asks for. Nothing in
`plan/use-cases.md` mentions a counter, a set or a tag. Both were built ahead of a caller.

B keeps two ways to say one thing, and the deletion is most of the value: one change model on the
wire, three tags instead of six, and a second implementation with half as much to agree with.

C is the honest minimum and would have been right if the lattices had a caller. They do not.

**D22-A is what makes this safe.** An unrecognised change kind is now kept and parked rather than
refused, so a later build can add a lattice back and older builds hold its events instead of
dropping them. Deleting is no longer one-way, which is the whole reason to delete now rather than
carry it until someone needs it.

## Watch out

- **`merge` is not a type.** It changes how two writes reconcile, never what the column holds. A
  column that merges by `max` still reads as the number some author wrote.
- **Only numbers order.** `max` and `min` pick by value, and "the larger of two booleans" has no
  answer. The types refuse it and `table()` panics behind them, for a cast that gets past.
- **This does not stop anyone losing a write.** `t.text()` still discards a concurrent write and
  always will — that is what a cell is. The option makes the choice *visible* for numbers; for
  everything else the answer is a table, and only a doc line can say so.
- **Re-adding a lattice is additive, not free.** It costs a wire tag, a codec, frozen vectors and
  a compaction story. D22-A means old builds park it; it does not mean they understand it.

## Decision

**A.** `t.text()`, `t.integer()`, `t.float()`, `t.boolean()`, `t.timestamp()`, `t.blob()`,
`t.uuid()`, `t.json()` — each taking `{ merge }`, which is `"lastWrite" | "max" | "min"` on a
number and `"lastWrite"` on everything else. `.onConflict()`, `t.counter()` and `t.set()` are
gone, and with them `CellChange`, `applyCellChange`, `counter.ts`, `set.ts`, the kernel's
set compaction, `crdt-codec.ts`, wire tags 3–5, `cell-vectors.json` and E26.

`lww` is renamed `lastWrite` in the same move. It never travelled — `MergeSpec` is built from the
schema and read by the fold — so the rename costs nothing and stops the one name a developer sees
from being an acronym.

Lists, tags and memberships are tables. That is not a workaround; it is the shape that already
converges, already tombstones, already compacts, and already carries who added the row and when.
