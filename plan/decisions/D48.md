## Context

D17 chose one discriminated `onEvent` union across engine, mesh and relay, and left one question
for E24: "whether the relay's variants carry peer identity (a privacy question, not a design
one)". E24 records the seam as built on all three layers and the question as still open, with
"none do today" (`plan/epics/E24.md`).

What the code holds on main at `d01bb92`. `RelayTelemetry` in `packages/engine/src/telemetry.ts`
has six variants (`relay.join`, `relay.catchup`, `relay.event`, `relay.blob.put`,
`relay.blob.get`, `relay.retention.unbounded`). Each carries `sizes` and a `duration` and nothing
else: no peer id, no room name, no event id, no payload byte. Its doc comment and the one on
`packages/relay/src/telemetry.ts` both say why: the question was open, and an identity never
emitted can be added later, while one that reached a metrics pipeline cannot be taken back.
`relay.catchup.unsendable` is counted rather than named for the same reason, because "an event id
is a peer id with a number after it".

Three later decisions bear on it:

- **D40** made a room name a bearer secret in an open room (`open: true`): whoever knows it can
  join. A room name in a metrics pipeline is then a credential in a metrics pipeline.
- **D40 / D44** made gated rooms check the socket's grant. The relay knows who a socket is in a
  gated room; that knowledge exists to decide access, not to report it.
- **D17** itself: a listener never affects correctness, and the inspector is a consumer of the
  seam, not a reason to widen it.

## Options

- **A · No.** `relay.*` variants never carry a peer id, a room name, an event id or anything
  derived from them. Per-peer diagnosis happens on the device, which already names its own
  events (`Engine.stranded`, `mesh.*` telemetry, devtools on the device). An operator who must
  know who connected uses the host's own access log at the point that authenticated them
  (`verifyJoin`, the grant check), under that host's retention rules.
- **B · Yes.** Variants carry the socket's peer id and the room. Makes a relay dashboard easy;
  makes every telemetry sink a store of who talked to whom and when, and of open-room
  credentials.
- **C · Pseudonymous.** An opt-in host option adds a keyed hash of the peer id and room, stable
  per key, so an operator can correlate without reading identity. Better than B, but a keyed hash
  of a low-entropy set (the peers of one deployment) is reversible by whoever holds the key, and
  it is still a correlation record a sink keeps.

## Decision

**A**, decided 2026-11-08 (Jace delegated the call). It ratifies what the code does and turns the
code's "the safe side of an open question" into the rule. A relay is custody, not an observer of
people; telemetry answers "how big, how long", and "who" stays where access is decided. C is not
rejected for ever, but it needs its own decision with a caller who has a question A cannot
answer; nothing in `plan/use-cases.md` asks one today.

## What building it involves

- **Comments.** The doc comments on `RelayTelemetry` (`packages/engine/src/telemetry.ts`) and on
  `packages/relay/src/telemetry.ts` say the question is open; they cite this decision instead.
- **E24.** The `[~]` `onEvent` box drops "D17 deliberately left open whether relay variants may
  carry peer identity"; the inspector is the only open part left.
- **A pin.** A relay test that drives a room through join, catch-up, an event, a blob put and a
  get, collects every `relay.*` event, and asserts no emitted value contains the room name, a
  joiner's peer id in hex, or an event id. It must fail when a variant is given a `peer` field.
  The type alone cannot pin this: any new `string` field could carry a peer id.

## Watch out

- **Counts can identify too.** A room with one socket makes `receivers: 1` a statement about one
  person. That is the floor of any metric and is accepted; do not add per-socket breakdowns that
  would make it sharper.
- **`mesh.*` variants are the device's own** and may name what the device knows about itself.
  This decision is about the relay, which sees many people's traffic.
- **Logs are not telemetry, and not covered here.** A host's own `console` and access logs are
  the operator's, under the operator's rules. The show-all-logs rule still holds for them.
