## Context

E12's last open task: *surface the relay's durability `ack` as a mesh-level signal (`synced()` in
RFC-0010's words) — needs a way to name the relay in `engine.acknowledge`, which wants a device
key the relay does not hold; decide before building.*

What exists. The room answers every ingested event with `ack { id, o }` (`packages/relay/src/
ingest.ts`), for a duplicate as much as a first, so a retry is never left waiting. Until the
authority-visibility work the client ignored the frame entirely; it now feeds `o` into
`visibility.token()` (RFC-0020 §3.2), and nothing else reads it.

What `delivered()` already answers. `mesh.delivered({ event, to })` settles when a **peer** says,
in its own cursors, that it holds the write. Through a relay that works today — the relay forwards
each device's `cursors` frame byte-identical (E12, `mesh-relay.test.ts`) — and it is keyed by the
peer's device key, because `engine.acknowledge(peer, cursors, at)` is a map from `PeerId` to what
that peer holds.

The relay is not a peer. It holds no device key, signs nothing a device can verify against a
grant (its link key, D36, is a transport identity and not an account's), and its `ack` is one
event id, not a set of cursors. So *"the relay durably took it"* has nowhere to land in the
acknowledgement map without inventing a peer id for something that is not one.

## Options

- **A · A per-transport signal, not an acknowledgement.** The relay transport records the ids it
  has had acked (bounded — the newest per author is enough, since the room appends in order per
  socket and acks in that order) and exposes `durable(event) → Promise<void>` as an optional
  capability beside `visibility`. `mesh.synced({ event })` resolves when any running transport
  that declares the capability has had it acked; a mesh with none answers `NoSuchCapability`,
  exactly as `mesh.visibility` does. `engine.acknowledge` is untouched.
- **B · The relay as a pseudo-peer.** Name the relay by its D36 link key and record its acks into
  `engine.acknowledge` as cursors (`{ author: seq }` per ack). `synced()` becomes
  `delivered({ to: relayKey })`, no new surface. Cheap, and it makes a transport identity look
  like a device to every reader of the acknowledgement map — `mesh.peers`, the sync column, the
  devtools roster — which will each have to learn to skip it.
- **C · No mesh-level `synced()`.** `delivered({ to })` for the peer you care about, and
  `visibility.visibleAt(token)` for read-your-write, already answer the two questions an app
  asks. The relay's durability is an operator's concern, reported through telemetry.

## What the research points to

**A.** It is the shape the last two capabilities took (`blobs`, `visibility`): a fact about the
medium, declared by the medium, `NoSuchCapability` where it is absent. It answers the one
question neither existing call does — *may I close the laptop?* — without the acknowledgement
map having to admit something that is not a device. B is attractive because it is no new code
in the client, and that is the problem: every reader of `acknowledge` today may assume a key it
can look a grant up by, and the sync column (E18) would start counting a relay's ack as a
peer holding the row. C is honest but leaves the `ack` frame with no reader past `visibility`,
which is the state RFC-0010 already called a gap.

## Watch out

- An ack names an id, and the room's log can be replaced (a new epoch). A durable answer from the
  old lineage is not durable in the new one — the same trap `VisibilityLost` exists for. Whatever
  is built must drop recorded acks on a hello with a new epoch.
- A duplicate is acked too. That is the point (a retry must settle), and it means an ack is not
  evidence the room *appended* it this time — only that it holds it, which is the claim wanted.
- A gated room (D24) acks a device's write to an ungated table like any other; a device never
  writes a gated one, so there is nothing for the gate to say here.

## Decision

**A**, decided 2026-11-08 (Jace delegated the call; taken as recommended). `durable` is a
transport capability beside `visibility` and `blobs`: the relay transport records the newest acked
sequence per author, drops it on a hello with a new epoch, and `mesh.synced({ event })` resolves
once any running transport declaring the capability has had the event acked. A mesh with none
answers `NoSuchCapability`. `engine.acknowledge` and the acknowledgement map are untouched, so no
reader of `mesh.peers` or the sync column ever sees the relay as a peer.

## Built (2026-11-08)

What landed, and where it departs from the text above.

- **The capability.** `Transport.durable?: (event: EventId) => Promise<void>` sits beside
  `visibility` and `blobs` (`transport/src/transport.ts`). `relayTransport` declares it, backed by
  one record per link (`relay/src/durability.ts`). `mesh.synced({ event })` (`client/src/synced.ts`)
  races every running transport that declares it and returns `Result<void, NoSuchCapability>`;
  with none it answers `NoSuchCapability { capability: "durable" }` at once. A local id panics, as
  it does for `delivered`. `engine.acknowledge` and the acknowledgement map are untouched, and a
  test says the map stays empty after a relay ack.
- **Persistent rooms are told apart from memory rooms** (review point 1). The `hello` gains one
  additive element: `1` when the room's log outlives the process, absent otherwise. Absent decodes
  as not durable, so a relay built before this is never taken for durable. Where the claim comes
  from: `RelayRoomOptions.durable` and `RoomStore.durable` (default `false`); `durableRoomStore`
  (the Bun and Node `dataDir` default) and the Durable Object and Rivet hosts set it; a caller's
  `startRelay({ store })` is not durable unless it also passes `durable: true`. A link drops every
  ack from a room whose hello did not say so, so `synced()` over a memory room waits rather than
  settles. The capability is still declared there, because the transport cannot know which room
  it will reach until it says hello.
- **Acks are recorded exactly, not as the newest per author** (review point 2). The text above
  says "the newest acked sequence per author". That is wrong: `pushOutstanding` is queued behind
  the fold chain while a live write goes straight out, so the room can ack seq 5 before seq 4
  arrives. The link keeps, per author, the run the room holds without a hole: it adopts the
  hello's cursors (the room's own contiguous coverage), and each ack is noted by id with the
  engine's `trackCoverage`, which holds an ack above a hole until the hole fills. Bounded:
  `MAX_ACKS_AHEAD` (1024) acks per author may wait above a hole; past that an ack is left for the
  next hello to cover.
- **A lost ack recovers on the next session** (review point 3). If the room stored the event and
  the socket closed before its ack arrived, the next hello's cursors cover it, the push after the
  last page sends nothing, and the waiter settles from the hello. If the room holds it past a hole
  (the event before it was lost on the way), the hello cannot cover it; the push re-sends both,
  the room acks the duplicate, and that ack settles it. A client restart has no waiters to
  recover: a new `synced()` call after it settles on the first hello that covers the event.
- **A new epoch** drops everything recorded, as the decision says. ~~Waiters are kept, not
  failed: the join re-offers the write to the new log, and its ack there settles them.~~ Superseded
  below: a waiter of the old epoch now settles as `DurabilityLost`.
- **Not built:** a timeout on `synced()` (it waits like `delivered`), and the Rust client and
  `relay-vectors.json` do not carry the new hello element yet; both decode it as absent.

Tests: `relay/src/__tests__/durability.test.ts` (out-of-order acks, a lost ack settled by the
hello, a lost ack settled by the duplicate's ack, memory against durable rooms, the epoch drop,
the bound), `relay/src/__tests__/frames.test.ts` (the hello element, and its absence), and
`client/src/__tests__/synced.test.ts` (`NoSuchCapability`, `startRelay`'s durable default, a
caller's memory store).

## Follow-up built (2026-11-08, on `fix/access-followups`, #30)

Decided 2026-11-08 (Jace delegated the call): **`synced()` settles as a typed loss when the room's
epoch changes**, instead of carrying the waiter over. An ack in the old log is not durability in
the new one, and the waiter cannot tell a re-offer's ack from the old lineage's claim. So:

- `Transport.durable` now answers `Promise<Result<void, DurabilityLost>>`, and
  `DurabilityLost { event, expected, actual }` is exported from `@syncmesh/transport`. This is a
  change to a public seam: a transport outside this repo that implements `durable` and resolves
  `void` no longer type-checks, and resolves `Result.ok(undefined)` instead.
  `relay/src/durability.ts` binds each waiter to the epoch it began under (a waiter that began
  before any hello takes the first hello's); a hello under another epoch settles it lost.
- `mesh.synced()` answers `Result<void, NoSuchCapability | DurabilityLost>`: the first hop to hold
  the event wins, and it is lost only once every durable hop it waited on has lost it. The write
  itself is untouched and re-offered on the join; a caller asks `synced()` again for the new log.
- **No timeout**, as decided: a caller that wants one races its own.
- **Kept:** `startRelay({ store })` is not durable unless the caller also passes `durable: true`.

Tests: `relay/src/__tests__/durability.test.ts`, "a new epoch settles a waiter of the old one as
DurabilityLost" (fails with the epoch check disabled), and `client/src/__tests__/synced.test.ts`,
"a relay restarted over a fresh log settles a waiting synced as DurabilityLost". The memory-room
case that went from a memory hello to a durable one under a new epoch now stays in one epoch.
