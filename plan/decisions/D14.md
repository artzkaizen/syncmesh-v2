## Context

The event core carries `v: 1`; the join/hello handshake carries no version at all. For a project whose deliverable is byte-frozen vectors for other-language ports, a handshake that cannot tell a v1 peer from a v2 one is a hole, and adding it later is a breaking change.

## Options

- **A · `join` carries `v`; `hello` replies `v` + a floor; mismatch closes with a typed reason; an *additive* vector for the new frames.**
- **B · Leave it; rely on the event core's `v`.** Peers only find out mid-stream.

## What the research points to

A, early — it is half a day now and a retrofit later.

**Prior art — automerge-repo.** Exactly this, in ~15 lines: `join { supportedProtocolVersions }` → `peer { selectedProtocolVersion }` or `error` then close. A second `join` from the same peer id disconnects the old socket first. See `research/prior-art-automerge.md` §6.

## Decision

**A — the handshake is versioned from the first byte.**

`join` carries the client's `supportedProtocolVersions`; the relay answers `hello` with the
one `selectedProtocolVersion` it picked (the highest both sides speak) — or an `error` frame
with a typed reason, then closes. No overlap is a clean, explainable refusal, never a
mid-stream decode failure. The relay's control frames live in their own additive tag space
above the session frames (grants/events keep their existing tags and stay byte-identical
through the relay), so a future v2 adds tags without renumbering v1.

A second `join` from the same device key disconnects the old socket first — one socket per
peer, never a silent room switch. B (rely on the event core's `v`) is rejected: peers would
discover incompatibility only after decoding began, and retrofitting a handshake field is
exactly the breaking change this project's frozen-vector deliverable cannot absorb.
