## Context

D04 left one door open: full CRDTs only for collaborative prose, as a separate column kind. D25
closed the two lattices built ahead of a caller and made `merge` an option on the column, and the
counter came back through that option without a wire tag: an increment travels inside an
ordinary `update`, the kernel joins per-author totals, the projection reads the sum.

`research/crdt-cells.md` walks the five seams a merge kind touches (declare, capture, check, fold,
read) and the four libraries that could do the arithmetic. Two later decisions bound the answer.
D35 vectors the kernel's joins and binds them from Rust; a join that exists only in JavaScript
breaks that. RFC-0015 forbids per-keystroke events; a text cell is written at the pace the app
commits, and `$drafts` holds what is in between.

Nothing in `plan/use-cases.md` asks for collaborative prose today. This is drafted so the shape
is agreed before a caller arrives, not built before one.

## Options

- **A · An append-only table of updates, no kernel change.** `note_update { id, note, op:
  t.blob() }`, one row per library update, the client folds rows into a doc, compaction inserts a
  merged row and tombstones the rest. PowerSync's and Electric's published pattern, and D04's own
  answer for anything that is not a register. Works now. The body cannot be read by SQL and every
  reader reconstructs.
- **B · A merge kind: a named lattice over bytes, injected through the schema.** `t.text({
  merge: loroText })`. The kind is an object from an adapter package (`adapters/crdt-loro`,
  `adapters/crdt-automerge`) with five members: `name`, `empty`, `join`, `read`, `edit` plus
  `accepts`. The kernel folds it as a strategy, capture derives the delta from the engine's state
  cell and the new app value, the wire carries bytes inside an ordinary `update`, the projection
  reads a string. Normal form `{ snapshot, pending }` so a delta whose deps this device lacks is
  held in the cell rather than dropped on re-encode. Vectored under `conformance/`, one Rust
  implementation everywhere, so the Rust device binds the same crate.
- **D · Document columns (RFC-0023).** Added 2026-11-08, because the code went there while this
  record was a draft. `merge: { name: "lww", content: loro }` on an ordinary binary column; the
  edits travel as their own change kind (tag 6) into a per-(row, column) doc log in syncmesh's
  event store, signed and action-grouped; the column holds the latest compacted snapshot; a
  versioned adapter (`@syncmesh/loro`, `loro@1`; Rust `syncmesh-loro`) is the only code that
  reads the bytes, and **the fold never runs it** (RFC-0023 §3, §6.4). The owner approved the
  shape on 2026-09-27 (RFC-0023 §2) and answered its open questions on 2026-11-08 (§16).
- **C · Custom merge functions on a column.** Rejected by D04 and still rejected: a function the
  app writes can be pure here and different there, and nothing local can tell.

## What the research points to

**A now; B when a use case names prose.** They are not in tension: A is the app-level pattern for
an app that needs it before B exists, and B is the engine-level pattern that removes A's costs
once a caller justifies a wasm library in every folding peer.

For B's first adapter, **Automerge 3** over Loro unless Loro #1163 (2026-09-28: an insert
concurrent with a delete baked into an imported snapshot lands at the wrong position) is closed
and covered by a vector. The case it fails is the one a relational fold produces constantly: a
peer joins from a snapshot page and then folds an older concurrent delta. Both libraries are one
Rust implementation with wasm, Swift and Kotlin bindings, which is what D35 needs. Yjs has the
better update format and the wrong provenance: a JavaScript reference and two Rust ports that a
project exists to keep honest.

## Watch out

- **The kernel imports no library.** A kind is injected; `@syncmesh/kernel` keeps its two
  dependencies. The adapter package is the one place the library is imported, as with a SQLite
  binding.
- **`merge` is still not a type.** A text column with a kind reads as a string and is written as
  a string. The kind changes how two writes reconcile and nothing else, which is D25's rule.
- **The normal form must carry pending ops.** Automerge and Loro hold an op with missing deps
  outside what they export. A join that is "import both, export snapshot" loses it. Yjs does not
  have the problem, and the shape costs Yjs nothing.
- **Version skew is the D04 risk, wearing a library.** The adapter pins the library and ships
  vectors for its join; a convergence bug is a vector regression before it is a field report.
- **Key rotation.** A text cell is per-author. `stranded.ts` applies unchanged.
- **Bundle.** Loro is about 1 MB gzipped, Automerge less but not small. The relay does not fold
  and carries neither. Every device and the authority do.
- **Not in this decision:** an editor binding (`mesh.$doc`), rich text marks, a JSON kind. Each
  is a later kind or a method on one.

## Decision

**D**, decided 2026-11-08 (Jace delegated the call). A CRDT lives in a column as RFC-0023's
document column, not as a lattice the kernel folds. This record's draft proposed B, Automerge
first; the code and two later calls overtook it, so the draft's recommendation is not taken:

- **A caller arrived.** licnep's artboards are Loro documents (RFC-0023 §1), so "built when a use
  case names it" has happened, and what was built is D, not B.
- **B puts the library in the fold, and D does not.** Under B the kernel folds a cell by calling
  the kind's `join`, so every peer that folds needs the
  library and its exact version, and a peer without it cannot fold the row at all. Under D the
  fold, the park and the digest are adapter-independent; a device or relay without the adapter
  keeps and forwards the events and refuses only to edit (RFC-0023 §2.4, §10). That is the
  property D35 needs from a join bound from Rust, met without putting a CRDT in the kernel.
- **Automerge-first is overturned by D41.** Its gate (loro#1163 closed and frozen by a vector) is
  met: `conformance/loro-vectors.json` holds that scenario in both runtimes. Loro is first.
- **A stays an app pattern, not a recommendation.** RFC-0023 §1 lists what it cost licnep: a row
  per edit never deleted, a second delivery system for big updates, a hand-rolled lineage rule.
  An app may still do it; syncmesh does not point anyone at it.
- **B is not built and not planned.** If a second kind of in-cell lattice ever earns a caller (a
  JSON kind, rich-text marks), it is a new decision against D's adapter SPI, not a revival of B.

## What building it involves

Nothing new beyond RFC-0023's own plan (§14), most of which has landed: P1–P2 in #2 and #3, the
`loro@1` adapter (P3) in #11 under D41. What is left is E30's open boxes: DocCheckpoints riding
RFC-0019 snapshot pages (P5), blob-carried updates past 64 KiB (D18), the React Native binding
(D41), `ctx.docs.change`, `DocRef` and `useDoc` (P4), doc compensation for undo (P6), and
cross-runtime live interop (P7). Each is tracked there, not here.

## Watch out (decided)

- **This record's own watch-outs mostly carry over.** The kernel imports no library (true under D:
  the fold does not even call one); the normal form must keep pending ops (now the adapter's job,
  covered by the SPI's conformance suite); version skew is a vector regression before it is a
  field report (D41's vectors); bundle size falls on every device that edits, never on the relay.
- **"`merge` is still not a type" changed shape.** Under D a document column is opened, never
  read like a value (RFC-0023 §4.2): it reads as the library's own document type, not a string.
  D25's rule (a merge option changes how writes reconcile and nothing else) holds for the row
  rules and not for `content`.
- **The lineage cell must be versioned before doc columns ship** (RFC-0023 §16.1, decided
  2026-11-08). Until it is, every peer holding doc columns has to upgrade together.
