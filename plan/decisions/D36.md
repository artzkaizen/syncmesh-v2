## Context

D33 made a relay join prove the key it names — the room challenges, the join signs — and said in
the same breath what it did not do: the relay still read every frame it forwarded, and the link's
secrecy was still `wss://`'s. Every peer-to-peer link already runs the signed X25519 handshake in
`transport/src/handshake.ts`; the relay socket was the one link in the system that skipped it, for
three stated reasons — the room forwards bytes it did not seal, a hibernating Durable Object would
have to keep session keys across sleeps, and every frame would cost a seal. D33 deferred it as
option C and put it on E24's list.

## Options

- **A · Leave it.** TLS to the relay, a challenge for identity. Rejected: a relay operator, a
  reverse proxy in front of the relay, and anything that terminates TLS reads every row a device
  syncs; and the relay socket stays the one link whose security story is different from the rest.
- **B · Seal end to end, through the relay.** Only the two devices hold the key; the relay
  forwards opaque bytes. Rejected for the link layer: the room has to read joins, cursors and
  grants to do its job, and content confidentiality against the relay is a different thing —
  the sealed partition (book ch. 14), which exists and is per partition by design.
- **C · Run the link handshake on the relay socket.** Both ends send a signed hello first; a
  session key falls out; everything after travels sealed, per socket. The room opens what it
  receives and seals what it sends, per client. Identity comes from the hello, so the join proves
  nothing itself and the challenge is redundant.

## Decision

**C**, as protocol version 3. `RELAY_PROTOCOL_VERSIONS` becomes `[3]`. A room lists 3 alone or
leaves it out: it speaks a hello first or a challenge first, and a socket cannot be told both, so
a list that mixes them is a definition mistake and throws at open.

- **The room speaks first, still.** Its first frame is a hello signed by the room's own key
  (`RelayRoomOptions.identity`; fresh per open when not given, kept beside the epoch by hosts
  with a durable store so a room has one name across evictions). A device answers with its own
  hello, in the clear, and from then on every frame either way is sealed under the session keys
  `sessionKeys` derives — the same bytes `handshake-vectors.json` freezes.
- **The join names the key the hello proved.** A join naming any other key is refused
  `impostor`, fatal, before the seat is taken. A join in the clear, or a sealed frame that does
  not open, is refused `handshake`, fatal. A proof on a v3 join is not required; one that is
  present and wrong is still a refusal.
- **The client decides by the room's first frame.** A hello opens a sealed link; a CBOR
  challenge is a v2 room, answered only if the client was told to offer 2, and otherwise a
  permanent refusal like a `version` error. Nothing this device sends on a sealed link leaves in
  the clear but its hello; a send asked for before the handshake is reported dropped.
- **Hosts keep the link across sleeps.** The Durable Object's resume script head grows from
  `[nonce]` to `[nonce, secret, hello, seal, open, peer]`, so a socket that slept between the
  room's hello and the device's answer finishes the handshake with the secret it offered, and one
  that slept after it opens the next sealed frame. `RelayConnection` splits into `open` (bytes →
  plaintext frame, or a handshake step) and `replay` (one frame acted on), so a host can read what
  belongs in its script before the room acts on it.
- **v1 and v2 stay where an operator lists them**, as before, with the challenge and the proof
  exactly as D33 left them. This build offers neither.

## What this costs

- One X25519 agreement and two Ed25519 operations per socket; one XChaCha20-Poly1305 seal per
  frame per recipient, so a room fanning one event to *n* clients seals it *n* times. Measured
  against the load rig this is noise beside the JSON and SQLite around it; the rig still passes.
- 41 bytes per frame (`SEAL_OVERHEAD`); `maxFrameBytes` is measured on the plaintext and the
  cap on the socket allows for the overhead.
- Test fakes had to learn the handshake: `secureProbe` in the relay fixtures and the device
  helpers in the Durable Object tests speak it; every scripted bare-join test opens its room at
  `[1, 2]` through `scriptedRoom`, as it must, because a room that speaks the hello cannot be
  scripted with a plaintext join.

## Watch out

- **This is link confidentiality, not content confidentiality.** The relay still reads what it
  forwards; a partition that must be unreadable at the relay is a sealed partition.
- **The client does not pin the room's key.** A hello from anyone is accepted, and `wss://` is
  still what stops a machine in the middle presenting its own. The room now *has* a stable key a
  posture could pin; pinning is not decided here.
- **The ephemeral secret sits in the Durable Object attachment** between the hello and the
  answer, and the session keys after. That is the object's own storage, and what the socket
  itself is worth; it is not less exposed than the room's log beside it. A host that cannot keep
  it should not accept sockets it cannot finish talking to.
- **The challenge frame (tag 19) stays in the vocabulary** for v2 rooms. Nothing renumbers.
