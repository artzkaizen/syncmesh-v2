## Context

RFC-0016 commits the name `AccountCore` and the phrase "an account registry feeding attribution
and `owner()`". It commits no fields, no wire shape, and no signature scheme. This decision fills
that gap — and starts by disputing the goal.

**In a mesh that has an issuer, `owner()` is already cross-device.** The issuer mints Alice's
phone-grant and her laptop-grant with the same `account` string, and `evaluate.ts`'s
`cell(ctx, node.column) === ctx.grant.account` is then true on both. An account layer that feeds
`owner()` there re-derives what the grant already says, from a key nobody vetted, in front of the
one function that decides what a device may do.

What is actually missing is `owner()` in the two rungs of RFC-0016's ladder that have **no
issuer** — the trusted mesh and the device-key-only mesh. There `grantFor` is `null`,
`checkAuthor` returns `undefined`, and `checkPolicy` returns early without evaluating anything, so
`owner()` never runs at all. That is the hole worth filling, and D08's "the engine has no users"
is why it is the only one.

## Options

- **A · Links are rows, consulted only when no grant is held.** An account is an Ed25519 keypair
  whose public-key hex *is* the account id. It vouches for a device by signing a link core, which
  travels as an ordinary row in a fourth reserved table `_links`, keyed `instance:device`. The
  validator resolves device→account at one point — `checkAuthor` — out of the `RowLookup` it
  already holds, and only in the `grantFor === null` arm. A grant always wins, because in a
  granted mesh the link is never read.
- **B · Links as credential frames**, carried on the handshake beside grants, held in an account
  registry next to `GrantRegistry`. The symmetric-with-grants shape, and the one most reachable
  from RFC-0016's wording.
- **C · An account registry feeding `owner()` in every mesh**, granted or not — the RFC's literal
  reading, where the registry is the authority on identity and the grant's `account` is a hint.

## What the research points to

**A.** B and C each fail on something the codebase has already learned the hard way.

**B is the divergence bug we keep re-finding.** Grants ride the handshake and do not converge by
anti-entropy. Let peer P hold Alice's link and peer Q not: P builds a principal, evaluates
`owner()` and may deny; Q has no principal, skips policy and admits. Two peers that disagree once
disagree forever — the failure `checkRevoked`'s doc comment names, that E21's revocation rung was
rewritten to avoid, and that the grace rung reintroduced through the wall clock before review
caught it. **Anything that feeds a verdict must arrive the way `_revocations` arrives.** Rows also
persist for free, which is the tuition E21 already paid when `GrantStore` had to be built because
the registry was a bare `Map`.

**C hands a self-minted key authority over a configured trust anchor.** The issuer's public key is
shipped config; an account key is vetted by nobody. If a link could override a grant, the account
layer is a one-line escalation gadget. Under A the link is not merely out-ranked, it is *never
read* in a granted mesh — so there is no second answer sitting anywhere for a future code path to
reach.

Seven further choices follow from A, each with the failure it avoids.

**The account id is `hex(account public key)`.** `AccountId` beside `PeerId`, reusing `PEER_ID_HEX`.
If `account` were free-form text, anyone could mint a key in a millisecond, sign "I am `acct_ada`",
and take every row whose owner column holds that string. Self-authenticating ids also delete an
entire vouching apparatus — there is nothing left to vouch for.

**Reserved gains a second author class, and exactly one table uses it.** A link is a *mutual*
claim, and unilateral either way is an attack: an account alone could bind a stranger's device, a
device alone could claim any account. One `[core, sig]` envelope carries one side — but every
event is already signed by its author, so **the account signs the core and the device signs the
envelope**, and `event.peerId === core.device` is the second signature for free. The cost, stated
plainly: `checkReserved` can no longer say "the authority's, full stop". Dispatch becomes a lookup
of the table's author class, never a name check, so the next reserved table must choose
deliberately rather than inherit an ambiguity.

**There is no registry.** Because links are rows, the state *is* the registry: `checkAuthor` reads
one row, the shape `checkRevoked` already uses. `Principal` gains no field, and `evaluate.ts`,
`read-filter.ts` and `rls.ts` change by zero lines — which is evidence for the single-resolution
rule, not a promise about it. `checkAuthor` returns a widened `Author = Principal & { partitions? }`
that `Grant` already satisfies structurally; without that, switching accounts on in a
device-key-only mesh would refuse every `org:` write, since a link signs no partition list.

**A link is scoped to the instance and its partition is inside the signed core.** Reserved rows
skip the partition check, so an unscoped link lands in some partition anyway and is then invisible
to exactly the peers that needed it; and unsigned, a device could replay its `org:acme` link into
`org:victim`. This answers RFC-0016's open question "which partition carries it?" with the answer
E21 gave for revocations, for the same reason: *a device that is Alice's here may mean nothing in
another org.*

**On disagreement, report rather than resolve.** A `_links` row naming account B for a device
whose grant names account A is still *held* — rows converge, and you cannot un-fold one because a
grant arrived later. So it surfaces through `accounts.disputes()` and telemetry. A dispute is
impossible in every mesh running today by construction rather than by luck: it requires
`grant.account` to parse as an `AccountId`, and an `acct_42`-shaped string is not in that namespace.

**Accounts are off until shipped config turns them on**, identical on every peer like `issuer` and
`authority` — never gated on holding an account secret, which would make a peer's verdict depend
on which keys it happens to carry. Rollout divergence is then one-way: a peer with accounts off
admits strictly more, never less, the same shape a validator with no clock already has.
Attribution is the half that needs no flag and improves everywhere — `grants.all()` keyed by
device first, then the live links — with **no synthetic device-as-account fallback**, because a
device that has said nothing about who it belongs to is not somebody, and a device hex rendered as
an account id is indistinguishable from a real one in the same 64-hex space.

The wire, modelled line-for-line on `grant.ts`:

```ts
export interface AccountCore {
  readonly v: 1;
  readonly op: "link" | "unlink";
  readonly account: AccountId;        // the id IS the verification key
  readonly device: PeerId;
  readonly partition: PartitionKey;   // in the core, or a device replays its link elsewhere
  readonly at: Temporal.Instant;
}
const KEY = { v: 0, account: 1, device: 2, op: 3, partition: 4, at: 5 } as const;
```

`verifyLink` takes **no issuer and no clock**: the core names its own verifier, and a link does
not lapse. There is deliberately no `LinkExpired` — expiry is a staleness bound on a *capability*,
a link is a label, and `unlink` is the only verb that ends one.

## Watch out

- **In a granted mesh this earns nothing for `owner()`.** That is the price of grant-wins, not an
  oversight. What it earns is `owner()` in the serverless and device-key-only rungs, and
  attribution that survives grant expiry.
- **In an ungranted mesh, whoever holds the account secret is the account.** No issuer contradicts
  them. That is the trust level a trusted mesh already runs at.
- **Account ids and peer ids share the 64-hex space.** Shipping device-as-owner today means
  adopting accounts later is a data migration of those columns — and there is deliberately no
  helper for it, because rewriting `grant.account` from `acct_42` to a hex id makes every row that
  device owns unreadable to its owner. That is an app-level rewrite with `correct()`, and a helper
  would imply it were safe.
- **First asymmetric crypto on the validation path.** Cheap rungs before the verify, memoized per
  row. And a `_links` row can enter state through a snapshot the validator never judged, so the
  row's wire must be re-verified before it can name a principal — the one place "no registry"
  costs something.
- **A link event must carry nothing else.** An un-upgraded peer quarantines it as `UnknownTable`,
  which is refusal without loss — but only while it is alone. Bundled with an ordinary write, one
  link event poisons that write on every old peer. This is the deliberate contrast with
  `correct()`, which bundles for the opposite reason.
- **`can()` will disagree with the validator** unless its deps take the same resolver — the bug
  fixed for synced policy docs, waiting to be reintroduced here.
- **Interest can starve `_links`**, as it already starves `_revocations` and `_policy`. Inherited,
  not introduced; fix once for all reserved tables.
- `_links` grows one row per (instance, device) forever, the shape `_revocations` already has, and
  should inherit whatever cap that gets.

Left open, and staying open: account key rotation (rotating the key rotates the *id*, hence every
`owner` cell), key custody, and a skew bound on `at` — omitted for the reason a validator with no
clock must not start refusing what it admitted, which leaves a far-future `at` from a clock-wrong
account able to pin a pair against its own later unlink.
