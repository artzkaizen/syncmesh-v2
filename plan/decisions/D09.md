## Context

Every engine has a server component: Zero has zero-cache, LiveStore a Durable Object, Iris Redis. Ours can be embedded in a backend you already run, and the same room logic can be hosted three ways.

## Options

- **A · Embedded** — `startRelay()` inside your existing Bun/Node process, room log in SQLite, the authority peer in the same process. Zero extra deployments. Single box.
- **B · A fleet with a fan-out port** — several relays behind a load balancer, Redis (or NATS, or Postgres LISTEN/NOTIFY) as best-effort pub/sub between them; correctness never depends on it because cursors re-request anything missed.
- **C · One actor per room** — Durable Object or Rivet actor: the platform routes every socket for a room to one actor, so there is no fleet problem; durability, hibernation and multi-region come from the host.

## What the research points to

Write the room logic once against two tiny ports (an event store, a socket that can `send`) and host it three ways — A first because it is the minimum and it is what tests run against; C second because it is the strongest managed shape; B when someone has two boxes. Rivet is blocked on D05 being async.
**Prior art — automerge-repo.** `repo.flush()` settles even when some saves fail and takes a concurrency cap the docs tell you to tie to the storage's constraining resource (fd ceiling, ~6 HTTP/1.1 connections, ~100 HTTP/2 streams); `shutdown()` is flush then close. Adapters can be added and removed at runtime. See `research/prior-art-automerge.md` §1.

## Watch out

The exploration's relay was an in-memory array in one process for months because 'clients are full replicas so relay loss is not data loss' — true, and not a product. `ws.send()` returning 0 means *not sent*: the 100k-event load rig found a joiner that received exactly the buffer's worth and hung forever. Never a raw send; at the backlog ceiling, *close* the socket.

## Decision

**A — embedded first, written against ports so B and C are hosts, not rewrites.**

The room logic is one pure core, `createRelayRoom`, that depends on exactly two ports: the
`EventStore` (RFC-0004 — the same port the engine persists through, so E04's SQLite store is
the durable room log for free) and a `RelaySocket` that can `send` with an honest outcome
(`sent | buffered | dropped`) and `close`. `startRelay()` is the first host: Bun's WebSocket
server in the process you already run, log in SQLite under `.syncmesh/relay/`. Zero extra
deployments; it is also what every test runs against.

B (a fleet) is the same core plus a `Fanout` port — best-effort pub/sub between instances,
never load-bearing because cursors re-request anything it misses. C (one actor per room) is
the same core mounted in a Durable Object or actor, where the platform does the routing and
the hibernation. Neither changes a line of the room.

Not chosen as the *first* shape: B needs two boxes nobody has yet; C couples the minimum
viable relay to a host platform. Both stay reachable by construction — that is the decision.
