## Context

E27 opens with "Decide first: is this a supported shape or a demo?" Company OS has decided the
question for us: the inbox, the call log and the mail store are tables of millions of rows, and a
web tab shows a window of fifty. A device that folds holds whole partitions (book ch. 3, E13's
rescope), and a mail partition is not something a browser tab should replicate to render one
screen. Without a windowed shape, the web half of Company OS has nowhere to stand.

Three facts on `main` (2026-11-07) bound the answer:

1. **The relay folds nothing.** A room holds a log of signed event bytes (`relay/src/room.ts`).
   It has no state store, no rows and no projection. To window a table it would have to fold
   one first.
2. **The relay holds no payload keys.** A sealed partition's events reach it as opaque bytes
   (`SyncEvent.sealed`, D22-A). An unsealed event's cells can be read, but reading cells is not
   holding rows. The relay would still have to fold every event for the room to know what a row
   *is* now.
3. **Interest narrows by partition and nothing finer** (`engine/src/interest.ts`). The table and
   `where` filters were removed from the wire filter because a filtered log does not fold to
   identical state. A window is the place where row-level narrowing belongs, because a window
   is *not* folded.

## What the relay can and cannot order or filter on

|                                                                | relay room (log only) | row-holding peer |
| -------------------------------------------------------------- | --------------------- | ---------------- |
| partition (envelope, always cleartext)                         | filter                | filter           |
| author, sequence, HLC (envelope)                               | filter, order         | filter, order    |
| table, row key, cells of an **unsealed** event                 | read, never fold      | fold, filter, order |
| anything inside a **sealed** event                             | nothing               | fold if it holds the key |
| the current value of a row                                     | nothing (no rows)     | everything       |
| `ORDER BY column LIMIT n` over current rows                    | nothing               | yes              |

So the relay can serve partition interest (E13, built), and that is where its reach ends. Any
query that names a column ordering or a cell predicate needs folded state, so it runs on a peer
that has folded state.

## Options

- **A · A demo.** Keep E27 as a sketch. Company OS's web client then replicates whole
  partitions or uses a bespoke REST endpoint beside syncmesh. Either option leaves two
  read paths that disagree about freshness.
- **B · Supported: the row path runs on a row-holding peer, not in the relay room.** A
  `ClientView` per socket lives in a peer that already holds rows. That peer is an authority or
  server peer: an engine with a store, or E17's Drizzle/Postgres where the rows are the app's
  own tables. It needs the payload keys for the partitions it serves, which it holds as a
  member. The relay package ships the socket handler (`serveWindows`) and its E12 backpressure,
  so any host can mount it over a `RowSource`: `relay-embedded` beside a database, a Durable
  Object with its SQLite, or a Node server beside Postgres. A relay room with no `RowSource`
  serves no windows. The relay keeps its current posture ("the relay interprets nothing").
- **C · Supported, and the relay folds.** The relay grows a state store per room and maintains
  views itself. This contradicts fact 2 for sealed partitions, multiplies relay memory by every
  room's state, and turns the one component an attacker can reach (E24) into one that executes
  queries. Rejected.

## Decision

**B**, decided by the owner on 2026-11-07, in the windowed-sync thread, on this draft's recommendation. The wire is three tags in the relay's control space, deliberately above the range the
gated-visibility and read-permission work is filling: `desire` 32, `undesire` 33 and `rows` 34
(`conformance/window-vectors.json`). They are additive in D14's sense: a build that does not
know them reads `unknown` and ignores them.

- **The query is E13's predicate grammar plus an order and a limit.** It is
  `{ table, where?: PolicyNode, order: [[column, "asc" | "desc"], …], limit, after?: { cells, key } }`.
  `where` is the policy AST, parsed by the policy package's own parser, so there is still one
  grammar. The row key is always the final tiebreak, so `after` is a keyset bound and opening a
  window costs O(log n + scanned) on an ordered source, never O(offset). `scanned` is `limit`
  when the read policy and `where` accept most rows. When they accept few (one tenant's mail in
  a shared table), an index on the order alone scans until it has `limit` rows or reaches the
  end, so a source for that case needs an index that leads with what the policy narrows on.
- **Patches are versioned (E24).** A view's stream is `(epoch, version)`, with `version`
  incremented by exactly one per `rows` frame. A frame that is not `last + 1` in the same epoch
  is a gap. On a gap the client re-desires with `since: [epoch, last]`. A view whose stream is
  anywhere else answers with a reset: a new epoch, then the whole view as a snapshot. A client
  with no position yet names `["", 0]`, which no view is at. Every reset starts a new epoch, so
  a client still waiting for its reset that sees a patch in an epoch it never saw reset knows the
  reset was lost, and asks again; a `rows` frame that does not decode makes it ask again at once.
  A dropped patch, the reset included, therefore costs one resnapshot, never a silently wrong or
  frozen screen (RFC-0010's lesson). Replaying the missed run from a
  bounded ring is what `since` leaves room for; it is not built. A gap is seen only when the next
  patch arrives: there is no heartbeat, so an idle stream that lost its last patch shows the
  screen before it until the source changes or the client desires again.
- **A reconnect never blanks a window.** The client rebuilds its rows beside the old screen and
  swaps them in once the new view has named or refused every window it desires.
- **Rows are refcounted per socket.** A row reaches the client once, however many of that
  socket's windows hold it, and is evicted (a `del`) when the last window that held it moves
  off. Each window's order travels as its key list, at most `limit` keys, so the thin client
  needs no engine to render in order.
- **The thin client** (`@syncmesh/window`) holds rows and windows in memory, applies patches
  and detects gaps. It imports no engine, store or signer.

## What a thin client cannot do (its honest name)

- **Write.** It has no log and no signer for events. Writes go through the app's procedures
  (oRPC, per the procedures decision) on the server peer, and the window then reflects the
  committed row. Nothing in its API looks like `mutate`.
- **Verify rows.** Signatures cover events, and the server peer folded those. The thin client
  trusts the row-holder for the content of a row, as a REST client trusts its API. This is the
  threat-model change E27 warned about, stated here rather than implied away.
- **Work offline beyond the last window.** It can render what it last received and nothing
  else. A reconnect resnapshots.

## What this costs

- The row-holding peer keeps per-socket state: `Σ limit` rows per socket and each window's key
  list. It is bounded by configuration and never by table size: a socket holds at most
  `maxWindows` windows (64 by default) of at most `MAX_LIMIT` (1000) rows, and a desire for a new
  window past that is refused. Each source batch is checked against every open window, so the
  number of windows a change can touch is bounded by `maxWindows`. The work is not: each window a
  change touches is read again from the source, and a read costs `scanned`, not `limit` (see the
  query above). A window that is not full is touched by every change its `where` accepts, and
  with a selective `where` or read policy its read scans to the end of an index that does not
  lead with what they narrow on. One client with 64 such windows over a million-row memory table
  can cost 64 full scans per matching write. The bound is the source's indexes, not the view.
- A reset is the costly frame, and a client can ask for one. A desire whose `since` is not the
  stream's position makes the view send every held row again: up to `maxWindows × MAX_LIMIT`
  (64 000) rows, encoded into one frame before the sender's byte ceiling is checked. The rows
  are ones the reader may already read, so this leaks nothing, but nothing rate-limits it
  either. A host that serves untrusted clients lowers `maxWindows`; a per-socket reset budget
  is not built.
- A refusal is sent once, in the patch that answers its desire. When that patch is lost, the
  reset that answers the gap does not name the window, and the client counts it as settled
  without a reason: it shows no rows and `refusal` says nothing until the client desires it
  again.
- The source's memory is not per socket and grows with the table, as a database's does. The
  memory `RowSource` keeps one sorted index per order a window names, each one entry per row,
  and at most `maxIndexes` (8 by default) per table: an order past that drops the index used
  least recently. A query names at most `MAX_ORDER` (4) order terms. A column no row holds is
  not refused (the memory source has no schema); it orders as null and costs one index slot.
  Building an index is O(n log n), so a client that cycles through more orders than
  `maxIndexes` makes every such desire pay it. The memory source is for tests and tables a host
  can sort in memory; a Postgres source uses the indexes the database already has.
- A source must answer "first `limit` rows matching `where` after `bound`, in `order`" and say
  which rows changed. The memory `RowSource` does this with a sorted index. A Postgres source
  is `ORDER BY … LIMIT` plus the CDC feed E17 already has, and is the next slice, not this one.

- A refusal's reason can name what the source holds: a table the source does not hold is
  refused with `no table …`, while one it holds and the policy hides answers with an empty
  window. That tells a client which tables exist. Table names are the schema's and not secret
  today; a host whose table names are must refuse unknown and hidden tables alike.

## Watch out

- An interest still narrows only after policy (E13). A `RowSource` must apply the read policy
  before `where`, never instead of it. `serveWindows` takes the reader's `admits(table, row)`
  and applies it first.
- The tags 32–34 are chosen to stay clear of parallel relay work. If those land first and
  overlap, the vectors file is the place to renumber, before anything ships.
