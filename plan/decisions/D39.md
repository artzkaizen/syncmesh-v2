## Context

The log is the half of a store that cannot be recomputed (RFC-0022). A torn page in it means the
disk lost committed bytes. Nothing local can bring them back. What the store must not do is
behave as if they were never written.

Measured 2026-11-07 on `bun:sqlite` (`adapters/sqlite-bun/src/__tests__/torn-log.test.ts`): a
store with 10,000 committed events had half a page of zeros written at 40 positions through the
log file. 29 of the 40 reopened without error, and `allSince` returned a subset, for example
9,991 of 10,000. 2 were refused as values (`allSince failed`). 9 hit no event page. `lastSeq`
fails on a damaged page. `openStores`, `allSince` and `all` do not. SQLite keeps no page
checksums, so a b-tree walk past a zeroed leaf just ends early.

What a silent subset costs:

- **Refold.** A state file lost or rebuilt (a schema change, a torn state WAL) is refolded from
  `allSince`. The rows in the missing events are gone, and the cursor ends at the highest
  sequence it saw, above the hole.
- **Anti-entropy.** `eventsSince` answers peers from the same read, and peers never hear about
  the missing events. If every other holder has compacted them, they are lost everywhere.
- **The invariant.** "No acknowledged event is ever absent from a converged replica" (gap audit
  P2). This is the one path where it fails with no fault in the sync code.

Postgres checksums pages when the cluster was initialised with `--data-checksums` (the default
since 18). PGlite and older clusters may not. The same question applies there, at a lower rate.

## Options

- **A · `PRAGMA quick_check` on the log at every open.** It catches every structural tear. It
  costs O(log size) at every launch: seconds on a large device log, which defeats the open-state
  boot RFC-0004 measured at 5.9× faster than a refold.
- **B · A contiguity check where the log is read.** `allSince` and `all` already walk
  `(peer, seq)` in order. A gap in an author's sequence above the compaction floor is
  `StoreFailure("log has a hole")` instead of a shorter list. It costs nothing extra on reads
  that already happen and catches every tear that removes events from the middle of an author's
  run. It does not catch a tear that removes an author's newest events. `lastSeq` already fails
  there, and boot reads it.
- **C · B, plus `quick_check` on demand.** `mesh.inspect.verify()` runs it, and boot runs it once
  after an unclean shutdown. How boot detects an unclean shutdown (a marker written at clean
  close, for example) is part of building it.
- **D · Leave it.** A torn page is the disk's failure, and SQLite's guarantees assume the disk
  keeps its fsync promises.

## Recommendation

**C.** B is the part that turns a silent subset into a value, at no cost on the hot path. The
run check is already implied by how the store numbers events (gap-free per author, D13). The
on-demand and after-crash `quick_check` covers the tears B cannot see, but only when there is a
reason to look, so ordinary launches stay O(live rows). D fails the invariant on hardware that
exists (consumer SSDs and SD cards without power-loss protection).

The torn-log test is `test.failing` until this is decided and built. When detection lands it
flips, and the `.failing` comes off.

## Decision

**C**, decided 2026-11-08 (Jace delegated the call; taken as recommended). The log's reads check
per-author contiguity above the compaction floor and answer `StoreFailure("log has a hole")`
instead of a shorter list. `quick_check` runs on demand through `mesh.inspect.verify()` and once at
boot after an unclean shutdown, detected by a marker written at clean close. Ordinary launches
stay O(live rows). The torn-log test loses its `.failing` when this lands.

## Built

Built 2026-11-08 on `feat/torn-log-detection`.

- **The reads refuse a hole.** `sqlEventStore`'s `allSince` and `all` walk each author's run in
  each scope. A run missing below a later event of the same author, which neither the compaction
  floor nor the gap table (below) accounts for, answers `StoreFailure("log has a hole: …")`
  instead of a shorter list. Everything that reads the log goes through these two:
  `engine.eventsSince` (anti-entropy), the relay's catch-up, a refold at boot, compaction. A
  healthy log pays only the walk: the floors and the gaps are read only when the entries show a
  hole. The entries, the floors and the gaps are three statements, and an append between them
  can make a sound log look torn: a late event that fills a gap deletes its row after the entries
  were read without it. So a read that finds an unaccounted hole reads all three again in one
  transaction, in the driver's turn, and on Postgres under `REPEATABLE READ` (`GapSql.snapshot`),
  and refuses only if the hole is still there. A store opened `nested` inside `Stores.atomic`
  reads again in its caller's transaction as it stands. `packages/storage/src/holes.ts`,
  `event-store.ts`.
- **How a hole made on purpose is told from a torn one** (CodeRabbit on #17). A log has holes
  nobody damaged: a scoped catch-up filters events out (D23), a withheld run is stepped over
  (D40), a snapshot join starts an author's run high, an event is parked by the validator, or one
  simply has not arrived yet. The first three are recorded only as cursor jumps
  (`adoptCoverage`, `installSnapshot`, `takeWithheld`), which live in memory and in the state
  half's `cursors`. The last two are recorded nowhere. The state half is exactly the one that is
  lost and refolded, so the check cannot rest on any of them. Instead the log records each hole
  when it is made: a new log table, `gaps` (`dialect-gaps.ts`). An event that lands above its
  author's highest held sequence plus one records the run between it and that sequence, in the
  same transaction. An event that lands below it is taken out of the gap that held it. On
  Postgres, where two processes can append to one log at once, the append takes a transaction
  advisory lock on each of its authors (in one order) before it reads their heads: two writers
  that read the same head would each record a gap from it, the second row would be dropped on
  the key, and the healthy log would then read as torn. SQLite takes no lock: its appends run in
  the driver's turn, one at a time. A driver with no `transaction` (Rivet's, when its `db` has
  none) gets neither, so two appends of one author racing on it could still drop a gap row; the
  relay room that uses it serializes its own appends, and nothing else appends there. Every
  hole the log was written with is then in the table, whatever made it, and a page the disk
  lost takes events the log held, which nothing recorded. The driver suite pins both halves: a
  scoped log (filtered runs, a high snapshot start, a late fill, local writes) reads whole
  through `allSince`, `all`, `eventsSince` and a refold, and the same log with one event deleted
  under it is refused by each of them.
- **On demand.** `verifyLog(driver)` in `@syncmesh/storage`, and `mesh.inspect.verify()`. A
  device's SQLite runs `PRAGMA syncmesh.quick_check` on the log file. Postgres and PGlite run
  `amcheck` (`verify_heapam` on each log table, `bt_index_check` with `heapallindexed` on its
  b-tree indexes) where the extension is installed, and answer `NoIntegrityCheck` where it is
  not; creating an extension is the operator's call. A Durable Object or Rivet log refuses
  `PRAGMA` and answers `NoIntegrityCheck`. So does a Postgres role that may not execute
  `verify_heapam` and `bt_index_check`: `amcheck` revokes them from `PUBLIC`, so an app's role
  usually cannot run them, and that is no verdict on the log. The mesh answers either as
  `NoSuchCapability`, as it does for a mesh over a bare event store. The grant is checked on the
  exact overloads the check calls, `verify_heapam(regclass,boolean,boolean,text,bigint,bigint)`
  and `bt_index_check(regclass,boolean)`: a grant on another `bt_index_check` does not count.
- **After an unclean shutdown.** `openStores` keeps a `session` row in the log's `meta`: `open`
  from the open until `Stores.close()` or `Stores.markClean()` writes `closed`. An open that finds
  it not `closed` on a log that holds anything runs `quick_check` once first and refuses a
  damaged log as a `StoreFailure`. A mesh over the app's own connection marks the session clean
  at `stop()` without closing the connection.
- **Tests.** `torn-log.test` is no longer `test.failing`; its cases are now the shared
  `tornTests(harness)` in `@syncmesh/storage/driver-tests`, run on `bun:sqlite` and on
  `node:sqlite` under Node: a tear read with no check at open is refused by the read (none of the
  eight positions reads a subset), an unclean shutdown checks the pages at open, `verifyLog`
  finds the tears. `holeCases` in the driver suite runs on every driver (bun, node, wasm, expo,
  Durable Object, Rivet, PGlite, Postgres). `adapters/postgres/src/__tests__/verify.test.ts`
  covers `amcheck` on PGlite, including a role without the grant and a role granted only another
  overload. `holeCases` also fills a gap between a read's statements on every driver;
  `adapters/postgres/src/__tests__/concurrent-append.test.ts` races two writers on one author,
  and a writer filling gaps between a reader's statements, against a real server.

Where it departs from the text above:

- **Contiguity alone was not enough.** The decision says the check costs nothing on the write
  path. Telling deliberate holes from torn ones needs the gap table, so an append now reads its
  author's highest sequence once per batch (one indexed `MAX`) and writes a row when it makes or
  fills a hole. A single `append` now runs in a transaction, since it can write two rows.
- **What the read check still does not see.** A tear that takes an author's newest events, or all
  of them, leaves no later event to show the hole; `lastSeq` refuses the first, the page check
  covers the rest. Once that author writes again, the next append records the torn run as a gap
  the log was written with, and from then on only the page check can find it. For this device's
  own author it is worse than a missed tear: if `lastSeq` ever answered below a torn tail, the
  engine would issue again sequence numbers its peers already hold, which is equivocation.
  Nothing checks that a device's own head never goes down. The step that adds the gap table backfills it from the log as it stands, so a
  hole already in a log written before this build is taken as one it was written with. A tear in
  the gap table itself loses gap rows, which makes reads refuse more, not less.
- **The boot check is a device's SQLite only.** A Postgres log is shared by every process that
  opens it, so one process's clean close says nothing about the others, and the server's own
  crash recovery (full-page writes) repairs torn pages. An inline log has no check to run.
- **An ordinary launch now writes one row.** Detecting an unclean shutdown needs the marker
  cleared or set at open, so every open of a device's SQLite writes the `session` row once (the
  schema-fingerprint test now counts two statements on a reopen, not one).
- **On phones and in browsers, "after an unclean shutdown" is most launches.** The session is
  marked clean only by `Stores.close()`, `Stores.markClean()` and the mesh's `stop()`. Nothing
  marks it on `pagehide`, `visibilitychange` or a React Native `AppState` change, and an app
  swiped away or a tab closed never reaches `stop()`. So the next open finds the session open
  and runs `quick_check` over the whole log file: the O(log size) launch cost the decision
  rejected option A for. A server or a desktop process that stops cleanly gets the profile the
  decision describes. Marking the session clean on background and open again on foreground
  would fix it, but changes what a backgrounded app writes, and is left for the owner to call.
- **The page check runs after the ladder.** `openSession` runs once `sqlEventStore` has migrated
  the log. On the first open after an upgrade, the gap-table backfill (a write) runs before any
  page check and records a tear already in the log as a gap it was written with.
- **A scoped log reads its whole gap table.** A healthy unscoped log pays only the walk. A scoped
  device always has holes, so each `allSince` or `eventsSince` on it also reads the compaction
  floors and every row of `gaps`, not only the rows of the authors with holes.
- **What is not tested.** No test shows `amcheck` finding damage, and no tearing test runs on
  PGlite (`tornTests` runs on `bun:sqlite` and `node:sqlite`); `holeCases` runs on PGlite and a
  real server. The gap-tracking write path runs on the Durable Object and Rivet drivers only
  through their adapter suites, never on a real `workerd`; its backfill uses `WITHOUT ROWID` and
  `LAG`.
- **A refused read has no way back yet.** The refusal says "rejoin from a peer", and that is all:
  nothing in the mesh shows it as a status or offers a rejoin. Not built.
- **`verify` checks the log only.** The state half is derived and is refolded from the log.
- **Names.** The modules this touched had their `*For`/`*Of` helpers renamed under the naming
  skill: `schemaName`, `statePath`, `lockPath`, `storeFiles`, `storeName`, `logPlacement`.

## Follow-ups built (2026-11-08, on `fix/access-followups`, #30)

Two of the limits above, decided 2026-11-08 (Jace delegated the call) and built.

**The session follows the app into the background and back.** The mesh marks the log's session
clean when the app goes to the background and open again on the way back, so the page check at
open runs after a real crash rather than after every swipe-away. Wired in the mesh's lifecycle,
not app code:

- `Stores.markOpen()` (`storage/src/open-stores.ts`, `reopenSession` in `integrity.ts`) marks the
  session open again without the check an open runs. `Booted.session` carries both marks wherever
  the mesh marks the session at `stop()` — over the app's driver or the default store, never over
  stores the caller opened.
- The platform seam is the existing `Knock`: its `wake` may now name an `AppPhase`
  (`"background" | "foreground"`). A knock naming the background wakes no medium and marks the
  session clean; the foreground marks it open and wakes every medium as before; a plain knock is
  unchanged. `@syncmesh/react-native`'s `foreground()` now says `background` on `AppState`
  `background` (not `inactive`, which is passing) and `foreground` on `active`.
- On a browser page the mesh listens by default — `visibilitychange` to `hidden` and `pagehide`
  are the background, `visible` and `pageshow` the foreground (`client/src/session-marks.ts`
  `pagePhases`) — and a returning tab marks the session without redialling anything. Only a
  change is written, marks run in order, and `stop()` waits for them before it closes.
- Why marking clean in the background is safe: the check exists for a page the disk lost on power
  loss or an OS crash. A platform ending a backgrounded process is a process kill, which SQLite's
  journal already survives; a write made while backgrounded commits through that same journal.
- Tests: `client/src/__tests__/session-marks.test.ts` (a phased knock marks clean without waking,
  the foreground reopens and wakes; on a page, hidden, visible, `pagehide` and `pageshow`), each
  failing with the marks disabled.

**A refused log read is a `$recovery` issue, and the mesh rejoins by itself.** D46's `$recovery`
shape is on main, so this extends it:

- The refusal carries its runs: `StoreFailure("log has a hole")` now has a `LogTorn { runs }`
  cause (`tornRuns(error)` in `@syncmesh/engine`), and the engine says a torn read of
  `eventsSince` on `onError`, once per tear.
- `$recovery.torn()` lists `TornIssue { run, state }` — `waiting`, `rejoining`, or `lost` for a run
  of local-only events nothing else held — with `onTorn`, and `mesh.status` reads
  `blocked-recovery` while any is open (`client/src/torn.ts`).
- The rejoin: once a peer whose cursors this device holds — the run's author, or one whose cursors
  pass the run — is linked, the mesh calls the new `engine.reopen(runs)`: each run is recorded as a
  gap the log admits to (through `EventStore.evict`, which deletes nothing that is not there), so
  the log reads again, and the cursor drops below the run with what is held above it kept as held
  past a gap (`CoverageTracker.reopen`, the one place a cursor is lowered). Every medium is asked
  again (`Transport.resync`), the peer sends the run, the delivery fills the gap, and the issue
  clears once the cursor passes the run — by the events, or by state where every holder compacted
  them (D46).
- `$recovery.acceptTorn(run)` takes a run as gone, so the log reads without it: what a `lost` run
  needs, and what a synced run no peer will ever send can be given; a synced run accepted that way
  is still asked for as a hole.
- Tests: `client/src/__tests__/torn.test.ts` (two meshes; two events deleted under the device's
  log; the read is refused, the issue raised, the status blocked, and the mesh rejoins from the
  author until the log reads whole — fails with the rejoin disabled; and a waiting run accepted)
  and `engine/src/__tests__/coverage.test.ts` (the cursor lowered and closed again).

Where it departs, or stops:

- **A mesh hosted in `@syncmesh/browser`'s tab worker hears no page lifecycle.** The elected tab's
  dedicated worker has no `document`, so it still checks after every close until the tab forwards
  its phases to the worker (gap U32). A mesh on the page itself, and React Native, are covered.
- A tear is found only when something reads that part of the log: a peer asking from below it, a
  refold, compaction. The engine raises the issue from `eventsSince`; a tear in local-only events
  is seen by the reads that walk them (refold, compaction), which do not raise it yet.
- A device that never heard the author's or a holder's cursors waits; the issue says `waiting`.
- Tested with another device's run over a peer link. A torn run of this device's own synced
  events goes the same way (a peer whose cursors pass it holds it), and the relay path re-joins
  from the lowered cursors through `resync`; neither has a test of its own yet.
