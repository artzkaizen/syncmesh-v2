## Context

The log is the half of a store that cannot be recomputed (RFC-0022). A torn page in it means the
disk lost committed bytes. Nothing local can bring them back. What the store must not do is
behave as if they were never written.

Measured 2026-11-07 on `bun:sqlite` (`adapters/sqlite-bun/src/__tests__/torn-log.test.ts`): a
store with 10,000 committed events had half a page of zeros written at 40 positions through the
log file. 29 of the 40 reopened without error, and `allSince` returned a subset, for example
9,991 of 10,000. 2 were refused as values (`allSince failed`). 9 hit no event page. `lastSeq`
fails on a damaged page. `openStores`, `allSince` and `all` do not. SQLite keeps no page
checksums, so a b-tree walk past a zeroed leaf just ends early.

What a silent subset costs:

- **Refold.** A state file lost or rebuilt (a schema change, a torn state WAL) is refolded from
  `allSince`. The rows in the missing events are gone, and the cursor ends at the highest
  sequence it saw, above the hole.
- **Anti-entropy.** `eventsSince` answers peers from the same read, and peers never hear about
  the missing events. If every other holder has compacted them, they are lost everywhere.
- **The invariant.** "No acknowledged event is ever absent from a converged replica" (gap audit
  P2). This is the one path where it fails with no fault in the sync code.

Postgres checksums pages when the cluster was initialised with `--data-checksums` (the default
since 18). PGlite and older clusters may not. The same question applies there, at a lower rate.

## Options

- **A · `PRAGMA quick_check` on the log at every open.** It catches every structural tear. It
  costs O(log size) at every launch: seconds on a large device log, which defeats the open-state
  boot RFC-0004 measured at 5.9× faster than a refold.
- **B · A contiguity check where the log is read.** `allSince` and `all` already walk
  `(peer, seq)` in order. A gap in an author's sequence above the compaction floor is
  `StoreFailure("log has a hole")` instead of a shorter list. It costs nothing extra on reads
  that already happen and catches every tear that removes events from the middle of an author's
  run. It does not catch a tear that removes an author's newest events. `lastSeq` already fails
  there, and boot reads it.
- **C · B, plus `quick_check` on demand.** `mesh.inspect.verify()` runs it, and boot runs it once
  after an unclean shutdown. How boot detects an unclean shutdown (a marker written at clean
  close, for example) is part of building it.
- **D · Leave it.** A torn page is the disk's failure, and SQLite's guarantees assume the disk
  keeps its fsync promises.

## Recommendation

**C.** B is the part that turns a silent subset into a value, at no cost on the hot path. The
run check is already implied by how the store numbers events (gap-free per author, D13). The
on-demand and after-crash `quick_check` covers the tears B cannot see, but only when there is a
reason to look, so ordinary launches stay O(live rows). D fails the invariant on hardware that
exists (consumer SSDs and SD cards without power-loss protection).

The torn-log test is `test.failing` until this is decided and built. When detection lands it
flips, and the `.failing` comes off.

## Decision

**C**, decided 2026-11-08 (Jace delegated the call; taken as recommended). The log's reads check
per-author contiguity above the compaction floor and answer `StoreFailure("log has a hole")`
instead of a shorter list. `quick_check` runs on demand through `mesh.inspect.verify()` and once at
boot after an unclean shutdown, detected by a marker written at clean close. Ordinary launches
stay O(live rows). The torn-log test loses its `.failing` when this lands.

## Built

Built 2026-11-08 on `feat/torn-log-detection`.

- **The reads refuse a hole.** `sqlEventStore`'s `allSince` and `all` walk each author's run in
  each scope. A run missing below a later event of the same author, which neither the compaction
  floor nor the gap table (below) accounts for, answers `StoreFailure("log has a hole: …")`
  instead of a shorter list. Everything that reads the log goes through these two:
  `engine.eventsSince` (anti-entropy), the relay's catch-up, a refold at boot, compaction. A
  healthy log pays only the walk: the floors and the gaps are read only when the entries show a
  hole. The entries, the floors and the gaps are three statements, and an append between them
  can make a sound log look torn: a late event that fills a gap deletes its row after the entries
  were read without it. So a read that finds an unaccounted hole reads all three again in one
  transaction, in the driver's turn, and on Postgres under `REPEATABLE READ` (`GapSql.snapshot`),
  and refuses only if the hole is still there. A store opened `nested` inside `Stores.atomic`
  reads again in its caller's transaction as it stands. `packages/storage/src/holes.ts`,
  `event-store.ts`.
- **How a hole made on purpose is told from a torn one** (CodeRabbit on #17). A log has holes
  nobody damaged: a scoped catch-up filters events out (D23), a withheld run is stepped over
  (D40), a snapshot join starts an author's run high, an event is parked by the validator, or one
  simply has not arrived yet. The first three are recorded only as cursor jumps
  (`adoptCoverage`, `installSnapshot`, `takeWithheld`), which live in memory and in the state
  half's `cursors`. The last two are recorded nowhere. The state half is exactly the one that is
  lost and refolded, so the check cannot rest on any of them. Instead the log records each hole
  when it is made: a new log table, `gaps` (`dialect-gaps.ts`). An event that lands above its
  author's highest held sequence plus one records the run between it and that sequence, in the
  same transaction. An event that lands below it is taken out of the gap that held it. On
  Postgres, where two processes can append to one log at once, the append takes a transaction
  advisory lock on each of its authors (in one order) before it reads their heads: two writers
  that read the same head would each record a gap from it, the second row would be dropped on
  the key, and the healthy log would then read as torn. SQLite takes no lock: its appends run in
  the driver's turn, one at a time. A driver with no `transaction` (Rivet's, when its `db` has
  none) gets neither, so two appends of one author racing on it could still drop a gap row; the
  relay room that uses it serializes its own appends, and nothing else appends there. Every
  hole the log was written with is then in the table, whatever made it, and a page the disk
  lost takes events the log held, which nothing recorded. The driver suite pins both halves: a
  scoped log (filtered runs, a high snapshot start, a late fill, local writes) reads whole
  through `allSince`, `all`, `eventsSince` and a refold, and the same log with one event deleted
  under it is refused by each of them.
- **On demand.** `verifyLog(driver)` in `@syncmesh/storage`, and `mesh.inspect.verify()`. A
  device's SQLite runs `PRAGMA syncmesh.quick_check` on the log file. Postgres and PGlite run
  `amcheck` (`verify_heapam` on each log table, `bt_index_check` with `heapallindexed` on its
  b-tree indexes) where the extension is installed, and answer `NoIntegrityCheck` where it is
  not; creating an extension is the operator's call. A Durable Object or Rivet log refuses
  `PRAGMA` and answers `NoIntegrityCheck`. (Superseded for the Durable Object: workerd allows
  `PRAGMA quick_check(<table>)`, and an inline log is now checked per log table; see "Built: the
  kill and tear tests on the other drivers (O16)".) So does a Postgres role that may not execute
  `verify_heapam` and `bt_index_check`: `amcheck` revokes them from `PUBLIC`, so an app's role
  usually cannot run them, and that is no verdict on the log. The mesh answers either as
  `NoSuchCapability`, as it does for a mesh over a bare event store. The grant is checked on the
  exact overloads the check calls, `verify_heapam(regclass,boolean,boolean,text,bigint,bigint)`
  and `bt_index_check(regclass,boolean)`: a grant on another `bt_index_check` does not count.
- **After an unclean shutdown.** `openStores` keeps a `session` row in the log's `meta`: `open`
  from the open until `Stores.close()` or `Stores.markClean()` writes `closed`. An open that finds
  it not `closed` on a log that holds anything runs `quick_check` once first and refuses a
  damaged log as a `StoreFailure`. A mesh over the app's own connection marks the session clean
  at `stop()` without closing the connection.
- **Tests.** `torn-log.test` is no longer `test.failing`; its cases are now the shared
  `tornTests(harness)` in `@syncmesh/storage/driver-tests`, run on `bun:sqlite` and on
  `node:sqlite` under Node: a tear read with no check at open is refused by the read (none of the
  eight positions reads a subset), an unclean shutdown checks the pages at open, `verifyLog`
  finds the tears. `holeCases` in the driver suite runs on every driver (bun, node, wasm, expo,
  Durable Object, Rivet, PGlite, Postgres). `adapters/postgres/src/__tests__/verify.test.ts`
  covers `amcheck` on PGlite, including a role without the grant and a role granted only another
  overload. `holeCases` also fills a gap between a read's statements on every driver;
  `adapters/postgres/src/__tests__/concurrent-append.test.ts` races two writers on one author,
  and a writer filling gaps between a reader's statements, against a real server.

Where it departs from the text above:

- **Contiguity alone was not enough.** The decision says the check costs nothing on the write
  path. Telling deliberate holes from torn ones needs the gap table, so an append now reads its
  author's highest sequence once per batch (one indexed `MAX`) and writes a row when it makes or
  fills a hole. A single `append` now runs in a transaction, since it can write two rows.
- **What the read check still does not see.** A tear that takes an author's newest events, or all
  of them, leaves no later event to show the hole; `lastSeq` refuses the first, the page check
  covers the rest. Once that author writes again, the next append records the torn run as a gap
  the log was written with, and from then on only the page check can find it. For this device's
  own author it is worse than a missed tear: if `lastSeq` ever answered below a torn tail, the
  engine would issue again sequence numbers its peers already hold, which is equivocation.
  Nothing checks that a device's own head never goes down. The step that adds the gap table backfills it from the log as it stands, so a
  hole already in a log written before this build is taken as one it was written with. A tear in
  the gap table itself loses gap rows, which makes reads refuse more, not less.
- **The boot check is a device's SQLite only.** A Postgres log is shared by every process that
  opens it, so one process's clean close says nothing about the others, and the server's own
  crash recovery (full-page writes) repairs torn pages. An inline log has no check to run.
- **An ordinary launch now writes one row.** Detecting an unclean shutdown needs the marker
  cleared or set at open, so every open of a device's SQLite writes the `session` row once (the
  schema-fingerprint test now counts two statements on a reopen, not one).
- **On phones and in browsers, "after an unclean shutdown" is most launches.** The session is
  marked clean only by `Stores.close()`, `Stores.markClean()` and the mesh's `stop()`. Nothing
  marks it on `pagehide`, `visibilitychange` or a React Native `AppState` change, and an app
  swiped away or a tab closed never reaches `stop()`. So the next open finds the session open
  and runs `quick_check` over the whole log file: the O(log size) launch cost the decision
  rejected option A for. A server or a desktop process that stops cleanly gets the profile the
  decision describes. Marking the session clean on background and open again on foreground
  would fix it, but changes what a backgrounded app writes, and is left for the owner to call.
- **The page check runs after the ladder.** `openSession` runs once `sqlEventStore` has migrated
  the log. On the first open after an upgrade, the gap-table backfill (a write) runs before any
  page check and records a tear already in the log as a gap it was written with.
- **A scoped log reads its whole gap table.** A healthy unscoped log pays only the walk. A scoped
  device always has holes, so each `allSince` or `eventsSince` on it also reads the compaction
  floors and every row of `gaps`, not only the rows of the authors with holes.
- **What is not tested.** No test shows `amcheck` finding damage, and no tearing test runs on
  PGlite (`tornTests` runs on `bun:sqlite` and `node:sqlite`); `holeCases` runs on PGlite and a
  real server. The gap-tracking write path runs on the Durable Object and Rivet drivers only
  through their adapter suites, never on a real `workerd`; its backfill uses `WITHOUT ROWID` and
  `LAG`.
- **A refused read has no way back yet.** The refusal says "rejoin from a peer", and that is all:
  nothing in the mesh shows it as a status or offers a rejoin. Not built.
- **`verify` checks the log only.** The state half is derived and is refolded from the log.
- **Names.** The modules this touched had their `*For`/`*Of` helpers renamed under the naming
  skill: `schemaName`, `statePath`, `lockPath`, `storeFiles`, `storeName`, `logPlacement`.

## Follow-ups built (2026-11-08, on `fix/access-followups`, #30)

Two of the limits above, decided 2026-11-08 (Jace delegated the call) and built.

**The session follows the app into the background and back.** The mesh marks the log's session
clean when the app goes to the background and open again on the way back, so the page check at
open runs after a real crash rather than after every swipe-away. Wired in the mesh's lifecycle,
not app code:

- `Stores.markOpen()` (`storage/src/open-stores.ts`, `reopenSession` in `integrity.ts`) marks the
  session open again without the check an open runs. `Booted.session` carries both marks wherever
  the mesh marks the session at `stop()` — over the app's driver or the default store, never over
  stores the caller opened.
- The platform seam is the existing `Knock`: its `wake` may now name an `AppPhase`
  (`"background" | "foreground"`). A knock naming the background wakes no medium and marks the
  session clean; the foreground marks it open and wakes every medium as before; a plain knock is
  unchanged. `@syncmesh/react-native`'s `foreground()` now says `background` on `AppState`
  `background` (not `inactive`, which is passing) and `foreground` on `active`.
- On a browser page the mesh listens by default — `visibilitychange` to `hidden` and `pagehide`
  are the background, `visible` and `pageshow` the foreground (`client/src/session-marks.ts`
  `pagePhases`) — and a returning tab marks the session without redialling anything. Only a
  change is written, marks run in order, and `stop()` waits for them before it closes.
- **A write marks the session open again.** A backgrounded mesh is not a stopped one: a hidden
  tab keeps its relay socket and a phone may still fold what arrives, so the log is written after
  the clean mark. The first write after the mark through the opened `Stores` marks the session
  open first and only then writes (`openBeforeWrite` in `storage/src/open-stores.ts`), and the
  next trip to the background marks it clean again. That is every method that writes: `atomic`,
  the log's `append`, `appendBatch`, `compactBelow` and `evict`, the state's `commit`, `clear`,
  `remove` and `derive`, and the doc log's `append`, `relineage`, `refreshHead`, `cover` and
  `forget`. One write is left out: `Stores.rowSync.acknowledge`, which the client calls from
`client/src/sync-state.ts` and which updates the `acked` watermark in the state file. That file is
not what `quick_check` reads, so a write there under a clean mark puts no log page at risk. The write ledger (`operationStore`) lives in the log's file and is written from frames that
  arrive in the background — a peer's receipt, vouch or refusal — on `Stores.driver`, not through
  the stores, so it now takes `beforeWrite` and runs it before each of `record`, `acknowledge`,
  `vouch`, `refuse` and `correct`; the boot passes the opened stores' new `Stores.beforeWrite`.
  Found by CodeRabbit in review of #30, round 4 (Jace delegated the call). The
engine compacts and a torn rejoin evicts on their own turn, outside `atomic`, so
  wrapping only the appends left those two writing under a clean mark. Added 2026-11-08 in review
  of #30, round 2 (Jace delegated the call).
- The window left: the check exists for a page the disk lost on power loss or an OS crash. While
  the session is marked clean nothing has been written through the stores since the mark, so a
  power loss or OS crash then skips a check over pages the last session already closed. A
  platform ending a backgrounded process is a process kill, which SQLite's journal already
  survives. What is not covered: a write the engine had begun before the background mark landed
  commits after it, and the session stays clean until the next write; a mark is a plain
  statement, so one issued while another transaction holds the connection lands inside it; and a
  statement an app runs on `Stores.driver` itself, outside the mesh and outside `atomic`, does not
  reopen the session unless the app awaits `Stores.beforeWrite()` first.
- The phase starts at `foreground` (`sessionPhases` in `client/src/session-marks.ts`) and reads
  neither `document.visibilityState` nor `AppState.currentState`, so a mesh booted in a hidden
  tab or a background launch marks nothing until the first change of phase. That keeps the open
  mark the boot wrote, which is the safe direction: the next launch after a kill runs the check.
- An app's knocks report a phase only while the transport set runs (`answerKnock` returns early
  when it is stopped), so a React Native mesh with no transports, or one not started yet, marks
  nothing on background and keeps the check. The page's own lifecycle has no such limit.
- Tests: `client/src/__tests__/session-marks.test.ts` (a phased knock marks clean without waking,
  the foreground reopens and wakes; a write made in the background marks the session open before
  it lands; on a page, hidden, visible, `pagehide` and `pageshow`), each failing with the marks
  disabled — the write case with `openBeforeWrite` disabled — and
  `storage/src/__tests__/open-stores.test.ts` (each writing method, after `markClean`, leaves the
  session open; the `compactBelow`, `evict`, `state.commit`, `state.clear` and `docs.forget`
  cases fail with their wrap removed; and each write of the ledger over the stores'
  `beforeWrite`, which fail with the call removed from `operationStore`). The session-marks file
  also boots over a driver, marks the session clean and writes a receipt: the session reads open,
  and the case fails with the boot not passing `beforeWrite` to the ledger.

**A refused log read is a `$recovery` issue, and the mesh rejoins by itself.** D46's `$recovery`
shape is on main, so this extends it:

- The refusal carries its runs: `StoreFailure("log has a hole")` now has a `LogTorn { runs }`
  cause (`tornRuns(error)` in `@syncmesh/engine`), and the engine says a torn read of
  `eventsSince` on `onError`, once per tear.
- `$recovery.torn()` lists `TornIssue { run, state }` — `waiting`, `rejoining`, or `lost` for a run
  of local-only events nothing else held — with `onTorn`, and `mesh.status` reads
  `blocked-recovery` while any is open (`client/src/torn.ts`).
- The rejoin: once a peer whose cursors this device holds — the run's author, or one whose cursors
  pass the run — is linked, the mesh calls the new `engine.reopen(runs)`: each run is recorded as a
  gap the log admits to (through `EventStore.evict`, which deletes nothing that is not there), so
  the log reads again, and the cursor drops below the run with what is held above it kept as held
  past a gap (`CoverageTracker.reopen`, the one place a cursor is lowered). Every medium is asked
  again (`Transport.resync`), the peer sends the run, the delivery fills the gap, and the issue
  clears once the cursor passes the run — by the events, or by state where every holder compacted
  them (D46).
- `$recovery.acceptTorn(run)` takes a run as gone, so the log reads without it: what a `lost` run
  needs, and what a synced run no peer will ever send can be given. The issue is dropped either
  way, so the status stops blocking on it; a synced run accepted that way is still asked for as a
  hole, and a peer that holds it still fills it.
- Until a peer sends it, a synced run accepted that way keeps this device's cursor for its author
  below the run (`CoverageTracker.reopen` lowered it), so the `cursors` frames this device sends
  hold back the compaction floor its peers compute for that author by the same amount. A run no
  peer will ever send holds that floor back for good; recorded in review of #30, round 2.
- A rejoining run clears only after its reopen has landed. The issue turns `rejoining` at once,
  but `engine.reopen` runs later, on the watch's queue, and until it lowers the cursor the synced
  cursor still claims the run. A fold in that window, for example an unrelated batch, used to read
  the run as back and clear the issue, so a device left with the hole stopped reporting it. The
  watch now keeps the runs whose reopen is under way and does not settle them (`reopening` in
  `client/src/torn.ts`). Fixed in review of #30, round 3 (Jace delegated the call).
- Tests: `client/src/__tests__/torn.test.ts` (two meshes; two events deleted under the device's
  log; the read is refused, the issue raised, the status blocked, and the mesh rejoins from the
  author until the log reads whole — fails with the rejoin disabled; and a waiting run accepted,
  after which `torn()` is empty and the status no longer blocks — fails with the accept keeping
  the issue; and, against a fake engine whose reopen waits on a gate, a fold that lands before
  the reopen does not clear the run — fails with the `reopening` check removed)
  and `engine/src/__tests__/coverage.test.ts` (the cursor lowered and closed again).

Where it departs, or stops:

- **A mesh hosted in `@syncmesh/browser`'s tab worker hears its tabs' lifecycle**, built for U32 on
  `feat/browser-lifecycle` (decided 2026-11-08, Jace delegated the call); see "Built: the tab
  worker" below. Before it, the elected tab's dedicated worker had no `document` and checked the
  log after every close.
- A tear is found only when something reads that part of the log: a peer asking from below it, a
  refold, compaction. The engine raises the issue from `eventsSince`; a tear in local-only events
  is seen by the reads that walk them (refold, compaction), which do not raise it yet.
- A device that never heard the author's or a holder's cursors waits; the issue says `waiting`.
- Tested with another device's run over a peer link. A torn run of this device's own synced
  events goes the same way (a peer whose cursors pass it holds it), and the relay path re-joins
  from the lowered cursors through `resync`; neither has a test of its own yet.

## Built: the tab worker (U32)

Built 2026-11-08 on `feat/browser-lifecycle` (#33; decided 2026-11-08, Jace delegated the call).

- **Every tab says its phase over its link.** `openMeshLink`'s link (`tabs.ts`, `hold`) posts
  `{ kind: "phase", phase }` (`PhaseBody` in `protocol.ts`) when it opens and on every
  `visibilitychange`: `hidden` is `background`, anything else `foreground`. `pagehide` already
  posts `bye`, which takes the window out of the count rather than marking it hidden.
- **The host works out the origin's phase.** `serveMesh(mesh, { phases })` counts the windows it
  serves: the origin is in the background once none is shown (the last one hidden, or the last
  shown one gone) and in front again with the first one back. A window that has said nothing
  counts as shown, the safe direction. Told once per change; `host.stop()` tells nothing.
- **The mesh hears it as a knock.** `createTabPhases()` returns `{ knock, tell }`: the knock goes
  in the mesh's `knocks` at construction, the same object in `serveMesh`'s `phases`. So
  `background` marks the session clean and wakes nothing, and `foreground` marks it open and
  wakes every transport, which resets the relay's reconnect backoff (`RelayLink.wake`). A mesh
  that starts listening after the origin went to the background hears `background` at once.
  `apps/issues`' worker passes it.
- Tests: `adapters/browser/src/__tests__/phases.test.ts` (over `MessageChannel`s: the origin's
  phase from two windows, a window leaving and arriving, the last window leaving, `stop()`, the
  session marked `closed` then `open` with the medium woken once on return, the late listener, and
  a tab posting its phase at open and on each change — each fails with its part disabled) and
  `two-tabs.test.ts` (Chromium: both tabs hidden marks the worker's session `closed`, one shown
  marks it `open` — fails with the host's count or the tab's forwarding disabled).

Where it departs, or stops:

- The wake is the origin's, not each tab's: a tab coming back while another window of the origin
  is shown wakes nothing, because the origin never left the front and its sockets were in use.
  Switching between two tabs of one origin in one window can pass through "none shown" for a
  moment, which marks the session clean, opens it again and redials the relay; nothing delays the
  background mark, because a browser may freeze the worker right after the last `hidden`.
- The wiring is the app's two lines, not automatic as on a page: the knock has to exist before
  the mesh, and the host after it. `serveMesh` without `phases` behaves as before.
- A page restored from the back/forward cache said `bye` on `pagehide`, so its old link is gone
  from the host; the tab does not relink by itself. Unchanged by this work.


## Built: the kill and tear tests on the other drivers (O16)

Built 2026-11-09 on `test/crash-drivers` (#51; decided 2026-11-09, Jace delegated the call: the Durable
Object through Miniflare, OPFS through the Playwright setup, expo through its testable layer).
Before it, `crashTests` and `tornTests` ran on `bun:sqlite`, `node:sqlite` and PGlite only.

- **Durable Object, on a real workerd.** `adapters/cloudflare-do/src/__tests__/crash.test.ts`
  bundles a fixture object (`workerd/room.ts`: `doSqliteDriver` over its own `ctx.storage.sql`)
  and runs it in Miniflare over one persist directory. The child is the object stepped one batch
  per call (`crashWriter`, split out of `crashChild` for a child that cannot loop forever, since a
  Durable Object's turn is its transaction). It dies two ways: `sigkill` sends SIGKILL to workerd
  itself while batches are in flight, and `reset` has the object call `ctx.abort()` at a chosen
  statement inside a batch, a different one each round. Both crash cases pass for both deaths. The
  `reset` cases fail with the driver yielding to the event loop between statements (the turn no
  longer one transaction: "a batch is one transaction, so the log ends on a boundary: expected 0,
  got 18"); the `sigkill` cases did not catch that sabotage in the run tried, since where the kill
  lands is timing. The torn suite runs on the object's file (its WAL folded in first with
  `bun:sqlite`, since workerd leaves it unindexed on disk), less "after an unclean shutdown, the
  open checks the pages first": an inline log keeps no session (see "The boot check is a device's
  SQLite only" above). The read refuses the tears there; with the read's hole check disabled it
  returns a subset (8 positions, 9,805 to 9,991 of 10,000).
- **`verifyLog` checks a Durable Object's pages.** The text above said a Durable Object refuses
  `PRAGMA` and answers `NoIntegrityCheck`. Measured in workerd: it refuses `integrity_check`,
  `user_version` and `journal_mode` (`not authorized: SQLITE_AUTH`), and allows `quick_check`,
  `quick_check(<table>)` among them. `verifyLog` on an inline log now runs `PRAGMA quick_check` on
  each log table present (the state's tables share the file and are not the log), and answers
  `NoIntegrityCheck` when the runtime refuses it, which is what a Rivet actor gets if its
  runtime does. A refusal is recognised by its words, workerd's authorizer ("not authorized",
  `SQLITE_AUTH`) or another runtime's gate ("not allowed", "not permitted", "not supported", but not
  "unsupported", which SQLite says of a garbled header as "unsupported file format"), and
  carries the runtime's refusal as its `cause`; anything else is damage. Damage cannot be matched
  by name instead: workerd reports a torn page that `quick_check` reads as an assertion
  (`false == true`), not as `SQLITE_CORRUPT`, which the torn suite's `verifyLog` case on workerd
  showed when it was tried. `storage/src/integrity.ts`; `storage/src/__tests__/integrity.test.ts` (an inline
  log over `bun:sqlite` passes, one whose runtime refuses `PRAGMA` answers `NoIntegrityCheck` in
  workerd's words or in "not supported", and a check failing in other words is damage; the first
  fails with the old answer, the "not supported" case with the authorizer-only match), and the torn suite's `verifyLog` case on
  workerd (finds the tears, passes the sound log; failed with the old answer).
- **OPFS, in Chromium.** `adapters/sqlite-wasm/src/__tests__/opfs-crash.test.ts` builds a page
  (`opfs-crash/`) with Vite and runs the suites inside it, since only the browser reaches the
  files. Reads go through `wasmSqliteDriver` from the window, so through the package's own worker,
  as an app's page does. The writer is a dedicated worker on the access-handle pool, ended by
  `worker.terminate()` or by Playwright closing the page that started it. The torn suite tears the
  log through a file worker that exports, zeroes and imports the pool's file. The profile is on
  disk (`launchPersistentContext`), as a browser's own is: an off-the-record context keeps OPFS in
  memory, which is not what a device runs (the crash cases pass there too with the WAL fix). A
  third group checks the open itself. What they found, all fixed in the adapter:
  - A pool reopened in the same worker reserved its slots before waking: a paused pool holds no
    handles and so counts no slots, so `reserveMinimumCapacity` added a full new set, and the VFS
    stayed unregistered. The next open failed, and its cleanup threw `Unknown sqlite3_vfs name`.
    Any app that closes its stores and opens them again in one worker met it. Now woken first
    (`holdPool` in `pool.ts`). Fails with the order reversed (the mid-fold crash case).
  - Every OPFS directory shared one pool: `installOpfsSAHPoolVfs` keeps one pool per VFS name and
    the adapter never gave one, so a second `directory` (the documented way to run two meshes in
    one origin) wrote into the first one's files, and closing either paused both. Each directory
    now registers its own VFS name (`poolVfs`), named in the `ATTACH` URI. The case "two
    directories in one thread are two pools" fails without it.
  - A log that would not attach (a schema page the disk lost: `SQLITE_CORRUPT` on `ATTACH`) left
    the derived half open, so giving the pool back threw and the open panicked instead of
    answering `OpfsUnavailable`. The half that opened is closed first now (`pairOn` in
    `databases.ts`). The case "a log that will not attach is refused as a value" fails without it.
  - A pool taken while a killed context was still being reaped was left half-acquired:
    sqlite-wasm takes the slots all at once and, when one is refused, gives back those it had
    while the rest still arrive, leaving handles held, the VFS unregistered, and the pool reading
    as awake; a failed install is remembered under its name the same way. The 100 ms retry loops
    asked again into that state. Now the adapter opens and closes each slot's handle first, under
    the lease, and takes the pool only once none is held elsewhere (`slotsHeld`, `reaped`); under
    `"refuse"` a held slot is `OpfsPoolHeld` at once. With the probe disabled 6 and 7 of 10 cases
    fail.
  - The worker host answered nothing when an answer threw, so the page awaited that request for
    ever (the first symptom of the bugs above). A thrown answer is now replied to as an error
    (`serveSqlite` in `host.ts`). `worker-host.test.ts` pins it with a request that throws as the
    host reads it; the file fails without the fix.
  - Two opens of one directory at once in one worker (two scoped stores opened by `Promise.all`,
    D07) raced. Each asked the Web Lock before either held it, so the second was refused the lease
    its own thread was taking (`OpfsPoolHeld` under `"refuse"`; under `"wait"` it queued behind
    it for as long as the first store stayed open). Past the lease, the second found no pool yet
    and probed the slots the first was installing on. Opens of a directory now run one at a time
    in a thread (`inTurn` in `pool.ts`), a failed open gives the lease back only if it took it,
    and a close that lands while another open of the directory is under way gives the pool back
    after that open, which then holds a reference (`releaseWhenIdle`). Cases "two databases
    opened at once in one directory share its pool" (fails without the turns, `OpfsPoolHeld`) and
    "a close that lands while another open grows the pool leaves that one the lease" (fails with
    the release run at once: the pool is paused under the growing open, which panics).
  - The `ATTACH` spliced its URI into the SQL, and the URI carried the VFS name unescaped. A store
    name with a quote broke the `ATTACH` (on every VFS, `memdb` too); once each pool's VFS name
    carried the app's directory, a directory with a quote, `&` or `#` did too. The URI is now a
    bound parameter and the VFS name is URI-escaped (SQLite decodes it before the lookup); file
    names on disk are unchanged. Cases: "a store whose name carries a quote opens"
    (`worker-host.test.ts`) and "a directory whose name is not SQL or URI safe still opens its own
    pool" (OPFS), each failing without its half of the fix.
  - **The log was never in WAL (U46).** A writer ended mid-write left a log the next open refused
    as `SQLITE_CORRUPT`: 2 of 13 full runs on disk, 2 of 4 crash cases in one loaded gate run, and
    about half the mid-fold runs in an off-the-record context, with WAL or the rollback journal
    asked for and `synchronous` NORMAL or FULL. Read back: `main` was `wal`, `syncmesh` was
    `delete`. `PRAGMA journal_mode = WAL` before the `ATTACH` reaches only `main` (`locking_mode`
    is inherited, `journal_mode` is not), so the log ran on the rollback journal, and the pool's
    VFS answers every reserved-lock check with "held": SQLite never took a dead writer's journal
    for a hot one and never rolled it back. The log is now asked for WAL and `synchronous =
    NORMAL` after the attach, and read back (`logDurably`). The case "the log keeps a WAL like the
    derived half" fails without it; in an off-the-record context the four crash cases ran green 8
    runs of 8 with it, 3 of 4 without.
- **expo, as far as a runner reaches.** `adapters/sqlite-expo/src/__tests__/crash.test.ts` runs
  both suites through `expoSqliteDriverOver` (the binding conversion, prepared reads, WAL and
  `synchronous = NORMAL` as `expoSqliteDriver` sets them, the log attached as on a phone) over
  `bun:sqlite` files in a child killed with SIGKILL (`fake-expo.ts`, which the driver suite now
  shares). All pass. No runner here drives `expo-sqlite`'s native module or the SQLite build it
  ships, so the process killed is Bun and the file layer is the host's. With the read's hole check
  disabled the torn case fails as on the Durable Object; dropping the driver's `transaction` did not
  fail the crash cases (a batch is one statement, and the boot repair closes the rest).

Where it departs, or stops:

- **U47, open.** The same `journal_mode` slip leaves the log off WAL on `bun:sqlite`,
  `node:sqlite` and expo (read back on Bun: `delete`, `synchronous` 2). Their VFSes check locks,
  so it is no corruption there, only not what RFC-0004 measures; changing it moves every device's
  write path and the benches, so it is left for its own change.
- A log whose build declines WAL on OPFS keeps the rollback journal, and U46's risk with it.
- `tornTests`' file calls may now answer a promise (the file is behind a worker on OPFS and behind
  a runtime on workerd); the Bun and Node harnesses are unchanged.
- The torn tail case asked `lastSeq` to refuse a tear in the file's last half page, which holds
  only where the file ends in the log's newest events (a device's log file on the rollback
  journal). On OPFS after the WAL fix and on a Durable Object's one file the last page can be
  another table's, so the case now also passes when `lastSeq` and both reads answer the whole log;
  it still fails on a shorter answer, which is what D39 forbids.
- Names: `linesOf` is `streamLines`, `bindingFor` is `databaseBinding` (off the naming allowlist).
