## Context

`reentitle` re-pages a device under a narrower entitlement, and a narrowed grant closes its socket
(D40 §3). Both stop what comes next. Neither touches what the device already holds: gated rows it
was admitted to before stay on its disk, and nothing removes them (`plan/use-cases.md`, *Entity
access is a snapshot*). For Company OS, someone leaving a project keeps that project's rows on
their laptop until they sign out.

## Options

- **A · Purge locally on narrowing.** When a device is re-seated under a narrower scope, it evicts
  the rows, doc logs and cached blobs of every partition the new scope no longer covers. Eviction
  is local: it writes no event, so peers and the log are untouched, and a later widening re-pages
  the rows back (D23's widened-scope re-join). An `onNarrowed({ partitions })` hook runs before
  the eviction so an app can tell the user.
- **B · Keep held rows (today).** The snapshot rule: what you were shown, you keep.
- **C · Purge only on request.** `mesh.purge(partitions)`, called by the app.

## Decision

**A**, decided 2026-11-08 (Jace delegated the call). It is what a person expects when they are
removed from a project, and it is the posture GDPR-bound users need. It is hygiene on an honest
device, not a security boundary: a modified client can keep anything it was ever sent, which only
sealing with key rotation (D40 C) addresses.

**How it holds, as amended before the build** (2026-11-08). Review found five places the first
text did not hold; each is settled here, narrower where the honest answer is narrower.

1. **Two narrowings, both covered.** A partition narrowing is the device's own grant naming fewer
   partitions than the one it held (D40); the device sees it itself and purges those partitions.
   A row narrowing is the authority's gate admitting fewer rows of a `visibility: "authority"`
   table with no partition changing (D24). The device cannot evaluate the authority's `admits`,
   so it learns this from the relay: `reentitle` re-pages it from nothing under the new
   entitlement, and once the last page names that entitlement, every held event of another
   device that writes a gated table, that the join asked for, that the room scanned — it stands
   inside the coverage the page named — and that the room did not send again, is one the gate
   now refuses. Those are purged. A re-entitlement that only widens refuses nothing and purges
   nothing.
2. **The log goes too.** An engine without a state store refolds its log at boot, so dropping
   rows alone would put them back on the next start. Purge deletes the other devices' events it
   matched from the log (`EventStore.evict`, which records no compaction floor) and from the
   quarantine, then drops the rows they wrote and rebuilds each from the events still held for it.
3. **Widening restores by re-paging.** An evicted event is one the device does not hold, so when
   it is sent again it is stored and folded as new. After a partition purge the device's cursors
   are re-scoped to the narrower entitlement, so a later wider grant re-pages it from nothing
   (D23, D40) instead of standing on cursors that claim it holds
   what was purged (tested on the relay path; a peer link reads the same scope through
   `transport/src/repage.ts`). A row narrowing already re-pages on every re-entitlement. When the source has
   compacted those events away, the re-page cannot bring them back as events: that is D40's known
   limit for scoped acks, unchanged here.
4. **This device's own writes are never purged.** Pending or delivered, they are kept in the log
   and folded into the rebuilt row. One written before the narrowing may still be valid where it
   is going (the authority accepts what was granted when it was written, D24 A), and a peer may
   already have folded it; dropping it would lose legitimate work and could leave peers
   disagreeing. The device keeps only its own words of a scope it lost, which it already knew.
5. **So nothing is discarded, and there is no discard to report.** D32's report stays the report
   for a write a peer refuses. The app hears the narrowing itself through `onNarrowed`.

`createMesh({ onNarrowed })` runs before anything is removed, is awaited, and is told
`{ partitions, tables }`: the partitions the own grant lost, or the gated tables the re-page
withheld rows of. A hook that throws is warned about and the purge goes ahead.

## Watch out

- A device that narrows while offline purges when it next learns of the narrowing. The narrower
  grant is persisted only once its purge is done, so a device stopped in between restarts on the
  wider grant and learns of the narrowing again from the next session that carries it.
- An event of a lost partition can still arrive after the purge: it was in flight before the far
  side heard of the narrower grant. The device remembers the partitions it purged, for the life of
  the process or until they are granted again, and purges such an event on arrival without telling
  the app a second time.
- Content that reached a row only through compaction of this device's own log, with no event
  left, is not rebuilt; the rebuilt row is the fold of what the log still holds.
- A row narrowing is found only on a relay that gates by `admission` (D24). Peers never carry
  gated rows, so no peer-only path needs it.
- A narrowed device stops carrying the purged partition's events for others, sealed or not.

## Built (2026-11-08)

On `feat/gated-blobs-and-purge`:

- `engine/src/purge.ts`: `engine.purge({ events, rows? })` — evicts the matched events of other
  devices from the log and the quarantine, drops and rebuilds the rows they or `rows` name, drops
  and re-records those rows' doc logs, commits through `atomic` when the engine has it, writes no
  event, lowers no cursor, and emits one fold with source `purge`. New store methods:
  `EventStore.evict`, `StateStore.remove`, `DocStore.forget` (memory, SQLite, Postgres,
  `localStorage`); `Projection.remove` and `RowSync.remove` take the rows out of the app's tables.
- `client/src/narrowing.ts`: watches this device's own grant; on a narrowing tells `onNarrowed`,
  purges the lost partitions, drops cached blobs only the purged rows named (blobs this device
  made are kept), and re-scopes the cursors. The same queue serves the relay's row-level purge,
  through `TransportContext.purge`. `client/src/grants.ts`: grants persist in one queue, each
  after the purges started before it.
- `relay/src/refused.ts` and `scoped.ts`: the row-level half — a re-page from nothing notes what
  it delivered, and a last page naming an entitlement purges what it did not.
- Tests: `engine/src/__tests__/purge.test.ts` (log, rows, state store, a restart refolding the
  log, no event, no cursor moved, re-delivery restoring), `relay/src/__tests__/authority-visibility.test.ts`
  (a gated row purged on narrowing and back on widening; a widening purges nothing),
  `client/src/__tests__/narrowing.test.ts` (end to end: hook first, rows, log and cached blob gone,
  own write kept, widening restores), `client/src/__tests__/narrowing-late.test.ts` (a late event
  of a lost partition), `client/src/__tests__/grants-narrowing.test.ts`, and the driver suite
  (`evict`, `remove`, doc `forget`, on SQLite and Postgres). `client/src/__tests__/read-permissions.test.ts` now expects the
  revoked partition purged rather than kept.

Fix round 1 (review of #23):

- A purge and a write no longer interleave. `engine/src/gate.ts` gives writes a shared turn on
  the stores and a purge an exclusive one: the purge waits for the writes already running, and
  writes started after it wait for it. The purge reads the log inside that turn and sets the
  in-memory state from the state as it stands at the end. Before this, a write made while a purge was in
  flight vanished from memory while the log and state store kept it. The quarantine is emptied
  of matched events only after the commit succeeds.
- `mesh.blobs.put` stores the bytes with `put`, so the store records them as `mine`; it used
  `putAt`, which records `cached`, and a narrowing deleted bytes this device had uploaded.
  `memoryBlobStore` now records origin the same way `sqlBlobStore` does; before, it answered
  `mine` for everything, so the default cache never dropped a purged row's blob.
- The late-arrival guard also watches `snapshot` and `repair` folds, not only `remote` ones.
- Tests: three concurrency cases in `purge.test.ts`, `gate.test.ts`, the made-here-kept and
  default-cache cases in `narrowing.test.ts`, a snapshot case in `narrowing-late.test.ts`, and
  the memory store's origin in `storage/src/__tests__/blob.test.ts`.

Fix round 2 (review of #23):

- A snapshot install or a repair merges into memory at once, with no turn, but its write to the
  state store now takes a shared turn (`turn` in `engine/src/gate.ts`, no transaction). Before,
  that write ran outside the gate: one landing between the purge's `remove` and its `commit` put
  a purged row back on disk while memory had dropped it, and it came back on the next start.
  Now a snapshot's write that started first finishes before the purge begins; one that starts
  after waits, and writes the rows as the purge left them. A snapshot or repair that lands while
  a purge runs is kept for every row but the purged ones; for those, what only the snapshot
  carried is dropped, as for content that reached a row only through compaction, and the
  late-arrival guard purges whatever the next fold of a lost partition brings. The same holds
  for a row the purge rebuilds and keeps readable — one that also holds this device's own
  events or events outside the lost scope, or one that moved partition: what only the snapshot
  carried for it is dropped, while the snapshot's coverage is still adopted, so the device does
  not ask for those events again.
- The blob pass keeps a cached blob that any row still held names, not only a rebuilt one. Before,
  a row in a partition the device keeps lost its cached copy when a purged row named the same
  hash, and in a gated room it could not fetch it again if the bytes' homes were only the lost
  partition. This is looser than D44: a gated relay would not serve those bytes to this device
  again if their homes are only the lost partition. The device keeps them because the authority
  named the hash in a row it may still read.
- `memoryBlobStore.irreplaceable()` now lists only what `put` stored (`mine`), as
  `sqlBlobStore` does; before round 1 it listed every hash it held. Only `relay/src/blob-cap.ts`
  passes it through, and nothing reads it there.
- Tests: a snapshot and a repair case in `purge.test.ts` (each stalls the purge between `remove`
  and `commit`), and a shared-blob case in `narrowing.test.ts`.

Fix round 3 (review of #23):

- Round 2 made a snapshot that lands during a purge adopt its coverage after the purge, and so
  after `rescope()`. Its scope replaced the cut one: `undefined` for an unscoped snapshot, or,
  for an unvouched join, the coverage read before the purge. Either is as wide as before the
  narrowing, so a later widening did not re-page and the purged rows never came back. Now, while
  a partition is lost, every snapshot fold queues `rescope()` again with the grant held when it
  landed (`client/src/narrowing.ts`). Test: `narrowing-late.test.ts` holds the purge's commit and
  the snapshot's write, and checks the scope after both.
- Not covered: a snapshot with no rows sends no fold, so an empty unscoped snapshot adopted after
  the rescope still widens the scope.
- The row-level (D24) purge in `relay/src/refused.ts` has no late-arrival guard. A snapshot or
  repair that brings a newly refused row during or after that purge keeps it, until the next
  re-page from nothing refuses it again.
- `refused.ts` treats every held gated event in the scanned coverage that the re-page did not
  deliver again as refused. That includes events the relay could not build bytes for
  (`unsendable` in `catchup.ts`) and events whose verify failed on this device; both are purged
  as refused.

Merged with main (#20, #21, #22):
- #21 (D39) made the log's reads refuse a hole in an author's run that the new gap table does not
  account for. A purge's evict left such holes, so after a narrowing the device read its own log
  as torn. `evict` (`storage/src/evict.ts`) now records each hole it leaves below the author's
  remaining head as a gap, under the same Postgres lock an append takes; a later delivery of the
  event fills it. Tested by the driver case "evicting from the middle of a run leaves a log that
  still reads" (`storage/src/driver-tests/events.ts`), which fails without the gap rows.
- #22's derived columns are written outside the record; a purge's `remove` deletes the row, its
  derived columns with it, and a `derive` that lands after a purge finds no row and is skipped.

Where it departs from the first text: own writes are kept (not dropped and reported), so no new
report exists; `onNarrowed` receives `{ partitions, tables }` rather than `{ partitions }`, because
a row narrowing changes no partition; and widening restores only what a source still holds as
events.

## Follow-ups built (2026-11-08, on `fix/access-followups`, #30)

The three gaps fix round 3 listed, each closed; decided 2026-11-08 (Jace delegated the call).

- **An empty snapshot no longer widens the scope.** The engine now says every coverage taken on
  from outside the fold — `adoptCoverage`, and a snapshot install with rows or none — on a new
  `engine.onAdopt` (`engine/src/coverage-path.ts`). The narrowing watch cuts the scope back on any
  adoption that reads wider than the grant while a partition is lost, instead of on snapshot
  folds, which an empty snapshot never sends (`client/src/narrowing.ts`). An empty snapshot is
  still not a fold. Test: `narrowing-late.test.ts`, "an empty unscoped snapshot adopted after the
  rescope does not widen it back", which fails with the cut disabled.
- **The row-level purge has a late-arrival guard.** `relay/src/refused.ts` is now one memory per
  relay link (`refusalsOver`), outliving its sessions: what the last re-page from nothing refused
  is kept, with the stamps its events wrote, and a remote, snapshot or repair fold that writes a
  row carrying one of those stamps purges it again on arrival, without telling the app a second
  time (`TransportContext.purge` with an empty `Narrowed` purges quietly). An event a later
  re-page delivers again leaves the memory, and each re-page from nothing replaces it. Test:
  `authority-visibility.test.ts`, "a refused row that arrives again after the purge is purged on
  arrival" (as state and as the event), which fails with the guard disabled.
- **Unsendable and unverifiable events are kept, not purged as refused.** The room's scanned
  coverage (`relay/src/catchup.ts`) now stops below an admitted event it holds and can never send
  (no envelope), as its advertised cursors already did, so a re-paged device never judges it, or
  anything above it in that author's run, as withheld; the room's `relay.catchup` telemetry already
  counts it as `unsendable`. An event the re-page sent whose signature fails on the device is
  noted by the id its envelope claims, kept, and said on the link report ("failed to verify here;
  they are kept"). A forged claim can only make the device keep an event, never purge one. Tests:
  "an event the room holds and cannot send is not taken as refused" and "an event the re-page sent
  that fails to verify here is kept and said", each failing with its fix disabled; and "a re-page
  over a room whose copy of an event does not verify keeps the event", end to end over a room,
  which fails with the session's `unverified` note removed (added in review of #30).

Where it departs: an unsendable event stops the room's scan for its whole author run above it, so
a refused event of that author above the hole is kept until the hole is gone — the safe direction.

Two limits of the row-level guard, recorded in review of #30:

- Its memory lives as long as the relay transport runs, not the process: `RelayLink.stop()` drops
  it, so a transport stopped and started again forgets what the last re-page refused until the
  next re-page from nothing. The partition memory above is the process-long one.
- A late purge takes the refused set as it stood when the purge was queued. A widening re-page
  that delivers one of those events again before the queued purge runs still sees it evicted;
  the next re-page from nothing brings it back. The window is one queued purge long.
