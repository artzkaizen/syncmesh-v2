## Context

Everything downstream inherits this. The exploration was TypeScript on Bun, one package, `bun test`, no build step, no `exports` map. The two native radios will be Swift/Kotlin regardless; the wire is language-neutral by design (frozen vectors), so a Rust core is possible later without a rewrite.

## Options

- **A · TypeScript on Bun, one package** — fastest to iterate; `bun:sqlite` built in; matches all reference code and tests. Node consumers need care (`bun:sqlite` must be lazy).
- **B · TypeScript, runtime-neutral from day one** — Node + Bun + browser + Expo all first-class; every runtime binding behind a port. More discipline, slower start.
- **C · Rust core + TS bindings** — the wire and kernel in Rust, TS for client/react. Highest ceiling, highest cost, and you would be building two things.

## What the research points to

A to start, with B's discipline where it is free: every runtime-specific import (`bun:sqlite`, `node:fs`, sqlite-wasm) behind a small port from the first commit, so B is a refactor rather than a rewrite. C is a later port that the frozen vectors make possible; do not start there.
## Watch out

The exploration shipped `bun:sqlite` at top level and it made the package unloadable on Node. reflectdb's `verify-node-consumer.ts` (installs the packed tarball into a throwaway Node project) is the test that catches this class.

## Decision

**B — TypeScript, runtime-neutral from day one, as a Bun-workspaces monorepo run by Turborepo.**

- **Language.** TypeScript everywhere in phases 0–4. Strict `tsconfig` (`exactOptionalPropertyTypes`, `noUncheckedIndexedAccess`) shared from `tooling/tsconfig`. No Rust core to start; the frozen wire vectors keep that port open (D03, E03).
- **Runtime neutrality.** Nothing under `packages/` imports `bun:sqlite`, `node:*`, sqlite-wasm, or any DOM/RN API directly. Each runtime binding is its own adapter package behind a port (`SqliteDriver`, `Transport`, `StateStore`, …) so Node, Bun, browser, Expo, and Durable Objects are all first-class consumers. `verify-node-consumer` (packed tarball installed into a throwaway Node project) runs in CI from E00.
- **Workspace and task runner.** Bun workspaces (`workspaces` in the root `package.json`) with Turborepo on top for the task graph and caching (`build`, `typecheck`, `test`, `lint`, `bench`). `bun test` is the runner inside every TypeScript package. Turbo's only job is ordering and caching; it does not replace the language toolchain.
- **Non-TypeScript packages.** The BLE and Wi-Fi Aware native modules (E22, E23) and any later Rust port live in the same workspace as packages whose `package.json` scripts wrap `xcodebuild` / `gradle` / `cargo`, per Turborepo's multi-language guide. They are excluded from the root `test` filter until their epics begin, so no package ships a no-op test that lies.
- **Publishing.** Every package has a real `exports` map and a build step (`tsc` emit to `dist/`); no bare `src/` exports leaking across packages.

Why B over the research's recommendation of A: the research's own caveat is that A only stays cheap if every runtime import is already behind a port — at which point the delta to B is the workspace layout, and a layout is far cheaper to commit to in E00 than to migrate to in E09 when the client, React, Expo, and Durable Object consumers all exist.
