## Context

Everything downstream inherits this. The exploration was TypeScript on Bun, one package, `bun test`, no build step, no `exports` map. The two native radios will be Swift/Kotlin regardless; the wire is language-neutral by design (frozen vectors), so a Rust core is possible later without a rewrite.

## Options

- **A · TypeScript on Bun, one package** — fastest to iterate; `bun:sqlite` built in; matches all reference code and tests. Node consumers need care (`bun:sqlite` must be lazy).
- **B · TypeScript, runtime-neutral from day one** — Node + Bun + browser + Expo all first-class; every runtime binding behind a port. More discipline, slower start.
- **C · Rust core + TS bindings** — the wire and kernel in Rust, TS for client/react. Highest ceiling, highest cost, and you would be building two things.

## What the research points to

A to start, with B's discipline where it is free: every runtime-specific import (`bun:sqlite`, `node:fs`, sqlite-wasm) behind a small port from the first commit, so B is a refactor rather than a rewrite. C is a later port that the frozen vectors make possible; do not start there.
## Watch out

The exploration shipped `bun:sqlite` at top level and it made the package unloadable on Node. reflectdb's `verify-node-consumer.ts` (installs the packed tarball into a throwaway Node project) is the test that catches this class.
