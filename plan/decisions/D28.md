## Context

D27 removed the per-write copy count and left one reading in its place: `unsettled()` — the writes this device holds that nobody has acknowledged. `detach.ts:39` already gates on it, and RFC-0022's eviction sweep is going to.

Tracing it for D27 turned up that the reading is built on **a peer's word about itself**. Receipt rows are written in `client/src/operations.ts` out of `engine.acks()`, which is the map fed by arriving *cursor frames*. `transport/src/custody.ts` says in its own header why that is not the same thing:

> "A cursor says 'I have your events' and proves none of it, so a device counting copies off cursors is counting claims. A receipt is that claim signed, and it names the holder's storage lineage — which is what lets an author tell 'still holding' from 'holding again, having lost what it had'."

And the signed path it describes was **wired to nothing**. Two ends, both dangling: `incarnation` was supplied by no caller, so `vouch()` returned early at `custody.ts:48` and this device signed nothing; `onReceipt` was passed by no caller, so an arriving receipt was decoded, verified and dropped. No device in this codebase had ever sent or stored one. The codec, the frame kind, the signer and the verifier were all built, tested, and inert.

That matters in the direction that costs something. A gate that refuses is safe when it is wrong; this one **permits**. A false or stale claim empties `unsettled()`, and an empty `unsettled()` is what will let a sweep delete the only copy of somebody's work.

## Options

- **A · Cursor acks are enough.** Today's behaviour, now that it is written down. Cheapest, and it licenses a wipe on a peer's word — including the word of a relay that has since been redeployed over an empty volume.
- **B · Signed custody only.** Every receipt row comes from a verified signature; the cursor tier goes. Rejected: a peer that cannot sign — an older build, a bare event store, a device whose lineage would not read — never receipts at all, so `unsettled()` never empties against it and every device looks like the sole holder of everything forever. A gate that never opens is a gate nobody keeps.
- **C · Two tiers.** A cursor ack makes a write *delivered*; a signed receipt with a live incarnation makes it *held*, and **only held licenses anything destructive.** Degrades correctly: a peer that cannot sign still syncs, still acknowledges, and simply never licenses a deletion.

## Decision

**C.** Two readings, two tables, and the words for them in the places that report them.

```ts
ledger.unsettled()    // nobody has TOLD us they hold this      — report it
ledger.soleCustody()  // nobody has SIGNED for holding this     — gate on this
```

1. **Two tables rather than a column, because they are two facts with two provenances.** `receipts` keeps exactly the meaning it had — a holder's cursor covered this. `vouches` is new: `(peer, seq, holder, incarnation, at_ms)`. Storing them in one table would have made the stronger fact a nullable column on the weaker one, and every reader would have had to remember which. It also means no migration: a new table is `CREATE TABLE IF NOT EXISTS` in the ledger's own DDL, and the operations tables were never on the schema ladder.

2. **The incarnation is what a claim cannot carry, and `vouch` acts on it before it records anything.** Every insert runs `deleteStaleVouches (holder, incarnation)` first, so learning that a peer came back under a new lineage is what takes away the custody it claimed with the store it lost. Without that step a wiped relay counts as a holder of writes it threw away — which is the failure this whole tier exists to prevent, arriving by a different door.

3. **A device's lineage lives beside its device key, in `_device`, for the reason that table exists.** `identity.ts` already argues it: *"A key in the file is gone when the file is, which is the only version of this fact that stays true."* The lineage is the same fact about the same database, so it is the same table and the same helper (`remembered`), minted on first boot and never derived from the contents — a store rebuilt from an identical backup is a different incarnation, and should be.

4. **It earns its keep on the peers whose key outlives their storage.** A device mints a new key with a new database, so a rebuilt device is a new peer and the incarnation tells you nothing you did not know. A **relay or an authority** is configured with a keypair and redeployed over an empty volume under the same name — and those are exactly the peers an app leans on for durability. This tier is for them.

5. **A lineage that will not read is not fatal; a key that will not read is.** Without a key there is no name to sign events under and nothing to open. Without a lineage the device reads, writes, syncs and acknowledges — it just cannot sign for what it holds, so no peer counts it as a custodian. `boot.ts` warns and carries on. Refusing to open over it would trade every working thing for one that only other devices consult.

6. **The stronger reading is served across the browser port**, because that is where the destructive button is. A tab offering "clear this device" that cannot ask what only this device holds is a tab asking the person to decide blind. `LedgerPath` gains `soleCustody` and `vouchesOf`.

7. **The receipt wire is frozen now** (README rule 3): `conformance/receipt-vectors.json`, three vectors including two lineages of one holder. It was not frozen before because nothing sent one — a wire nobody speaks is not a wire anybody can diverge from. It is one now.

## What this costs, accepted

- **Two readings where there was one**, and a reader has to know which is which. Mitigated by making the names say it — `unsettled` is a report, `soleCustody` is a gate — and by the doc comments on both saying what the other one is for.
- **A second table on every ledger**, including the ones that will never hold a vouch because nothing on that link signs.
- **`soleCustody()` is a `LEFT JOIN` with no `LIMIT`**, same as `unsettled` (`devtools/src/source/writes.ts:12` already says so). Fine as a guard on a destructive action, wrong as a subscription re-read on every fold.

## Watch out

- **The relay cannot vouch, and the relay is the common deployment.** Signed custody runs over `bridgeFramedLink`, whose control frames carry the `receipt` kind. The relay speaks its own frame union — `hello`, `page`, and `session` of `presence | grant | cursors | grant-request | event` — and has no receipt in it. So two devices linked directly sign for each other, and **everything through a relay is still claims only**. Closing it means a frame kind on the relay protocol, which is a version bump under D14 and new frozen vectors under rule 3. Until then: `soleCustody()` is honest but pessimistic in relay-only deployments — it will list writes a relay really does hold, which is the safe direction and a bad user experience.
- **A vouch is delivery, not approval.** Unchanged from every other custody statement in this codebase: a peer holding an event has not accepted it, and a peer that quarantines one never lifts its cursor past it (D27's watch-out) — so a refused write stays in both readings for good. Copy that says "not yet saved anywhere else" is honest; copy that says "syncing…" is a spinner that cannot stop.
- **Nothing gates on `soleCustody()` yet.** `detach.ts` still reads `unsettled()`, which is the weaker tier — deliberately, for now, because switching it while the relay cannot sign would make detaching impossible for every relay-only deployment. Flip it with the relay frame, not before, and make that the same change.
- **Do not let the two tiers drift into a third.** If a reading appears that is neither "somebody said" nor "somebody signed" — a timer, a heuristic, a count — it is the copy count coming back with a new name (D27).
