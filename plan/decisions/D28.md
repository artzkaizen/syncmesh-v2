## Context

D27 removed the per-write copy count and left one reading in its place: `unsettled()` — the writes this device holds that nobody has acknowledged. `detach.ts:39` already gates on it, and RFC-0022's eviction sweep is going to.

Tracing it for D27 turned up that the reading is built on **a peer's word about itself**. Receipt rows are written in `client/src/operations.ts` out of `engine.acks()`, which is the map fed by arriving *cursor frames*. `transport/src/custody.ts` says in its own header why that is not the same thing:

> "A cursor says 'I have your events' and proves none of it, so a device counting copies off cursors is counting claims. A receipt is that claim signed, and it names the holder's storage lineage — which is what lets an author tell 'still holding' from 'holding again, having lost what it had'."

And the signed path it describes was **wired to nothing**. Two ends, both dangling: `incarnation` was supplied by no caller, so `vouch()` returned early at `custody.ts:48` and this device signed nothing; `onReceipt` was passed by no caller, so an arriving receipt was decoded, verified and dropped. No device in this codebase had ever sent or stored one. The codec, the frame kind, the signer and the verifier were all built, tested, and inert.

That matters in the direction that costs something. A gate that refuses is safe when it is wrong; this one **permits**. A false or stale claim empties `unsettled()`, and an empty `unsettled()` is what will let a sweep delete the only copy of somebody's work.

## Options

- **A · Cursor acks are enough.** Today's behaviour, now that it is written down. Cheapest, and it licenses a wipe on a peer's word — including the word of a relay that has since been redeployed over an empty volume.
- **B · Signed custody only.** Every receipt row comes from a verified signature; the cursor tier goes. Rejected: a peer that cannot sign — an older build, a bare event store, a device whose lineage would not read — never receipts at all, so `unsettled()` never empties against it and every device looks like the sole holder of everything forever. A gate that never opens is a gate nobody keeps.
- **C · Two tiers.** A cursor ack makes a write *delivered*; a signed receipt with a live incarnation makes it *held*, and **only held licenses anything destructive.** Degrades correctly: a peer that cannot sign still syncs, still acknowledges, and simply never licenses a deletion.

## Decision

**C.** Two readings, two tables, and the words for them in the places that report them.

```ts
ledger.unsettled()    // nobody has TOLD us they hold this      — report it
ledger.soleCustody()  // nobody has SIGNED for holding this     — gate on this
```

1. **Two tables rather than a column, because they are two facts with two provenances.** `receipts` keeps exactly the meaning it had — a holder's cursor covered this. `vouches` is new: `(peer, seq, holder, incarnation, at_ms)`. Storing them in one table would have made the stronger fact a nullable column on the weaker one, and every reader would have had to remember which. It also means no migration: a new table is `CREATE TABLE IF NOT EXISTS` in the ledger's own DDL, and the operations tables were never on the schema ladder.

2. **The incarnation is what a claim cannot carry, and `vouch` acts on it before it records anything.** Every insert runs `deleteStaleVouches (holder, incarnation)` first, so learning that a peer came back under a new lineage is what takes away the custody it claimed with the store it lost. Without that step a wiped relay counts as a holder of writes it threw away — which is the failure this whole tier exists to prevent, arriving by a different door.

3. **A device's lineage lives beside its device key, in `_device`, for the reason that table exists.** `identity.ts` already argues it: *"A key in the file is gone when the file is, which is the only version of this fact that stays true."* The lineage is the same fact about the same database, so it is the same table and the same helper (`remembered`), minted on first boot and never derived from the contents — a store rebuilt from an identical backup is a different incarnation, and should be.

4. **It earns its keep on the peers whose key outlives their storage.** A device mints a new key with a new database, so a rebuilt device is a new peer and the incarnation tells you nothing you did not know. A **relay or an authority** is configured with a keypair and redeployed over an empty volume under the same name — and those are exactly the peers an app leans on for durability. This tier is for them.

5. **A lineage that will not read is not fatal; a key that will not read is.** Without a key there is no name to sign events under and nothing to open. Without a lineage the device reads, writes, syncs and acknowledges — it just cannot sign for what it holds, so no peer counts it as a custodian. `boot.ts` warns and carries on. Refusing to open over it would trade every working thing for one that only other devices consult.

6. **The stronger reading is served across the browser port**, because that is where the destructive button is. A tab offering "clear this device" that cannot ask what only this device holds is a tab asking the person to decide blind. `LedgerPath` gains `soleCustody` and `vouchesOf`.

7. **The receipt wire is frozen now** (README rule 3): `conformance/receipt-vectors.json`, three vectors including two lineages of one holder. It was not frozen before because nothing sent one — a wire nobody speaks is not a wire anybody can diverge from. It is one now.

## What this costs, accepted

- **Two readings where there was one**, and a reader has to know which is which. Mitigated by making the names say it — `unsettled` is a report, `soleCustody` is a gate — and by the doc comments on both saying what the other one is for.
- **A second table on every ledger**, including the ones that will never hold a vouch because nothing on that link signs.
- **`soleCustody()` is a `LEFT JOIN` with no `LIMIT`**, same as `unsettled` (`devtools/src/source/writes.ts:12` already says so). Fine as a guard on a destructive action, wrong as a subscription re-read on every fold.

## Watch out

- **Update 2026-11-09 (U38):** the relay room signs its own custody and `detach.ts` gates on `soleCustody()`; see "Built: the relay room as a holder (U38)" below. The watch-outs that follow are as they stood before it.
- **Update 2026-11-08 (U17, PR #36):** devices in a relay room now sign for each other through it — a receipt passes the room as a session frame and is handed to its author alone (`relay/src/custody-route.ts`) — so a relay-only deployment's `soleCustody()` counts the other devices that signed. In a grant-gated room a holder's cursor is scoped, and it signs the run it was actually sent (`Coverage.held`, D32), so a write behind one the holder was not entitled to stays unvouched by that holder. A holder's latest receipt is now its whole claim for that author: a vouch withdraws the same holder's earlier vouches above its `throughSeq` (`deleteWithdrawnVouches`), so a holder whose run went down — a D45 purge, a D39 torn log — stops counting for what it no longer has without a new incarnation. The relay room itself still signs nothing (U38), and `detach.ts` still reads `unsettled()`. What follows is the watch-out as written.
- **The relay cannot vouch, and the relay is the common deployment.** Signed custody runs over `bridgeFramedLink`, whose control frames carry the `receipt` kind. The relay speaks its own frame union — `hello`, `page`, and `session` of `presence | grant | cursors | grant-request | event` — and has no receipt in it. So two devices linked directly sign for each other, and **everything through a relay is still claims only**. Closing it means a frame kind on the relay protocol, which is a version bump under D14 and new frozen vectors under rule 3. Until then: `soleCustody()` is honest but pessimistic in relay-only deployments — it will list writes a relay really does hold, which is the safe direction and a bad user experience.
- **A vouch is delivery, not approval.** Unchanged from every other custody statement in this codebase: a peer holding an event has not accepted it, and a peer that quarantines one never lifts its cursor past it (D27's watch-out) — so a refused write stays in both readings for good. Copy that says "not yet saved anywhere else" is honest; copy that says "syncing…" is a spinner that cannot stop.
- **Nothing gates on `soleCustody()` yet.** `detach.ts` still reads `unsettled()`, which is the weaker tier — deliberately, for now, because switching it while the relay cannot sign would make detaching impossible for every relay-only deployment. Flip it with the relay frame, not before, and make that the same change.
- **Do not let the two tiers drift into a third.** If a reading appears that is neither "somebody said" nor "somebody signed" — a timer, a heuristic, a count — it is the copy count coming back with a new name (D27).

## Built: the relay room as a holder (U38)

Built 2026-11-09 on `feat/relay-room-custody` (PR #44). Decided 2026-11-09 (Jace delegated the call).

- **The room signs.** A room given `custody` (`RelayRoomOptions.custody`, and through
  `RelayHostOptions` / `startRelay`) issues a `CustodyReceipt` under its own key with its epoch as
  the incarnation: the room's held run for the author (every event of its from the first through N
  is in the log — the contiguous cursor every `hello` advertises, except for an author whose events
  compaction removed before this open, which is never signed for), sent to that author's socket
  alone as a session frame (tag 7), which the device already keeps (`relay/src/room-receipts.ts`). One when the author sits
  down, and one per author per `every` (default one second) while it writes, so a burst of writes
  is one signature over the run, not one per event: the batching this gap asked for. Nothing is
  sent when the run has not moved since the last receipt to that seating. A room that loses its
  log and opens a new one opens a new epoch, so the author's ledger drops what the room signed out
  of the old one the moment it hears from the new one (§2): the room's `hello` names its epoch, and
  over a sealed link (D36) it is proven to come from the room's key, so the device retires that
  key's vouches from every other incarnation at the hello (`OperationStore.retireLineages`,
  `TransportContext.onLineage`), before anything is re-pushed or re-signed — and whether or not the
  new room signs at all, or holds anything of the author's (`client/relay-custody.test.ts`, "a
  relay room that lost its log"). Fix round 2 of #44: before it, the drop waited for the new
  lineage's first receipt, which never comes for an author whose writes the new room refuses.
- **Only when the receipt stays true.** `custody` throws at open on a room whose key is not given
  (one minted per process would be a new holder after a lost log, and the old key's vouches are
  never withdrawn, because `deleteStaleVouches` is per holder), whose log is not `durable`, or
  that trims its log (`retention.keepEventsFor`: a receipt says "everything through N"). A host
  throws the same way without a configured `identity`, and passes `custody` only to a durable room
  whose store does not bring its own key — a Durable Object's key kept beside its log is lost with
  it. Absent `custody`, a room signs nothing, as before: opt-in, because the key has to be one the
  operator keeps.
- **`detach.ts` gates on `soleCustody()`.** Flipped in the same change, as the watch-out asked:
  a write a peer only acknowledged refuses the detach until a holder signs for it
  (`storage/detach.test.ts`). `DetachRefused.unsent` keeps its name; it now lists what no peer has
  signed for.
- **A holder's latest receipt is its whole claim** — the rule built in #36 (vouch withdrawal
  above `throughSeq`, and the skip of a receipt older than one the ledger holds) is kept, decided
  2026-11-09 (Jace delegated the call). The relay room's run only rises (it neither purges nor
  trims while it signs), so the rule withdraws nothing of the room's in practice.
- **The newer-vouch check, the withdrawal and the insert are one transaction** (with the
  incarnation delete and the refusal retirement beside them), where the driver offers one: a
  failure part way leaves the holder's earlier claim whole (`storage/operation-store.test.ts`).

Where it departs:

- **No frame and no version bump for the receipt.** The watch-out expected the relay to need a
  frame kind "under D14's version bump"; the receipt passes as the session frame it already was.
  The one wire addition in this change is the relay's `seated` tag 23 (D32's bound), additive.
- **Opt-in, not on by default.** A relay that would sign by default would sign under a key minted
  per process, which is exactly the over-claim §2 exists to prevent.
- **A room that trims signs nothing**, even for authors it has never trimmed: retention is per
  room, and a receipt the room cannot keep true is one it does not sign.
- **A log trimmed before this open is not refused.** A room opened with `custody` over a log a
  past run (or the caller's store) already compacted advertises its floors, so nobody is sent what
  was trimmed again, but an author with a floor is never signed for, and every other author is
  (`room-receipts.test.ts`, "a log trimmed before this open"). Fix round 1 of #44 did this by
  seeding the held run empty under the floors; fix round 2 skips the floored authors at signing
  instead, because a held run that can never close kept every later event of those authors in
  memory for the room's life, in every room over a compacted log, signing or not
  (`room.test.ts`, "a log compacted before this open"). One edge stays: receipts an earlier run
  signed under the same epoch, before custody was turned off and the log trimmed, are not
  withdrawn — same holder, same incarnation. Turning `custody` off and trimming is the operator's
  call to make knowing that.
- **A room that comes back without `custody`** still retires its old lineage at the hello, but
  only over a sealed link: a challenging room (D33) proves no key in its hello, so there the old
  vouches stop counting at the new lineage's first receipt, as before.
- **The holder is the key, the lineage is the room.** Every room on one host signs under the
  host's `identity` (D36), each with its own epoch, and so does each fleet instance with its own
  file; `deleteStaleVouches` and `retireLineages` work per holder. A device whose transports reach
  two rooms of one host, or that moves between fleet instances, has each room's receipt or hello
  retire the other's vouches. That errs toward keeping data (a spurious `DetachRefused`), never
  toward deleting it; keying the holder per room would need the room's name in the receipt, a
  wire change, and is not built.
- **The Rust embedded room signs no custody.** `crates/syncmesh-client/src/room.rs` sends `seated`
  (tag 23) but has no `custody` of its own; a deployment whose relay is the embedded room is where
  the TS relay was before U38.
- **Detach needs a signature now, and custody is opt-in.** In a deployment whose only other
  holder is a relay that was not given `custody`, `detachScope()` and the client's sweep under
  disk pressure refuse until a device signs for the writes; before this change the relay's cursor
  ack was enough. That is the safe direction, and the fix is to configure the room's `custody`.
- **A host room that cannot sign says so.** A host given `custody` whose room store brings its own
  key, or is not durable, opens that room unsigned and `console.warn`s it the first time that room
  opens (once per name per host, not again after an idle eviction), so an operator does not
  believe it signs.
- **`sweepFor` is now `createMeshSweep`** in `@syncmesh/client`'s exports (the naming rule for a
  touched file); a breaking rename with no alias.
- **The relay's ack still answers `synced()`** (D42) and is not a receipt; a durable room's ack
  and its receipt can arrive up to `every` apart.
