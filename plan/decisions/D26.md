## Context

D20 decided that SQL is the data API and that "the mesh never appears at a call site". The first half of that has held everywhere it was aimed: a procedure handler reads and writes the app's own tables with the app's own ORM, capture turns the transaction into one signed event, and there is no second write path and no second permission model. That is not in question here.

The second half turned out to be aimed at the wrong call site. Writing the first React Native example against the shipped surface produces this in a component:

```ts
const handle = mesh.on("org:acme").unwrap()
const { rows, ready } = useLiveQuery(handle, handle.db.select().from(notes).orderBy(notes.id))
```

Three things are wrong with it and none of them is fixed by a better ORM. The handle has to be threaded to every component that reads anything, so `@syncmesh/react` is four hooks that each take their source as the first argument and there is no provider anywhere in the package — no `createContext`, no `useContext`. Query construction lands in the view layer, so the shape of a read is decided in the place least able to test it. And the operation has no name: `db.select().from(notes).orderBy(notes.id)` can be read but not referred to, listed, or shared with the server that also needs to know what "the notes list" is.

The deciding fact is what an app developer names. A procedure is a name — `books.list` — and a name can be typed at both ends, enumerated, given errors, and *dispatched*: served over HTTP where it needs the authority, or run in-process where it does not. A query builder at a call site is a construction; it can only be read, and only where it was written. Every app that has consumed a sync engine ends up building the named layer anyway. The question is whether syncmesh ships it or watches each app rebuild it worse.

Two further facts constrain the answer. oRPC's `call(procedure, input, { context })` executes a procedure **in-process, with no HTTP and no router** — `packages/orpc/src/__tests__/index.test.ts` already drives every case that way. And Zero, having shipped the closest thing to this, [recommends "fire and forget" for mutations](https://zero.rocicorp.dev/docs/writing-data) and offers no mutation hook at all, splitting the two facts a caller might want into separate `.client` and `.server` promises rather than one status object.

## Options

- **A · Keep D20's surface as written.** The app writes Drizzle at call sites; procedures exist only for logic that needs the authority. Rejected: it is the code above, and it makes `@syncmesh/react`'s missing provider a permanent tax rather than a gap.
- **B · One named surface.** Every read and every write an app performs is a procedure. `api.books.list(...)` and `api.books.create(...)` are the whole API. Drizzle appears only inside handlers, where D20's argument for it is untouched.
- **C · Both, documented** — Drizzle for local reads, procedures for server logic. Rejected, and for D20's own reason: it is D20's option C wearing a different hat. Two surfaces, and the developer must know at every call site which one to reach for.

## Decision

**B — the only surface an app touches is `api.*`. No handle, no `db`, no Drizzle at a call site. Drizzle lives inside procedure handlers and nowhere else.**

```ts
// books.ts — defined once, and the only file in the app that imports drizzle-orm
export const books = {
  list: local.query
    .input(z.object({ page: z.number().default(1) }))
    .handler(({ input, context: { mesh } }) => {
      const b = mesh.read(book)
      return mesh.db.select().from(b).limit(20).offset((input.page - 1) * 20)
    }),

  create: local.mutation
    .input(z.object({ title: z.string() }))
    .handler(({ input, context: { mesh } }) =>
      mesh.db.insert(book).values({ id: crypto.randomUUID(), ...input })),

  checkout: authority.mutation
    .input(z.object({ id: z.string() }))
    .errors({ NOT_FOUND: {}, ALREADY_OUT: {} })
    .handler(async ({ input, context: { mesh }, errors }) => { /* the outside world */ }),
}
```

```tsx
const { data, isPending, isSettled } = useLiveQuery(api.books.list({ page: 1 }))
api.books.create({ title: "Dune" })
```

1. **This does not contradict D20's argument; it reverses its conclusion about who writes SQL.** D20 rejected its option C because it was *two* surfaces — "SQL for reads, mesh verbs for writes and live UI" — and a handler that read through `mesh.jobs.get()` while the real queries happened in Drizzle was two sources of truth in one function. This is **one** surface. A procedure is a named operation, not a second ORM: it has no `where` clause of its own, no query grammar, nothing to keep in step with Drizzle. Underneath, D20's mechanism is untouched — the state store still materialises rows into real tables, handlers still read and write them with the app's ORM, capture still turns one transaction into one signed event, and the validator's ladder is still the only judge. What changes is that the ORM stops being the *app's* API and becomes the *handler's*.

2. **D10's rule inverts, and the local/authority split replaces it.** D10 warns: "If a procedure only writes a synced collection, it should not exist: the client can do that offline with no round trip." Under one surface, every write is a procedure, so the rule as written would forbid the API. What it was actually protecting is real and is now carried by the declaration instead. A `local.*` procedure runs in-process against the device's own store — offline, no round trip, exactly what D10 wanted. An `authority.*` procedure is `fetch`, fails offline, and is typed as such at the call site. The test D10 names — *other rows, the clock, or the outside world* — is now the test for `authority` rather than the test for "procedure at all".

3. **`local.query` is lazy; `local.mutation` is eager.** `useLiveQuery(api.books.list({ page: 1 }))` must not execute — the hook subscribes to it — while `api.books.create({ title })` must execute on call, or fire-and-forget silently does nothing. One thenable cannot be both, so the procedure declares which it is. A query call returns a **descriptor**: the procedure, the input, and a stable key derived from both, inert until something runs it. A mutation call returns `Promise<WriteResult>` and has already started. Call sites are unaffected by the distinction; only the definition names it.

4. **`local.*` running in-process keeps D10's "syncmesh does not ship an RPC system" true.** The local caller is oRPC's own `call()`. No router, no request channel, no handler map, no wire format, and nothing on the relay — which still carries events, grants and blobs and nothing else. The same procedure definition is served over HTTP by the authority and called in-process by the device, from one file, with one set of types.

5. **The read result uses React Query's names, minus what a live query makes meaningless.**

   ```ts
   const { data, error, status, isPending, isError, isSuccess, isSettled } = useLiveQuery(api.books.list({ page: 1 }))
   ```

   Absent, each for a reason: `queryKey` and `invalidateQueries`, because the fold already says which tables changed and D20 §4 already re-runs the queries that touch them — invalidation is derived, never written by hand; `staleTime`, `gcTime` and `isStale`, because live data is never stale; `refetch`, `isFetching` and `refetchOnWindowFocus`, because it is a subscription and not a poll; `useMutation`, for the reason in §6.

6. **`isSettled` is the one word React Query has no need for and this does.** "Empty because there are no books" and "empty because the relay has not answered yet" are different states, and only the second should draw a spinner. `mesh.settled()` already answers exactly this — its own doc calls it "what to await before drawing an empty state (RFC-0019)", and sources answer nearest first, so a radio holding nothing never resolves ahead of the relay that holds everything.

7. **A write throws or returns; there is no `.confirmed` promise.**

   ```ts
   const { eventId, data } = await api.books.create({ title: "Dune" })
   ```

   `WriteResult` is `{ eventId, data }` and nothing more. `eventId` cannot be on a synchronous return because the sequence number is allocated during the write. The call throws `ColumnCheckFailed` when the input fails the schema, `PolicyDenied` when the caller's `allow` rules refuse it, and `StoreFailure` when local SQLite cannot commit — all three settle immediately, online or off, because the only thing awaited is the local write.

   A `.confirmed` promise was drafted and rejected on two counts. It conflates arrival with acceptance, which `packages/client/src/delivered.ts` already refuses to do in as many words: *"Delivery, not approval — every receiver runs the same policy itself, so this says the bytes arrived and nothing about whether anyone accepted them."* And it is a promise that legitimately never resolves, because being offline is the normal state of a local-first device and not a failure. Every later fact is opt-in instead, each naming exactly one thing: `mesh.delivered({ event })` for a peer's cursors covering it, `mesh.delivered({ event, to })` for a named peer, `mesh.received({ event })` for this device having folded a reply, and `mesh.corrections` for the authority having overruled it (E16).

8. **There is no mutation hook.** For a `local.*` write there is nothing to hold: the write lands in the device's SQLite, the fold fires, and the query re-runs before the promise resolves. `isPending` would be true for about a millisecond and `error` is what `try`/`catch` is for. This is Zero's conclusion too, reached from the same place. Where a form genuinely needs a disabled button during an `authority.*` round trip, that is two lines of `useState` in the app and does not deserve a hook in the library.

9. **Sync state is observed per row, not awaited per call.** A write made offline on Tuesday syncs on Thursday; by then the promise from that call is gone, the component unmounted, the process restarted twice. So the live query projects it:

   ```ts
   book.$sync        // "local" | "delivered" | "remote"
   book.$correction  // undefined | { by, reason, at }
   ```

   `"local"` is this device's write that no peer has acknowledged; `"delivered"` is this device's write that some peer's cursors cover; `"remote"` is a row another peer wrote, for which delivery is not this device's question — the same reason a chat app shows a receipt under your messages and never under theirs. `$correction` is a separate field rather than a fourth state because delivered-and-corrected must be representable: the journey of the write and the current value of the row are different axes. Not built: this needs the state store to carry each row's authoring event id, and the live query to project it alongside the row.

10. **What syncmesh ships for this, and nothing more.** `@syncmesh/orpc` grows the `local` / `authority` builders, the call descriptor and the in-process caller — `withMesh` stays what it is underneath. `@syncmesh/react` grows `MeshProvider` and the descriptor-taking `useLiveQuery`, and its four existing hooks stay as the testable core that the context versions delegate to, for the same reason React Query keeps `queryClient.fetchQuery` beside `useQuery`. No new package.

## What this costs, accepted

- Every read an app performs is now a named thing someone has to write, including the trivial ones. That is the point, but it is a real cost against `db.select().from(books)` for a throwaway.
- Two builders (`local`, `authority`) that look nearly identical and differ in exactly one property nobody sees at the call site until they are offline.
- The typed-error surface is oRPC's, so the app inherits its shape for defined errors — including that `FORBIDDEN` arrives on every procedure whether it declared it or not, from `withMesh` mapping `PolicyDenied`.
- `$sync` needs a per-row authoring event id in the state store, which is storage work in service of a UI affordance.

## Watch out

- **A remote peer's quarantine never reaches the author, so `$sync` has no `"rejected"` state.** `engine.onQuarantine` fires on the device that *refused* the event, and there is no quarantine report anywhere in `wire`, `transport`, `relay` or `client` — the three mentions outside the engine are the codec keeping unknown tags whole (D22-A), the outbox prioritising a grant so the far side does not park, and the holdback's own bookkeeping. Worse than silent: because a parked event holds the receiver's cursor below it and *"the cursor still stops below it on the wire"* (`transport/src/holdback.ts`), a quarantining peer's acknowledgement never covers the refused event, so `mesh.delivered` never settles and the row reads `"local"` forever — indistinguishable from a device that has simply not synced yet. Naming a `"rejected"` state would be inventing a fact the system cannot observe. Closing it means a quarantine report on the wire, which is protocol work and gets its own decision.
- **A write that syncs and is then overruled is not a rollback.** D10 is explicit that an offline device's write cannot be rejected after the fact; the authority overwrites it with a reason (E16). So `$correction` appearing on a row is the system working, and any API that presents it as an error — or that quietly reverts the row — is lying about what happened to someone's offline work. This is where syncmesh must differ from Zero, whose server is authoritative and does roll back an optimistic write.
- **A thin client (E27) has no local store, so `local.*` cannot run there.** Every procedure becomes `authority.*` on that device, which means an API written for a device with a store does not port to one without by changing a transport. If E27 is ever built, this is the seam that decides whether it is the same product.
- **`isSettled` must not be confused with `isPending`.** A query that has run and returned nothing is `isSuccess` with an empty `data`; whether to draw "no books" or a spinner is `isSettled`'s question alone. Getting this backwards shows an empty state to every user on every cold start, which is the exact failure RFC-0019 exists to prevent.
- **Do not let `local.query` handlers write.** Nothing in the type system stops a `.query` handler from calling `mesh.db.insert`, and a lazy descriptor that a hook may run, re-run, or never run is the worst possible place for a side effect.
