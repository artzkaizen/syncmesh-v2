## Context

§1 of the plan settles what a refusal at the fold is: not a veto, because a fold-time veto is
divergence, but a **failure state** — *"it means the world changed between write and fold —
expiry, revocation, a policy change — and it fails badly"* (`plan/api-gaps.md:52-54`, `:67-70`).
§3.4 names the hole behind it: *"a refused write is indistinguishable from an unsynced one,
forever, to its author"* (`plan/api-gaps.md:305-308`). D26 and D27 each found the same hole from
their own side and deferred it here.

**The mechanism, in one chain.** A peer whose ladder refuses an event parks it with the verdict
(`packages/engine/src/admit.ts:138-142`) and stops the author's cursor **below** it, because
advancing past would be "this device telling every peer it holds something it is still waiting
to understand" (`admit.ts:117-121`). The cursor is what travels: *"The cursor still stops below
it on the wire, so peers keep offering the event itself"*
(`packages/transport/src/holdback.ts:15`). Every custody reading is built from cursors — the
receipt rows are written from `engine.acks()`, which cursor frames feed
(`packages/transport/src/bridge.ts:239`; `packages/relay/src/session.ts:194`) — so the refusing
peer's acknowledgement never rises to cover the refused write. `SyncState` therefore has no
`"rejected"` on purpose: *"a refused write is indistinguishable from one still in flight —
naming a state for it would be inventing a fact the system cannot observe"*
(`packages/client/src/sync-state.ts:10-13`). The row reads `"local"` forever.

**Who knows, today.** Only the refuser. `engine.onQuarantine` fires on the device that parked
the event, carrying `{ event, reason: ValidationError }` (`packages/engine/src/engine.ts:85-88`,
`:217`), once per event per verdict tag (`admit.ts:168-174`). `$recovery` reads that local
quarantine back as `RecoveryIssue { kind, event, author, verdict, message }` with a
per-verdict next step — *"The author's grant has expired: renew it"*, *"issue one, or relay the
one it has"* (`packages/client/src/recovery.ts:22-36`, `:118-140`, `:198`). Every word of that
is addressed to the operator of the refusing device, about somebody else's write. The author,
who could actually renew the grant, hears nothing.

**What the author's surfaces have to say instead.** `unsettled()`'s doc is the honest version and
it is weak on purpose: *"a write some peer quarantined stays here for good … So a screen built on
this says* nobody has this yet, *never* syncing…" (`packages/client/src/operations.ts:24-34`).
`Write.status()` returns an `OperationRow` whose `status` is `"applied" | "blocked" |
"superseded"` and whose only "somebody disagreed" field is `correction?: { by, reason }`, set
when an authority overwrote the value (`packages/storage/src/operation-store.ts:21-37`;
`packages/orpc/src/write.ts:39-42`). D27's watch-out and D28's both end at the same sentence:
*"Until a quarantine report exists on the wire, the copy has to say the weaker thing"*
(`plan/decisions/D27.md:107`); *"a refused write stays in both readings for good"* (D28).

**The twin that already exists.** A custody receipt is a peer's cursor claim, signed:
`CustodyReceipt { v, holder, author, throughSeq, incarnation, issuedAt }`
(`packages/wire/src/receipt.ts:26-40`), encoded as `[core, sig]` (`receipt.ts:77-87`), verified
against the holder the receipt itself names so a peer cannot pass off another's
(`receipt.ts:89-101`). It rides frame kind 7, added "additive, so an older peer ignores it"
(`packages/transport/src/frame-parts.ts:28-29`), and an unknown tag is ignored at both decode
(`packages/transport/src/frame.ts:165-171`) and dispatch (`packages/transport/src/custody.ts:87-88`).
The bridge signs one after every batch lands durably — *"durable now, so the claim can be
signed"* (`bridge.ts:222-228`) — and on arrival keeps only receipts about this device's own
writes (`custody.ts:61-62`). A quarantine report is that object with the verdict inverted: *I have
your `(peer, seq)`, and I will not fold it, and here is the tag that says why.*

**Why the refuser's identity is the whole point.** `QuarantineReason` is three buckets, and they
mean different things to an author: `unknown-table` and `unknown-kind` say *the refuser is on an
older build than you* and an upgrade on their side clears it; `refused` says *the ladder said
no* — `NoGrant`, `GrantStale`, `GrantRevoked`, `PartitionNotGranted`, `SchemaViolation`,
`PolicyDenied` (`packages/engine/src/quarantine.ts:17-29`; `packages/engine/src/errors.ts:120-134`).
A `GrantStale` from a laptop across the room and a `PolicyDenied` from the authority are not the
same news, and the author already knows which peer is the authority — it is a configured id
(`packages/engine/src/validate.ts:81-82`). A report without a signed refuser is a report the
author cannot weigh.

## Options

- **A · Do nothing; keep the weaker copy.** Today. Every custody surface says "nobody has told me
  they have this" and means it. Rejected on the plan's own framing: the refusal is a failure
  state, and a failure state nobody is told about is the one class of failure a local-first
  system cannot route around, because the only device that can fix it (renew the grant, move
  the row, upgrade) is the one kept in the dark.
- **B · An unsigned frame.** `[9, author, seq, reason, verdict]`, sent by the refuser. Rejected:
  the common deployment is a relay that forwards bytes it does not read (D28's watch-out), and an
  unsigned report is one any relay, any peer in the room, or anything on the path can mint about
  anyone's write in anyone's name. It would be the first unsigned fact on the wire that changes
  what a screen says about a person's work, and `custody.ts:14-18` already argues the same case
  for cursors: *"a device counting copies off cursors is counting claims."*
- **C · A signed frame mirroring `CustodyReceipt` — a `RefusalReceipt` — landing in the author's
  ledger beside receipts and vouches, shown as `refused-by` next to `delivered`/`held`.** Same
  envelope, same verify-against-the-named-signer rule, same "keep only what is about my writes"
  rule, one new frame kind. Information only: it cannot un-fold anything anywhere.
- **D · Route refusals to the authority only, which re-emits a correction with a reason.**
  Rejected as the whole answer, composes as a part. A correction is an *overwrite* — the fixed
  value and the `_corrections` row in one event (`packages/engine/src/authority.ts:123-131`,
  `:134-155`). A refused event never folded on the refuser, so on that peer there is nothing to
  overwrite; on peers where it did fold, a correction is right, and that is D24-B, which D24
  deferred until the correction path is built. Two further holes: a refusal by a peer that is not
  the authority (an older build, a peer whose grant view differs) is not the authority's to speak
  for, and a sealed partition has no corrections at all (`plan/api-gaps.md:72-75`). The authority's
  own refusal is the one that matters most, and under C it arrives signed like any other.

## Decision

**Recommend C.** A refusal is a receipt with the verdict inverted, built from the receipt's own
parts, and it changes exactly one thing: what the author's ledger can say.

```ts
// packages/wire — beside CustodyReceipt (receipt.ts:26-40)
interface RefusalReceipt {
  readonly v: 1;
  readonly refuser: PeerId;          // who parked it; the signature is checked against this key
  readonly author: PeerId;           // whose event
  readonly seq: SeqNum;              // one event, not a run: a refusal is about a (peer, seq)
  readonly reason: QuarantineReason; // "unknown-table" | "unknown-kind" | "refused"
  readonly verdict: string;          // the ValidationError._tag — "GrantStale", "PolicyDenied", …
  readonly issuedAt: Temporal.Instant;
}
// encoded [core, sig]; verified against `refuser`; kept only when author === identity.peerId
```

1. **Frame kind 9, additive.** `KIND.refusal: 9` beside `receipt: 7` and `routes: 8`
   (`frame-parts.ts:20-32`). `classOf` reads the tag as one byte for anything under 24
   (`frame-parts.ts:54-56`), `KINDS` is derived from `KIND` (`:61`), and an older build's decoder
   returns `{ kind: "unknown" }` and its dispatcher ignores it (`frame.ts:165-171`;
   `custody.ts:87-88`). Nothing on an old peer changes. New vectors go in `conformance/` beside
   `receipt-vectors.json` before it ships (README rule 3).

2. **What it carries, and what it does not.** Author, `(peer, seq)`, the bucket, the verdict's
   tag, the refuser, a timestamp, a signature. **No free text**: `ValidationError.message` is a
   sentence written by a peer's build, and a peer's prose on the author's screen is a vector.
   The author's own `$recovery.explain` already turns a tag into a sentence
   (`recovery.ts:118-140`); reuse it on the receiving side. **No `incarnation`**: a refusal is not
   custody, and the thing that supersedes it is not a new lineage but a fold (§5).

3. **When it is sent.** Where `custody.vouch(author)` runs today — after `receiveBatch` returns
   (`bridge.ts:222-228`) — the bridge also sends one refusal per event that batch parked. And
   again on every cursor exchange while the event is still parked, the way `vouch` re-signs the
   current cursor each time: the report is idempotent on `(refuser, author, seq, verdict)`, so
   repeating it costs bytes and nothing else. `admit`'s own once-per-verdict dedupe
   (`admit.ts:168-174`) is for the local hub and stays as it is.

4. **Where it lands.** A fourth ledger table beside `operations`, `receipts`, `vouches`
   (`operation-store.ts:24-55`): `refusals (peer, seq, refuser, reason, verdict, at_ms)`.
   D28 §1's argument for a table per provenance applies unchanged — a refusal is a third fact
   with a third provenance, and a nullable column on `receipts` would make the strongest negative
   fact a footnote on the weakest positive one. `CREATE TABLE IF NOT EXISTS` in the ledger's own
   DDL; no migration.

5. **What supersedes it.** Nothing needs a retraction frame. When the refuser later folds the
   event — the grant arrived, the build upgraded, `retryQuarantined()` ran — its cursor rises past
   the seq and it vouches (`bridge.ts:228`). A `CustodyReceipt` from the same holder with
   `throughSeq ≥ seq` **deletes** the refusal row on insert, the same shape as
   `deleteStaleVouches` (D28 §2). The positive fact retires the negative one, and both are signed
   by the same key.

6. **Where it surfaces.** Three places, one axis, no fourth `SyncState`:
   - `OperationsView.refusalsOf(peer, seq)` beside `receiptsOf` and `vouchesOf`
     (`operations.ts:42-59`), and a `refusals?: readonly { by, reason, verdict }[]` beside
     `correction?` on `OperationRow` (`operation-store.ts:36`). D26 §9's argument for
     `$correction` being a field and not a state holds here word for word: *"delivered-and-
     corrected must be representable: the journey of the write and the current value of the row
     are different axes."* A write can be `delivered` to three peers and refused by one.
   - `unsettled()`'s copy can finally say the stronger true thing when it applies:
     *"peer 3f2a… refused this (GrantStale)"* rather than *"nobody has this yet"*, and the
     D27/D28 watch-outs close.
   - `$operations` is where it lives; `$recovery` stays *"what is stuck here"*
     (`packages/orpc/src/client.ts:49-52`). The two are mirror images and should not be merged —
     one is about others' writes on this device, the other about this device's writes elsewhere.

7. **What it must never do.** It cannot un-fold, revert, or block anything, on any peer,
   including the author. The event is signed and in the author's log; peers that admitted it
   hold it; the plan's rule stands — *"Refusing an event other peers already folded cannot be
   undone across a mesh"* (`plan/api-gaps.md:52-54`). A refusal receipt is information about one
   peer's verdict, and the only thing it is allowed to move is text on the author's screen. If a
   future reader is tempted to gate on it — "do not compact", "do not detach", "mark superseded" —
   that is a veto arriving by the ledger door, and D28's two tiers already say what may gate:
   a signature for holding, and nothing else.

## What this costs

- **A wire addition, frozen.** Frame kind 9 and a receipt-shaped core; both need vectors. Small,
  permanent.
- **The relay does not carry it, for the same reason it does not carry receipts.** The relay's
  session union is `presence | grant | cursors | grant-request | event` (`session.ts:189-200`), so
  a refusal through a relay is dropped by the client-side session exactly as a receipt is today
  (D28's watch-out). Closing that is a relay frame under D14's version bump, and it should be the
  **same change** as the receipt's, because it is the same shape and the same argument. Until
  then, refusals are learned only across a direct link — which is also where the refuser most
  often is: the laptop across the room.
- **A fourth ledger table** on every device, including the many that will never hold a row.
- **Two packages and the react surface move.** `@syncmesh/wire` (the receipt), `@syncmesh/transport`
  (the frame and the send), `@syncmesh/storage` (the table), `@syncmesh/client` (`refusalsOf`,
  the copy), `@syncmesh/react` (whatever renders `refused-by`). No new package.

## Watch out

- **A false refusal is bounded to a display, and it must stay bounded.** A malicious or merely
  wrong peer can sign a refusal for any event it has seen. What it buys is one line on the
  author's screen that says *this peer said no* — which is true, in that the peer said it — beside
  the peer's identity. It buys nothing else, because nothing gates on it (§7). The moment a
  reader weighs a refusal into `soleCustody()`, into a compaction floor, or into a `status` flip,
  the bound is gone and the forgery becomes an attack on somebody's data instead of on their
  patience.
- **Weight by refuser, not by count.** Three old builds saying `unknown-table` is one fact —
  *they have not upgraded*. One `PolicyDenied` from the configured authority is a different fact
  altogether, and it is the one D24 says will eventually become a correction. The UI should say
  which, using the id the app already has (`validate.ts:81-82`). A count of refusers is the copy
  count D27 deleted, coming back as a negative.
- **Retention is "as long as it is parked", and the quarantine is memory.** `createQuarantine`
  holds `Map`s (`quarantine.ts:139`) and the engine builds it fresh at boot (`engine.ts:263`); no
  storage implementation exists. A refuser that restarts forgets what it parked — but its cursor
  below the event is durable, peers re-offer the event (`holdback.ts:15`), it parks again, and
  under §3 it reports again. So the refuser needs no memory *of the report*; it re-derives it.
  What ends the reporting is eviction: at the per-reason cap the oldest parked event is dropped
  loudly and "nothing will offer it again unless the gap below it is still open"
  (`quarantine.ts:85-87`, `:151-162`). The last report before eviction is therefore the last the
  author will ever hear from that peer, and the author's row should not be deleted for silence.
- **Do not let the report grow a `message`.** The refuser's `ValidationError.message` is exactly
  what an author wants to read and exactly what a malicious peer wants to write. The tag is
  enough; the author's own build owns the sentence.
- **`unknown-kind` reports are about the refuser's build, not the author's event.** A report
  whose reason is a park-until-upgrade bucket (`quarantine.ts:56`) should read *"3f2a… is on an
  older build and cannot read this yet"*, never *"refused"*. Getting this backwards tells a person
  their write was rejected when the only thing wrong is that somebody else has not updated.
- **D31 leans on this.** Its case 3 — an old client writing a table a newer build has retired —
  is told nothing today; under C it hears `unknown-table` from every upgraded peer, which is the
  upgrade nudge D31's option A wanted and could not deliver without a wire.
