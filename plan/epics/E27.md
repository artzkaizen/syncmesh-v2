## Goal

A device with **no** store: it holds no log, folds nothing, and asks the relay to maintain its
queries and push row patches. A second product lane, named as one.

> **Split out of E13 (2026-08-27).** E13 carried this as "the relay's row path" alongside a
> client IVM. D20 retired the client IVM outright — a device with a store re-runs SQL locally —
> which leaves this as what it always actually was: a different product for a different device.
> Worth building when something needs it; worth *not* building meanwhile, because a relay that
> maintains materialised views is a relay that executes something, and that is a real departure
> from "the relay interprets nothing".

## Decisions needed

D11 (its option C — TanStack's `db-ivm` — is the engine if this is built; not ours, per D20 §5)

## Tasks

- [x] Decide first, in the RFC: is this a supported shape or a demo? A relay holding per-socket
      materialised state changes its threat model, its memory profile and its failure modes. It
      still cannot forge — signatures are end to end — but "drop traffic only" stops being the
      whole story
- [x] `ClientView` — one per socket; rows refcounted across that socket's queries and evicted at
      zero; patches **queued** through E12's backpressure, never sent raw (RFC-0010's lesson: a
      dropped row patch is unrecoverable where a dropped event is not)
- [x] Relay frames `desire / undesire / rows`, additive over E12's versioned handshake
- [x] The query on the wire is E13's predicate grammar plus an order and a limit — **not** a new
      language, and not a ZQL. If joins are needed, `db-ivm` behind this seam (D11-C)
- [x] A client that consumes patches without an engine: no fold, no cursors, no signatures to
      check beyond the relay's own — and an honest name for what it therefore cannot do offline

> **Built 2026-11-07 (D39-B).** `@syncmesh/window` holds the query (`parseQuery`, the policy
> AST as `where`, `order`, `limit`, keyset `after`), the frames, `ClientView`, a memory
> `RowSource` with sorted indexes, and the thin client (`createWindowClient`, no engine).
> `relay/src/windows.ts` serves it on a socket through E12's sender. The row path runs on the
> peer that holds rows, not in a relay room (D39). The tags are 32–34, clear of 8–19, and an
> older relay reads them as `unknown`. D11-C's `db-ivm` is not used: there are no joins, and a
> window re-reads its rows from an ordered source in O(log n + scanned) only when a cheap check
> says a change can move it. `scanned` is `limit` when the read policy and `where` accept most
> rows; when they accept few, the memory source scans until it finds `limit` or runs out, and a
> window that is never full is re-read on every accepted insert. A Postgres source must push the
> policy into its `WHERE` for the same reason. One socket holds at most `maxWindows` windows
> (64 by default), and the memory source keeps at most `maxIndexes` sorted indexes a table (8
> by default), dropping the one used least recently. Not yet built: a Postgres `RowSource` (E17's CDC feed plus
> `ORDER BY … LIMIT`, text under `COLLATE "C"`), and a host that mounts `serveWindows` on a
> sealed link.

## Watch out

- Patches carry an epoch and a monotone version (E24). A gap, or a reconnect, costs one
  resnapshot of the view's Σ limit rows. A server does not replay a stretch of missed patches.
- A thin client cannot write offline in any meaningful sense. If the API lets it look like it
  can, that is the bug.

## Tests

- [x] `window/view.test` (open, scroll, refcount and eviction, insert/delete inside and outside the
  window, `where` in and out, gap → resnapshot, re-desire on a new socket, refusals, policy before
  `where`), `window/million.test` (1M rows: a window opens and scrolls 500k deep reading exactly
  `limit` rows), and `relay/windows.test` (100 disjoint queries over 16 KB rows, ~32 MB in one
  burst through backpressure without stalling; a stalled socket closed, not trimmed, and
  resnapshotted on the next socket).

## Done when

The relay serves 100 disjoint queries without stalling, and a store-less client renders rows it
never folded.
