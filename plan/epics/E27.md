## Goal

A device with **no** store: it holds no log, folds nothing, and asks the relay to maintain its
queries and push row patches. A second product lane, named as one.

> **Split out of E13 (2026-08-27).** E13 carried this as "the relay's row path" alongside a
> client IVM. D20 retired the client IVM outright — a device with a store re-runs SQL locally —
> which leaves this as what it always actually was: a different product for a different device.
> Worth building when something needs it; worth *not* building meanwhile, because a relay that
> maintains materialised views is a relay that executes something, and that is a real departure
> from "the relay interprets nothing".

## Decisions needed

D11 (its option C — TanStack's `db-ivm` — is the engine if this is built; not ours, per D20 §5)

## Tasks

- [x] Decide first, in the RFC: is this a supported shape or a demo? A relay holding per-socket
      materialised state changes its threat model, its memory profile and its failure modes. It
      still cannot forge — signatures are end to end — but "drop traffic only" stops being the
      whole story
- [x] Server windows (`createServerWindows`, was `ClientView`) — one per socket; rows refcounted across that socket's queries and evicted at
      zero; patches **queued** through E12's backpressure, never sent raw (RFC-0010's lesson: a
      dropped row patch is unrecoverable where a dropped event is not)
- [x] Relay frames `desire / undesire / rows`, additive over E12's versioned handshake
- [x] The query on the wire is **not** a new language and not a ZQL: a window names a `query`
      procedure and its input, and the handler is the query (D43, revised). Joins would be a
      handler that joins; nothing on the wire changes
- [x] A client that consumes patches without an engine: no fold, no cursors, no signatures to
      check beyond the relay's own — and an honest name for what it therefore cannot do offline

> **Built 2026-11-07 (D43-B), reshaped the same day.** A windowed read is an ordinary `query`
> procedure over a table marked `sync: "window"`, read with `useLiveQuery(api.mail.inbox({ … }))`
> and paged with a keyset `after` in its input. The device sees the handler reads a served table
> and sends `{ path, input }` over the window channel; the server runs the same handler on
> Postgres with the read rule substituted for each table (`servedReads`, fail-closed), and
> re-reads when E20's logical replication reports a commit to a table it read (`commitFeed`).
> `@syncmesh/window` holds the frames, `createServerWindows` (one socket's windows, server
> side), the `PageSource` seam, and the thin client the api drives; `@syncmesh/window/testing`
> holds the memory source. `relay/src/windows.ts` serves it on a socket through E12's sender. The
> row path runs on the peer that holds rows, not in a relay room (D43). The tags are 32–34, clear
> of 8–19, and an older relay reads them as `unknown`. D11-C's `db-ivm` is not used: there are no
> joins, and a keyset page on an index reads `limit` rows. One socket holds at most `maxWindows`
> windows (64 by default). Not yet built: a host that mounts `serveWindows` on a sealed link, and
> narrowing a re-read to the windows a change can move (it is per table today).

## Watch out

- Patches carry an epoch and a monotone version (E24). A gap, or a reconnect, costs one
  resnapshot of the view's Σ limit rows. A server does not replay a stretch of missed patches.
- A thin client cannot write offline in any meaningful sense. If the API lets it look like it
  can, that is the bug.

## Tests

- [x] `window/server.test` (open, next page, half page, refcount and eviction, insert/delete
  inside and outside the window, `where` in and out, a commit to another table not read, gap →
  resnapshot, several windows on a new socket, `maxWindows`, refusals, permission before the
  read), `relay/windows.test` (100 disjoint windows over 16 KB rows, ~32 MB in one burst through
  backpressure without stalling; a stalled socket closed, not trimmed, and resnapshotted on the
  next socket).
- [x] Against a real Postgres with logical replication (`orpc/served-postgres.test`): the same
  behaviours with `INSERT`/`UPDATE`/`DELETE` written in SQL, another reader's rows never entering,
  refusal of a served table with no read rule, an unknown read and a refused input.
  `orpc/served-million.test`: 1M rows from `generate_series`; opening, a scroll 500k deep and a
  live insert each read 50 rows by `EXPLAIN ANALYZE` (one Index Scan, no Sort).
  `orpc/served-e2e.test`: `createClient({ windows })` over a real WebSocket to `serveWindows` →
  `servedReads` → Postgres; the descriptor `useLiveQuery` holds answers, and a row `INSERT`ed in
  SQL arrives live with its diff.

## Done when

The relay serves 100 disjoint queries without stalling, and a store-less client renders rows it
never folded.
