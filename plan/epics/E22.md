## Goal

A phone-to-phone radio implementing the frame link: discovery, a 3-frame handshake, fragmentation and acks over a 128 KiB reassembly cap, encryption on.

## Decisions needed

D12

## Tasks

- [x] Native module (Swift / Kotlin) exposing `send(frame)` + `onFrame(cb)` + connection events — **already exists and is published**: `@syncmesh/rn-ble` 0.1.0, its own repo, central *and* peripheral on both platforms. More general than this task asked for: a GATT API rather than a frame pipe, which is why the fragmentation below is ours to write. It exposes bytes as base64; whether that costs anything real is for this transport to find out before anyone changes it
- [~] Port the old repo's proven handshake / fragmentation / ack / backoff. **"Proven" turned out to mean proven against a fake radio** — the manual device checklist exists with every box unchecked, and two of the four are wrong:

  - **The ack scheme loses data silently.** The receiver acks inside `case "data"`, once per *fragment*, carrying the `messageId`; the sender then clears the whole message from `outboundQueue` and `inflight` on the first ack. Fragments 3–7 of an 8-fragment message are never retried and the receiver's partial expires quietly 30 s later. Neither side errors. Not ported — v2's model is that `send` throws and `resync()` recovers, so no message-level ack is needed at all.
  - **Frame sizing ignored the MTU.** `maxFrameBytes = 140` bounded a base64 slice *before* JSON wrapping and a second base64, ≈350 bytes on air against a typical 182-byte ATT payload. Centrals survived on long writes; notifications have no long write, so the peripheral→central direction was likely truncating on hardware and no test could see it.

  What was worth taking: the dial-ownership rule, the binary fragment header from the Swift side, and MTU-derived sizing per direction.
- [x] Fragmentation and reassembly as a `FrameLink` — `packages/ble`, sized from what each direction can actually write
- [x] XChaCha20-Poly1305 on frame payloads — `handshake.ts` (the crypto, pure) and `session.ts` (a `FrameLink` wrapped in one that encrypts). Two hellos crossing without waiting for each other: each end signs a fresh X25519 key with the Ed25519 key that *is* its peer id, and the transcript of both hellos salts the HKDF, so anyone who swapped a frame in the middle leaves the two ends holding different keys and their traffic stops opening. The two directions are separate keys, chosen by peer id order rather than by who dialled, so neither end shares a nonce space with the other.

  **There was no plaintext path to delete.** The donor's bare-frame fallback and `createDeterministicIdentity` are its own; v2 never grew either, and the way that stays true is that `bleTransport` wraps every link unconditionally rather than offering a setting. What did need care is the other direction: frames the bridge hands over before the key exists are *held*, because it sends its grants and cursors the instant it attaches and dropping those would cost a whole resync for nothing.
- [x] `bleTransport` over `createFrameTransport` — publish, advertise the hint, scan; the dial rule decides the role; packets route to a link by connection id (notifications) or central id (writes). A dropped connection closes the link **and forgets the peer**, so the next advertisement re-dials; `resync()` comes free with the fresh bridge. Not `class Ble extends`: `createFrameTransport` is the seam, and a class would only wrap it
- [ ] Then wire `pickRoutes`: tag each outbound message with a traffic class; the send path scores

## Watch out

- RFC-0017's three radio holes all live in the donor stack. The port deletes them; do not carry them over.
- BLE is ~24 kbps: a 2 MB blob is eleven minutes of blocked radio. This is why blobs are out of band and why routing exists.

## Tests

- Loopback contract tests pass unchanged against the real radio; two phones in airplane mode converge; a sniffer sees only ciphertext.
