## Goal

Which physical links a device opens, keeps and drops — and, falling out of that, which single
link carries a frame to a given peer. RFC-0012 calls this the missing component and names it the
**mesh manager**: no leader, no coordinator, one loop per device over purely local knowledge,
with the lexicographically smaller peer id dialling so two managers never duel.

## Why now

The route scorer has been built and wired since E22, and it decides almost nothing. Its only two
callers are `requestGrant` and `sendPresence`, both through `every()` with `redundancy` set to
the transport count — so every routable link gets the frame and the *order* is never read. Events
do not pass through it at all; each bridge sends on its own link.

That is the correct behaviour today and not a bug: a transport publishes no per-peer link list,
so narrowing a broadcast to the winner would silently stop talking to a peer whose only path was
the link that lost. Losing a peer beats wasting a send, every time. But it means three of the six
penalty constants (`COSTLY_SMALL`, `COSTLY_SMALL_URGENT`, `DORMANT`) are unreachable — nothing
declares `costly` or `dormant`, and BLE opts out of `costly` deliberately — and the scorer's
ordering is dead weight until something can use it.

The ordering was also **wrong** and nobody could tell. `scoreRoute` clamped with
`Math.max(score, ROUTABLE_FLOOR)`, so a 2 MB snapshot scored `1` on a 24 kbps radio and `1` on
the relay and the tie broke on the transport's *name* — `"ble"` sorts first, so the winner was
eleven minutes of blocked radio. Fixed (the score now compresses into `(0, ROUTABLE_FLOOR]`
rather than clamping), and it was latent only because nothing reads the order. Everything this
epic builds reads the order.

## Decisions taken

RFC-0012 §1 is `proposed` and left two questions open. Both are answered here rather than in a
record of their own, because each follows from something this epic's own Watch-out already says.

**Budgets are the medium's to declare, never the app's to configure.** `Transport.maxLinks()`
sits beside `route()` and `reaches()`. A budget is a property of the radio — a BLE controller
degrades every link past roughly six — and an app handed a way to raise it has been handed a way
to break the links it already has. Raising the number does not give the controller capacity; it
gives more links that all work worse.

**The rotation slot ships from the start.** Not a refinement to add once selection works, because
selection *without* it is wrong in a way nothing observes: pure greedy coverage makes every
device keep the same well-connected neighbours, the graph settles into cliques, and a clique is a
partition that looks like a working mesh — everyone inside it is synced and nobody is watching
the edge that stopped existing. Greedy-only would be a bug whose symptom is that everything looks
fine.

## Tasks

- [x] **`Transport.reaches?()` — the per-peer link list.** The one fact whose absence makes the
      scorer a filter. Optional, like every other capability: a transport that cannot say returns
      nothing and keeps today's broadcast behaviour exactly.
- [x] **`RouteMessage.to`, and `route` narrowing to the transports that reach it.** With `to`
      absent, unchanged — a broadcast is still a broadcast. With `to` set and at least one
      transport claiming the peer, the scorer becomes a chooser for the first time, and its order
      starts mattering.

  Narrowing is an optimisation and never a refusal, and that is the property the whole epic rests
  on: a medium that cannot enumerate its links stays absent rather than claiming nobody, a peer no
  link claims falls back to the broadcast, and offline stays the only fact that removes a
  candidate outright. BLE answers it from `secureLink`'s `onEstablished` — **proven peers only**,
  because an advertisement's hint is a lossy derivation of a peer id that anyone can put in the
  air, and routing at one would be routing at a signature nobody checked. Writing that test found
  a bug: `close()` cleared `held` and left the proven peers behind, so a stopped radio went on
  claiming them.
- [x] Route events through it, which is where the bandwidth arithmetic finally pays: a row edit
      on the radio two metres away, a snapshot page on the wide link. Both are already what the
      numbers say; nothing reads them yet.
- [x] The admission state machine, per discovered peer:
      `discovered → scored → (dial | hold) → session → stale → backoff (400 ms → 15 s) → re-dial`.
      The dial rule is already in `packages/ble` and is the same rule: smaller peer id dials.

  Built as its four moving parts rather than one object, because each is separately testable and
  the whole is not: `backoff` gates the dial (`packages/ble`), `admit` chooses who to keep,
  `enforceBudget` acts on that choice, and `Transport.drop` is what acting means.

  **The manager lives in `packages/client`, not in a radio**, and that placement is the finding.
  It selects on cursor freshness and partition overlap — both the *engine's* facts, which a radio
  does not have. That is why RFC-0012 calls it a **mesh** manager. `enforceBudget` takes an
  `AdmissionFacts` slice rather than the engine and the registry, the same way `@syncmesh/ble`
  takes a `BleRadio`, so a test hands it three functions.

  It runs when its inputs change — an acknowledgement moves a cursor, a grant changes overlap —
  and never on a timer, because there is no clock in that file and adding one to ask a question
  whose inputs announce themselves would be the worse answer. A set of transports where none can
  name its links, state a budget and close one is never swept at all: a budget nothing can act on
  is a number, not a budget.

  Still missing from the RFC's state machine: `stale` detection. A link that is up but has gone
  quiet is not distinguished from one that is working, so the only thing that reclaims a slot is
  the budget sweep or an outright failure.
- [x] Per-transport budgets (`maxLinks`) — BLE ~6, Wi-Fi Aware 1–2, a relay socket 1. Declared
      where `route()` is declared, so a medium describes itself in one place. Absent means no
      limit worth enforcing, which is the honest answer for a relay socket multiplexing rooms.
- [x] Neighbour selection over budget: cursor freshness, partition overlap, link quality, and one
      slot kept for random rotation. Coverage, not signal strength.

  `admit(neighbours, { maxLinks })` — pure, like `pickRoutes`, with one difference worth naming:
  this needs **no** cross-device agreement. Two phones may keep different neighbours and the mesh
  is still connected, so the rotation slot can be genuinely random; what has to hold is that one
  device's own answer is reproducible in a test, which is why the source is injected and ties
  break on the peer id.

  Coverage outweighs signal by design: a strong link to a peer holding nothing this device lacks
  is a slot spent on nothing. The slot is spent only under pressure — with room to spare every
  neighbour is kept — and a one-link radio spends its only slot on the best peer it found,
  because a rotation that is the whole mesh is not a mesh.
- [x] Hysteresis and backoff, so a marginally better candidate cannot churn a live session and a
      peer that will not connect cannot pin the radio.

  Hysteresis is a margin on a live neighbour's score, because churn costs a handshake, a catch-up
  and the frames in flight.

  Backoff fixed a bug rather than anticipating one. BLE called `seen.forget(hint)` on a failed
  dial, so the peer's **next advertisement read as a fresh sighting and dialled again** — several
  times a second, indefinitely, spending the controller on a link that was not going to open. It
  is loud and recoverable each time, which is exactly what kept it from being noticed. Now
  400 ms doubling to 15 s, per peer, cleared when a session opens so one bad night costs nothing
  the next day.
- [→] `costly` / `dormant` declared by a transport that means them — **moved to E23**, which is
      the only epic that can close it. Nothing shipping means either flag: BLE opts out of
      `costly` deliberately and the relay declares nothing, so the three constants and the
      presence refusal that depends on `dormant` are exercised by the scorer's tests and by
      nothing else. That is a fact about which radios exist, not work left undone here.

## Watch out

- **A route this component declines to pick is a frame nobody sends, and that is divergence, not
  routing.** Every online link must stay above `UNROUTABLE`; narrowing must never empty the set.
- Greedy coverage scoring forms cliques. The random slot is not a nicety.
- The manager is per device over local knowledge only. Anything that needs two devices to agree
  belongs in the deterministic tie-break, never in a negotiation.
- Budgets are a property of the radio, not of the app. An app that can raise BLE past what the
  radio sustains has been handed a way to degrade every link it owns.

## Tests

`pickRoutes` with `to` set picks one link and the same one on both devices; with `to` absent the
broadcast is byte-for-byte what it is today. A peer reachable on exactly one transport is never
narrowed away. Over budget, the dropped link is the one that costs the least coverage, and a
flapping candidate does not churn a live session. Property: for any candidate set and message,
the chosen set is non-empty whenever any candidate is online.

## Done when

An event to a peer on both BLE and a relay takes the radio; a snapshot page to the same peer
takes the relay; and a device over its BLE budget keeps the six links that cover the most.
