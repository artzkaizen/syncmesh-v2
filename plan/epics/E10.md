## Goal

Live queries maintained incrementally from the fold batch's exact touched keys, a ref-counted registry so identical questions share one subscription, and React hooks that take a descriptor (no deps) or a builder (deps required).

## Decisions needed

D11

## Tasks

- [x] `LiveQuery`: full filtered result in sort order + key index; on a batch, per touched key decide enter / leave / move / update-in-place by binary search; full scan only on first run, spec change, or unattributable batch (in `@syncmesh/client`)
- [x] `QueryRegistry`: ref-counted; structural keys shared; closure filters unshared; `release`
- [ ] Query builder (`from / where / orderBy / select`)
- [ ] `useLiveQuery(descriptor)` and `useLiveQuery(builder, deps)` normalising to one `LiveQuery` before any hook runs
- [ ] `useLiveInfiniteQuery` — keyset windows only
- [ ] `useLiveQueryEffect`
- [x] One render per fold batch, load-tested (5,000-event catch-up = one notification) — `live-query-load.test`: 200 open queries, one notification each
- [ ] `useCan("books.update", row)` — the hook form of `mesh.can`, re-evaluating when the grant or the row changes

## Watch out

- The safety invariant: a maintained result must equal what a full re-run would produce, always. Property-test it against a re-run oracle; it will find your off-by-one.
- Hermes returns `"[native code]"` for `fn.toString()` — the builder form needs a mandatory deps array; the descriptor form does not.
- Offset pagination is unstable under live edits. Keyset only.

## Tests

- `live-query.test`, `live-query-ivm.test` (the oracle, randomised), Playwright e2e (relay sync, offline divergence + field-merge, multi-tab, reload persistence).

## Done when
