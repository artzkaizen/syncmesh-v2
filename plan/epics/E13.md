## Goal

A device says what it wants; the sender filters before the bytes leave. One row-predicate grammar, shared with the read filter, so there is never a second query language to keep honest.

> **Rescoped against D20 (2026-08-27).** This epic was "incremental view maintenance and the
> relay's row path" — an operator dataflow (`Pred`, `Source → Filter → Take`, `ivmQuery`) that a
> relay would use to serve row patches to many subscribers. D20 decided the unit of sync is the
> **partition**, not the query: a device holds its partitions and re-runs SQL locally, so nothing
> on the client needs an IVM, and E10 has already replaced the maintained `LiveQuery` with
> `live(query)` re-run on exact table invalidation. What survived that decision is **interest** —
> which was never an IVM concern, and which E14's scoped join and E16's last task both need. The
> relay's row path is real but is a different product (a device with *no* store): it moved to
> **E27**, where it can be judged on its own merits rather than smuggled in as an optimisation.

## Tasks

- [x] **D23-A: a filtered catch-up hands over the coverage it filtered to.** The relay ends a filtered run with the contiguous reach of the **unfiltered** scan it did — computed with the joiner's own `trackCoverage`, so both ends apply one rule and two relays holding the same events answer the same number — carried on the last page as one additive element and adopted like `installSnapshot` adopts a snapshot's coverage.

  Three things the build turned up that the decision did not name. The coverage claims events the pages *did* deliver but the holdback was still holding behind the filtered-out hole, so those are folded **before** the cursor moves past them — the same ordering `installSnapshot` keeps for its rows, and for the same reason. A widening re-page is handed a run this device's cursor already claims, so the gap rule reads every event in it as one already held and drops the whole repair; that re-page skips the holdback and lets `admit` dedup on what is *stored*, which is the question that actually matters. And the scope has to outlive the process or a device that widens between runs cannot tell that its numbers describe a slice it no longer asks for, so `Coverage.scope` persists beside the cursors, in the same transaction.

  `narrows(next, previous)` decides whether a cursor survives an interest change, and answers `false` whenever it is unsure — predicates are compared as written rather than reasoned about. A wrong yes skips events for the life of the device; a wrong no costs one catch-up.

- [x] Row predicates as data, by **extending the policy AST** rather than inventing a second
      grammar: `rowIs / any / all / not` already compose row conditions; add the comparisons
      an interest needs (`ne / lt / lte / gt / gte / isIn`). One grammar, three consumers —
      `evaluate` on a device, `compileRead` into SQL, and interest on the wire (D20 §5)
- [x] `Interest { partitions?, tables?, where? }` and `matchesInterest(interest, event)`;
      a stable `interestKey` so two devices asking the same thing are one subscription (`since` dropped: cursors already carry it, and a second way to say the same thing is a second thing to keep honest)
- [x] `engine.eventsSince(cursors, interest)` — filtered at the **sender**, so an uninterested
      event never becomes bytes. The cheap wins first: partition and table, which need no
      predicate evaluation at all
- [x] `join` carries an interest (E12's handshake is already versioned, so this is additive); the
      relay filters catch-up pages and live fan-out by it, and remembers it per socket
- [x] What an interest may **not** do: widen what a device is allowed to see. Interest narrows;
      the read policy is still the only thing that decides. A test that proves an interest naming
      another org's partition returns nothing rather than more

## Watch out

- Interest is a **request**, not a permission. The relay must apply it *after* the policy filter,
  never instead of it — the one way this feature could become a data leak.
- A device that changes its interest has a gap: what it did not want yesterday it did not
  receive. Re-desiring must re-request from a cursor the sender still honours, not from "now".
- Filtering by `where` costs the sender a predicate evaluation per event; partition and table
  cost a map lookup. Prove the cheap path carries the common case before optimising the dear one.

## Tests

- [x] `engine/interest.test`: partition and table narrowing; a `where` predicate against real rows; an
  interest that names a partition the caller has no grant for yields nothing; `matchesInterest`
  agrees with the same predicate run through `evaluate`.
- [x] `relay/interest.test`: a joiner with an interest gets filtered pages and filtered fan-out, and
  a second joiner with a different one is unaffected.

> **Built 2026-08-27.** One thing the design gained while building: `where` on an **update**
> matches when the patch satisfies the predicate *or* touches a column the predicate names, so a
> row moving *out* of an interest is still visible as it leaves. Without that a device would keep
> a row forever at the value it held when it stopped matching — the stale-row hole E27 exists to
> close properly. A **delete** always travels, for the same reason. An unreadable interest on the
> wire falls back to everything the policy allows, never to nothing: silently starving a device
> looks exactly like a working relay with an empty room.

## Done when

A device that wants one board out of fifty receives one board's events, and a device that asks
for a board it may not read receives nothing.
