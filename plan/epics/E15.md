## Goal

Bytes that do not belong in a log: content-addressed, verified on put and on fetch, travelling out of band.

## Decisions needed

D18

## Tasks

- [x] `hashOf` (sha-256, the wire's lowercase hex), `verifyBlob`, `memoryBlobStore`; `BlobCorrupt / BlobNotFound / BlobTimeout` as values, because each is a thing an app must decide about
- [x] Relay channel — four additive frames (`blob-put / blob-get / blob / blob-missing`) verified at the relay before storing — and the client cache; `mesh.blobs.put / fetch / has`, with a fetch answering from the local cache first, verifying what arrives, and caching it. A medium that cannot carry bytes says `NoSuchCapability` rather than pretending
- [x] `sqlBlobStore(driver)` over either dialect — a relay's durable home, or a device that wants its photos after a restart; in the driver contract suite, so every adapter proves it
- [x] Answered in RFC-0015 and D18: the **author** holds it until a relay acks; the **relay** holds it while a visible row references the hash; every other device holds a **cache** it may evict. A delete does not delete the blob — the relay sweeps only after a retention window with no reference, and a stale reference is `BlobNotFound`, recoverable because anyone with the bytes can put them back under the same name
- [x] The sweep itself, and per-partition quotas refused at the put as a typed value — `relay/src/blob-keeper.ts`, driven by the room's retention pass (`keepUnreferencedBlobsFor`, `maxBlobBytesPerPartition`, both absent by default). Tests: `relay/src/__tests__/blob-keeper.test.ts`, `client/src/__tests__/blobs.test.ts` (quota through a real relay), `conformance/src/__tests__/relay-vectors.test.ts` (+ `crates/syncmesh-core/tests/frame_vectors.rs`).
  - **What a reference is, honestly.** A relay does not fold cells, so it cannot know a *visible row*; it follows the one part of a row it can without a schema, whether the row exists (gaps U18, decided 2026-11-08, Jace delegated the call). A hash-spelled string anywhere in a written cell is a reference, held by the row that carried it until a delete stamped after that row's latest write — the kernel's own rule, by max-joins, so arrival order changes nothing — and the blob is swept a `keepUnreferencedBlobsFor` window after that delete, not after its put, because an offline write can still bring the row back (D18). A cell written over still counts (whether the newer write won depends on a merge rule the relay does not know), and a delete of a row not yet tracked is not remembered; both keep. References outlive the log: `storage/src/blob-ledger.ts` (`sqlBlobLedger`, beside `blob_homes`) keeps them, saved before every trim and joined into what was kept (every name, the later of each stamp, one transaction), and a trim waits for a save that failed. Each blob's window start is saved too, so a room that reopens more often than `keepUnreferencedBlobsFor` (eviction, actor sleep, deploys) still sweeps on time; a window moved after the last save starts over at the next open, which only keeps longer. With a ledger that has seen the whole log, the blobs an earlier run left on disk are read from the store at open, billed to one of their homes and swept a window after the open that first found them; a ledger started over a log already trimmed vouches for nothing it did not see, so those rooms keep an earlier run's blobs unswept and unbilled, as before. A sealed event keeps the blobs put into its partition and those put into none, for good (sealed partitions are saved and never cleared); one sealed with no partition keeps everything. Every pass emits `relay.blob.sweep` (counts and bytes). An instance knows only the references it ingested, booted with or read back; the byte ceiling still counts only what passes through it this run. Tests: `relay/__tests__/blob-keeper.test.ts` ("references follow rows"), `blob-references.test.ts`, the driver suite's `blobLedgerCases`.
  - **The wire, additive.** `blob-put` gains an optional fourth element, the partition the bytes are billed to (the putter's claim: a budget, not access control). In an open room it is still only a claim. In a grant-gated room it is checked (D44, built): a put billed to a partition the socket's grant does not name is refused `blob-refused` code `ungranted` (`BlobNotGranted` on the client), and every put that lands records its partition as one of the blob's homes (`blob_homes`, beside the bytes). A fetch is served only to a grant naming a home, or for bytes put with no partition, and is otherwise `blob-missing`; a row naming the hash authorises nothing (`relay/src/__tests__/gated-blobs.test.ts`). Two new tags: `blob-stored [hash]` (20) and `blob-refused [hash, code, limit, used, partition?]` (21). A client waits up to `BLOB_ANSWER_WAIT` (10 s) for one, so a relay that predates them costs a put that long and is never read as a refusal. A room of this build that keeps no blobs (`blobs: false` on `startRelay`, the Durable Object or the Rivet host) answers `blob-refused` with code `no-store` at once; no client reads that code as a quota, so the put succeeds and the putter stays the holder. `mesh.blobs.put(bytes, { partition })` answers `BlobQuotaExceeded { partition, limit, used }`; a fetch every carrier answered `blob-missing` is now `BlobNotFound` (silence stays `BlobTimeout`). The Rust core speaks both frames and its room answers `blob-stored`; it keeps no quota. Its client reads the answer (gaps U18): `Mesh::blob_put(bytes, partition)` waits up to the same 10 s and answers `BlobError::QuotaExceeded` or `NotGranted`, and anything else a stored put. A put made with no live link answers at once (`Action::BlobPutUnsent`): nothing could answer it. Unlike the TypeScript channel, it is not resent on the next session; the caller puts again once the mesh is online.

## Watch out

- Junk must not squat a hash — verify **before** storing.

## Tests
