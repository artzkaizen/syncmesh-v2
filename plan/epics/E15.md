## Goal

Bytes that do not belong in a log: content-addressed, verified on put and on fetch, travelling out of band.

## Decisions needed

D18

## Tasks

- [x] `hashOf` (sha-256, the wire's lowercase hex), `verifyBlob`, `memoryBlobStore`; `BlobCorrupt / BlobNotFound / BlobTimeout` as values, because each is a thing an app must decide about
- [x] Relay channel — four additive frames (`blob-put / blob-get / blob / blob-missing`) verified at the relay before storing — and the client cache; `mesh.blobs.put / fetch / has`, with a fetch answering from the local cache first, verifying what arrives, and caching it. A medium that cannot carry bytes says `NoSuchCapability` rather than pretending
- [x] `sqlBlobStore(driver)` over either dialect — a relay's durable home, or a device that wants its photos after a restart; in the driver contract suite, so every adapter proves it
- [x] Answered in RFC-0015 and D18: the **author** holds it until a relay acks; the **relay** holds it while a visible row references the hash; every other device holds a **cache** it may evict. A delete does not delete the blob — the relay sweeps only after a retention window with no reference, and a stale reference is `BlobNotFound`, recoverable because anyone with the bytes can put them back under the same name
- [x] The sweep itself, and per-partition quotas refused at the put as a typed value — `relay/src/blob-keeper.ts`, driven by the room's retention pass (`keepUnreferencedBlobsFor`, `maxBlobBytesPerPartition`, both absent by default). Tests: `relay/src/__tests__/blob-keeper.test.ts`, `client/src/__tests__/blobs.test.ts` (quota through a real relay), `conformance/src/__tests__/relay-vectors.test.ts` (+ `crates/syncmesh-core/tests/frame_vectors.rs`).
  - **What a reference is, honestly.** A relay does not fold, so it cannot know a *visible row*; it knows every event it holds. A hash-spelled string anywhere in a written cell is a reference, and it holds for the life of the instance, **through log trims**: a row inserted once and never rewritten is still live on every device after `keepEventsFor` trims its event, and the relay is that blob's durable home, so a trim must not free it. The sweep therefore frees only uploads no row ever named, and deleting a row frees nothing — telling a deleted row from a live one would take a fold the relay does not run. Bytes put again that an earlier run left on disk are kept and unbilled, since their event may have been trimmed before this boot. A room that sees a sealed event stops sweeping for good (a reference it cannot read is still one). Only blobs put since the room opened are swept or billed — the `BlobStore` port cannot enumerate an earlier run's — and an instance knows only the references it ingested or booted with.
  - **The wire, additive.** `blob-put` gains an optional fourth element, the partition the bytes are billed to (the putter's claim: a budget, not access control). Two new tags: `blob-stored [hash]` (20) and `blob-refused [hash, code, limit, used, partition?]` (21). A client waits up to `BLOB_ANSWER_WAIT` (10 s) for one, so a relay that predates them costs a put that long and is never read as a refusal. A room of this build that keeps no blobs (`blobs: false` on `startRelay`, the Durable Object or the Rivet host) answers `blob-refused` with code `no-store` at once; no client reads that code as a quota, so the put succeeds and the putter stays the holder. `mesh.blobs.put(bytes, { partition })` answers `BlobQuotaExceeded { partition, limit, used }`; a fetch every carrier answered `blob-missing` is now `BlobNotFound` (silence stays `BlobTimeout`). The Rust core speaks both frames and its room answers `blob-stored`; it keeps no quota.

## Watch out

- Junk must not squat a hash — verify **before** storing.
