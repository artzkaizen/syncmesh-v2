## Goal

Durable event log and materialised state behind small ports, one SQLite implementation with N drivers, a durable platform default, and boot invariants that never let the clock regress.

## Decisions needed

D05 storage ports · D15 retention

## Tasks

- [x] `SqliteDriver` port — `run / all / get / transaction? / close?` (sync or async per D05)
- [x] **One** `sqliteEventStore(driver)`: schema, migration (add `partition` to old databases), `appendBatch` in one transaction, `allSince(floor)` pushed into SQL, `lastSeq`, `maxHlc`, `compactBelow`, snapshot slot
- [x] Drivers: `bun:sqlite`, `node:sqlite`, the Durable Object's `ctx.storage.sql` and sqlite-wasm over OPFS all ship and all run `driverTests`. Writing the three taught that almost nothing in a driver is the binding — SQLite has no boolean and no date type, so both bind as the integers the dialect writes and reads back; `transaction` wants `BEGIN IMMEDIATE`, because a deferred one takes its write lock at the first write and failing to take it there throws away work already done; the dialect tag and the promises the port returns are identical everywhere. All of it is `sqliteDriver(binding)` in the storage package now, and an adapter is the ~8 lines its binding genuinely calls differently. `ctx.storage.sql` is the one that stays hand-written: `sql.exec` refuses `BEGIN`, so it has no `transaction` at all and rides the object's turn instead.

  **A binding gets a package only when it ships with the runtime.** `node:sqlite`, `bun:sqlite` and `ctx.storage.sql` are versioned by the runtime carrying them: no second version matrix, no release of ours per release of theirs, so the package costs nothing to keep and stays honest by construction. A binding the app installs — `expo-sqlite`, `@op-engineering/op-sqlite`, `better-sqlite3` — gets none. Against the public `SqliteBinding` port it is eight lines the app can read in full, and the public `driverTests` certifies those eight lines exactly as well as it certifies ours; wrapping them would add a dependency, a version matrix and a release cadence and buy the app nothing. **React Native therefore ships without an adapter and is not missing one** — it is the case the rule was decided on; the worked `expo-sqlite` driver and the certification recipe are in `packages/storage/README.md`. So `adapters/` is at its final three SQLite entries and names *bindings that come free with a runtime*, not *platforms syncmesh supports*.

  **The browser was the hole this leaves, and this epic then corrected itself in the wrong direction.** It first argued that OPFS is synchronous only behind a sync access handle inside a dedicated worker, so a browser binding callable from the app's own thread is async and *cannot be a `SqliteBinding` at all* — and exported `bindSqlite` for precisely that driver. It then withdrew that, claiming `opfs-sahpool` "runs on the page's own thread and needs no cross-origin isolation", and recorded that `bindSqlite` went unused. **The first reading was right and the correction was wrong**, and the adapter shipped with the wrong claim in its doc comment until it was measured on a real page.

  `createSyncAccessHandle` is `[Exposed=DedicatedWorker]`. Read it off `FileSystemFileHandle.prototype` in a window and it is `undefined`, in every browser, cross-origin isolated or not — TypeScript's own libraries say so, declaring it in `lib.webworker.d.ts` and not in `lib.dom.d.ts`. Both OPFS backends gate on exactly that method, so **a driver constructed in a window can only be `memory`**. What is true of `opfs-sahpool` is the *other* half: it needs a dedicated worker and nothing else — no `SharedArrayBuffer`, no COOP/COEP. The older `opfs` VFS needs the worker **and** the headers, and serving the headers alone does not buy it: its feature check reads `createSyncAccessHandle` before it will spawn its proxy, so a page with `crossOriginIsolated === true` still gets `Missing required OPFS APIs.`

  **What the async reading also got wrong is that async is not an exception.** `SqlDriver.run`, `.all`, `.transaction` and `.close` have always returned promises; only the *binding* is synchronous. So a database in a worker and a driver in the page is not a change to the port, it is a use of it — `asyncSqliteDriver` beside `sqliteDriver` in `packages/storage`, over `bindSqlite`, which now does what its doc comment always said it was for. `wasmSqliteDriver` starts the worker itself when it is called from a window, so `adapters/` is still one binding and `apps/issues` needed no change to become durable. Measured: 0.0142 ms per page↔worker round trip over 2000 calls, which is not the reason to choose anything. Full argument in `research/browser-durability.md`.

  **Which puts `@syncmesh/sqlite-wasm` in `adapters/`, and that needs saying out loud**, because the rule above closed `adapters/` at three and said a binding the app installs gets no package. The rule's *purpose* is what decides it: no second version matrix, no release of ours per release of theirs. `@sqlite.org/sqlite-wasm` is the SQLite project's own build, there is exactly one of it, and it is versioned by the same people who version `node:sqlite` — a browser has no bundled SQLite, and this is the closest thing a browser has to one. An `expo-sqlite` wrapper would still buy nothing and still gets no package. So `adapters/` is at four, and the rule is unchanged: *a binding gets a package when nobody has to pick its version.*

  **And it stays at four.** The worker host that makes the browser durable is inside `@syncmesh/sqlite-wasm`, not a fifth entry beside it, because it is not a fifth binding: it is `@sqlite.org/sqlite-wasm` again, on the one thread where the File System API will talk to it. A package per *place a binding runs* is a different rule from a package per binding, and it would put `adapters/` on a path to one entry per hosting trick. The rule's purpose still decides it — nobody has to pick a version of anything new.

  **Then stage 2 arrived carrying something that is not a binding at all, and the rule as written does not reach it.** Making a *second* tab live is not SQLite's problem and not `@sqlite.org/sqlite-wasm`'s: it is `navigator.locks` electing one browsing context, a `SharedWorker` passing ports, and the mesh itself served over a `MessagePort` so every other tab is a thin client of the elected one (`research/browser-durability.md` §4). There is no library underneath it, so the test the rule is made of — *a binding gets a package when nobody has to pick its version* — answers a question nobody asked.

  What decides it is the other rule, D01-B: `packages/*` is runtime-neutral and lint-enforced, and this code names `Worker`, `SharedWorker`, `MessagePort` and `navigator.locks` in its first ten lines. So it cannot be a package, and `adapters/` is the only shelf left. Nor does it go *inside* `@syncmesh/sqlite-wasm`, and that is the sharper half: the host constructs a whole mesh, so putting it there would make the browser's **storage binding** depend on `@syncmesh/client` and `@syncmesh/drizzle` — a driver importing the engine that drives it. The worker host in the paragraph above is `@sqlite.org/sqlite-wasm` on the one thread that will talk to it and belongs beside it; a *mesh* host is a different thing wearing the same word.

  So `adapters/` is at **four bindings and one entry that is not a binding** — `@syncmesh/browser`, the origin's concurrency layer — and the rule is amended out loud rather than stretched quietly: *`adapters/` holds a package per binding that comes free with a runtime, **and** a package per runtime capability that is no binding at all and that `packages/*` may not name.* Exactly one such capability exists today, and it is the browser's, because the browser is the only target that forbids two contexts of one origin from opening the same database — the constraint is the platform's, so the package is the platform's. `expo-sqlite` is still not a package, and a fifth *binding* still is not one.

  **What is still open is concurrency, not storage — and it is bigger than a lock.** The pool is exclusive per origin *directory*, not per database: the first browsing context to install it takes exclusive access handles for every slot, so a second tab asking for a name nobody has ever opened is refused just as firmly. That refusal is now its own tag, `OpfsPoolHeld`, decided by an exclusive Web Lock taken **before** SQLite is touched — a plain yes/no instead of a `DOMException` about writable streams thrown from halfway through an install — and `apps/issues` says "another tab owns the database" rather than implying the browser cannot save.

  What it does **not** do is let two tabs share one database, and the reason is worth writing down because the obvious fixes are unsound. A `SharedWorker` hosting the file, or a Web Locks leader owning the file with followers proxying SQL to it, both produce *two engines over one log under one device identity*: two boots read the same `lastSeq(peer)` and both allocate upward from it, which is this epic's own "Watch out" — "new events stamped below ones peers already saw → silently discarded as stale. Invisible." And neither makes the second tab live, because a live query re-runs only on its own engine's `FoldBatch` hub and nothing re-reads the log after boot.

  A `SharedWorker` is not the way out either, and that is measured rather than argued: `createSyncAccessHandle` reads `undefined` in a `SharedWorker` exactly as it does in a page, because `SharedWorkerGlobalScope` is not a `DedicatedWorkerGlobalScope`. Anything that owns an OPFS database is a dedicated worker; a `SharedWorker` can only be the origin's rendezvous, and Chrome on Android has none at all.

  So the answer is **one engine per origin** — RFC-0004's "one engine per storage scope", which `research/tanstack-db-validation.md` already cites as the reason not to import a tab leader-election library. The leader's dedicated worker holds the mesh, `navigator.locks` elects it and hands over for free when its context dies, a `SharedWorker` passes ports and touches no file, and a follower is a **thin client sharing the leader's identity and log** — not a peer, because a peer owns a log and only one context of an origin can persist one, which would make every follower a *memory* peer and re-introduce the failure this work removed. Web Locks elects the owner of the *engine*, not of a file. That is a build, not a lock, and it is specified in `research/browser-durability.md` §4. Until it lands, exactly one tab of an origin is durable and every other tab says so in the header.

  **Building that needs a home the rule above does not name, so `adapters/` gains an entry that is not a binding.** Tab election, the `SharedWorker` rendezvous and the re-plumbing of followers after a handover install nothing and wrap nothing: the only thing they depend on is the browser itself — `Worker`, `SharedWorker`, `navigator.locks`, `MessagePort`. `packages/*` cannot have them, because they are precisely the DOM that D01-B forbids and lints for. `@syncmesh/sqlite-wasm` cannot have them either, and the reason is the direction of the arrows rather than taste: what the leader's worker serves is the **mesh**, so putting the host there would pull `@syncmesh/client` into an adapter, while `@syncmesh/client` already depends on this one's two siblings (`sqlite-bun`, `sqlite-node`) — an adapter below the client, importing the client. It would also make the package's own sentence false. `@syncmesh/sqlite-wasm` is "the `SqlDriver` a local-first web app needs", and an app that wants only that should not be made to carry an engine to get it.

  So `@syncmesh/browser`, and the amendment is stated rather than smuggled: **`adapters/` names what a runtime forces, of which a binding is the usual case; a runtime earns a second kind of entry when it forbids the database being where the app is.** Exactly one runtime does. Node, Bun and a Durable Object all let SQLite sit on the thread that called it, so for them the binding is the whole story and a host beside it would be the "package per place a binding runs" this epic already refused. A browser forbids it twice over — `createSyncAccessHandle` is `[Exposed=DedicatedWorker]`, and the pool is exclusive per origin *directory* — so there the placing is not an implementation detail of the binding, it is the product: which tab holds the engine, how the others reach it, what happens when that tab closes, and what the rest are told on a platform with no rendezvous at all. That is a different subject from SQLite and it is why it is a different package rather than a fifth file in one. The purpose test still decides and is why this is not a slope: nobody has to pick a version of anything new, because the dependency is the browser. The four SQLite entries are still four, and a second entry of this kind would need a second runtime that forbids the same thing.

  **The seam, because two halves were built against it at once.** `@syncmesh/browser` splits at a port and nothing else. The RPC half owns `src/link.ts` — the `MeshLink` type and `linkOver`, which is a link over an already-connected port plus the `lost()` button that declares the host dead — and `src/protocol.ts`. The election half owns `src/election.ts`, `src/host-worker.ts`, `src/rendezvous.ts`, `src/broker.ts`, `src/rendezvous-worker.ts`, `src/errors.ts` and `src/tabs.ts`, and presses that button: `openMeshLink` hands back a connected `MeshLink` and keeps handing back a fresh one across handover, `hostWorker(serve)` is what a tab's dedicated worker entry calls, and the `serve` it is given is the RPC half's. Neither half needs the other to be tested — the election is certified against a fake `LockManager` and a real `MessageChannel`, the RPC against a `MessageChannel` with no election at all. `WirePort` is imported from `@syncmesh/sqlite-wasm`, not declared again: page-to-own-worker, follower-to-leader's-worker and a `MessageChannel` in a test runner are the same two members, which is the reason that type was named in the first place.
- [x] `LocalStorageEventStore` — corrupt log recovers empty **and** surfaces a typed error, and a damaged head no longer takes the *numbering* with it. The reported gap is closed: resetting `lastSeq`/`maxHlc` to zero made the device re-issue sequence numbers its peers already held under different ids, and `has()` then dropped every new event on every peer, silently, for the life of the device.

  A damaged head now keeps the surviving log's marks and discards only its contents — sound rather than optimistic, because `persist` runs before `outbound.emit` in the write path, so a sequence the log never recorded was never sent to anyone either. Where **both** keys are damaged nothing on the device can know where it had got to, only a peer holding its past can; that case reports `numberingLost` instead of quietly starting again at one.

## Watch out

- `maxHlc`/`lastSeq` wrong → the clock regresses → new events stamped below ones peers already saw → silently discarded as stale. Invisible.
- The two SQLite stores in the exploration drifted: one migrated old databases, one did not, and the missing migration corrupts every signature on re-ship. One store, N drivers.
- `saveSnapshot` must copy synchronously — the caller's object keeps mutating after the call.
- A memory default silently loses every write on restart. Durable by default.
