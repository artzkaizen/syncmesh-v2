## Goal

The server peer materialises synced rows into your own Drizzle tables so your SQL, joins, cron and reports work on them. The one legitimate consumer of the fold notification on the server.

## Decisions needed

D05 (async ports — Postgres needs them) · D10

## Tasks

- [ ] `drizzleStateStore(db, { tables, schema })` implementing the state port: UPSERT/DELETE into your tables by primary key in one transaction; sidecar `_syncmesh_state` (stamps) and `_syncmesh_cursors`; validation at construction (`InvalidTableDefinition` for unknown table / missing column / PK mismatch); `_partition` → `partition` column if present else stripped; date columns receive `Date`
- [ ] Async variant (D05) so `drizzle-orm/postgres-js` works; a real-Postgres test behind an env var
- [ ] Rule in the docs: a table is defined once in Drizzle, synced through the mesh, materialised into that same table; never write synced tables with raw SQL on the server
- [ ] `drizzleEventStore(db)` implementing the `EventStore` port (RFC-0004 names it) so the log lives in the same Postgres as the rows: one `_syncmesh_events` table holding the canonical envelope bytes as `bytea`, unique on `id`, indexed `(peer_id, seq_num)`; `allSince(floor)` pushed into SQL; `appendBatch` in one transaction; `lastSeq` / `maxHlc` as indexed `MAX()`; `compactBelow` and the snapshot slot when E04 adds them. The shipped store suite from `packages/testing` passes against real Postgres behind the same env var
- [ ] Log and state in one transaction: `appendBatch` + `commit(rows, cursors)` commit together when both stores share the `db`, closing the crash window between "event durable" and "row materialised" that the cursor sidecar otherwise recovers
- [ ] The relay (E12) accepts any `EventStore`, so a server that runs relay and app in one process keeps one log — the deep archive of RFC-0015 §5 with ordinary Postgres retention

## Watch out

- The exploration built the sync version, then found every Postgres Drizzle driver is async. Decide D05 before this epic, not after.
- Column named `tbl`, not `table` — `TABLE` is reserved in both dialects.
- The event store holds signed bytes: store the envelope verbatim, never decompose an event into typed columns and re-encode on read — re-encoding breaks every signature and byte-identical store-and-forward (E04 lists the migration that did exactly this in the exploration).
- `sqliteEventStore`'s SQL is SQLite dialect (`INSERT OR IGNORE`, `?`); the Postgres log is a second implementation of the seven-method port, not a driver for that store.

## Tests

- `drizzle-state-store.test` — plain `select` reads the row; update touches only changed columns; delete; restart boots from the sidecar over an empty log; definition errors; 5,000 folds = one transaction.
- `drizzle-event-store.test` — the shipped store suite; bytes out equal bytes in for every frozen vector; `allSince` is one range query; boot reads `maxHlc` / `lastSeq` exactly after a crash mid-batch; event and row land in one transaction or neither does.

## Done when

◆ A phone writes offline; on reconnect the row appears in `SELECT * FROM jobs` on the server with no code between. `DELETE FROM jobs` then a refold from `_syncmesh_events` restores it byte-identical.
