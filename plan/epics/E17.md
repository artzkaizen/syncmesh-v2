## Goal

The server peer materialises synced rows into your own Drizzle tables so your SQL, joins, cron and reports work on them. The one legitimate consumer of the fold notification on the server.

## Decisions needed

D05 (async ports — Postgres needs them) · D10

## Tasks

- [ ] `drizzleStateStore(db, { tables, schema })` implementing the state port: UPSERT/DELETE into your tables by primary key in one transaction; sidecar `_syncmesh_state` (stamps) and `_syncmesh_cursors`; validation at construction (`InvalidTableDefinition` for unknown table / missing column / PK mismatch); `_partition` → `partition` column if present else stripped; date columns receive `Date`
- [ ] Async variant (D05) so `drizzle-orm/postgres-js` works; a real-Postgres test behind an env var
- [ ] Rule in the docs: a table is defined once in Drizzle, synced through the mesh, materialised into that same table; never write synced tables with raw SQL on the server

## Watch out

- The exploration built the sync version, then found every Postgres Drizzle driver is async. Decide D05 before this epic, not after.
- Column named `tbl`, not `table` — `TABLE` is reserved in both dialects.

## Tests

- `drizzle-state-store.test` — plain `select` reads the row; update touches only changed columns; delete; restart boots from the sidecar over an empty log; definition errors; 5,000 folds = one transaction.

## Done when

◆ A phone writes offline; on reconnect the row appears in `SELECT * FROM jobs` on the server with no code between.
