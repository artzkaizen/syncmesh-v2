## Goal

The app's tables are the data API (D20): synced rows are materialised into real per-table SQL — SQLite on a device, your Drizzle tables on the server — so the app's ORM reads them, and the app's own writes to those tables are captured at commit into events. The state store is the one consumer of the fold notification; change capture is the one producer of local events.

## Decisions needed

D05 (async ports — Postgres needs them) · D10 · D20

## Tasks

- [x] Change capture (D20 §3): `tableDdl` builds the per-table SQL from the manifest (`_partition` included); `captureDdl`/`installCapture` add `_syncmesh_changes`, a guard row, and `AFTER INSERT/UPDATE/DELETE` triggers that log OLD/NEW as `json_object` (bytes as lowercase hex) only while the guard is armed, so the fold's own UPSERTs are never re-captured; `captureChanges(driver, tables, fn)` runs the app's SQL in one transaction and returns kernel `Change[]` in statement order — inserts whole, updates as the columns that changed, no-op updates dropped, a throw rolls everything back. A row touched twice in one transaction is one change, its net effect (first OLD vs last NEW) — one event has one stamp, so two changes to a row could not both survive a merge. In the driver contract suite, so every SqliteDriver proves it
- [x] Commit → event (D20 §3): `createWriter({ engine, validate, driver, tables })` in the client runs the app's SQL through `captureChanges` with the engine's own validator as the in-transaction `check` — schema and policy judged on the captured changes before COMMIT, so a refused write is rolled back and never reaches the table — then `engine.mutate` replays the net changes as one labelled, signed event. Pinned: two statements → one event and the engine's state agrees with the table; a schema violation and a viewer's policy denial both roll back with no row and no event; nothing changed is `EmptyMutation`. Still open here: `_partition` injected by the pinned handle, and log + tables in one SQLite transaction (the append/commit window below)
- [x] The fold writes the same tables (D20 watch-out, two writers): `openStores(driver, { tables })` creates the per-table SQL with capture installed and gives the SQLite state store a `tablesProjection` — every commit UPSERTs visible records into their table (values in the column's SQL form, `_partition` alongside) and DELETEs tombstones, in the same transaction as the stamps sidecar and cursors, with the capture guard at rest so none of it is logged as the app's own. `inTransaction` now serializes transactions per driver, so an app transaction in flight and a fold commit take turns on one connection instead of failing with a nested BEGIN. `createMesh`'s durable default passes the manifest's tables through. Driver suite: values and bytes land, upsert by key, tombstone then restore, stamps still in the sidecar, clear empties both, and the two-writers interleaving; client: a peer's event lands in this device's table uncaptured and its own write is still captured. `tableDdl` constrains only the key (D19: absence reads as null)
- [x] Read rules → SQL (D20 §2): `compileRead(table, ladder, allow, principal)` in storage turns a table's `read` rule into a `WHERE` predicate over its own columns — `role()` a constant from the ladder, `owner()` an equality on the account, `claimHas` an `IN` over the claim's scalars, `claimEquals`/`rowIs` equalities (`IS NULL` for null), `claimIncludes` a constant, `patchOnly` always true on a read, `any/all/not` as `OR/AND/NOT`; a comparison `evaluate()` could never make true (wrong kind, json/blob column, unknown column) compiles to `0`. Pinned in the driver suite: for eleven rule shapes × four principals the compiled `WHERE` admits exactly the rows `evaluate()` admits. This is what `mesh.as(principal).db` puts under every source
- [x] `@syncmesh/drizzle` — `meshDrizzle({ engine, validate, driver, schema, partition, as })` (D20's face): Drizzle runs through its sqlite-proxy driver over the mesh's own SqliteDriver, so one connection and one transaction order. `db.insert/update/delete` — a statement on its own is one event, labelled `<table>.<op>` from its SQL; Drizzle's own `db.transaction(async (tx) => …)` is the capture boundary — the proxy intercepts `begin`/`commit`/`rollback`, so several statements are one event with a derived label (`jobs.insert+jobs.update`), a read-only transaction is no event, and a denial surfaces as the transaction rejecting with the tagged error on `cause`; `read(table)` is the table as the principal may read it — a subquery with the compiled `read` rule and the partition pin — and `live(query)` re-runs when a fold touches the query's tables (walked off the query object), notifying once per batch and only on change, after the state store commit (the engine now emits fold batches after persist). Acting `as` a principal also gates writes: a change their rules deny is `PolicyDenied` before COMMIT, via the writer's actor gate
- [x] The state port on Postgres — not a Drizzle-bound store but the same `sqlStateStore` over a `SqlDriver` whose `dialect` is `postgres` (D20: drivers, not one ORM): `tablesProjection` UPSERTs/DELETEs into your tables by primary key inside the commit, sidecar `_syncmesh_state` and `_syncmesh_cursors`, booleans as booleans and timestamps as `Date` in the Postgres dialect; `partitionColumn` names the column that takes the partition key (`_partition` by default, `false` to keep it in the sidecar only). Still open from the original wording: validation at construction against your table's actual columns
- [x] Async variant — the ports were already async (D05); `@syncmesh/postgres` ships `postgresDriver(sql)` over the postgres.js client Drizzle's `postgres-js` uses, so app and mesh share one pool and, inside a transaction, one connection, plus `pgliteDriver(db)` for tests with no server. The store contract (`storeTests`: events, state, compaction — 16 cases) runs on PGlite always and on a real server behind `SYNCMESH_PG_URL`, one schema per case
- [ ] Async variant (D05) so `drizzle-orm/postgres-js` works; a real-Postgres test behind an env var
- [x] `@syncmesh/drizzle` on Postgres: one adapter, two faces. The proxy callback, the live re-run and the read predicate are shared; each dialect's face binds Drizzle's own proxy driver (`sqlite-proxy`, `pg-proxy`) over the mesh's connection so the app's statements run inside the capturing transaction. `pg-proxy` refuses `db.transaction()`, so the Postgres face constructs its session from `PgRemoteSession` with a `transaction` that sends `begin`/`commit`/`rollback` through the callback the way `sqlite-proxy` does — Drizzle's own `transaction()` stays the capture boundary on both. The dialect is a type parameter end to end: `SqliteDriver` narrows to `dialect?: "sqlite"`, `PostgresDriver` to `"postgres"`, and `meshDrizzle`, `createMesh`, `mesh.on()` and `withMesh` hand out the handle for that dialect statically. `compileRead` takes the dialect for its constants and cell forms. The six drizzle cases run on both faces (PGlite for Postgres)
- [x] Rule in the docs: stated on `meshDrizzle`'s own doc — a table is defined once in Drizzle, synced through the mesh, materialised into that same table; a raw-SQL write on the server passes no capture, makes no event, and diverges from every peer
- [x] Change capture on Postgres: each dialect now owns its `CaptureSql` — table DDL, trigger DDL, arm/disarm, log select/clear, partition stamp — and `captureChanges` is written once over it. Postgres gets one plpgsql function and one `AFTER INSERT OR UPDATE OR DELETE` trigger per table, guarded by a transaction-local `SET LOCAL syncmesh.armed` (dies with the transaction, locks no row across the pool) instead of SQLite's guard row; the logged image is the same shape in both dialects (hex bytes, epoch-ms timestamps, JSON as text), so one decoder reads it back. Mesh-created Postgres tables use `BOOLEAN`/`TIMESTAMPTZ`/`JSONB`/`BYTEA`/`BIGINT` — what a `pg-core` column would be. `captureTests` (capture, its rules, the app's tables — 11 cases) is the dialect-neutral half of the driver contract; it passes on PGlite alongside the store contract, and the suite's SQL speaks each dialect through `sqlText`
- [x] The `EventStore` port on Postgres: `sqlEventStore` over the same driver, `_syncmesh_events` holding the canonical core bytes and signature as `bytea` verbatim, primary key `(peer, seq, local)`, indexed on the stamp; `allSince` pushed into SQL through `jsonb_each_text` on the bound cursor map; `appendBatch` in one transaction; `lastSeq` / `maxHlc` as `MAX()`; `compactBelow` with `GREATEST` floors in `_syncmesh_compaction`. Each dialect owns its statements outright (`dialect-sqlite.ts`, `dialect-postgres.ts`) — one store, never one string pretending to be two SQLs. Migrations are versioned in `_syncmesh_meta`; the SQLite-only version-1 history case stays in `driverTests`
- [x] Log and state in one transaction: `openStores` returns `atomic(fn)` — one `inTransaction` on the shared connection, handing `fn` store instances built `nested` (they write into the open transaction instead of opening their own). The engine's new `atomic` option wraps every write path in it: `mutate` numbers, appends and commits state inside one transaction, `receiveBatch` likewise, and the fold notification fires only after it resolves so live queries re-read committed rows. A state-commit failure inside `atomic` aborts the transaction and takes the append with it — the crash window between "event durable" and "row materialised" is closed rather than recovered. `createMesh` threads it through whenever the stores are one `openStores` pair (the durable default, or your `driver`); separate `store`/`stateStore` keep the sidecar-recovery behaviour. Pinned in the dialect-neutral suite (both SQLite adapters and PGlite) and in the engine's `atomic.test`
- [x] The relay (E12) accepts any `EventStore` (`openRelayRoom({ store })` took the port from day one), so a server that runs relay and app in one process keeps one log — hand it the Postgres store and RFC-0015 §5's deep archive is ordinary Postgres retention

- [x] RLS from the read rules (the deferred "part 2"): `rlsDdl`/`installRls` compile every table's `read` rule into a Postgres SELECT policy over the same AST `evaluate()` runs — `role()` via `array_position` on the ladder, `owner()` and `claimEquals`/`claimHas` against transaction-local settings (`set_config(…, true)`, so the principal dies with COMMIT/ROLLBACK and a pooled connection carries nothing over), `claimAt`'s dot-path walk as nested `jsonb` cases that refuse arrays mid-path, timestamps compared as epoch milliseconds, and every comparison leaf in `COALESCE(…, FALSE)` so `NOT` never flips SQL's unknown. RLS is ENABLEd and FORCEd; write policies are open on purpose — capture judges writes before COMMIT; superusers bypass RLS by Postgres's own rules, so the app reads through a plain role. `principalSettings(principal, { partition? })` emits the four `set_config` statements, the partition pin included. Proven on PGlite: all 11 rules × 4 principals return exactly the rows `evaluate()` admits through a plain `SELECT` under `SET ROLE`, and the pin dies with its transaction. Not yet wired into the drizzle face — whether RLS replaces `read()` at server call sites or backs it is a call to make with the integration

- [x] RLS wired through the face, `read()` retired at server call sites: the Postgres face runs `principalSettings` inside every transaction — after `db.transaction()`'s `begin`, before a lone write's capture, and a bare read gets a queued transaction of its own to hold the settings — so with `createMesh({ rls: true })` a plain `db.select().from(jobs)` on an authority is already the caller's view, no wrapper anywhere. Without `rls` the settings are inert and `read()` remains the explicit filter; with it, `read()` still works (double-filtering is harmless). Proven through the handle on PGlite under `SET ROLE`: bare selects, selects inside the caller's transaction, and the write within it landing, per principal

## Watch out

- The exploration built the sync version, then found every Postgres Drizzle driver is async. Decide D05 before this epic, not after.
- Column named `tbl`, not `table` — `TABLE` is reserved in both dialects.
- The event store holds signed bytes: store the envelope verbatim, never decompose an event into typed columns and re-encode on read — re-encoding breaks every signature and byte-identical store-and-forward (E04 lists the migration that did exactly this in the exploration).
- `sqliteEventStore`'s SQL is SQLite dialect (`INSERT OR IGNORE`, `?`); the Postgres log is a second implementation of the seven-method port, not a driver for that store.
