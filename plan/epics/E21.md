## Goal

A stolen device loses its powers within one catch-up, not at grant expiry; an account can vouch for its devices so 'mine' means the same thing on all of them.

## Decisions needed

D08, D21 (accounts)

## Tasks

- [x] Revocation as a signed settlement event in the partition it concerns, travelling by ordinary anti-entropy — `_revocations`, a third reserved table keyed `instance:device`, so E16's authority-only rung guards it with no new code and it routes by partition. `revokeDevice(engine, {device, partition, reason, at?})`; `revocations(engine)` reads them back.

  Two comparisons decide the rung, both there to keep peers agreeing rather than merely refusing. Against the grant's `issuedAt`, so re-issuing readmits with no second verb. Against the **event's own stamp**, so what the device wrote before the revocation stands: comparing only `issuedAt` makes the verdict depend on fold order, and two peers that disagree once disagree forever. What remains is RFC-0016's honest window.
- [x] Short-validity issuance + a renewal loop on the authority; grace window in the `_policy` row — `grace` is a column on `_policy` (not a key in the rules AST, which is keyed by table), written only when set so an older peer keeps folding policy updates. The rung reads it in `author.ts` against **the event's own stamp**, for the reason revocation does; the authority is exempt from the window it publishes, or a grace wider than its own validity locks it out of the instance it governs.

  Renewal is a primitive plus a documented pattern, not a timer: `grants.expiring(within)` and `grants.renew(device, validFor)`. `expiring` measures against `expiresAt - grace`, since that is when a device is actually cut off, and **omits revoked devices** — `renew` re-mints with a fresh `issuedAt`, which is exactly what the revocation rung lets through, so an unguarded loop would readmit every device the authority had thrown out. A deliberate `issue` still readmits, which is the path that should need someone to mean it
- [ ] `AccountCore`, link/revoke-device events, an account registry feeding `owner()` — **blocked on D21**, which disputes the goal: in a mesh with an issuer `owner()` is already cross-device, because the issuer mints both of Alice's grants with the same `account`. The hole is `owner()` in the rungs with *no* issuer, where `grantFor` is `null` and policy never runs at all. D21 proposes links as rows in a fourth reserved table, consulted only when no grant is held, with no registry — the state is the registry.

  Tasks, once D21 lands:

  - [ ] `AccountId` + `parseAccountId` in the kernel, reusing `PEER_ID_HEX`; extract `splitEnvelope` into `wire/envelope.ts` and route `splitGrant` and `decodeAndVerify` through it — they are already two copies of the same split
  - [ ] `packages/wire/src/account.ts` — `AccountCore`, the `KEY`/`OP` maps, `signLink`, `verifyLink`, `MalformedLink`, `BadLinkSignature`; fixed-seed vectors beside the grant vectors
  - [ ] `linksTable` in `reserved.ts`, fourth in `reservedTables`; `account`/`kind`/`at` as columns as well as core fields, for the reason `_revocations.at` already is one — `checkAuthor` is a hot path and must never decode a blob to answer
  - [ ] `packages/engine/src/accounts.ts` — `linkKey`, `checkLink`, `linkDevice`, `unlinkDevice`, `links`, `disputes`. Six rungs, cheap ones before the Ed25519 verify: key shape, columns agree with the core, monotonic `at`, authorship (**a device may claim only itself; any author may relay an unlink, because a stolen device will not unlink itself**), isolation, signature
  - [ ] `checkReserved` dispatches on the table's author class (a lookup, never a name check); `validate.ts` gains one delegating line and no logic
  - [ ] `checkAuthor` returns `Author`, resolves the link in the `grantFor === null` arm only, re-verifying the row's wire (memoized) so a snapshot cannot launder a binding in; `ValidatorOptions.accounts?: boolean`
  - [ ] `can.ts` takes the same resolver, so `can()` and `validate` cannot answer differently — the bug already fixed once for synced policy docs
  - [ ] `mesh.ts`'s two attribution sites become one `accountOf`; `createMesh({ accounts, accountKey })`, `mesh.accounts.{link,unlink,disputes}`, a mismatched `accountKey` panicking at construction as `issuerKey` does

- [x] ~~Per-peer sync state keyed by device key survives reconnects~~ — resolved by E12, and for a reason that was never relay-specific: a session opens by volunteering its own contiguous cursors (`bridge.ts`, grants then `resync()`), exactly as a relay `join` does, so there is no round trip to skip on a radio either. The second half needs nothing per-peer: a revocation is an ordinary synced row, so a peer that has folded it refuses that device from state it already holds
- [x] **Grants survive a restart.** The gap this task was standing next to: `createGrantRegistry` holds a bare `Map` and nothing ever writes it down, so a restarted device quarantines every author on `NoGrant` until peers re-send — D08's own watch-out, reached by rebooting rather than by a missing frame. Revocations persist for free, being rows; grants do not. `GrantStore` in `@syncmesh/storage` (`_syncmesh_grants`, keyed by device so a re-issue supersedes rather than joins), filled at boot by `rememberGrants` and kept in step after it through `onRegistered` / the new `onForgotten`. Every stored wire goes back in through `register`, so the issuer's signature is checked again and an expired grant does not return — a store cannot launder a grant into something the registry would not have accepted from a peer. What fails to come back is deleted rather than re-read every boot

## Watch out

- Under partition the window is bounded only by validity — propagation is best-effort, the short window is the guarantee.

## Tests

- [x] `engine/revocation.test`: only the authority may write one, refused at the forger's own engine; a revoked device's writes quarantine at every peer that folded the revocation, while what it wrote before the instant stands; once it folds the revocation it refuses its own writes; it withdraws one instance and not the device; re-issuing readmits; it travels as one ordinary signed event in the instance it concerns.
- [x] `client/grants-durable.test`: a peer met before a reboot is still known after it; a re-issued grant replaces the stored one; the store cannot launder an expired grant back in and stops holding it; a locally revoked grant does not come back.
- A revoked device's events quarantine at every peer within one catch-up; a renewal keeps a live device working across the boundary.
- Accounts, once D21 lands: **`accounts-blast-radius.test`** is the one that matters — two devices, two grants, one account, a row owned by it; then fold a *fully valid* `_links` row binding an attacker's device to that account and assert all three engines' verdicts, `can()`, and the compiled SQL text are unchanged, and `disputes()` names it. Written to fail the instant anyone wires links into the granted path. Plus: every existing verdict byte-for-byte unchanged with `accounts` unset and the frozen grant vectors still round-tripping; the second author class refused at the forger's own engine and again at every receiver; two linked devices of one account both satisfying `owner()` in an ungranted mesh; links surviving a restart, being rows.

## Done when

Revoke a device from the server; every peer refuses it on next contact.
