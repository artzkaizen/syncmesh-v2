## Goal

Columns where two devices editing the *same value* at the same time both keep their edit. E01's kernel is already a CRDT (an LWW register per cell); this epic adds three column kinds whose merge happens *inside* the cell: a counter (sum of per-peer increments), a set (adds survive concurrent removes by id), and text (a sequence CRDT — every character has an identity, concurrent inserts interleave deterministically). Each is one more per-column strategy and one more change kind on the wire; the row, stamps, tombstones and engine do not change.

## Decisions needed

D04 (decided: A, this epic is the deferred C) · a new decision for the text CRDT algorithm (RGA vs Fugue vs Peritext-style rich text) before the text task starts

## Tasks

- [x] `counter` strategy: state `{ [peerId]: { inc, dec } }`, value = Σ inc − Σ dec; change kind `increment`; join = per-peer max. Proves the seam with the cheapest kind
- [~] `set` strategy (OR-Set): adds tagged with a unique id, remove tombstones the ids it has seen; change kinds `add` / `remove`. **Not built**: tombstone compaction below the snapshot floor — every removed id keeps a `[]` entry forever, which is this epic's own "Watch out"
- [~] Schema: `t.counter()` and `t.set(t.text())` shipped — the kind **is** the strategy, and `onConflict` refuses both in the types and at definition time, because naming a cell strategy as a conflict rule silently destroyed the column. `t.richText()` does not exist and waits on the text algorithm decision. `onConflict` now refuses `counter` and `set` in the types and at definition time (the kind *is* the strategy); `StrategyFor<T>` names the three declarable strategies and no more. What is missing is the column kinds themselves
- [~] Wire: one new change kind per column kind, canonical CBOR — `crdt-codec.ts` encodes and decodes all three. **Not built**: the frozen vectors, which is the whole point of the task (`conformance/` has none), and no encoder can put a cell kind into an event yet, so neither half has a producer
- [ ] Decide the text algorithm (new decision file); then `text` strategy: per-character ids, insert-after, deterministic tie order by stamp, delete tombstones, compaction
- [ ] Client: `mesh.collections.<t>.update` drafts expose `count.increment(n)`, `set.add / remove`, `text.insertAt / deleteAt` instead of whole-value assignment
- [x] Property tests per kind: commutativity, associativity, idempotence under random order + duplication; text additionally: no interleaving of one peer's contiguous insert

## Watch out

- Do counter → set → text, in that order. Text is a project of its own; do not start it before counter and set have proven the strategy + change-kind seam end to end.
- Text state grows with every edit ever made; without compaction below the snapshot floor (E14) a long document never shrinks.
- The Swift/Kotlin ports (E22/E23) must implement the identical algorithm; that is what the vectors are for. Pick the algorithm once.
- None of these kinds change how `lww | max | min` columns work; a table can mix them freely.

## Tests

- `counter.test`, `set.test`, `text.test` — each kind's collision matrix in both delivery orders.
- `properties.test` extended — random schedules across all kinds in one row.
- Conformance vectors for every new change kind.

## Done when

Two engines fold the same counter / set / text changes in any order and hold identical cells, at thousands of random schedules, and the vectors for each change kind are frozen.
